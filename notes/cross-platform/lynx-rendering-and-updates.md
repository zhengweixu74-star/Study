## 页面描述到平台 UI 的渲染流程

开发时用 TSX、JSX 和样式描述页面，构建工具把它们转换、打包成 Lynx bundle。客户端加载 bundle 后，引擎解析脚本、样式和配置，执行渲染逻辑生成元素树，再计算样式和布局，创建或更新平台 UI，最后由系统绘制。

不是把同一段 TypeScript 直接交给 Swift 或 Kotlin 编译器，也不能把 Lynx 统一理解为 WebView。需要相机、相册、账号等宿主能力时，通常通过 Native 组件或 JSBridge 接入；宿主需要提供相应实现，平台能力和版本仍可能不同。

跨平台依赖两端集成的 Lynx 引擎、统一页面描述与平台适配层，分别创建和更新本平台 UI。

### 渲染阶段与原生视图的关系

以下以 iOS、Android 上的 Lynx 为范围。Element 树保存引擎侧的界面节点关系和属性；布局节点用于计算位置与尺寸；平台 UI 树由 UIView 等平台对象组成。三种结构的职责不同，节点数量不要求一一对应。仅用于布局的节点可能被扁平化，嵌套文本也可能合并处理，具体行为取决于元件和配置。

首帧可以按“加载 bundle → 执行首帧逻辑并生成 Element 树 → 解析样式 → 计算布局 → 创建或更新平台 UI → 系统绘制”解释。启用首帧直出时，主线程先构建首帧，后台并行初始化完整的组件环境；不能说首帧一定要等待后台完成。

## 双线程、首帧直出与后台接管

Lynx 的双线程架构主要分为主线程和后台线程，两边都有独立的 JS 执行环境。主线程负责初始界面构建、应用 UI 更新和主线程脚本；后台运行完整的组件运行时，处理业务逻辑、组件状态、普通事件回调和更新计算。

以 ReactLynx 为例，构建阶段会生成面向两个线程的代码。页面启动时，主线程执行精简的首帧逻辑，利用已经准备好的数据先显示界面；后台同时初始化组件运行环境，准备好后与主线程已有节点建立对应关系，接管后续更新。

状态变化后，后台计算差异，生成 Patch，也就是界面修改指令，异步发送给主线程；主线程根据指令更新对应 Element，由渲染链路完成必要的布局和绘制。

这样既能减少首屏等待，也能降低业务计算对主线程的占用。代价是跨线程传递和调度延迟；拖拽、跟手动画等场景可以用主线程脚本 MTS 就近处理交互，减少往返。

**框架与执行引擎的分工。**

| 层次 | 负责什么 |
|-|-|
| ReactLynx | Lynx 官方的 React 风格 UI 框架，底层基于 Preact；管理组件、Hooks、状态和更新计算，将页面描述转为 Lynx 引擎调用。 |
| Lynx 引擎 | 提供 Element 操作、样式、布局及平台 UI 渲染能力。 |
| PrimJS／JavaScriptCore | 执行 JavaScript 的引擎，为框架和业务代码提供运行基础。 |

React 风格指“组件化、声明式 UI、状态驱动更新”：开发者描述当前状态应该显示什么，框架处理更新。思路类似 SwiftUI 的 `@State` 驱动 `body`。例如下面的计数器示例：

```jsx
import { useState } from '@lynx-js/react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <view bindtap={() => setCount(count + 1)}>
      <text>{count}</text>
    </view>
  );
}
```

这里使用 Lynx 的 `view`、`text` 元件。

主线程和后台线程具有独立的 JS 运行环境。对象、闭包和状态不会自动共享，需要通过框架提供的机制传递。ReactLynx 是 UI 框架，不是 JS 引擎；具体使用的 JS 引擎由平台、框架版本和配置决定。

**编译期的双线程产物。**

是按线程职责生成不同产物，并非把源码机械地切成互不重叠的两半。首帧所需的组件求值可能在两侧执行；普通事件回调、`useEffect` 等后台专属逻辑按编译规则裁剪，MTS 则在主线程执行。

编译器还会提取稳定的宿主元件结构，为可变属性、文本和子树预留位置。比如计数器外层 `view` 和内部 `text` 的结构稳定，`count` 是动态值；后续更新可以定位动态位置，减少重复创建、比较静态结构。

**Element 树与后台组件结构。**

- **Element 树**是 Lynx 引擎中的元件节点层级，保存界面结构及相关属性，由主线程侧操作；平台视图和布局由引擎进一步处理。
- **“逻辑树”**是本文中的概括，指后台组件／虚拟节点、模板实例及动态数据等用于描述和计算 UI 的结构，不是一个统一的官方类型名。后台组件运行时另外管理状态和回调；它不持有主线程的真实 Element 引用。

例如计数器在后台记录“这里应显示 count”，主线程侧则持有实际承载该内容的 Element。两者通过对应关系协作。

**后台接管与实例对应关系。**

以计数器为例：

1. 主线程沿首帧路径创建 Element，先显示 `0`。
2. 后台初始化组件状态 `count = 0`、回调和节点结构，为后续更新建立基础。
3. 框架匹配两侧结构并建立实例 ID 对应关系，后台由此知道后续修改应落到主线程的哪个实例。
4. 相同部分复用；若动态值不同就更新对应值，若动态子树不同就局部调整。例如首帧价格为 `199`、后台结果为 `179` 时，修正价格文本；这是差异处理示例，不表示必然存在差异。

后台这次计算是为了建立可持续更新的组件环境，不是在后台创建另一套 UIView。接管后主线程仍持有 Element，后台负责驱动后续状态更新。后续计数器流程：

```text
主线程收到点击
  → 后台执行普通点击回调，count 从 0 变成 1
  → 后台计算变化并发送 Patch
  → 主线程按实例对应关系找到文本位置，应用修改
  → 必要的布局与绘制后，显示 1
```

Patch 可以表达属性修改及节点增删等变化，无须每次传整棵树。

**首帧直出与双线程的适用条件。**

- 首屏所需 bundle 和初始数据应可同步使用。例如 Native 已提供商品名和价格，主线程可以先显示；如果价格必须等网络请求，就只能先显示已知内容或占位，不能消除数据等待。
- 后台繁忙仍会延迟普通事件处理与页面更新；MTS 用于减少高频交互的跨线程往返，其自身计算也占用主线程。MTS 捕获的后台数据是经同步传入的值，不是可随意修改的共享变量。
- “双线程”描述主要脚本职责，不表示整个 App 只有两个 OS 线程，也不表示所有 JS 都在后台；布局等任务的具体线程安排仍需结合引擎版本与配置说明。

### 状态更新到界面的执行顺序

状态是框架管理、用于描述界面的数据。在前面的计数器中，`useState(0)` 提供当前 `count` 和更新函数 `setCount`。更新函数向框架请求状态更新；普通变量赋值不会自动触发同样的框架流程。

对于前面示例中的普通 `bindtap`，后台接管后的一次更新可按以下顺序理解：

1. 平台接收点击事件，后台执行注册的点击回调。
2. 回调调用 `setCount`。框架安排状态更新，并计算受影响组件的新界面描述。
3. 框架比较相关新旧描述，将需要修改的文本、属性或子节点组织为 Patch。
4. 框架序列化并异步传递修改指令。主线程侧解析并应用指令，更新对应 Element。
5. 引擎执行必要的样式、布局和平台 UI 更新。系统绘制完成后，用户才能看到新值。

`setCount` 返回不表示新界面已经显示。一次更新也不意味着重新创建整页原生视图；是否需要重新布局，要看变化是否影响尺寸或位置。主线程脚本有单独的执行路径；具体引擎和布局线程安排仍取决于版本与配置。

### useState 的返回值与更新时机

在 `const [count, setCount] = useState(0);` 中，`useState` 是 ReactLynx 提供的 Hook。Hook 是组件调用框架状态等能力的函数。`count` 和 `setCount` 都由开发者命名：第一个变量接收本次渲染读取的状态值，第二个变量接收框架返回的状态更新函数。`0` 是首次建立这份状态时使用的初始值。

调用 `setCount(1)` 是开发者编写的代码，实际调用的是框架返回的函数。框架记录更新并安排后续计算，不会把当前回调中的 `count` 变量立即改成新值。多次更新可能合并处理；如果状态按框架的比较规则没有改变，或者最终界面描述没有变化，就不一定产生可见更新。函数返回、组件重新执行和新画面显示是不同的时刻。

### key、组件身份与状态保存

界面描述表示本次渲染希望显示哪些组件、给组件传入哪些属性，以及组件怎样排列。属性（props）是父组件传给子组件的输入。组件状态是框架为某个持续存在的组件身份保存的数据；状态不只是写在一次性的界面描述中的属性。

`key` 是开发者为同一父节点下的同级子元素指定的身份标识。父节点与组件类型不变时，稳定的 `key` 可以帮助框架在重排前后匹配同一个组件。匹配的作用是保留组件状态，并复用仍然适用的界面节点；`key` 本身不负责把元素分组或决定排列顺序。

假设列表从 A、B、C 变成 C、A、B。B 的 `key` 始终是 `"b"`，组件类型和父节点不变。B 内部通过 `useState` 保存的输入内容是“你好”，父组件同时把 B 的标题改为“新标题”。更新按以下顺序发生：

1. 父组件产生新的子元素描述。新描述将 B 放在第三位，并给 B 传入“新标题”。
2. 框架根据父节点范围、组件类型和 `key`，将新的 B 描述与原有 B 的组件身份匹配。
3. 框架继续使用 B 已保存的状态，并让 B 接收新的属性。B 再次执行时，`useState` 读取保留的“你好”，不因位置变化就重新采用初始值。
4. 框架计算需要修改的内容，调整相关界面节点的顺序并更新标题。输入内容仍属于 B。

可以把框架维护的组件状态记录理解为持续保存数据的位置；这是概念说明，不是要求 ReactLynx 必须采用某个固定的内部类型。框架复用的是匹配组件的状态和可复用节点，不是把旧描述中的全部属性复制到新描述。新属性来自本次父组件传入的值。

同一组件内，框架还依靠 Hook 的调用顺序识别各份状态。因此，不应在会改变调用顺序的条件或循环中调用 `useState`。组件被移除、`key` 改变或类型改变后，重新创建的组件通常会建立新的状态。列表允许插入、删除或重排时，按位置生成的 `key` 可能让状态跟随位置，从而落到错误的数据项上。

## 动态资源与客户端发版边界

客户端安装包中已有 Lynx 引擎、容器和桥接能力；页面 bundle 可以由资源系统独立下发。客户端取得新的兼容 bundle 后，用已有引擎加载它，就能更新页面布局、文案和部分业务逻辑。

动态更新的边界是现有客户端能力：若需要新的 Native 接口、平台组件、权限声明、引擎能力或不兼容的协议，仍可能需要客户端发版。下载新资源也不等于所有用户立即生效，还取决于版本匹配、缓存、下发时机、灰度和加载入口；不能说任意原生功能都可动态更新。

Native 页面代码随客户端发布；选型需要权衡动态迭代能力、原生体验与长期维护成本。

分析页面加载耗时时，可以分别测量资源获取、容器初始化、bundle 解析执行、数据请求、布局和图片加载。先确认资源包是否已在本地可用，再判断页面加载是否需要等待远程资源。
