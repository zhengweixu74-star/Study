## 页面描述到平台 UI 的渲染流程

开发者用 TSX、JSX 和样式描述页面，构建工具把这些源文件转换并打包成 Lynx bundle。客户端加载 bundle 后，Lynx 引擎依次完成：解析脚本、样式和配置 → 执行渲染逻辑，生成元素树 → 计算样式和布局 → 创建或更新平台 UI → 交给系统绘制。

TypeScript 代码由 Lynx 引擎中的 JS 引擎执行，不经过 Swift 或 Kotlin 编译器；Lynx 最终创建的是平台原生 UI，与 WebView 渲染网页是两种方式。页面需要相机、相册、账号等宿主能力时，通常通过 Native 组件或 JSBridge 接入。宿主 App 必须提供这些能力的实现，各平台提供的能力和版本也可能不同。

Lynx 跨平台的方式是：两端各自集成 Lynx 引擎，使用同一份页面描述，再由各端的平台适配层创建和更新本平台的 UI。

### 渲染阶段与原生视图的关系

以下内容针对 iOS 和 Android 上的 Lynx。渲染过程用到三种结构：

- Element 树保存引擎侧的界面节点关系和属性。
- 布局节点用于计算位置和尺寸。
- 平台 UI 树由 UIView 等平台对象组成。

三种结构的节点数量不必一一对应。例如只参与布局的节点可能被扁平化，不生成平台视图；嵌套文本可能合并成一个平台视图。具体行为取决于元件类型和配置。

首帧的渲染顺序是：加载 bundle → 执行首帧逻辑，生成 Element 树 → 解析样式 → 计算布局 → 创建或更新平台 UI → 系统绘制。启用首帧直出时，主线程先构建首帧，后台同时初始化完整的组件环境，首帧不必等待后台初始化完成。

## 双线程、首帧直出与后台接管

Lynx 的双线程架构包括主线程和后台线程，两个线程各有一个独立的 JS 执行环境。主线程负责构建初始界面、应用 UI 更新、执行主线程脚本。后台线程运行完整的组件运行时，负责业务逻辑、组件状态、普通事件回调和更新计算。

以 ReactLynx 为例，构建阶段分别为两个线程生成代码。页面启动时按以下方式分工：

1. 主线程执行精简的首帧逻辑，用已经准备好的数据先显示界面。
2. 后台线程同时初始化组件运行环境。
3. 后台线程准备好后，与主线程已有的节点建立对应关系，接管后续更新。

状态变化后，后台线程计算差异，生成 Patch，并异步发给主线程。Patch 是描述界面如何修改的指令。主线程按 Patch 更新对应的 Element，再由渲染链路完成必要的布局和绘制。

双线程分工让首屏更早显示，也让业务计算少占主线程。代价是跨线程传递和调度带来延迟。拖拽、跟手动画等场景可以用主线程脚本（MTS，Main Thread Script）直接在主线程处理交互，省掉线程间往返。

**框架与执行引擎的分工。**

| 层次 | 负责什么 |
|-|-|
| ReactLynx | Lynx 官方的 React 风格 UI 框架，底层基于 Preact；管理组件、Hooks、状态和更新计算，将页面描述转为 Lynx 引擎调用。 |
| Lynx 引擎 | 提供 Element 操作、样式、布局及平台 UI 渲染能力。 |
| PrimJS／JavaScriptCore | 执行 JavaScript 的引擎，为框架和业务代码提供运行基础。 |

React 风格指组件化、声明式 UI 和状态驱动更新：开发者描述某个状态下界面应该显示什么，框架负责在状态变化时更新界面。这种思路类似 SwiftUI 中 `@State` 驱动 `body`。例如下面的计数器：

```jsx
import { useState } from '@lynx-js/react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <view bindtap={() => setCount(count + 1)}>
      <text>{count}</text>
    </view>
  );
}
```

计数器使用 Lynx 的 `view`、`text` 元件。

主线程和后台线程的 JS 运行环境互相独立，对象、闭包和状态不会自动共享，需要通过框架提供的机制传递。ReactLynx 是 UI 框架，运行在 JS 引擎之上；具体使用哪个 JS 引擎，由平台、框架版本和配置决定。

**编译期的双线程产物。**

编译器按线程职责为两个线程分别生成产物，两份产物的内容可以重叠。首帧所需的组件求值可能在两个线程都执行；普通事件回调、`useEffect` 等只在后台执行的逻辑，按编译规则从主线程产物中裁掉；MTS 在主线程执行。

编译器还会提取稳定的宿主元件结构，并为可变的属性、文本和子树预留位置。例如计数器外层的 `view` 和内部的 `text` 结构固定，`count` 是动态值。后续更新时，框架直接定位到动态值所在的位置修改，无需重复创建或比较固定的结构。

**Element 树与后台组件结构。**

- **Element 树**是 Lynx 引擎中的元件节点层级，保存界面结构和属性，由主线程操作。引擎再根据 Element 树处理平台视图和布局。
- **“逻辑树”**是本文的概括说法，泛指后台用来描述和计算 UI 的结构，包括组件／虚拟节点、模板实例和动态数据，没有对应的统一官方类型名。后台组件运行时另外管理状态和回调；后台组件运行时不持有主线程中真实 Element 的引用。

例如在计数器中，后台记录“这里显示 count”，主线程持有实际显示这个值的 Element。两侧通过对应关系协作。

**后台接管与实例对应关系。**

以计数器为例：

1. 主线程按首帧路径创建 Element，先显示 `0`。
2. 后台初始化组件状态 `count = 0`、回调和节点结构，为后续更新做准备。
3. 框架匹配两侧的结构，建立实例 ID 对应关系。后台据此知道后续修改应作用到主线程的哪个实例。
4. 两侧相同的部分直接复用。动态值不同时，框架更新对应的值；动态子树不同时，框架局部调整子树。例如首帧显示价格 `199`，后台算出的价格是 `179`，框架就修正价格文本。两侧结果相同时，这一步没有修改。

后台的这次计算用于建立可以持续更新的组件环境，后台不会另外创建一套 UIView。接管后，Element 仍由主线程持有，后台负责驱动后续的状态更新。之后点击计数器的流程是：

```text
主线程收到点击
  → 后台执行普通点击回调，count 从 0 变成 1
  → 后台计算变化并发送 Patch
  → 主线程按实例对应关系找到文本位置，应用修改
  → 必要的布局与绘制后，显示 1
```

Patch 可以表达属性修改、节点增删等变化，每次只传变化部分，无需传整棵树。

**首帧直出与双线程的适用条件。**

- 首屏所需的 bundle 和初始数据必须能同步拿到。例如 Native 已经提供商品名和价格，主线程可以直接显示。如果价格要等网络请求返回，主线程只能先显示已知内容或占位，数据等待时间仍然存在。
- 后台线程繁忙时，普通事件处理和页面更新仍会延迟。MTS 减少了高频交互的跨线程往返，但 MTS 自身的计算也占用主线程。MTS 捕获的后台数据是同步传入的值，MTS 和后台不共享同一个变量。
- “双线程”描述的是主要脚本的分工。整个 App 仍有其他 OS 线程，主线程上也有 JS 在执行。布局等任务具体在哪个线程执行，取决于引擎版本和配置。

### 状态更新到界面的执行顺序

状态是由框架管理、用来描述界面的数据。在计数器中，`useState(0)` 返回当前的 `count` 和更新函数 `setCount`。调用 `setCount` 会请求框架更新状态；直接给普通变量赋值，框架不会感知，也不会更新界面。

后台接管之后，计数器中普通 `bindtap` 触发的一次更新按以下顺序执行：

1. 平台接收点击事件，后台执行注册的点击回调。
2. 回调调用 `setCount`。框架安排状态更新，并重新计算受影响组件的界面描述。
3. 框架比较新旧界面描述，把需要修改的文本、属性或子节点整理成 Patch。
4. 框架序列化 Patch，异步传给主线程。主线程解析并应用 Patch，更新对应的 Element。
5. 引擎执行必要的样式、布局和平台 UI 更新。系统绘制完成后，用户才看到新值。

`setCount` 返回时，新界面还没有显示。一次更新只修改变化的部分，不会重建整页原生视图；只有变化影响尺寸或位置时才需要重新布局。主线程脚本走单独的执行路径；具体的 JS 引擎和布局线程安排取决于版本和配置。

### useState 的返回值与更新时机

在 `const [count, setCount] = useState(0);` 中，`useState` 是 ReactLynx 提供的 Hook。Hook 是组件用来获取框架状态等能力的函数。`count` 和 `setCount` 都由开发者命名：第一个变量接收本次渲染读到的状态值，第二个变量接收框架返回的状态更新函数。`0` 是框架首次创建这份状态时使用的初始值。

开发者调用 `setCount(1)`，实际调用的是框架返回的函数。框架记录这次更新并安排后续计算；当前回调中的 `count` 变量仍是旧值。框架可能把多次更新合并成一次。如果按框架的比较规则状态没有改变，或者最终界面描述没有变化，用户就看不到更新。`setCount` 返回、组件重新执行、新画面显示，是先后发生的三个时刻。

### key、组件身份与状态保存

界面描述表示本次渲染要显示哪些组件、给组件传入哪些属性、组件如何排列。属性（props）是父组件传给子组件的输入。组件状态是框架为某个持续存在的组件身份保存的数据；每次渲染重新生成的界面描述中只有属性，状态保存在框架中。

`key` 是开发者为同一父节点下的同级子元素指定的身份标识。父节点和组件类型不变时，框架用稳定的 `key` 在重排前后找到同一个组件。找到之后，框架保留这个组件的状态，并复用仍然适用的界面节点。`key` 只用于识别身份，元素的分组和排列顺序由界面描述决定。

假设列表从 A、B、C 变成 C、A、B。B 的 `key` 始终是 `"b"`，组件类型和父节点不变。B 内部用 `useState` 保存的输入内容是“你好”，父组件同时把 B 的标题改为“新标题”。更新按以下顺序发生：

1. 父组件生成新的子元素描述。新描述把 B 放在第三位，并给 B 传入“新标题”。
2. 框架根据父节点、组件类型和 `key`，把新的 B 描述与原有 B 的组件身份对应起来。
3. 框架沿用 B 已保存的状态，并把新属性传给 B。B 再次执行时，`useState` 读到保留的“你好”，位置变化不会让状态回到初始值。
4. 框架计算需要修改的内容，调整界面节点的顺序并更新标题。输入内容“你好”仍属于 B。

可以把框架为每个组件维护的状态记录理解为一个持续保存数据的位置；ReactLynx 内部用什么类型实现这份记录，不影响这里的结论。框架复用的是匹配组件的状态和可复用的节点；新属性取自本次父组件传入的值，旧描述中的属性不会被复制过来。

在同一个组件内，框架按 Hook 的调用顺序区分各份状态。所以 `useState` 只能在组件顶层按固定顺序调用，不能放进会改变调用顺序的条件或循环。组件被移除、`key` 改变或组件类型改变后，框架通常为重新创建的组件建立新的状态。列表允许插入、删除或重排时，如果用位置作为 `key`，状态会跟着位置走，最终落到错误的数据项上。

## 动态资源与客户端发版边界

客户端安装包中已经包含 Lynx 引擎、容器和桥接能力；页面 bundle 可以由资源系统单独下发。客户端拿到新的、兼容的 bundle 后，用已有引擎加载，就能更新页面布局、文案和部分业务逻辑。

动态更新只能使用客户端已有的能力。需要新的 Native 接口、平台组件、权限声明、引擎能力，或者协议不兼容时，仍可能需要客户端发版。新资源下发后，用户何时生效还取决于版本匹配、缓存、下发时机、灰度和加载入口。

Native 页面代码随客户端一起发布。选择 Lynx 还是 Native，需要权衡动态迭代能力、原生体验和长期维护成本。

分析页面加载耗时时，分别测量资源获取、容器初始化、bundle 解析执行、数据请求、布局和图片加载。先确认资源包是否已在本地，再判断页面加载是否需要等待远程资源。
