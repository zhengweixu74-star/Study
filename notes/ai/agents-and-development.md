## 模型能力与 Agent 工具链

模型负责理解问题、分析证据和生成方案。Agent 宿主负责提供上下文、调度工具、检查权限和收集执行结果。任务质量由模型和宿主共同决定。

工具能力已经够用时，实现是否正确取决于模型的判断能力。例如实现异步 UI 更新时，模型要分清数据就绪和布局就绪，还要分清任务取消、动画取消和旧回调失效。找到文件、写出能编译的代码之后，这些判断仍需模型完成。

上下文、Skill 和验证工具可以补足工作流程，但模型仍可能误读证据。选择模型时，比较错误判断的次数、人工返工量和任务完成质量。

### Agent、Harness 与 Harness 工程

按 AI 工程中的常见用法：Agent 是根据任务目标选择动作、调用工具、再根据执行结果继续推进的系统。Harness 是支撑模型运行这个循环的外围程序和运行环境，通常负责组织上下文、执行工具、保存状态、控制权限和验证结果。Harness 是惯用说法，各产品划分的边界和命名不尽相同。

模型根据当前输入生成下一步动作或回答。Harness 把可用信息交给模型，接收模型生成的工具调用请求，检查权限和参数，执行工具，再把结果送回模型。工具是实际完成外部操作的程序或接口，例如读取文件或运行检查。模型只生成命令文本，命令由 Harness 调用工具执行。

一次典型循环是：Harness 整理任务与上下文 → 模型生成工具名称和参数 → Harness 检查并调用工具 → 工具返回结果 → Harness 保存必要状态并把结果加入后续输入 → 模型决定继续、结束或请求补充信息。

所以 Agent 与 Harness 是整体和部分的关系：模型、Harness 和可用工具组合成一个 Agent 系统，Harness 是其中支撑执行的部分。Agent 描述系统如何围绕目标行动，Harness 描述运行环境如何让这些行动实际发生并受到约束。

Harness 工程是设计和改进这套支撑环境的工作，例如提供准确的工具说明、维护可检索的项目导航、保存任务进度、限制可执行的操作、提供验证结果的检查入口。Harness 工程改善的是 Agent 的执行条件，模型本身没有被训练，判断仍可能出错。

## AI 生成技术方案的检查方法

技术方案是实现需求的具体安排，说明采用什么实现方式、各部分代码负责什么、执行步骤是什么、如何验证结果。AI 生成技术方案后，要依据需求、现有代码和实际验证结果检查方案；方案描述完整，只说明写得全，可行性要靠这些依据确认。

1. **检查实现方式是否满足需求：** 先明确三件事：功能接收什么输入、应产生什么结果、有哪些业务约束。业务约束是实现和运行时必须遵守的业务条件或规则。再逐项检查方案是否覆盖这些要求、是否遗漏异常情况、是否改变原有功能。“体验更好”这类笼统目标，要改写成可以观察和判断的预期结果。

2. **检查能否复用已有能力：** 能力复用指用已有代码或组件提供的功能完成当前需求。先查找现有实现，再核对现有实现的输入要求、执行结果和失败行为是否符合当前需求。三项都符合时，优先直接使用或做必要修改；名称或表面效果相似，还要逐项核对才能确定可以复用。确实需要新增实现时，说明现有能力不能满足哪项要求。

3. **检查方案选择是否有依据：** 说明为什么选择当前方案，以及当前方案相比其他可行方式的优点和代价。依据可以来自现有代码、接口约定或实际测量。按当前需求挑选需要比较的方面，例如实现复杂度、运行耗时、内存占用和后续修改成本。已经确认的事实、尚未验证的判断和成立条件分开记录。

4. **用最小示例和测试验证不确定结论：** 最小示例是一个可运行的程序，只保留验证某个具体问题所必需的代码、输入和运行条件。方案依据不足或关键结论尚未验证时，先明确要验证的问题和预期结果，再制作最小示例。交互效果通过实际操作观察，计算结果和规则通过测试检查。最小示例必须保留会影响结论的输入规模和执行时机。最小示例通过，只验证了被保留的条件；完整功能还要单独验证。

5. **沿执行链路检查风险及处理方式：** 执行链路是一次操作从触发到产生结果所经过的调用、数据传递和状态变化。先沿代码核对：谁调用谁、传入什么、谁修改哪些数据、何时交付结果。代码无法确定实际顺序或行为时，再通过运行、日志或测试观察。对确实可能发生的情况，写清触发条件、影响、由哪段代码处理、处理后的结果。例如用户可以重复发起操作时，要检查较早的操作完成后是否会覆盖较新操作的结果；如果会覆盖，就明确如何识别并丢弃过时的结果。

6. **检查代码架构是否合理：** 代码架构指代码职责如何划分，以及各部分如何互相调用、使用数据和依赖。依赖指一部分代码使用另一部分代码提供的类型、数据或功能。检查四点：每部分代码职责是否清晰，数据由谁保存和修改，调用关系是否容易理解，修改一个功能是否会牵动无关代码。代码组织遵循现有工程的约定，规模与当前需求相当；每个类、接口和状态都要有实际用途。

检查后，把已确认的问题和修改建议补回方案。对尚未验证的结论，记录还缺什么证据、准备怎样验证、什么结果能支持或否定当前判断。

## AI 代码审查与结果验证

代码审查（Code Review）依据需求和工程约定，检查代码是否正确实现了预期行为、是否影响已有功能。审查先读懂代码的实现方式，再逐项判断实现是否符合要求。

审查主线是：按需求行为分组 → 明确目的与判断条件 → 确认文件和函数职责 → 沿数据流与事件顺序审查 → 检查既有行为 → 核对验证证据。方案阶段检查需求理解、实现选择和已有能力复用；实现完成后，用最终代码差异和运行结果继续审查。AI 的说明只用来定位代码，结论以实际证据为准。

### 按需求行为分组

把一次改动分成若干代码组，每组都能单独说明目的和预期结果。例如字段解析、展示规则、刷新时机和事件上报分别审查。分组按需求行为划分，一个文件可以属于多组，公共组件常常同时参与多个行为。

检查每项需求是否都有对应实现，每项修改是否都有明确目的。对新增的状态、分支、辅助方法、默认值和重试逻辑，逐一追问：删除这段代码，哪项要求会无法成立？确实需要的输入校验和失败处理保留；既没有需求依据、也没有实际失败路径依据的复杂逻辑，重新评估是否需要。

### 明确目的与判断条件

根据已确认的需求，把目的拆成可以观察和判断的条件。业务约束是实现和运行时必须遵守的业务规则，例如适用页面、数值边界、更新时机和标识优先级。每个判断条件都写明触发输入、成立条件和预期结果。

例如，“列表标识更新正确”可以拆成“首次响应决定本批文案”“本地计数变化不重算文案”“刷新成功后重新计算”“刷新失败保留原列表”。同时考虑缺失数据、边界值、重复操作和中断操作。

判断条件从需求推出，再用来检查 AI 生成的实现。尚未确认的业务参数记录为待确认；示例值和 AI 自行设定的值，确认之前只是假设。

### 确认文件和函数职责

确认哪些代码负责解析输入、保存状态、修改状态、刷新界面和上报事件。明确入口函数、调用方、数据接收方，以及公共组件的其他使用入口。依赖是某段代码使用另一段代码提供的类型、数据或功能的关系。

除了查看最终差异（diff），还要读取改动函数的完整上下文和必要的调用方。未跟踪的新文件不会出现在普通 git diff 中，需要单独检查。函数名、注释和 Agent 总结只提供线索，职责和执行顺序以实际代码为准。

### 沿数据流与事件顺序审查

数据流是数据从输入开始，经过解析、传递、保存或转换，最终产生结果的路径。事件顺序是请求完成、用户操作、回调执行等事件之间已经确定的先后关系。异步代码的执行顺序可能与书写顺序不同。

对每组代码回答五个问题：输入是什么；谁改变了什么；什么时候改变；结果是什么；证据在哪里。输入包括接口数据、已有状态和用户操作。对每个状态，追踪由谁持有、谁能修改、何时创建和清除，以及页面退出或任务取消后旧结果是否还会被使用。

例如，列表文案按响应中的计数决定，规则要求文案只在刷新成功后切换。首次响应计数为 9，展示组件保存“未达标”。用户操作使当前计数变成 10，组件仍保留“未达标”。刷新成功并返回计数 10 后，组件才保存“已达标”。这里有两个状态：当前计数和已保存的文案。“计数 ≥ 10”的表达式只决定文案内容；更新时机是否正确，要检查文案在什么时候被重新计算。

快照是根据某一时刻的数据计算并保存下来的结果。使用快照时，要检查快照的创建、读取和清除入口。如果卡片复用时按当前计数重新判断，就会违反“刷新后才切换”的要求。还要检查缓存读取、加载更多和刷新失败分别如何影响已保存的结果。

### 检查既有行为

一组代码满足自身目的后，还要检查其他调用方和原有功能。回归验证指修改后重新检查受影响的既有行为。例如公共卡片组件增加标识后，需要检查无标识卡片、空标题、长标题、滚动复用和其他页面。

影响范围指一处修改可能改变多少调用方或功能的行为。业务判断、共享状态、异步回调、缓存和公共组件影响范围大，优先仔细阅读。缓存 key 是区分缓存记录的标识；某个条件会改变布局高度时，要检查缓存 key 是否包含这个条件。

代码量大时，重复的字段映射可以先确认规则，再逐处核对名称和类型；状态变化和公共组件要读取完整上下文。影响大小取决于改动的位置和内容，与新增行数没有直接关系。

### 核对验证证据

把每个判断条件对应到代码位置和必要的执行结果。静态检查指通过阅读或分析代码确认规则；运行验证指执行程序并观察实际结果。静态证据不足以确认行为时，补充有针对性的测试、操作、录屏或日志，并把仍未验证的条件记录为待验证。

| 验证方式 | 能支持的结论 | 不能据此直接认定 |
| --- | --- | --- |
| git diff --check | 差异没有该命令检查的空白格式问题 | 功能正确或编译通过 |
| 编译通过 | 该工具链和构建范围内的语法、类型与依赖通过编译 | 业务规则、交互和所有平台正确 |
| 自动化测试 | 指定输入、条件和断言覆盖的结果符合预期 | 未覆盖场景也正确 |
| Mock 与设备操作 | 指定模拟数据和操作下观察到预期行为 | 真实接口始终符合模拟结构 |
| 截图 | 指定状态下的最终可见样式 | 状态变化和异步执行顺序正确 |
| 录屏、日志或事件记录 | 记录范围内的操作结果、状态变化或上报内容 | 未记录的分支也已验证 |

断言是测试中检查实际结果是否符合预期的条件。用例和断言要从需求推出；如果照着实现写，测试会和实现犯同一个错误。验证记录要写明代码版本、输入、环境、操作和观察结果。代码修改后，旧版本的验证结果只对旧版本有效，新版本需要重新验证。测试基础见[自动化测试](../engineering/xcode-and-testing.md#自动化测试)。

代码很多时，每审完一组，就记录已确认和待验证的条件。各组都审完后，再检查组间的数据传递、共享状态和需求覆盖是否完整。发现问题后，针对失败场景修改并复测，再回归受影响的原有功能；重查范围限于有变化或仍有疑点的部分。

AI 可以辅助分组、解释调用链、生成用例和再做一轮审查。开发者仍要核对问题依据、修复后的差异和执行证据。AI 自称“已修复”或“检查通过”只是陈述，验收结论以这些证据为准。

### AI 辅助验收的执行流程

验收依据已经确认的需求，判断实际功能是否产生预期结果。AI 可以生成用例、准备数据、调用工具执行操作和整理证据。通过条件由需求和已确认的规则决定，再用实际观察结果支持；通过条件不能根据现有实现反推。

执行顺序为：明确输入与预期结果 → 生成用例 → 准备数据和环境 → 执行操作 → 比较实际结果 → 保存证据 → 修改后复测并检查受影响功能。设备操作的实现见 [命令行工具与设备端 Driver](../engineering/xcode-and-testing.md#命令行工具与设备端-driver)。

先确认每个用例的初始状态、输入、操作和预期结果。例如验证列表定位功能时，分别准备目标项存在、目标项不存在、响应延迟、用户开始拖动等条件。每个用例都检查目标项、最终位置和中断行为，“页面看起来正常”不能作为通过依据。

Mock 指在测试中人为提供指定的数据或行为，替代真实依赖。例如测试让某个接口在 2 秒后返回包含 A、B、C 的列表，响应时间和内容就都可控。用启动参数切换模拟数据时，App 必须读取这个参数并选择对应的模拟数据，网络响应才会改变。

模拟接口和操作界面是两种独立的能力。控制网络响应要用模拟服务、依赖注入或合适的代理工具；点击和滑动要用设备操作工具。能控制手机的工具，通常无法改写接口响应。

等待条件描述的是实际状态，而非固定的秒数。接口返回后，App 可能还在创建视图、更新列表或布局，目标元素可能尚未出现，位置也可能尚未稳定。所以测试要等待用例要求的元素、加载结束状态或布局条件出现，并设置合理的等待上限。

| 检查目标 | 需要明确的条件或证据 |
| --- | --- |
| 是否选中正确项 | 通过唯一标识、无障碍标识或可核对日志确认目标项，不能只看相似文案 |
| 最终位置是否正确 | 指定参考区域、比较项的顶部还是中心，以及允许的坐标误差 |
| 目标不存在时的行为 | 按需求检查提示、停止定位或其他明确结果，不擅自补出一个目标 |
| 用户接管是否生效 | 在自动操作期间发起拖动，检查自动动画是否停止及后续位置是否被覆盖 |
| 动画是否流畅 | 记录动画过程，并结合性能时间线或帧统计判断；单张截图只能检查某一时刻的状态 |

例如在固定设备上检查 B 的顶部与列表可视区域顶部对齐，约定两者距离不超过 2 点。测试记录目标标识 B、参考区域和实际距离。2 点是示例值，正式误差由需求确定。比较距离时，两个位置要使用同一个坐标系，屏幕坐标和视图内部坐标不能混用。

工具返回“点击成功”，只说明点击操作已经执行。验收还要检查操作后的业务结果，例如保存提示出现、文件生成或列表状态更新。证据只覆盖实际执行过的条件：用模拟数据通过，真实接口、其他设备和未执行的路径仍需另外验证。截图、日志和测试的证据范围见 [核对验证证据](#核对验证证据)。

AI 根据现象提出原因时，缺少依据的判断标记为待验证。先用日志检查关键输入、状态变化、分支选择和执行顺序，再判断原因；AI 生成的解释在得到日志证实之前只是假设。修改后重新执行失败用例，并检查受影响的既有行为。

评估 AI 辅助验收节省的时间时，在相同功能和用例范围内，比较数据准备、执行、检查和复测的耗时，同时计入自动化配置和维护的时间。有同条件的对比记录，才能给出提升比例。

人工检查的范围根据修改影响、规则复杂度和已有证据决定。共享状态、异步顺序或关键业务规则尚未验证时，要补充检查。功能是否正确要靠验证证据证明；AI 生成了完整代码、人工暂时没看出问题，都不算证据。

## AI 辅助开发与跨平台复用

AI 降低了两端分别维护原生代码的成本；跨平台技术让两端共享同一份实现，并长期复用。两者解决的问题有交集，但各有用途。

iOS 和 Android 分别实现同一条规则时，规则一变，两端都要分别修改、审查和验证。共享公共规则可以减少两端实现的分歧；平台差异明显的 UI、手势和系统能力，则可能更适合各自实现。

选型应比较可复用程度、平台差异、框架升级和调试成本，以及长期维护成本。Kotlin Multiplatform 可以共享业务逻辑，同时保留原生 UI。共享代码仍要在各平台分别集成验证；性能优劣以实际测量为准。

## 模型幻觉的成因与验证

模型通过训练学习上下文与后续文本之间的统计关系，生成在当前条件下语言上合理的输出，语言合理的输出仍可能与事实不符。知识缺失或过时、训练信息互相矛盾、上下文遗漏、推理错误、把相似事实安到错误对象上，都会产生看似可信的错误答案。

如果训练和评估更奖励作答、较少奖励承认不知道，模型在不确定时也会倾向于猜测。幻觉有多种成因，随机采样只是其中之一，所以降低 temperature 无法保证事实正确。检索可靠来源、调用工具验证、约束输出格式、允许模型表达不确定，都能降低幻觉风险；但检索内容本身有误或模型误读证据时，仍会出错。

## 工具调用的执行链路

Agent 宿主把可用工具的名称、用途和参数结构提供给模型。模型结合任务和训练中学到的调用模式，输出结构化的调用请求，例如“调用某个工具，并传入这些参数”。宿主解析请求，校验权限和参数，然后执行函数、脚本或 API，再把结果交回模型。模型根据结果继续回答或选择下一步。

```text
用户任务 + 工具说明
    → 模型生成工具名称和参数
    → Agent 宿主执行工具
    → 工具结果加入上下文
    → 模型继续推理／回答
```

运行脚本的是外部执行环境，模型本身只输出文本。没有工具协议和执行器时，模型写出的命令只是普通文本，不会运行。工具是否可用、调用是否成功、是否被允许，都由具体的宿主和工具决定。

## Skill、Tool 与 MCP 的分工

| 概念 | 核心作用 | 例子 |
|-|-|-|
| Skill | 可复用的做事说明与工作材料，通常含 SKILL.md，也可以带脚本和参考资料 | “修改资源位前先读 Schema，再预览、保存、验证”的流程 |
| Tool | 一项实际可调用的外部能力，有输入、执行逻辑和输出 | 读取文件、运行脚本、查询资源位 |
| MCP | AI 应用与外部服务之间发现、调用能力及交换上下文的标准协议 | 宿主通过 MCP 获取服务提供的工具清单，再调用查询工具 |

假设资源服务提供 `get_resource(id)`：这个查询能力是 Tool；用 MCP 的 `tools/list` 发现 `get_resource`、用 `tools/call` 调用 `get_resource`，属于协议层；“修改前先查询现状、预览差异”的说明是 Skill。Tool 也可以是本地内置函数或普通 API，不经过 MCP；MCP Server 除了 Tools，还可以提供 Resources 和 Prompts。三者可以组合使用，Skill 也可以不配 MCP Server。

## Skill 与普通 Markdown 的关系

Markdown 是一种文本标记格式，用标题、列表、代码块等语法组织文档。Skill 是供 Agent 复用的一组任务说明和配套材料，可以包含 Markdown 文档、脚本、参考资料与模板。两者处在不同层次：Markdown 规定内容的书写格式，Skill 规定内容如何组织、被宿主发现和使用。

Agent 宿主是负责组织模型输入、读取文件和执行工具的应用。按 Agent Skills 格式组织的技能目录以 `SKILL.md` 为入口。入口文件开头是 YAML 元数据，用字段记录技能名称、用途等信息，其中 `name` 和 `description` 是必需字段。`name` 标识技能，`description` 说明技能负责什么、何时使用。脚本和参考资料是可选内容。

文件名和字段格式统一后，支持这套约定的宿主可以按固定规则查找入口、解析元数据、列出可用技能。如果只用普通 Markdown，每个文件的名称和章节各不相同，宿主还要另外约定哪个文件是入口、如何提取适用条件。统一格式还让多个支持该格式的工具可以复用同一份技能。

一种常见的使用流程是：

1. 宿主从配置的目录或技能清单中发现技能，解析名称、用途和入口位置。
2. 宿主向模型提供简短的技能目录。模型根据用户任务选择相关技能，或者用户直接指定技能。
3. 宿主按自己的实现方式，把选中技能的正文提供给模型，例如执行模型发起的文件读取请求。
4. 模型根据正文中的步骤，在需要时请求读取参考资料或调用脚本。宿主检查权限并执行工具，再将结果交给模型。

普通 Markdown 也能描述流程、引用脚本，也能由宿主按需读取。模型拿到的说明、工具和权限相同时，普通 Markdown 中的流程同样能指导任务执行。Skill 的命名和格式只统一了发现和使用的约定，执行能力仍来自宿主提供的工具。

宿主要发现并加载 `SKILL.md`，文件必须放在宿主支持的位置，或者通过宿主支持的方式注册，只改文件名不够。正文中写的脚本路径只是文本；脚本能否运行，取决于宿主是否提供了执行工具、依赖和权限。

## Skill 的规模与上下文控制

一个 Skill 围绕一项明确任务组织，只保留完成该任务必需的说明。Agent Skills 的编写建议是：`SKILL.md` 正文控制在 5,000 token 以下，主文件保持在 500 行以下。这两个数字是控制体量的建议值，宿主不一定强制执行，也不必写满；具体宿主可能还有自己的限制。

token 是模型切分文本后使用的计量单位。一个 token 对应的汉字、英文单词或字节数不固定，所以数行数或字符数只能粗略估计 token 数。上下文是模型本次推理可以使用的输入信息，包括系统指令、对话、技能说明和工具返回内容，这些内容共同占用模型的输入容量。

控制上下文的关键是分阶段提供必要内容。这种做法称为渐进式披露，可以分为三层：

1. 技能目录只提供名称、用途和入口。用途说明写到足以判断技能是否适合当前任务即可，不复制整套流程。
2. 选中技能后，再提供 `SKILL.md` 正文。正文保留必要输入、主要步骤、必须遵守的要求和预期输出。
3. 当前步骤需要时，才读取详细接口说明、长示例或其他参考资料。正文写明在什么时候读取哪个文件。

例如一个技能支持十个接口，主文件列出每个接口的用途和资料路径。任务只调用一个接口时，只读取这个接口的详细说明。十份资料拆成十个文件后，如果仍然全部读入模型上下文，占用并不会减少。渐进式披露控制的是内容进入模型上下文的时机；宿主为解析元数据读取磁盘文件的方式，是另一回事。

脚本适合承担格式转换、数据计算等确定性工作。确定性工作指相同输入和条件下，按明确规则执行并得到固定结果的工作。脚本源码只有被读取时才进入模型上下文，脚本存放在磁盘上或被执行都不会占用上下文。工具返回的日志和数据会进入后续输入，所以工具只返回任务需要的结果摘要、必要字段和失败原因。

压缩内容时，优先删除重复的解释、无关的背景和重复加载的资料。必需的权限要求、输入约定和完成条件保留在主文件中；为减少 token 把关键要求移进附件时，主文件必须写明何时读取这个附件。上下文占用取决于实际读入的内容，与文件夹的磁盘大小无关；模型支持的最大上下文也不应全部留给单个 Skill。

判断规模是否合适，要同时看实际加载的 token 数和任务完成质量。主文件容易读懂、资料能按需找到、执行时没有遗漏关键步骤，拆分才算有效。如果说明变短后，模型反复搜索、重复读取或漏掉要求，就调整内容的组织方式，继续删字解决不了问题。

## 跨端 UI 一致性的验证方案

跨端 UI 一致性可以按以下步骤验证。

1. 以设计稿与明确规则为共同标准，补充间距、字体、圆角，以及加载、空数据、长文本等状态。
2. 建立经过验证的双端组件映射和模板／Skill，记录每个 iOS 视图约束对应 Android 的哪个 XML、ViewHolder 和动态样式。修正过的共性问题，写回规则或组件。
3. 固定测试数据、图片、语言、主题和设备尺寸，让两端自动进入同一业务状态并截图，按业务区域比较布局；系统栏和字体渲染的差异设置合理容差。两端还要各自对照设计稿，防止两端一致但都偏离设计。
4. 对异步交互检查状态变化和取消时机：用户中断后是否停止，页面退出后是否仍执行回调。这些检查需要实际操作，静态截图看不出来。
5. 把具体的差异报告交给 AI 小范围修正，再重新检查，并限制自动修正的次数；难以判断或反复失败时转人工处理。先验证单个组件，再扩展到完整页面。

## Codex 的 AGENTS.md 加载与代码定位

`AGENTS.md` 是提供给编码 Agent 的项目说明文件，可以记录目录职责、开发规则和常用代码入口。Agent 宿主是运行模型、提供文件读取和命令执行等工具的应用。`AGENTS.md` 的内容只有被宿主加载或被模型读取后，才进入模型可以使用的上下文。

### 启动时的自动加载

按 Codex 官方说明中的默认发现规则，Codex 启动时先读取用户级指令，再沿项目根目录到当前工作目录的路径查找项目级指令。当前工作目录是本次任务选定的起始目录，与搜索结果所在的目录无关。以下说明只针对 Codex 的默认机制；其他 Agent、其他宿主或额外配置要按各自规则判断。

用户级指令通常位于 `~/.codex`；配置了 `CODEX_HOME` 时，以该目录为准。Codex 优先读取 `AGENTS.override.md`，没有时再读取 `AGENTS.md`。项目路径上的每个目录也按 `AGENTS.override.md`、`AGENTS.md`、配置中的备用文件名顺序查找；每个目录最多选取一个文件。

项目级指令按从根目录到当前工作目录的顺序组合。在适用范围内，更深目录中的指令覆盖上层项目指令中冲突的部分，不冲突的规则继续有效。系统指令优先级更高，局部文件无法覆盖。

假设一个工程有四个文件：根目录的 `AGENTS.md`、`Modules/AGENTS.md`、`Modules/Community/AGENTS.md` 和 `Modules/Home/AGENTS.md`。从工程根目录启动时，默认项目指令链只包含根目录文件。从 `Modules/Community` 启动时，默认项目指令链包含根目录、`Modules` 和 `Community` 的三个文件，同级的 `Home` 文件不在其中。两种情况下，用户级指令都会另外加载。

所以 Codex 只查找根目录到工作目录这一条路径上的文件，不会递归遍历整个工程读取每个模块。启动时加载的指令总量还受配置中的大小限制，超出限制的内容不会被完整加载。

### 查代码时的主动读取

主动读取指模型根据任务和已有说明，调用文件工具获取更多内容。例如根目录说明列出了某个模块的 `AGENTS.md` 路径，模型按这个路径读取模块职责和实现入口。Markdown 链接只提供目标地址，模型调用文件工具读取后，目标文件的内容才进入上下文。

任务进入启动指令链之外的子目录时，模型要检查该目录及相关上级目录中适用的说明，这属于任务执行中的主动读取。搜索命中子目录里的源码时，宿主不会因此自动加载沿途的 `AGENTS.md`，本次会话的工作目录也保持不变。

判断实际读取了哪些内容时，要区分宿主预先注入的指令和工具读取的结果。工具记录能证明某次主动读取发生过；没有读取记录时，内容仍可能在启动时被宿主注入。“配置要求读取”和“已经观察到读取”要分开说明。

### 用分层导航缩小搜索范围

分层导航指把工程信息按“工程整体 → 业务模块 → 具体实现”分层组织。根目录说明记录模块职责、候选目录和导航文档入口。模块说明记录本模块负责的功能、关键类型或文件，以及进一步阅读的路径。详细实现留在源码或专题文档中，每层只写本层信息，不重复复制下层内容。

已有导航时，可以按以下顺序定位实现。这是一种常见做法，实际顺序由任务、已有上下文和工具结果决定。

1. 模型从用户描述中提取功能对象和行为，例如“详情页”“评论列表”“滚动”。
2. 模型读取已有导航，根据模块职责选择候选目录，并读取该范围内适用的说明。
3. 模型先在候选目录中查文件名、类型名或方法名，再查看相关代码。代码名称通常是 `Comment`、`scroll` 等英文词，所以要按含义换成英文关键词搜索。
4. 模型沿调用关系核对谁创建页面、谁持有列表、谁接收滚动回调，以及谁改变滚动位置。调用关系是代码中一个函数或对象使用另一个函数或对象的关系。
5. 如果候选目录没有证据，或者调用跳到其他模块，模型再扩大搜索范围或跟进其他模块。

所以全局关键词搜索是可选的方式，不必作为第一步。缺少导航时，先查看目录结构或做较宽范围的搜索，再逐步缩小范围。补充导航能减少重复搜索，有些任务仍然需要搜索。

### 从业务描述推断模块并验证

语义匹配指根据含义判断两段描述是否相关，而非只比较文字是否相同。假设某个模块说明写着“社区内容展示与互动”，模型可能把评论功能列为这个模块的候选职责。这只是根据描述作出的推断，某个详情页的评论是否在这个模块实现，还要用源码确认。

导航明确记录“内容详情页评论 → 某模块 → 某入口文件”时，模型可以直接沿路径读取。这种显式映射比根据模块名称推断更容易核查。导航可能过时，所以映射仍要用当前源码确认。

验证时，要确认页面实际引用了哪个评论组件，以及哪些代码负责滚动事件和位置变化。实现归属以调用关系为准，文件名、目录名和关键词命中只是线索。多个业务都有评论功能时，结合页面入口和任务上下文进一步区分；证据仍不足时，说明哪些页面范围待确认。

目录迁移、职责调整或入口变化时，导航文档要同步更新。导航文档帮助选择阅读路径，当前源码用于确认静态调用关系；源码确定不了的运行时行为，用日志或实际操作结果验证。
