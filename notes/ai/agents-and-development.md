## 模型能力与 Agent 工具链

模型负责理解问题、分析证据与生成方案。Agent 宿主负责提供上下文、调度工具、检查权限并收集执行结果。两者共同决定任务质量。

在基本工具能力已经满足需求时，模型的判断能力仍会影响实现正确性。例如异步 UI 更新需要区分数据就绪与布局就绪，并区分任务取消、动画取消和旧回调失效。找到对应文件或生成可编译代码，并不能替代这些判断。

可用上下文、Skill 与验证工具补足工作流程，但这些机制不能保证模型不再误读证据。选型应比较错误判断、人工返工和任务完成质量；本笔记没有提供具体模型的同条件评测结果。

## AI 生成技术方案的检查方法

技术方案是对如何实现需求的具体安排，说明采用什么实现方式、代码分别负责什么、执行步骤是什么，以及如何验证结果。AI 生成技术方案后，需要依据需求、现有代码和实际验证结果检查方案，不能仅凭描述完整就认定方案可行。

1. **检查实现方式是否满足需求：** 先明确功能接收什么输入、应产生什么结果，以及业务约束，也就是实现和运行时必须遵守的业务条件或规则。再逐项检查方案是否覆盖这些要求，是否遗漏异常情况，是否改变原有功能。把“体验更好”等笼统目标改成可以观察和判断的预期结果。

2. **检查能否复用已有能力：** 能力复用是利用已有代码或组件提供的功能完成当前需求。先查找现有实现，再核对输入要求、执行结果和失败时的行为是否符合当前需求。已有能力适用时，优先直接使用或做必要修改；只有名称或表面效果相似，不足以证明可以复用。确实需要新增实现时，说明现有能力不能满足哪项要求。

3. **检查方案选择是否有依据：** 说明为什么选择当前方案，以及当前方案相对于其他可行方式的优点和代价。依据可以来自现有代码、接口约定或实际测量。按当前需求比较实现复杂度、运行耗时、内存占用和后续修改成本，不要求每次都比较所有方面。把已经确认的事实、尚未验证的判断和成立条件分开记录。

4. **用最小示例和测试验证不确定结论：** 最小示例是只保留验证某个具体问题所必需的代码、输入和运行条件的可运行程序。当方案依据不足，或者关键结论尚未验证时，先明确要验证的问题和预期结果，再制作最小示例。交互效果可以通过实际操作观察，计算结果和规则可以通过测试检查。示例必须保留会影响结论的输入规模和执行时机；简化后的示例通过，不代表完整功能已经验证。

5. **沿执行链路检查风险及处理方式：** 执行链路是一次操作从触发到产生结果所经过的调用、数据传递和状态变化过程。先沿代码核对谁调用谁、传入什么、谁修改哪些数据，以及何时交付结果。仅凭代码无法确定实际顺序或行为时，再通过运行、日志或测试观察。针对确实可能发生的情况，写清触发条件、影响、由哪段代码处理，以及处理后的结果。例如，若用户可以重复发起操作，就要检查较早发起的操作完成后，是否会覆盖较新操作的结果；若存在风险，再明确如何识别并拒绝使用已经过时的结果。

6. **检查代码架构是否合理：** 代码架构是代码职责的划分，以及各部分之间如何调用、使用数据和依赖彼此的安排。这里的依赖指一部分代码要使用另一部分代码提供的类型、数据或功能。检查每部分代码是否有清晰职责，数据由谁保存和修改，调用关系是否便于理解，修改一个功能是否会牵动无关代码。代码组织应符合现有工程的约定和当前需求规模；不要为了形式上的分层增加无实际用途的类、接口或状态。

检查后，将已经确认的问题和修改建议补回方案。对尚未验证的结论，记录还缺什么证据、准备怎样验证，以及什么结果可以支持或否定当前判断。

## AI 代码审查与结果验证

先明确验收条件，再按方案审查、代码 Review、运行验证推进。

1. **方案审查：** 检查需求理解、计划修改的模块、接口与已有能力复用，以及是否引入不必要的复杂设计。新增行为时，也要检查原有交互和其他入口是否受影响。
2. **代码 Review：** 直接查看最终 diff，沿关键数据流和执行顺序核查。检查输入传递、状态更新、异步回调、取消时机和对象生命周期。另检查接口使用、错误处理、重复代码、修改范围和明显性能开销。
3. **运行验证：** 编译通过只是基础。独立的计算和状态逻辑适合自动化测试；手势、布局和动画需要运行交互验证。覆盖正常输入、边界输入、操作中断和页面退出等场景。截图用于检查最终样式，时序和交互还需操作、录屏或日志证据。发现问题后围绕失败场景修改、复测，并回归受影响的原有功能。

AI 可以辅助生成用例、操作设备和整理结果，但仍要检查用例是否覆盖需求、断言是否检查了真实结果，以及执行证据是否支持“通过”。不能将 AI 自述“已修复”当作验收结论，也不能让测试只重复实现中的同一个错误假设。相关基础见[自动化测试](../engineering/xcode-and-testing.md#自动化测试)。

## AI 辅助开发与跨平台复用

AI 可以降低分别维护原生代码的成本，跨平台技术则提供共享实现与长期复用能力。两者解决的问题有交集，但不能互相替代。

当 iOS 和 Android 分别实现相同规则时，规则变化后，两端仍需要分别修改、审查和验证。共享公共规则可以减少实现分歧；平台差异明显的 UI、手势和系统能力则可能适合独立实现。

选型应比较可复用程度、平台差异、框架升级和调试成本，以及长期维护成本。Kotlin Multiplatform 允许共享业务逻辑，同时保留原生 UI。共享代码仍需要各平台集成验证，不能未经测量就推断统一的性能优劣。

## 模型幻觉的成因与验证

模型通过训练学习上下文与后续文本的统计关系，生成的是在当前条件下合理的输出；“语言上合理”并不保证事实正确。知识缺失或过时、训练信息矛盾、上下文遗漏、推理错误，以及把相似事实拼接到错误对象上，都可能造成看似可信的错误答案。

训练和评估若更奖励作答而不是承认不知道，也可能鼓励不确定时猜测。幻觉不只是随机采样造成的，降低 temperature 不能保证事实正确。可以通过检索可靠来源、调用工具验证、约束输出并允许表达不确定性降低风险，但检索内容错误或模型误读证据时仍会出错。

## 工具调用的执行链路

Agent 宿主把可用工具的名称、用途和参数结构提供给模型。模型结合任务和训练中学到的调用模式，输出结构化的调用请求，例如“调用某个工具，并传入这些参数”。宿主解析、校验权限和参数后，真正执行函数、脚本或 API，再把结果交回模型，模型据此继续回答或选择下一步。

```text
用户任务 + 工具说明
    → 模型生成工具名称和参数
    → Agent 宿主执行工具
    → 工具结果加入上下文
    → 模型继续推理／回答
```

脚本能力来自外部执行环境，不是神经网络参数自己启动了进程。只有普通文本输出、没有工具协议和执行器时，模型写出命令也不会自动运行。调用是否可用、成功和被允许，均由具体宿主与工具决定。

## Skill、Tool 与 MCP 的分工

| 概念 | 核心作用 | 例子 |
|-|-|-|
| Skill | 可复用的做事说明与工作材料，通常含 SKILL.md，也可以带脚本和参考资料 | “修改资源位前先读 Schema，再预览、保存、验证”的流程 |
| Tool | 一项实际可调用的外部能力，有输入、执行逻辑和输出 | 读取文件、运行脚本、查询资源位 |
| MCP | AI 应用与外部服务之间发现、调用能力及交换上下文的标准协议 | 宿主通过 MCP 获取服务提供的工具清单，再调用查询工具 |

用 Swift 类比：Tool 很像宿主暴露的一个可调用函数；MCP 像一套统一的服务接口规范，规定如何列出能力、传参数、返回结果。Skill 则像团队操作手册，告诉你什么时候用哪些函数、按什么顺序做。

假设资源服务提供 `get_resource(id)`：这个查询能力是 Tool；用 MCP 的 `tools/list` 发现它、用 `tools/call` 调用它，是协议层；“修改前先查询现状、预览差异”的说明是 Skill。Tool 可以是本地内置函数或普通 API，不一定经 MCP；MCP Server 除 Tools 外还可提供 Resources、Prompts。三者不是互斥选项，也不要求每个 Skill 都自带 MCP Server。

## 跨端 UI 一致性的验证方案

跨端 UI 一致性可以按以下步骤验证。

1. 以设计稿与明确规则为共同标准，补充间距、字体、圆角，以及加载、空数据、长文本等状态。
2. 建立经过验证的双端组件映射与模板／Skill，记录 iOS 视图约束对应 Android 哪个 XML、ViewHolder 和动态样式。修正过的共性问题回写规则或组件。
3. 固定测试数据、图片、语言、主题和选定设备尺寸，自动进入同一业务状态并采集截图，按业务区域检查布局；对系统栏和字体渲染差异设合理容差。两端还要分别对照设计，避免共同偏离。
4. 对异步交互检查状态变化和取消时机：用户中断后是否停止，页面退出后是否仍执行回调。静态截图不能替代这些检查。
5. 把具体差异报告交给 AI 小范围修正并重新检查，限制自动修正次数；难以判断或重复失败时人工处理。先验证单个组件，再扩展到完整页面。

## Codex 的 AGENTS.md 加载与代码定位

`AGENTS.md` 是提供给编码 Agent 的项目说明文件，可以记录目录职责、开发规则和常用代码入口。Agent 宿主是运行模型并提供文件读取、命令执行等工具的应用。文件存在于磁盘上，不等于文件内容已经进入模型可使用的上下文。

### 启动时的自动加载

按 Codex 官方说明中的默认发现规则，Codex 启动时先读取用户级指令，再沿项目根目录到当前工作目录的路径查找项目级指令。当前工作目录是本次任务选定的起始目录，不是搜索结果所在的目录。以下说明针对这套默认机制；其他 Agent、不同宿主或额外配置不能直接套用。

用户级指令通常位于 `~/.codex`；配置了 `CODEX_HOME` 时，以该目录为准。Codex 优先读取 `AGENTS.override.md`，没有时再读取 `AGENTS.md`。项目路径上的每个目录也按 `AGENTS.override.md`、`AGENTS.md`、配置中的备用文件名顺序查找；每个目录最多选取一个文件。

项目级指令按从根目录到当前工作目录的顺序组合。更深目录中的指令在适用范围内可以覆盖上层项目指令的冲突部分；没有冲突的规则仍然有效。局部文件不能覆盖更高优先级的系统指令。

假设一个工程有四个文件：根目录的 `AGENTS.md`、`Modules/AGENTS.md`、`Modules/Community/AGENTS.md` 和 `Modules/Home/AGENTS.md`。从工程根目录启动时，默认项目指令链只包含根目录文件。从 `Modules/Community` 启动时，默认项目指令链包含根目录、`Modules` 和 `Community` 的三个文件，不包含同级的 `Home` 文件。两种情况都需要另行考虑用户级指令。

因此，“沿根目录到工作目录查找”不等于“递归遍历整个工程并读取每个模块”。启动时的指令总量还受配置中的大小限制，不能把任意长度的文件都视为已经完整加载。

### 查代码时的主动读取

主动读取是模型根据任务和已有说明，调用文件工具获取更多内容。例如，根目录说明列出了一个模块的 `AGENTS.md` 路径，模型可以沿该路径读取模块职责和实现入口。Markdown 链接本身只提供目标地址，不会自动把目标文件内容展开到上下文。

当任务进入启动指令链之外的子目录时，模型应检查该目录及相关上级目录的适用说明。这属于任务执行中的文件读取。不能仅因为搜索命中了子目录里的源码，就断言宿主已经自动加载了沿途的全部 `AGENTS.md`；搜索命中也不会改变本次会话选定的工作目录。

判断实际读取情况时，需要区分宿主预先提供的指令与工具读取结果。工具记录可以证明某次主动读取发生过；没有文件读取记录，也不能排除宿主在启动时已经注入了内容。“配置要求读取”与“已经观察到读取”应分别说明。

### 用分层导航缩小搜索范围

分层导航是把工程信息按“工程整体 → 业务模块 → 具体实现”组织起来。根目录说明记录模块职责、候选目录和导航文档入口。模块说明记录本模块负责的功能、关键类型或文件，以及进一步阅读的路径。详细实现留在源码或专题文档中，避免每层重复复制大量内容。

已有导航时，可以按以下顺序定位实现。实际顺序由任务、已有上下文和工具结果决定，不是 Codex 固定执行的算法。

1. 模型从用户描述中提取功能对象和行为，例如“详情页”“评论列表”“滚动”。
2. 模型读取已有导航，根据模块职责选择候选目录，并读取该范围内适用的说明。
3. 模型先在候选目录中查文件名、类型名或方法名，再查看相关代码。代码名称可能使用 `Comment`、`scroll` 等英文词，不一定包含用户描述中的中文字面量。
4. 模型沿调用关系核对谁创建页面、谁持有列表、谁接收滚动回调，以及谁改变滚动位置。调用关系是代码中一个函数或对象使用另一个函数或对象的关系。
5. 如果候选目录没有证据，或者调用跳到其他模块，模型再扩大搜索范围或跟进其他模块。

因此，全局关键词搜索是一种可选方式，并不是必须执行的第一步。缺少导航时，可以先查看目录结构或进行较宽范围的搜索，再逐步缩小范围。补充导航能减少重复搜索，但不能保证每次都无需搜索。

### 从业务描述推断模块并验证

语义匹配是根据表达的含义判断关联，而不是只比较文字是否相同。假设某个模块说明写着“社区内容展示与互动”，模型可能把评论功能列为该模块的候选职责。这是根据描述作出的推断，尚不能证明某个详情页的评论实现就在该模块。

如果导航明确记录“内容详情页评论 → 某模块 → 某入口文件”，模型就能直接沿路径读取。这样的显式映射比仅凭模块名称推断更容易核查。映射仍需用当前源码确认，不能把旧导航当作实现事实。

验证时，需要确认页面实际引用了哪个评论组件，以及滚动事件和位置变化由哪些代码负责。仅凭文件名、目录名或关键词命中，不能确定实现归属。如果多个业务都有评论功能，应结合页面入口和任务上下文继续区分；证据仍不足时，应说明待确认的页面范围。

导航文档应随着目录迁移、职责调整和入口变化同步维护。文档帮助选择阅读路径，当前源码用于确认静态调用关系；仅凭源码无法确定的运行时行为，还需要日志或实际操作结果验证。
