## 模型能力与 Agent 工具链

模型负责理解问题、分析证据与生成方案。Agent 宿主负责提供上下文、调度工具、检查权限并收集执行结果。两者共同决定任务质量。

在基本工具能力已经满足需求时，模型的判断能力仍会影响实现正确性。例如异步 UI 更新需要区分数据就绪与布局就绪，并区分任务取消、动画取消和旧回调失效。找到对应文件或生成可编译代码，并不能替代这些判断。

可用上下文、Skill 与验证工具补足工作流程，但这些机制不能保证模型不再误读证据。选型应比较错误判断、人工返工和任务完成质量；本笔记没有提供具体模型的同条件评测结果。

## AI 代码审查与结果验证

先明确验收条件，再按方案审查、代码 Review、运行验证推进。

1. **方案审查：** 检查需求理解、计划修改的模块、接口与已有能力复用，以及是否引入不必要的复杂设计。新增行为时，也要检查原有交互和其他入口是否受影响。
2. **代码 Review：** 直接查看最终 diff，沿关键数据流和执行顺序核查。检查输入传递、状态更新、异步回调、取消时机和对象生命周期。另检查接口使用、错误处理、重复代码、修改范围和明显性能开销。
3. **运行验证：** 编译通过只是基础。独立的计算和状态逻辑适合自动化测试；手势、布局和动画需要运行交互验证。覆盖正常输入、边界输入、操作中断和页面退出等场景。截图用于检查最终样式，时序和交互还需操作、录屏或日志证据。发现问题后围绕失败场景修改、复测，并回归受影响的原有功能。

AI 可以辅助生成用例、操作设备和整理结果，但仍要检查用例是否覆盖需求、断言是否检查了真实结果，以及执行证据是否支持“通过”。不能将 AI 自述“已修复”当作验收结论，也不能让测试只重复实现中的同一个错误假设。相关基础见[自动化测试](../engineering/xcode-and-testing.md#自动化测试)。

## AI 辅助开发与跨平台复用

AI 可以降低分别维护原生代码的成本，跨平台技术则提供共享实现与长期复用能力。两者解决的问题有交集，但不能互相替代。

当 iOS 和 Android 分别实现相同规则时，规则变化后，两端仍需要分别修改、审查和验证。共享公共规则可以减少实现分歧；平台差异明显的 UI、手势和系统能力则可能适合独立实现。

选型应比较可复用程度、平台差异、框架升级和调试成本，以及长期维护成本。Kotlin Multiplatform 允许共享业务逻辑，同时保留原生 UI。共享代码仍需要各平台集成验证，不能未经测量就推断统一的性能优劣。

## 模型幻觉的成因与验证

模型通过训练学习上下文与后续文本的统计关系，生成的是在当前条件下合理的输出；“语言上合理”并不保证事实正确。知识缺失或过时、训练信息矛盾、上下文遗漏、推理错误，以及把相似事实拼接到错误对象上，都可能造成看似可信的错误答案。

训练和评估若更奖励作答而不是承认不知道，也可能鼓励不确定时猜测。幻觉不只是随机采样造成的，降低 temperature 不能保证事实正确。可以通过检索可靠来源、调用工具验证、约束输出并允许表达不确定性降低风险，但检索内容错误或模型误读证据时仍会出错。

## 工具调用的执行链路

Agent 宿主把可用工具的名称、用途和参数结构提供给模型。模型结合任务和训练中学到的调用模式，输出结构化的调用请求，例如“调用某个工具，并传入这些参数”。宿主解析、校验权限和参数后，真正执行函数、脚本或 API，再把结果交回模型，模型据此继续回答或选择下一步。

```text
用户任务 + 工具说明
    → 模型生成工具名称和参数
    → Agent 宿主执行工具
    → 工具结果加入上下文
    → 模型继续推理／回答
```

脚本能力来自外部执行环境，不是神经网络参数自己启动了进程。只有普通文本输出、没有工具协议和执行器时，模型写出命令也不会自动运行。调用是否可用、成功和被允许，均由具体宿主与工具决定。

## Skill、Tool 与 MCP 的分工

| 概念 | 核心作用 | 例子 |
|-|-|-|
| Skill | 可复用的做事说明与工作材料，通常含 SKILL.md，也可以带脚本和参考资料 | “修改资源位前先读 Schema，再预览、保存、验证”的流程 |
| Tool | 一项实际可调用的外部能力，有输入、执行逻辑和输出 | 读取文件、运行脚本、查询资源位 |
| MCP | AI 应用与外部服务之间发现、调用能力及交换上下文的标准协议 | 宿主通过 MCP 获取服务提供的工具清单，再调用查询工具 |

用 Swift 类比：Tool 很像宿主暴露的一个可调用函数；MCP 像一套统一的服务接口规范，规定如何列出能力、传参数、返回结果。Skill 则像团队操作手册，告诉你什么时候用哪些函数、按什么顺序做。

假设资源服务提供 `get_resource(id)`：这个查询能力是 Tool；用 MCP 的 `tools/list` 发现它、用 `tools/call` 调用它，是协议层；“修改前先查询现状、预览差异”的说明是 Skill。Tool 可以是本地内置函数或普通 API，不一定经 MCP；MCP Server 除 Tools 外还可提供 Resources、Prompts。三者不是互斥选项，也不要求每个 Skill 都自带 MCP Server。

## 跨端 UI 一致性的验证方案

跨端 UI 一致性可以按以下步骤验证。

1. 以设计稿与明确规则为共同标准，补充间距、字体、圆角，以及加载、空数据、长文本等状态。
2. 建立经过验证的双端组件映射与模板／Skill，记录 iOS 视图约束对应 Android 哪个 XML、ViewHolder 和动态样式。修正过的共性问题回写规则或组件。
3. 固定测试数据、图片、语言、主题和选定设备尺寸，自动进入同一业务状态并采集截图，按业务区域检查布局；对系统栏和字体渲染差异设合理容差。两端还要分别对照设计，避免共同偏离。
4. 对异步交互检查状态变化和取消时机：用户中断后是否停止，页面退出后是否仍执行回调。静态截图不能替代这些检查。
5. 把具体差异报告交给 AI 小范围修正并重新检查，限制自动修正次数；难以判断或重复失败时人工处理。先验证单个组件，再扩展到完整页面。
