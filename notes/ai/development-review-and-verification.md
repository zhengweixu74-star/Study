## 从需求推出判断条件

AI 可以生成技术方案、代码、测试用例和验收记录。这些产物都用三类依据检查：已确认的需求、当前代码和实际运行结果。AI 的说明和总结用来定位代码；AI 报告“已修复”或“检查通过”是一条陈述，结论以证据为准。

判断条件是一条可以观察和判断的检查标准，写明触发输入、成立条件和预期结果。方案检查、代码审查和验收都从同一组判断条件出发。

推出判断条件前，先明确功能接收什么输入、应产生什么结果、有哪些业务约束。业务约束是实现和运行时必须遵守的业务规则，例如适用页面、数值边界、更新时机和标识优先级。“体验更好”这类笼统目标，要改写成可以观察的预期结果。

例如，“列表标识更新正确”可以拆成四条判断条件：首次响应决定本批文案；本地计数变化时保持文案；刷新成功后重新计算文案；刷新失败时保留原列表。每条条件还要考虑缺失数据、边界值、重复操作和中断操作。

判断条件从需求推出，再用来检查 AI 生成的方案、代码和测试。照着现有实现写出的条件和断言，会和实现犯同一个错误。尚未确认的业务参数记录为待确认；示例值和 AI 自行设定的值，在确认之前只是假设。

## 技术方案的检查

技术方案是实现需求的具体安排，说明采用什么实现方式、各部分代码负责什么、按什么步骤执行、如何验证结果。方案描述完整只说明内容写得全；方案是否可行，要用需求、现有代码和验证结果确认。

1. **实现方式是否满足需求：** 逐条对照判断条件，检查方案是否覆盖每项要求、是否遗漏异常情况、是否改变原有功能。
2. **能否复用已有能力：** 能力复用指用已有代码或组件提供的功能完成当前需求。先查找现有实现，再核对现有实现的输入要求、执行结果和失败行为。三项都符合当前需求时，优先直接使用或做必要修改；名称或表面效果相似的实现，也要逐项核对后才能复用。确实需要新增实现时，写明现有能力缺少哪项要求。
3. **方案选择是否有依据：** 写明选择当前方案的理由，以及当前方案相比其他可行方式的优点和代价。依据来自现有代码、接口约定或实际测量。按当前需求挑选比较的方面，例如实现复杂度、运行耗时、内存占用和后续修改成本。已经确认的事实、尚未验证的判断和成立条件分开记录。
4. **用最小示例验证不确定的结论：** 最小示例是一个可运行的程序，只保留验证某个具体问题所必需的代码、输入和运行条件。先写明要验证的问题和预期结果，再制作最小示例。交互效果通过实际操作观察，计算结果和规则通过测试检查。最小示例要保留会影响结论的输入规模和执行时机。最小示例通过，只验证了被保留的条件，完整功能还要单独验证。
5. **执行链路中的风险是否有处理：** 执行链路是一次操作从触发到产生结果所经过的调用、数据传递和状态变化。对确实可能发生的情况，写清触发条件、影响、由哪段代码处理、处理后的结果。例如用户可以重复发起请求时，较早的请求可能晚于较新的请求完成，并覆盖较新的结果；方案要写明如何识别并丢弃过时的结果。追踪链路的方法见[沿数据流与事件顺序审查](#沿数据流与事件顺序审查)。
6. **代码架构是否合理：** 代码架构指代码职责如何划分，以及各部分如何互相调用、使用数据和依赖。依赖指一部分代码使用另一部分代码提供的类型、数据或功能。检查四点：每部分代码职责是否清晰；数据由谁保存和修改；调用关系是否容易理解；修改一个功能是否牵动无关代码。代码组织遵循现有工程的约定，规模与当前需求相当，每个类、接口和状态都要有实际用途。

检查后，把已确认的问题和修改建议补回方案。对尚未验证的结论，记录还缺什么证据、准备怎样验证、什么结果能支持或否定当前判断。

## 代码审查

代码审查（Code Review）依据需求和工程约定，检查代码是否正确实现了预期行为、是否影响已有功能。审查先读懂代码的实现方式，再对照判断条件逐项判断。实现完成后，审查对象是最终代码差异和运行结果。

审查按以下顺序进行：按需求行为分组 → 确认文件和函数职责 → 沿数据流与事件顺序审查 → 检查既有行为 → 核对[验证证据](#验证证据的范围)。

### 按需求行为分组

把一次改动分成若干代码组，每组都能单独说明目的和对应的判断条件。例如字段解析、展示规则、刷新时机和事件上报分别审查。分组按需求行为划分，一个文件可以属于多组，公共组件常常同时参与多个行为。

检查每项需求是否都有对应实现，每项修改是否都有明确目的。对新增的状态、分支、辅助方法、默认值和重试逻辑，逐一追问：删除这段代码，哪项要求会无法成立？确实需要的输入校验和失败处理保留；既没有需求依据、也没有实际失败路径的复杂逻辑，重新评估是否需要。

代码很多时，每审完一组，就记录已确认和待验证的条件。各组都审完后，再检查组间的数据传递、共享状态和需求覆盖是否完整。

### 确认文件和函数职责

确认哪些代码负责解析输入、保存状态、修改状态、刷新界面和上报事件。明确入口函数、调用方、数据接收方，以及公共组件的其他使用入口。

除了查看最终差异（diff），还要读取改动函数的完整上下文和必要的调用方。未跟踪的新文件不会出现在普通 `git diff` 中，需要单独检查。函数名、注释和 Agent 总结只提供线索，职责和执行顺序以实际代码为准。

### 沿数据流与事件顺序审查

数据流是数据从输入开始，经过解析、传递、保存或转换，最终产生结果的路径。事件顺序是请求完成、用户操作、回调执行等事件之间已经确定的先后关系。异步代码的执行顺序可能与书写顺序不同。

对每组代码回答五个问题：输入是什么；谁改变了什么；什么时候改变；结果是什么；证据在哪里。输入包括接口数据、已有状态和用户操作。对每个状态，追踪由谁持有、谁能修改、何时创建和清除，以及页面退出或任务取消后旧结果是否还会被使用。代码确定不了实际顺序或行为时，通过运行、日志或测试观察。

例如，列表文案按响应中的计数决定，规则要求文案只在刷新成功后切换。首次响应计数为 9，展示组件保存“未达标”。用户操作使当前计数变成 10，组件仍保留“未达标”。刷新成功并返回计数 10 后，组件才保存“已达标”。这里有两个状态：当前计数和已保存的文案。“计数 ≥ 10”的表达式只决定文案内容；更新时机是否正确，要检查文案在什么时候被重新计算。

快照是根据某一时刻的数据计算并保存下来的结果。上例中已保存的文案就是快照。使用快照时，要检查快照的创建、读取和清除入口。如果卡片复用时按当前计数重新判断，就违反了“刷新后才切换”的要求。缓存读取、加载更多和刷新失败分别如何影响已保存的结果，也要逐一检查。

### 检查既有行为

一组代码满足自身目的后，还要检查其他调用方和原有功能。回归验证指修改后重新检查受影响的既有行为。例如公共卡片组件增加标识后，需要检查无标识卡片、空标题、长标题、滚动复用和其他页面。

影响范围指一处修改可能改变多少调用方或功能的行为。业务判断、共享状态、异步回调、缓存和公共组件影响范围大，优先仔细阅读。缓存 key 是区分缓存记录的标识；某个条件会改变布局高度时，要检查缓存 key 是否包含这个条件。

代码量大时，重复的字段映射可以先确认规则，再逐处核对名称和类型；状态变化和公共组件要读取完整上下文。影响大小取决于改动的位置和内容，与新增行数没有直接关系。

发现问题后，针对失败场景修改并复测，再回归受影响的原有功能。重查范围限于有变化或仍有疑点的部分。

## 验证证据的范围

静态检查指通过阅读或分析代码确认规则；运行验证指执行程序并观察实际结果。把每个判断条件对应到代码位置和必要的执行结果。静态证据不足以确认行为时，补充有针对性的测试、操作、录屏或日志，仍未验证的条件记录为待验证。

每种验证方式只支持一部分结论：

| 验证方式 | 能支持的结论 | 仍需另外验证 |
| --- | --- | --- |
| git diff --check | 差异没有该命令检查的空白格式问题 | 编译结果和功能 |
| 编译通过 | 该工具链和构建范围内的语法、类型与依赖通过编译 | 业务规则、交互和其他平台 |
| 自动化测试 | 用例的输入、条件和断言覆盖的结果符合预期 | 未覆盖的场景 |
| Mock 与设备操作 | 指定模拟数据和操作下的行为符合预期 | 真实接口返回的数据结构 |
| 截图 | 截图时刻的最终可见样式 | 状态变化和异步执行顺序 |
| 录屏、日志或事件记录 | 记录范围内的操作结果、状态变化或上报内容 | 未记录的分支 |

断言是测试中检查实际结果是否符合预期的条件，用例和断言从判断条件推出。验证记录写明代码版本、输入、环境、操作和观察结果。旧版本的验证结果只对旧版本有效，代码修改后要重新验证。测试基础见[自动化测试](../engineering/xcode-and-testing.md#自动化测试)。

工具返回“点击成功”，只说明点击操作已经执行；AI 报告“已修复”，只是 AI 给出的陈述。结论要靠操作后的业务结果，例如保存提示出现、文件生成或列表状态更新，以及修复后的代码差异。

人工检查的范围根据修改影响、规则复杂度和已有证据决定。共享状态、异步顺序或关键业务规则尚未验证时，要补充检查。功能是否正确由验证证据证明；代码看起来完整、人工暂时没看出问题，只说明尚未发现问题。

## AI 辅助验收

验收依据已确认的需求，判断实际功能是否产生预期结果。AI 可以生成用例、准备数据、调用工具执行操作和整理证据；通过条件来自判断条件，再用实际观察结果支持。设备操作的实现见[命令行工具与设备端 Driver](../engineering/xcode-and-testing.md#命令行工具与设备端-driver)。

执行顺序为：明确输入与预期结果 → 生成用例 → 准备数据和环境 → 执行操作 → 比较实际结果 → 保存证据 → 修改后复测并回归受影响功能。

### 用例、数据与等待条件

每个用例先确认初始状态、输入、操作和预期结果。例如验证列表定位功能时，分别准备目标项存在、目标项不存在、响应延迟、用户开始拖动等条件。每个用例都检查目标项、最终位置和中断行为，通过与否由这些检查结果决定。

Mock 指在测试中人为提供指定的数据或行为，替代真实依赖。例如测试让某个接口在 2 秒后返回包含 A、B、C 的列表，响应时间和内容就都可控。用启动参数切换模拟数据时，App 要读取这个参数并选择对应的模拟数据，网络响应才会改变。

控制网络响应和操作界面需要两类工具。模拟服务、依赖注入或代理工具控制网络响应；设备操作工具负责点击和滑动。能控制手机的工具通常只能操作界面，改写接口响应要另配工具。

等待条件描述的是实际状态，而非固定的秒数。接口返回后，App 可能还在创建视图、更新列表或布局，目标元素可能尚未出现，位置也可能尚未稳定。所以测试要等待用例要求的元素、加载结束状态或布局条件出现，并设置合理的等待上限。

### 检查目标与证据

| 检查目标 | 需要明确的条件或证据 |
| --- | --- |
| 是否选中正确项 | 通过唯一标识、无障碍标识或可核对日志确认目标项；相似文案只是线索 |
| 最终位置是否正确 | 指定参考区域、比较项的顶部还是中心，以及允许的坐标误差 |
| 目标不存在时的行为 | 按需求检查提示、停止定位或其他明确结果，不擅自补出一个目标 |
| 用户接管是否生效 | 在自动操作期间发起拖动，检查自动动画是否停止及后续位置是否被覆盖 |
| 动画是否流畅 | 记录动画过程，并结合性能时间线或帧统计判断；单张截图只能检查某一时刻的状态 |

例如在固定设备上检查 B 的顶部与列表可视区域顶部对齐，约定两者距离不超过 2 点。测试记录目标标识 B、参考区域和实际距离。2 点是示例值，正式误差由需求确定。比较距离时，两个位置要换算到同一个坐标系，屏幕坐标和视图内部坐标要先统一。

证据只覆盖实际执行过的条件：用模拟数据通过，真实接口、其他设备和未执行的路径仍需另外验证。

AI 根据现象提出原因时，缺少依据的判断标记为待验证。先用日志检查关键输入、状态变化、分支选择和执行顺序，再判断原因；AI 的解释在得到日志证实之前只是假设。修改后重新执行失败用例，并检查受影响的既有行为。

评估 AI 辅助验收节省的时间时，在相同功能和用例范围内，比较数据准备、执行、检查和复测的耗时，同时计入自动化配置和维护的时间。有同条件的对比记录，才能给出提升比例。

## 跨端 UI 一致性的验证

跨端 UI 一致性可以按以下步骤验证。

1. 以设计稿与明确规则为共同标准，补充间距、字体、圆角，以及加载、空数据、长文本等状态。
2. 建立经过验证的双端组件映射和模板或 Skill，记录每个 iOS 视图及约束对应的 Android 布局文件和列表项实现。修正过的共性问题，写回规则或组件。
3. 固定测试数据、图片、语言、主题和设备尺寸，让两端自动进入同一业务状态并截图，按业务区域比较布局；系统栏和字体渲染的差异设置合理容差。两端还要各自对照设计稿，防止两端一致但都偏离设计。
4. 异步交互要实际操作检查：用户中断后是否停止，页面退出后是否仍执行回调。截图只记录某一时刻的样式，看不出这类状态变化。
5. 把具体的差异报告交给 AI 小范围修正，再重新检查，并限制自动修正的次数；难以判断或反复失败时转人工处理。先验证单个组件，再扩展到完整页面。

## AI 辅助开发与跨平台复用

AI 降低了 iOS 和 Android 分别编写原生代码的成本；跨平台技术让两端共享同一份实现。两者解决的问题有交集：AI 减少的是每次编写的工作量，共享实现减少的是同一规则的实现份数。

iOS 和 Android 分别实现同一条规则时，规则一变，两端都要分别修改、审查和验证，两份实现也可能逐渐出现分歧。所以公共规则适合共享；平台差异明显的 UI、手势和系统能力，各自实现可能更合适。

选型时比较可复用程度、平台差异、框架升级和调试成本，以及长期维护成本。Kotlin Multiplatform 可以共享业务逻辑，同时保留原生 UI，机制见 [KMP 跨平台编译与鸿蒙库集成](../cross-platform/kmp-compilation-and-harmony-libraries.md)。共享代码仍要在各平台分别集成验证；性能优劣以实际测量为准。
