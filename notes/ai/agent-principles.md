## Agent 与 Harness

Agent 是根据任务目标选择动作、调用工具，再根据执行结果继续推进的系统。Harness 是支撑模型运行这个循环的外围程序和运行环境，也称 Agent 宿主，通常负责组织上下文、执行工具、保存状态、控制权限和检查结果。Harness 是 AI 工程中的惯用说法，各产品对 Harness 的边界和命名不尽相同。

工具是实际完成外部操作的程序或接口，例如读取文件、运行脚本和查询服务。模型、Harness 和工具组合成一个 Agent 系统：模型理解任务、分析证据并生成下一步动作；Harness 让这些动作实际执行，并限制动作的范围。任务质量由模型和 Harness 共同决定。

### 工具调用的执行循环

模型只输出文本。Harness 先把每个工具的名称、用途和参数结构提供给模型。模型结合任务和训练中学到的调用模式，输出结构化的调用请求，例如“调用 `read_file`，参数 `path` 为 `main.swift`”。Harness 解析这个请求，检查权限和参数，再执行对应的函数、脚本或 API。缺少工具协议和执行器时，模型写出的命令只是普通文本，不会运行。

一次循环按以下顺序进行：

```text
Harness 整理任务、上下文和工具说明
    → 模型生成工具名称和参数
    → Harness 检查权限和参数，调用工具
    → 工具返回结果
    → Harness 保存必要状态，把结果加入下一轮输入
    → 模型决定继续调用工具、给出回答或请求补充信息
```

工具是否可用、调用是否被允许、调用是否成功，都由具体的 Harness 和工具决定。

### 模型判断与 Harness 工程

Harness 工程是设计和改进 Harness 的工作，例如编写准确的工具说明、维护可检索的项目导航、保存任务进度、限制可执行的操作、提供检查结果的入口。Harness 工程改善的是模型的执行条件；模型参数保持不变，模型仍可能误读证据。

工具够用之后，结果是否正确取决于模型的判断。例如列表数据返回后要滚动到目标行：数据写入列表时，列表可能还没完成布局，这时算出的目标位置是错的。模型要分清“数据就绪”和“布局就绪”两个时机，才能把滚动安排在布局完成之后。找到文件、写出能编译的代码之后，这类判断仍由模型完成。所以比较模型时，要看错误判断的次数、人工返工量和任务完成质量。

## 模型幻觉的成因与降低方法

幻觉指模型生成的内容语言上合理，却与事实不符。模型通过训练学习上下文与后续文本之间的统计关系，输出在当前条件下语言上合理的文本。知识缺失或过时、训练信息互相矛盾、上下文遗漏、推理错误，以及把相似事实安到错误对象上，都会产生看似可信的错误答案。

训练和评估如果更奖励作答、较少奖励承认不知道，模型在不确定时也会倾向于猜测。temperature 是控制采样随机程度的参数。随机采样只是幻觉的成因之一，所以降低 temperature 只减少随机变化，其他成因仍然存在。

检索可靠来源、调用工具验证、约束输出格式、允许模型表达不确定，都能降低幻觉风险。检索到的内容本身有误，或模型误读了证据时，结果仍会出错。

## Skill、Tool 与 MCP 的分工

| 概念 | 核心作用 | 例子 |
|-|-|-|
| Skill | 可复用的做事说明与工作材料，通常含 `SKILL.md`，也可以带脚本和参考资料 | “修改资源位前先读 Schema，再预览、保存、验证”的流程 |
| Tool | 一项实际可调用的外部能力，有输入、执行逻辑和输出 | 读取文件、运行脚本、查询资源位 |
| MCP | AI 应用与外部服务之间发现能力、调用能力和交换上下文的标准协议 | Harness 通过 MCP 获取服务提供的工具清单，再调用其中的查询工具 |

假设资源服务提供 `get_resource(id)`。这个查询能力是 Tool；Harness 用 MCP 的 `tools/list` 发现 `get_resource`、用 `tools/call` 调用 `get_resource`，属于协议层；“修改前先查询现状、预览差异”的说明是 Skill。三者可以组合，也可以单独使用：Tool 可以是本地内置函数或普通 API，由 Harness 直接调用；MCP Server 除了 Tools，还可以提供 Resources 和 Prompts；Skill 也可以只配本地工具。

## Skill 与普通 Markdown 的关系

Markdown 是一种文本标记格式，用标题、列表、代码块等语法组织文档。Skill 是供 Agent 复用的一组任务说明和配套材料，可以包含 Markdown 文档、脚本、参考资料与模板。两者处在不同层次：Markdown 规定内容的书写格式；Skill 规定内容如何组织，以及 Harness 如何发现和使用这些内容。

按 Agent Skills 格式组织的技能目录以 `SKILL.md` 为入口。入口文件开头是 YAML 元数据，用字段记录技能名称、用途等信息，其中 `name` 和 `description` 是必需字段。`name` 标识技能，`description` 说明技能负责什么、何时使用。脚本和参考资料是可选内容。

文件名和字段格式统一后，支持这套约定的 Harness 按固定规则查找入口、解析元数据、列出可用技能，多个支持该格式的工具也能复用同一份技能。普通 Markdown 的文件名和章节各不相同，Harness 要另外约定入口文件和适用条件的提取方式。

一种常见的使用流程是：

1. Harness 从配置的目录或技能清单中发现技能，解析名称、用途和入口位置。
2. Harness 向模型提供简短的技能目录。模型根据用户任务选择适用的技能，或者用户直接指定技能。
3. Harness 把选中技能的正文提供给模型，例如执行模型发起的文件读取请求。
4. 模型按正文中的步骤，在需要时请求读取参考资料或调用脚本。Harness 检查权限并执行工具，再把结果交给模型。

Skill 格式统一的是发现和加载的约定，执行能力来自 Harness 提供的工具。模型拿到的说明、工具和权限相同时，普通 Markdown 中的流程同样能指导任务执行。所以 `SKILL.md` 要放在 Harness 支持的位置，或者通过 Harness 支持的方式注册，Harness 才能发现这个技能。正文中写的脚本路径只是文本；脚本能否运行，取决于 Harness 是否提供执行工具、依赖和权限。

## Skill 的规模与上下文控制

一个 Skill 围绕一项明确任务组织，只保留完成该任务必需的说明。Agent Skills 的编写建议是：`SKILL.md` 正文控制在 5,000 token 以下，主文件保持在 500 行以下。这两个数字是控制体量的建议值，Harness 不一定强制执行，也不必写满；具体 Harness 可能还有自己的限制。

token 是模型切分文本后使用的计量单位。一个 token 对应的汉字、英文单词或字节数不固定，所以行数和字符数只能粗略估计 token 数。上下文是模型本次推理可以使用的输入信息，包括系统指令、对话、技能说明和工具返回内容，这些内容共同占用模型的输入容量。

控制上下文的方法是分阶段提供必要内容，这种做法称为渐进式披露，分为三层：

1. 技能目录只提供名称、用途和入口。用途说明写到足以判断技能是否适合当前任务即可，不复制整套流程。
2. 选中技能后，再提供 `SKILL.md` 正文。正文保留必要输入、主要步骤、必须遵守的要求和预期输出。
3. 当前步骤需要时，才读取详细接口说明、长示例或其他参考资料。正文写明在什么时候读取哪个文件。

例如一个技能支持十个接口，主文件列出每个接口的用途和资料路径。任务只调用一个接口时，模型只读取这个接口的详细说明。十份资料拆成十个文件后如果仍然全部读入，上下文占用保持不变。渐进式披露控制的是内容进入模型上下文的时机；Harness 为解析元数据读取磁盘文件，是另一件事。

脚本适合承担格式转换、数据计算等确定性工作。确定性工作指相同输入和条件下，按明确规则执行并得到固定结果的工作。脚本源码只有被读取时才进入上下文；脚本存放在磁盘上或被执行，都不占用上下文。工具返回的日志和数据会进入后续输入，所以工具只返回任务需要的结果摘要、必要字段和失败原因。

压缩内容时，优先删除重复的解释、无关的背景和重复加载的资料。权限要求、输入约定和完成条件保留在主文件中；为减少 token 把关键要求移进附件时，主文件要写明何时读取这个附件。上下文占用取决于实际读入的内容，与文件夹的磁盘大小无关；模型支持的最大上下文也要留给对话和工具结果，单个 Skill 只占其中一部分。

判断规模是否合适，要同时看实际加载的 token 数和任务完成质量。主文件容易读懂、资料能按需找到、执行时没有遗漏关键步骤，拆分才算有效。说明变短后，模型如果反复搜索、重复读取或漏掉要求，就调整内容的组织方式，继续删字解决不了这类问题。

## Codex 的 AGENTS.md 加载

`AGENTS.md` 是提供给编码 Agent 的项目说明文件，可以记录目录职责、开发规则和常用代码入口。`AGENTS.md` 的内容被 Harness 加载或被模型读取后，才进入模型可以使用的上下文。以下说明针对 Codex 官方说明中的默认发现规则；其他 Agent、其他 Harness 或额外配置按各自规则判断。

### 启动时的自动加载

Codex 启动时先读取用户级指令，再沿项目根目录到当前工作目录的路径查找项目级指令。当前工作目录是本次任务选定的起始目录，由启动方式决定，与后续搜索结果所在的目录无关。

用户级指令通常位于 `~/.codex`；配置了 `CODEX_HOME` 时，以该目录为准。Codex 优先读取 `AGENTS.override.md`，没有时再读取 `AGENTS.md`。项目路径上的每个目录也按 `AGENTS.override.md`、`AGENTS.md`、配置中的备用文件名的顺序查找，每个目录最多选取一个文件。

项目级指令按从根目录到当前工作目录的顺序组合。在适用范围内，更深目录中的指令覆盖上层指令中冲突的部分，不冲突的规则继续有效。系统指令优先级更高，局部文件无法覆盖系统指令。

假设一个工程有四个文件：根目录的 `AGENTS.md`、`Modules/AGENTS.md`、`Modules/Community/AGENTS.md` 和 `Modules/Home/AGENTS.md`。从工程根目录启动时，项目指令链只包含根目录文件。从 `Modules/Community` 启动时，项目指令链包含根目录、`Modules` 和 `Community` 的三个文件，同级的 `Home` 文件不在其中。两种情况下，用户级指令都会另外加载。

所以 Codex 只查找根目录到工作目录这一条路径上的文件，不会遍历整个工程读取每个模块的说明。启动时加载的指令总量还受配置中的大小限制，超出限制的部分不会被完整加载。

### 任务中的主动读取

主动读取指模型根据任务和已有说明，调用文件工具获取更多内容。例如根目录说明列出了某个模块 `AGENTS.md` 的路径，模型按这个路径读取模块职责和实现入口。Markdown 链接只提供目标地址；模型调用文件工具读取后，目标文件的内容才进入上下文。

任务进入启动指令链之外的子目录时，模型要主动读取该目录及上级目录中适用的说明。搜索命中子目录里的源码时，Harness 不会因此自动加载沿途的 `AGENTS.md`，会话的工作目录也保持不变。

判断模型实际看到了哪些说明时，要区分 Harness 启动时注入的指令和工具读取的结果。工具记录能证明某次主动读取发生过；没有读取记录时，内容仍可能在启动时被注入。所以“配置要求读取”和“已经观察到读取”要分开说明。

## 用项目导航定位代码

### 分层导航与搜索顺序

分层导航指把工程信息按“工程整体 → 业务模块 → 具体实现”分层组织。根目录说明记录模块职责、候选目录和导航文档入口。模块说明记录本模块负责的功能、关键类型或文件，以及进一步阅读的路径。详细实现留在源码或专题文档中，每层只写本层信息，不复制下层内容。

已有导航时，可以按以下顺序定位实现。这是一种常见做法，实际顺序由任务、已有上下文和工具结果决定。

1. 模型从用户描述中提取功能对象和行为，例如“详情页”“评论列表”“滚动”。
2. 模型读取已有导航，根据模块职责选择候选目录，并读取该范围内适用的说明。
3. 模型先在候选目录中查文件名、类型名或方法名，再查看命中的代码。代码名称通常是 `Comment`、`scroll` 等英文词，所以要按含义换成英文关键词搜索。
4. 模型沿调用关系核对谁创建页面、谁持有列表、谁接收滚动回调，以及谁改变滚动位置。调用关系是代码中一个函数或对象使用另一个函数或对象的关系。
5. 候选目录中找不到证据，或者调用跳到其他模块时，模型再扩大搜索范围或跟进其他模块。

所以全局关键词搜索是可选的方式，可以放在缩小范围之后。缺少导航时，先查看目录结构或做较宽范围的搜索，再逐步缩小范围。补充导航能减少重复搜索，有些任务仍然需要搜索。

### 从业务描述推断模块并验证

语义匹配指根据含义判断两段描述是否相关，而非只比较文字是否相同。假设某个模块说明写着“社区内容展示与互动”，模型可能把评论功能列为这个模块的候选职责。这只是根据描述作出的推断，某个详情页的评论是否在这个模块实现，还要用源码确认。

导航明确记录“内容详情页评论 → 某模块 → 某入口文件”时，模型可以直接沿路径读取。这种显式映射比根据模块名称推断更容易核查。导航可能过时，所以映射仍要用当前源码确认。

验证时，要确认页面实际引用了哪个评论组件，以及哪些代码负责滚动事件和位置变化。实现归属以调用关系为准，文件名、目录名和关键词命中只是线索。多个业务都有评论功能时，结合页面入口和任务上下文进一步区分；证据仍不足时，说明哪些页面范围待确认。

目录迁移、职责调整或入口变化时，导航文档要同步更新。导航文档帮助选择阅读路径，当前源码用于确认静态调用关系；源码确定不了的运行时行为，用日志或实际操作结果验证。
