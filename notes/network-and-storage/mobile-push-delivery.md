## 系统推送通道的作用

远程推送是服务端主动发给手机、由系统展示或交给应用处理的消息。服务端发出的推送先交给系统的推送服务器，推送服务器再通过手机系统维护的一条长连接把消息送到手机。

服务端无法主动连接手机。手机上网时一般没有公网 IP，而是位于运营商的 NAT 之后。NAT（网络地址转换）是运营商的地址转换设备，让很多设备共用少量公网 IP。经过 NAT 的连接只能由手机主动发起，服务端拿不到可以直接连接的手机地址。

服务端要随时能把消息发到手机，手机就必须先主动连上一台服务器，并且一直保持连接。建立后长时间保持、反复用来收发数据的 TCP 连接叫长连接。

应用自己很难长期保持长连接。iOS 应用退到后台后很快被挂起，代码停止执行，连接随之中断，见[iOS 后台执行机制](../ios/background-execution.md#挂起与后台执行的前提)。Android 厂商系统也会清理后台应用。每个应用各自维护一条长连接，还会显著增加耗电。

所以手机系统用一个常驻进程替所有应用维护同一条长连接。任何应用的推送都经过这一条连接到达手机。

## 推送链路中的角色

```text
应用服务端 ──①──> 推送服务器 ──②──> 手机上的系统推送进程 ──③──> 通知栏 / 应用
```

| 角色 | iOS | Android（海外） | Android（中国大陆） |
| --- | --- | --- | --- |
| 推送服务器 | APNs（Apple Push Notification service） | FCM（Firebase Cloud Messaging） | 华为、小米、OPPO、vivo 等厂商各自的推送服务器 |
| 手机上维护长连接的进程 | 系统进程 `apsd` | Google Play 服务 | 厂商系统内置的推送服务 |

中国大陆的 Android 手机使用厂商通道，原因有两个：系统不预装 Google Play 服务，网络也无法稳定连接 Google 的服务器。FCM 依赖 Google Play 服务维护长连接，所以在这些手机上不可用。

## 注册与 device token

推送服务器要知道消息发给哪台设备上的哪个应用，所以应用先完成注册：

1. 应用向用户申请通知权限，再向系统请求注册远程推送。
2. 系统联系推送服务器，取回 device token。device token 是推送服务器分配的一串字符，唯一标识“这台设备上的这个应用”。FCM 中叫 registration token，各厂商的名称不同。
3. 应用把 device token 上传给应用服务端保存。

device token 可能因为重装应用、恢复系统等原因变化。应用每次启动取得 device token 后都上传一次，服务端保存最新值。

## 服务端调用推送服务器

服务端发送推送时，带上 device token 和 payload 调用推送服务器的接口。payload 是推送携带的 JSON 数据，包含通知标题、正文，以及应用自定义的字段，例如点击后要打开的页面地址。

| 推送服务器 | 服务端调用方式 |
| --- | --- |
| APNs | 通过 HTTP/2 + TLS 调用 APNs 接口；用开发者账号签发的密钥或证书证明身份 |
| FCM | 通过 HTTPS 调用 FCM 接口 |
| 厂商推送服务器 | 每个厂商有自己的 HTTPS 接口、鉴权方式和频率限制 |

服务端给中国大陆的 Android 用户发推送时，要先判断设备属于哪个厂商，再调用对应厂商的接口。所以服务端通常接入一个统一推送平台，由平台按设备厂商转发到各家通道。

## 推送服务器下发到设备：长连接与心跳

推送服务器按 device token 找到目标设备，通过设备上系统推送进程维护的长连接下发消息。这条长连接按以下方式维持：

- 系统推送进程启动后，主动连接推送服务器，完成 TCP 握手和 TLS 握手后保持连接。
- 系统推送进程定时发送心跳，让 NAT 设备保留这条连接的地址映射。心跳的作用和间隔取舍见[长连接：建立、心跳保活、断开检测与重连](long-connection-lifecycle.md#心跳保留-nat-映射与探活)。
- 网络切换后，例如从 Wi-Fi 切到蜂窝网络，系统推送进程重新建立连接。
- 设备离线时，推送服务器暂存消息，设备重新连上后再下发。暂存的时长和条数有上限。

应用也可以自建长连接，例如用来接收即时消息。自建长连接只在应用进程运行时有效；应用被挂起或进程被结束后，消息只能通过系统推送通道送达。自建长连接的建立、断开检测与重连见[长连接：建立、心跳保活、断开检测与重连](long-connection-lifecycle.md)。

## 通知展示：前台、后台与进程被结束

### iOS 的通知展示

- **应用在后台或进程已被结束**：`apsd` 收到推送后，由系统按 payload 中的标题和正文展示通知。这个过程不执行应用代码，所以应用进程不存在时也能展示。
- **应用在前台**：系统调用应用实现的 `userNotificationCenter(_:willPresent:withCompletionHandler:)`，应用在这个方法里决定是否展示横幅、是否播放声音。
- **静默推送**：payload 中设置 `"content-available": 1` 且不带展示内容时，系统不展示通知，而是在后台唤醒应用拉取数据。详见[静默推送：由服务端唤醒应用](../ios/background-execution.md#静默推送由服务端唤醒应用)。用户在多任务界面划掉应用后，静默推送不再唤醒应用。

### Android 的通知消息与透传消息

Android 推送分两类：

- **通知消息**：系统推送进程收到后直接在通知栏展示，不需要执行应用代码，所以应用进程不存在时也能展示。厂商通道在应用进程不存在时主要依靠这一类消息。
- **透传消息**：消息交给应用代码处理，由应用决定是否展示、展示什么。FCM 中叫 data message。应用进程不存在时，FCM 可以短暂启动应用进程处理消息；厂商通道的透传消息一般要求应用进程正在运行。

FCM 的通知消息在应用位于前台时由应用处理：FCM 调用应用的 `onMessageReceived`，应用自己创建通知。

## 点击通知：启动应用并取得 payload

### iOS 的点击回调

用户点击通知后，按以下顺序执行：

1. 系统启动应用；应用已在后台时，系统把应用切回前台。
2. 系统调用 `userNotificationCenter(_:didReceive:withCompletionHandler:)`，通过参数 `response.notification.request.content.userInfo` 把 payload 交给应用。

### Android 的 PendingIntent 与 Activity

Android 点击通知的流程涉及四个概念：

- **Activity**：Android 中承载一个页面的组件。
- **Manifest**：应用的配置文件 `AndroidManifest.xml`。Activity 要在 Manifest 中声明，系统才能启动它。
- **Intent**：描述“要启动哪个组件、传什么参数”的对象。
- **PendingIntent**：应用交给系统保存的 Intent，系统可以在之后替应用执行这个 Intent。

用户点击通知后，按以下顺序执行：

1. 系统取出通知上绑定的 PendingIntent。
2. 系统执行其中的 Intent。应用进程不存在时，系统先创建应用进程。
3. 系统启动 Intent 指定的 Activity，并把 Intent 中的参数交给这个 Activity。参数来自 payload。

厂商通道的通知在推送请求或厂商后台中配置点击动作，常见三种：打开应用首页、打开指定 Activity、打开一个 deeplink。

## 打开目标页面：deeplink 与路由

iOS 和 Android 打开目标页面的方式相同，都由应用自己完成：

1. payload 中带一个 deeplink。deeplink 是指向应用内某个页面的地址，例如 `app://post/detail?post_id=123`。
2. 应用把 deeplink 交给路由模块。路由模块事先登记“路径 → 页面”的对应关系，例如 `post/detail` 对应帖子详情页。
3. 路由模块解析出路径和参数，创建帖子详情页，并传入 `post_id=123`。

冷启动是指应用进程原本不存在，点击通知后从零启动。冷启动时登录状态、网络模块等可能还没初始化完成，立即跳转可能失败。应用通常先保存 deeplink，等首页和基础服务初始化完成后，再把 deeplink 交给路由模块。

## iOS 与 Android 的差异汇总

| 环节 | iOS | Android |
| --- | --- | --- |
| 推送服务器 | 只有 APNs | 海外使用 FCM；中国大陆使用各厂商通道 |
| 服务端对接 | 一套 HTTP/2 接口 | 中国大陆需要对接多家厂商，通常借助统一推送平台 |
| 设备上的长连接 | 系统进程 `apsd` 统一维护 | Google Play 服务或厂商推送服务统一维护 |
| 进程被结束后展示 | 系统展示 | 通知消息由系统展示；透传消息一般需要应用进程运行 |
| 应用在前台时 | 调用 `willPresent`，由应用决定是否展示 | FCM 通知消息调用 `onMessageReceived`，由应用自己展示 |
| 点击后启动应用 | 系统启动应用，调用 `didReceive` 并传入 payload | 系统执行 PendingIntent，启动 Manifest 中声明的 Activity |
| 打开目标页面 | 两端相同：解析 payload 中的 deeplink，交给路由模块跳转 | 同左 |
