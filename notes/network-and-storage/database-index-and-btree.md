本文以 MySQL 的 InnoDB 存储引擎为例。存储引擎是数据库中负责把数据写入磁盘、再从磁盘读出的模块。InnoDB 读写磁盘的最小单位是页（page），默认大小为 16KB；一次磁盘读取至少读入一整页。

下文的示例表为 `user(id 主键, name, age)`，并在 `age` 列上建立了索引。

## 索引与全表扫描

索引是存储引擎在表数据之外额外维护的有序数据结构。索引按一列或多列的值排序，并记录每个值对应的行。

- 没有索引时，执行 `SELECT * FROM user WHERE age = 20`，存储引擎需要逐行读取整张表并判断 age。这种读取方式叫全表扫描。
- 有 age 索引时，存储引擎沿着按 age 排序的树结构查找，只读取少量页。
- 索引占用额外的磁盘空间。插入或删除一行时，InnoDB 要维护这行对应的索引条目。修改参与索引的列值时，InnoDB 也要维护受影响的索引。

## B+ 树的结构

B+ 树是一种多叉平衡查找树。多叉指一个节点可以有很多个子节点；平衡指从根节点到任意叶子节点经过的层数相同。

不同类型的树有各自的平衡规则。B+ 树要求所有叶子节点同层。AVL 树是一种平衡二叉查找树，要求每个节点的左右子树高度最多相差 1，因此叶子可以位于不同层。

1. 每个节点对应一页。非叶子页存分界值、子页指针和管理页的信息。叶子页可以存多条记录。页可以留有空闲空间供后续插入。
2. 非叶子节点只存“分界值 + 子页指针”，用于指引查找方向，不存行数据。
3. 叶子节点存放索引的全部记录，记录按索引定义的键顺序排列。索引列默认按升序排列。
4. 同一层的叶子节点之间用双向链表按顺序连接。范围查询和排序可以沿链表顺序读取。

### 树高与读页次数

非叶子节点只存分界值和指针，所以一页能存很多条记录。以 bigint 主键为例：一条非叶子记录约为 8 字节主键加 6 字节指针，一页约能存 1170 条。叶子节点每行按 1KB 估算，一页存 16 行。3 层 B+ 树能存的行数约为 1170 × 1170 × 16 ≈ 2190 万。

因此，在约两千万行的表中查找一个值，存储引擎通常只需从根节点到叶子节点读取 3 页。没有索引时，1000 万行数据按每页 16 行计算约有 62 万页，全表扫描需要读取全部页。

### 与其他结构的比较

数据库查找的主要开销是读取磁盘页的次数，不是内存中比较的次数。下表按这一点比较几种结构：

| 结构 | 与 B+ 树的区别 |
| --- | --- |
| 有序数组二分查找 | 1000 万个元素需要约 24 次跳转（log₂10⁷ ≈ 24）。相邻两次跳转的位置相距很远，通常落在不同页上，所以要读取约 24 页。在数组中间插入元素时，后面的元素都要后移 |
| 二叉查找树、红黑树 | 每个节点只有 2 个子节点，一百万行时树高约 20。节点远小于一页，相邻两层的节点通常在不同页上，所以每下降一层通常要读一页，见[二叉查找树的读页次数](#二叉查找树的读页次数) |
| B 树 | 非叶子节点也存行数据，一页能放的分界值更少，树更高。范围查询需要在不同层之间来回遍历，不能只沿叶子链表读取，见[B 树](#b-树) |
| 哈希表 | 只支持等值查询，不支持范围查询、排序和前缀匹配，见[InnoDB 为什么不用哈希表做索引](#innodb-为什么不用哈希表做索引) |

B+ 树每读一页，就从一千多个分支中选择一个，查找范围缩小到原来的约千分之一；二分查找每次只能把范围缩小一半。B+ 树插入新键时只修改对应的叶子页；叶子页写满后，InnoDB 才把一页拆成两页。

### 二叉查找树的读页次数

二叉查找树的一个节点只存一个键和两个子节点指针，大约几十字节，远小于一页。二叉查找树每下降一层通常要读一页，原因如下：

1. 磁盘按页读取。InnoDB 一次至少读入一整页（16KB），不能只读几十字节。
2. 二叉查找树按插入顺序为节点分配位置。为了保持平衡，树还会旋转调整节点。所以查找路径上的父节点和子节点通常落在不同的页上。
3. 每下降一层，存储引擎就要读一个新页。读入的 16KB 中只有当前节点的几十字节有用，这几十字节只够做一次“二选一”的比较。

一百万行时，二叉查找树高约 20 层（log₂10⁶ ≈ 20），最坏情况下要读约 20 页。B+ 树把一个节点设计成一页，一个非叶子节点约存 1170 条记录，读一页就能在约 1170 个分支中选出一个。因为 1170 ≈ 2¹⁰，B+ 树读一页的效果相当于二叉查找树下降 10 层。

把二叉查找树上面 10 层的约 1000 个节点放进同一页，也能做到读一页连续下降 10 层。这种做法实际上是把二叉查找树改造成多叉树。B 树和 B+ 树直接按“一个节点对应一页、一个节点存很多键”设计。

## B 树

B 树是一种多叉平衡查找树。B 树的每个节点（包括非叶子节点）都同时存键和键对应的数据，这一点与 B+ 树不同。中文资料中的“B-树”就是 B 树，“-”是连字符，不是减号。

### 键与数据

键是节点中用来比较大小的值；数据是键对应的记录。以按 id 组织的 `user` 表为例，键是 id 的值，例如 30；数据是 id = 30 的整行 `(30, 赵六, 28)`。键是行中的一列，不等于整行数据。

B 树中的每个键有两个作用：

- 标识自己的记录：目标值等于这个键时，查找在当前节点取出这个键对应的数据，查找结束。
- 充当分界线：目标值不等于这个键时，查找用这个键比较大小，决定进入哪个子节点。

### 阶与结构规则

阶（m）是一个节点最多能有的子节点数量。一棵 m 阶 B 树满足以下规则：

1. 每个节点最多存 m−1 个键，键按从小到大排列。
2. 节点有 k 个键时，就有 k+1 个子节点指针。
3. 键 K 左边子树中的键都小于 K，右边子树中的键都大于 K。
4. 除根节点外，每个节点至少有 ⌈m/2⌉ 个子节点。这条规则保证节点至少半满，树不会过高。
5. 所有叶子节点在同一层，从根节点到任意叶子节点的路径长度相同。

一个有 2 个键的节点实际存放 2 个键、2 条数据和 3 个子节点指针：

```text
P0   (20, id=20 的行)   P1   (40, id=40 的行)   P2
```

20 和 40 是 id 取值范围上的两个切点。两个切点把取值范围切成 3 段，每段对应一个子节点指针：

```text
        P0 负责          20          P1 负责           40          P2 负责
 ───────────────────────●──────────────────────────────●───────────────────────
        id < 20                    20 < id < 40                   id > 40
```

k 个键把取值范围切成 k+1 段，所以有 k 个键的节点有 k+1 个子节点。

### 在 B 树中查找

以一棵 3 阶 B 树为例。3 阶表示每个节点最多 2 个键、3 个子节点：

```text
                 [20 | 40]
              /      |      \
       [5 | 10]   [25 | 30]   [45 | 50]
```

在根节点 `[20 | 40]` 上查找不同的 id：

| 目标 id | 与键比较的结果 | 下一步 |
| --- | --- | --- |
| 20 | 等于键 20 | 在根节点取出 id = 20 的行，查找结束 |
| 10 | 小于 20 | 落在第 1 段，进入 P0 |
| 30 | 大于 20、小于 40 | 落在第 2 段，进入 P1，在 `[25 \| 30]` 中找到 30 |
| 45 | 大于 40 | 落在第 3 段，进入 P2 |

查找 30 时读了 2 个节点，键 20 和键 40 只起分界线的作用。查找 20 时，键 20 起标识自己记录的作用，查找在第 1 层结束。

### 插入与分裂

B 树把新键插入叶子节点。叶子节点的键超过 m−1 个时，B 树执行分裂：

1. 叶子节点从中间断开，拆成两个节点。
2. 中间的键移动到父节点。
3. 父节点因此超过上限时，父节点继续分裂，分裂一直向上传递。
4. 根节点分裂时，中间的键成为新的根节点，树高加 1。

在上面的 3 阶 B 树中插入 35：

```text
① 35 插入叶子 [25 | 30] → [25 | 30 | 35]，超过 2 个键
② 叶子分裂成 [25] 和 [35]，中间键 30 移到根 → 根变成 [20 | 30 | 40]，也超过 2 个键
③ 根分裂成 [20] 和 [40]，中间键 30 成为新的根

                    [30]
                 /        \
            [20]            [40]
           /    \          /    \
     [5 | 10]  [25]     [35]   [45 | 50]
```

B 树只在根节点分裂时增高一层，而且从顶部增高。所以所有叶子节点始终在同一层。

### B 树与 B+ 树的区别

B 树和 B+ 树都是多叉平衡查找树，查找、插入和分裂的方式基本相同。两者的区别在于数据存放的位置：

| | B 树 | B+ 树 |
| --- | --- | --- |
| 数据存放位置 | 每个节点都存键和数据 | 只有叶子节点存数据，非叶子节点只存分界值和子页指针 |
| 同一个键出现的次数 | 一次 | 非叶子节点中的分界值会在叶子节点中再出现一次 |
| 叶子节点之间 | 没有连接 | 用双向链表按顺序连接 |
| 查找结束的位置 | 可能在非叶子节点结束 | 一定走到叶子节点 |
| 范围查询 | 在树的各层之间来回做中序遍历 | 找到起点后沿叶子链表顺序读取 |

B+ 树的叶子节点与 B 树的节点有一个共同点：每个键旁边都跟着这个键对应的数据。区别是 B+ 树的叶子节点没有子节点指针，而有指向前一个和后一个叶子节点的指针。

数据库选择 B+ 树有两个原因：

- 树更矮。B 树的非叶子节点也存数据，一页能放的键更少，每个节点的子节点更少，树就更高，查找要读的页也更多。
- 范围查询更快。执行 `WHERE age BETWEEN 20 AND 30` 时，B+ 树找到 age = 20 所在的叶子节点后，沿叶子链表读到 30 就结束。

B 树的优点是：目标键靠近根节点时，查找可以提前结束。

教材中的 B 树写成“k 个键、k+1 个子节点”。InnoDB 的 B+ 树中，非叶子节点的每条记录对应一个子页，记录中存子页的最小键，见[在 B+ 树中逐层查找](#在-b-树中逐层查找)。两种写法中，键都起分界线的作用。

## InnoDB 为什么不用哈希表做索引

InnoDB 不用哈希表作为索引结构，主要原因是哈希表只能做等值查询，不能做范围查询、排序和前缀匹配。

哈希表用哈希函数把键换算成桶的位置，再把记录放进这个桶。哈希函数是把键换算成整数的函数，换算结果决定记录存进哪个桶。哈希函数、桶和冲突的详细机制见[HashMap 的结构与实现原理](../data-structures/hash-map.md)。哈希函数的换算结果和键的大小没有关系：

```text
hash(20) → 桶 7
hash(21) → 桶 2
hash(25) → 桶 13
hash(30) → 桶 0
```

| 查询 | 哈希表 | B+ 树 |
| --- | --- | --- |
| 范围查询 `WHERE age BETWEEN 20 AND 30` | 20 到 30 之间的记录分散在各个桶中，只能扫描所有桶 | 找到 age = 20 所在的叶子节点，沿叶子链表读到 30 |
| 排序 `ORDER BY age` | 记录不按 age 排列，取出后还要再排序 | 叶子节点已按 age 排序，顺序读出即可 |
| 前缀匹配 `LIKE 'abc%'` | `hash('abc')` 与 `hash('abcd')` 没有关系，无法算出以 abc 开头的值在哪些桶 | 以 abc 开头的值在叶子节点中连续排列 |
| 联合索引 `(a, b)` 上只给出 `WHERE a = 1` | 哈希函数要用 a 和 b 一起计算桶的位置，缺少 b 就算不出位置 | 记录先按 a 排序，a = 1 的记录在叶子节点中连续排列，见[联合索引与最左前缀原则](#联合索引与最左前缀原则) |

哈希表存在磁盘上时还有两个问题：

- 扩容代价大。记录增多时，哈希表要增加桶的数量，并按新的桶数重新计算每条记录的位置，这个过程叫 rehash。在磁盘上做 rehash 要重写大量的页。B+ 树变大时只在局部做页分裂，一次只影响少数几个页。
- 冲突会变慢。两个不同的键算出同一个桶时，这两个键发生哈希冲突。冲突的记录在同一个桶中排成链表，冲突越多，查找时要比较的记录越多。

哈希表的等值查询是 O(1)，理论上比 B+ 树快。但 B+ 树查找一个值通常只读 2～4 页；Buffer Pool 是 InnoDB 在内存中缓存数据页的区域，B+ 树的上层节点通常已经缓存在 Buffer Pool 中，实际读磁盘的次数更少。为了省下这几次读页而放弃范围查询、排序和前缀匹配，代价过大。

### 自适应哈希索引

InnoDB 内部有一个自适应哈希索引（Adaptive Hash Index）：

1. InnoDB 监测 B+ 树上的查询。
2. 某些索引值被反复做等值查询时，InnoDB 自动在内存中为这些值建立哈希索引。
3. 之后再查这些值时，InnoDB 用哈希索引直接定位到 B+ 树叶子页中的记录，跳过从根节点向下查找的过程。

自适应哈希索引由 InnoDB 自动建立和维护，只存在于内存中，开发者不能手动创建。参数 `innodb_adaptive_hash_index` 控制这个功能：MySQL 8.0 默认开启，MySQL 8.4 起默认关闭。在 InnoDB 表上执行 `CREATE INDEX ... USING HASH`，InnoDB 实际创建的仍是 B+ 树索引。支持手动创建哈希索引的是 MEMORY 存储引擎。

## 聚簇索引与二级索引

InnoDB 中，每张表有一棵聚簇索引树；每个普通索引再各自对应一棵二级索引树。

- 聚簇索引：叶子节点存放整行数据的 B+ 树。InnoDB 按主键建立聚簇索引，每张表只有一个。表没有主键时，InnoDB 使用第一个所有列都非空的唯一索引；如果也没有，InnoDB 生成隐藏的 `row_id` 作为聚簇索引的键。
- 二级索引（也叫辅助索引）：叶子节点只存索引列的值和主键值的 B+ 树。

示例表 `user` 的两棵树：

| 树 | 排序依据 | 叶子节点存放的内容 |
| --- | --- | --- |
| 聚簇索引 | id | 整行数据 `(id, name, age)` |
| age 二级索引 | age；age 相同时按 id | `(age, id)` |

聚簇索引的一条叶子记录对应一行，主键是该行中的一列。一个叶子页可以容纳多条记录。例如，同一叶子页可以按主键顺序存放 `(20, '小李', 22)`、`(25, '小王', 20)` 和 `(33, '小张', 24)`。其中 `id` 就是聚簇索引的键。执行 `WHERE id = 25` 并使用主键索引时，`25` 是目标键值。InnoDB 先定位叶子页，再在页内找到 `(25, '小王', 20)`。

`age` 二级索引按 `age` 比较大小、定位记录，并保存 `id` 以便回表读取其他列。

age 二级索引不存 name，原因有两个：

- 如果每个二级索引都存放全部列，每个索引的大小都会接近整张表。
- 修改 name 时，InnoDB 需要同步更新所有存放 name 的索引，写入开销随索引数量增加。

### 回表

回表是指查询先在二级索引中找到主键值，再用主键值到聚簇索引中查出整行。执行 `SELECT name FROM user WHERE age = 20` 的过程如下：

```text
① 在 age 二级索引中找到 (20, id=5)
② 用 id=5 到聚簇索引中查出整行，取出 name   ← 回表
```

满足 age=20 的记录有多条时，每一条记录都要用自己的 id 回表一次。

## 覆盖索引

覆盖索引是指查询需要的列全部存放在某个索引的叶子节点中，存储引擎不需要回表。

- `SELECT id, age FROM user WHERE age = 20`：age 二级索引的叶子节点已经存有 age 和 id，所以不回表。
- 经常按 age 查询 name 时，可以建立联合索引 `INDEX(age, name)`。联合索引的叶子节点存放 `(age, name, id)`，查询 name 时直接在联合索引中取值。联合索引的排序方式见[联合索引与最左前缀原则](#联合索引与最左前缀原则)。

查询使用覆盖索引时，`EXPLAIN` 输出的 `Extra` 列显示 `Using index`。其他输出字段见[慢查询与 EXPLAIN](#慢查询与-explain)。

## 在 B+ 树中逐层查找

索引键是索引用来排序和比较的值。分界值也叫分隔键，用于划分每个子页负责的键值范围。InnoDB 的非叶子记录包含分界值和指向相应子页的指针。除用作下界的最左条目外，分界值来自对应子页的首条键。

查找规则：存储引擎在当前节点中找到最后一个“分界值 ≤ 目标值”的记录，然后读取这条记录指向的子页。存储引擎重复这一步，直到到达叶子节点。

示例：age 二级索引的根节点如下。

```text
根节点页：
  [ 1 → P1 ]  [ 18 → P2 ]  [ 35 → P3 ]  [ 60 → P4 ]

P1 存 age 1～17，P2 存 age 18～34，P3 存 age 35～59，P4 存 age ≥ 60
```

查找 `age = 20` 的过程：

1. 存储引擎读取根节点页，比较分界值：1 ≤ 20，18 ≤ 20，35 > 20。最后一个满足条件的记录是 `[18 → P2]`。
2. 存储引擎读取 P2。P2 仍是非叶子节点时，存储引擎按同样规则选择下一层的页。
3. 存储引擎到达叶子页，定位到第一条 age=20 的记录，再沿叶子链表向右读取，直到 age 不等于 20。

每层最左边的记录在比较时被视为比任何值都小，所以小于 1 的目标值也会进入 P1。

一页中有上千条记录时，存储引擎不会逐条比较。页内有一个页目录（Page Directory），页目录按顺序记录一部分记录的位置。存储引擎先在页目录上二分查找，再在相邻的少量记录中顺序比较。

## 重复键与分界值

age 不是唯一值，同一个 age 的记录可能跨越多个叶子页。InnoDB 在二级索引的非叶子节点中，把分界值存为“索引列值 + 主键值”，例如 `(age, id)`，使每个分界值都唯一。所以二级索引非叶子节点的每条记录包含索引列值、主键值和子页页号；聚簇索引非叶子节点的每条记录只包含主键值和子页页号。

示例：age = 20 的记录分布在三个叶子页上。P1 的末尾是 `(20, id=5)`，P2 从 `(20, id=9)` 开始，P3 从 `(20, id=15)` 开始。

```text
父节点：  [ (1, 2) → P1 ]  [ (20, 9) → P2 ]  [ (20, 15) → P3 ]

P1：……、(20, 5)
P2：(20, 9)、(20, 12)
P3：(20, 15)、(25, 3)、……

查找 age = 20：目标是第一条 age=20 的记录，相当于查找 (20, 比任何 id 都小)
  → (1, 2) ≤ 目标，(20, 9) > 目标
  → 进入 P1，找到 (20, id=5)
  → 沿叶子链表读到 P2、P3，继续读出 (20, 9)、(20, 12)、(20, 15)，直到 age 不等于 20
```

如果分界值只存 age，P2 和 P3 的分界值都是 20。按“最后一个分界值 ≤ 20”的规则，查找会直接进入 P3，漏掉 P1 和 P2 中 age = 20 的记录。

插入和删除也依赖唯一的分界值。删除 id = 12 这一行时，InnoDB 根据这一行的 age 和 id 得到二级索引记录 `(20, 12)`。因为 `(20, 9) ≤ (20, 12) < (20, 15)`，InnoDB 直接进入 P2。如果分界值只存 age，P2 和 P3 的分界值相同，InnoDB 无法判断 `(20, 12)` 在哪一页，只能从第一个可能的页开始逐条查找；重复值越多，需要读的页越多。插入 `(20, 10)` 时同理，InnoDB 靠主键比较确定新记录应放进 P2。

### 唯一索引中的主键

唯一二级索引的非叶子节点同样带主键值。唯一索引要求索引列的值不重复，但 B+ 树中仍可能出现索引列值相同的记录：

- 唯一索引允许多行的索引列为 NULL。
- InnoDB 删除记录时，先给记录打上删除标记。如果仍有快照读需要这条旧记录，InnoDB 的后台清理线程必须延后清除。旧版本的使用规则见 [MVCC 与两种读法](mysql-transactions-and-logs.md#mvcc-与两种读法)。清除之前插入相同值的新记录，树中就会同时存在两条索引列值相同的记录。

### 主键长度与索引大小

InnoDB 的二级索引记录带有对应行的主键值。主键越长，同样数量的二级索引记录占用的空间越大。8 字节的 `BIGINT` 主键比用 `BINARY(16)` 保存的 UUID 主键短。

如果同一个数据库统一分配 ID，通常可以选 `BIGINT AUTO_INCREMENT`。新分配的 ID 通常排在主键 B+ 树末端。例如，已有 `100、101、102` 时，`103` 排在 `102` 后面。随机生成的 UUIDv4 可能落在不同叶子页对应的键值范围内。随机插入更容易让页的空闲空间分布不均，也往往降低页的填充率。

UUID 是一种 128 位标识符。多个系统需要独立生成 ID 并在之后合并数据时，可以考虑 UUID。用 UUID 作为 InnoDB 主键时，可以选 UUIDv7 并按标准字节顺序存入 `BINARY(16)`。UUIDv7 把时间戳放在开头，生成时间相近的键通常也排在索引中相近的位置。

## 联合索引与最左前缀原则

联合索引是建在多列上的一个索引，例如 `INDEX(city, age)`。下文的示例表为 `user(id 主键, city, age)`，并建立了联合索引 `INDEX(city, age)`。

### 联合索引的键

联合索引的键是多个列的值按索引定义的顺序组成的一组值，形式类似元组，例如 `('上海', 22)`。InnoDB 比较两个键时先比较 city；city 相同时再比较 age。叶子节点中的每条记录由键和主键 id 组成：

```text
(city,   age,  id)
('上海',  22,   7)
 └──── 键 ────┘  └ 回表用的主键
```

记录中分别保存 city 的值和 age 的值，InnoDB 不会把两列拼成一个字符串 `"上海22"`。如果拼成字符串比较，`"上海3"` 会排在 `"上海22"` 后面，因为字符 `'3'` 大于字符 `'2'`，age 的数值顺序会被打乱。

### 联合索引的排序

假设城市的顺序是 北京 < 上海 < 深圳，叶子节点中的记录按下面的顺序排列：

```text
序号   city   age   id
 1     北京    18    3  ┐
 2     北京    25    1  │ 北京段：age 有序 18 < 25 < 30
 3     北京    30    6  ┘
 4     上海    20    2  ┐
 5     上海    22    7  │ 上海段：age 有序 20 < 22 < 35
 6     上海    35    4  ┘
 7     深圳    19    5  ┐
 8     深圳    28    8  ┘ 深圳段：age 有序 19 < 28
```

- city 在整个索引中有序。
- age 只在同一个 city 的段内有序。单独看 age 这一列，从上到下是 18, 25, 30, 20, 22, 35, 19, 28，整体无序。

通讯录先按姓排序、姓相同再按名排序，排列方式与联合索引相同。知道姓“王”，可以直接翻到姓王的一段；只知道名叫“伟”，只能翻遍整本通讯录，因为叫“伟”的人分散在各个姓中。

MySQL 8.0 的 InnoDB 支持在 B+ 树索引定义中指定列的排序方向。例如，`INDEX (user_id ASC, created_at DESC)` 先按 `user_id` 从小到大排序。同一个用户的索引条目再按 `created_at` 从新到旧排序。

查询 `WHERE user_id = 25 ORDER BY created_at DESC LIMIT 10` 时，如果 MySQL 选择升序联合索引 `(user_id, created_at)`，也可以从用户 25 的索引范围末端反向读取。假设索引里的时间依次为 `09:00 → 10:00 → 11:00`，反向扫描先读到 `11:00`。取满 10 条满足条件的记录后，查询就可以停止扫描。

### 联合索引的 B+ 树

假设每个叶子页放 3 条记录，`INDEX(city, age)` 的 B+ 树如下：

```text
                         根节点（非叶子节点）
   [ ('北京',18,3) → 页A ]  [ ('上海',20,2) → 页B ]  [ ('深圳',19,5) → 页C ]
            │                        │                        │
            ▼                        ▼                        ▼
  页A                        页B                        页C
  ('北京',18,3)        ⇄     ('上海',20,2)        ⇄     ('深圳',19,5)
  ('北京',25,1)              ('上海',22,7)              ('深圳',28,8)
  ('北京',30,6)              ('上海',35,4)
```

非叶子节点的每条记录存子页中最小记录的 `(city, age, id)` 和子页页号；分界值带上 id 的原因见[重复键与分界值](#重复键与分界值)。

- `WHERE city = '上海' AND age = 22`：在根节点比较 `('上海', 22)`，大于等于 `('上海', 20, 2)`、小于 `('深圳', 19, 5)`，进入页 B；在页 B 中找到 `('上海', 22, 7)`，得到 id = 7。查询还需要其他列时，用 id = 7 回表。
- `WHERE city = '上海'`：在根节点只比较 city，进入页 B，从页 B 的第一条记录开始读，读到 city 不等于 `'上海'` 时停止。
- `WHERE age = 22`：在根节点必须先比较 city 才能决定进入哪个子页。查询没有给出 city，InnoDB 无法判断 age = 22 的记录在页 A、页 B 还是页 C，只能读遍所有叶子页。

### 最左前缀原则

前缀是从索引最左边一列开始、连续的若干列。`INDEX(a, b, c)` 的前缀有 `(a)`、`(a, b)`、`(a, b, c)` 三个；`(b)`、`(b, c)`、`(a, c)` 都不是前缀。

最左前缀原则：查询条件从联合索引的第一列开始、连续地使用索引列时，InnoDB 才能用这些列在 B+ 树上定位记录。定位是指 InnoDB 通过比较大小直接跳到符合条件的一段记录，不需要从头逐条检查。查询条件没有用到第一列，或者中间跳过了某一列时，后面的列不能用来定位。

以上文的 `INDEX(city, age)` 为例：

| 查询条件 | 能用来定位的列 | 原因 |
| --- | --- | --- |
| `city = '上海'` | city | `(city)` 是前缀 |
| `city = '上海' AND age = 22` | city、age | city 确定后，age 在上海段内有序 |
| `age = 22 AND city = '上海'` | city、age | 优化器会调整条件顺序；最左前缀看条件用到了哪些列，与 WHERE 中的书写顺序无关 |
| `age = 22` | 无 | 缺少第一列 city，age 在整个索引中无序 |
| `city = '上海' AND age > 21` | city、age | city 是等值条件，上海段内 age 有序，从 age = 22 开始往后读 |
| `city > '北京' AND age = 22` | 只有 city | city 是范围条件，定位到上海段和深圳段；两段合在一起时 age 为 20, 22, 35, 19, 28，又变成无序，只能逐条检查 age；检查发生在回表之前还是之后，见[索引下推](#索引下推) |

最后一行说明：某一列使用范围条件后，范围跨越了多个段，后面的列不再有序，所以不能用来定位。

`INDEX(a, b, c)` 的规则相同：

- `WHERE a = 1 AND b = 2 AND c = 3`：三列都能用来定位。
- `WHERE a = 1 AND c = 3`：只有 a 能用来定位。c 只在 a、b 都相同的段内有序，跳过 b 之后 c 无序。
- `WHERE b = 2 AND c = 3`：不能用这个索引定位，因为缺少第一列 a。

### 最左前缀与索引设计

- 有了 `INDEX(city, age)`，只按 city 查询的语句也能使用这个索引，不需要再单独建立 `INDEX(city)`。
- 只按 age 查询的语句不能用 `INDEX(city, age)` 定位。这类查询常见时，需要单独建立 `INDEX(age)`。
- 建立联合索引时，把最常作为等值条件的列放在最左边。

MySQL 8.0.13 起有索引跳跃扫描（Index Skip Scan）。city 的不同值很少时（例如只有 3 个城市），优化器依次取出每个 city 值，分别在每个 city 段内查找 age = 22，`WHERE age = 22` 因此也能使用 `INDEX(city, age)`。索引跳跃扫描是优化器在特定条件下的优化，不能替代按最左前缀设计索引。

评估索引时，先看常用查询中哪些列能减少读取的记录数或省掉排序。

- `WHERE` 条件只匹配少量行时，索引可以直接定位较小的范围。条件匹配表中大部分行时，扫描整张表可能更便宜。
- `JOIN ... ON` 的配对列可以帮助数据库定位匹配行。例如，查询先找到用户，再根据 `orders.user_id = user.id` 查订单时，可以用 `orders.user_id` 上的索引定位。
- 当索引顺序配合 `ORDER BY` 或 `GROUP BY` 时，数据库可以利用相邻记录的顺序。在 `GROUP BY age ORDER BY COUNT(*) DESC` 中，`age` 索引提供年龄顺序。每组的行数仍须计算，再按人数排列各组。

例如，在已有 `(user_id, created_at)` 索引的订单表中，把订单 100 的 `user_id` 从 25 改成 30 时，InnoDB 会标记旧的二级索引条目为删除，并按新键值插入条目。

## 索引下推

索引下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的优化：存储引擎扫描二级索引时，先用索引记录中已有的列判断 WHERE 条件，只对满足条件的记录回表。索引下推减少的是回表次数，不减少扫描的索引记录数。

MySQL 分为 Server 层和存储引擎层。Server 层负责解析 SQL、选择执行方案，并判断 WHERE 条件；存储引擎层负责按索引读取记录。没有索引下推时，存储引擎只用能定位的条件在索引中查找，并对查到的每条索引记录回表；WHERE 中的其余条件都等回表后由 Server 层判断。

### 回表次数的变化

沿用[联合索引与最左前缀原则](#联合索引与最左前缀原则)中的 `INDEX(city, age)` 和 8 条记录，并假设表中还有 `name` 列。执行下面的查询：

```sql
SELECT * FROM user WHERE city > '北京' AND age = 22;
```

`city > '北京'` 是范围条件，InnoDB 用 city 定位到上海段和深圳段，共 5 条索引记录（序号 4～8）。这 5 条记录中 age 无序，`age = 22` 不能用来定位。查询需要 `name` 列，`name` 不在联合索引中，所以满足条件的记录都要回表。

没有索引下推时：

```text
存储引擎用 city > '北京' 定位到序号 4～8 的 5 条索引记录
→ 存储引擎用 id = 2、7、4、5、8 各回表一次，共 5 次，读出 5 行整行数据
→ 存储引擎把 5 行交给 Server 层
→ Server 层判断 age = 22，只保留 id = 7 这一行
```

有索引下推时：

```text
存储引擎用 city > '北京' 定位到序号 4～8 的 5 条索引记录
→ 存储引擎用索引记录中的 age 判断 age = 22，跳过 id = 2、4、5、8
→ 存储引擎只用 id = 7 回表一次
→ Server 层收到 1 行
```

回表次数从 5 次减少到 1 次。两种情况下存储引擎都扫描了 5 条索引记录：`age = 22` 仍然不参与定位，只是判断提前到了回表之前。每次回表都要到聚簇索引中查找一次，可能读取不同的数据页，所以索引记录过滤掉的越多，索引下推省下的开销越大。

“下推”指优化器把 WHERE 中只涉及索引列的条件，从 Server 层交给存储引擎层判断。

### 生效条件

- 索引下推只用于需要回表的二级索引访问。InnoDB 聚簇索引的叶子节点存放整行，没有回表可以减少；查询使用覆盖索引时也不回表。
- 只有索引中包含的列才能下推。条件中出现不在索引中的列（例如 `name = '张三'`）时，这部分条件仍要回表后由 Server 层判断。
- 包含子查询或存储函数的条件不能下推。
- 优化器开关 `optimizer_switch` 中的 `index_condition_pushdown` 控制索引下推，默认开启。
- 查询使用索引下推时，`EXPLAIN` 输出的 `Extra` 列显示 `Using index condition`。

## 索引失效的常见场景

索引失效是指查询条件不能让 MySQL 在 B+ 树上用索引定位记录，MySQL 只能扫描整张表或整个索引。常见场景按原因分为三类：

1. 条件中的索引列被函数、运算或类型转换包住，不是裸列。裸列指条件中直接出现、没有经过任何计算的列。
2. 条件匹配的记录在索引中不连续。
3. 优化器估算后认为使用索引比全表扫描慢。

这里的优化器是 MySQL 中负责选择执行方式的模块。对下面的普通索引示例，优化器可以用“索引列 比较运算符 常量”形式的条件定位数据。索引列被函数或表达式包住时，优化器不分析表达式是否保持原来的顺序，直接不用这一列的索引定位。例如 `YEAR(create_time)` 的大小顺序与 `create_time` 一致，但 `WHERE YEAR(create_time) = 2024` 仍然不能用 `create_time` 上的索引定位。

本节的示例表如下：

```sql
CREATE TABLE user (
  id          INT PRIMARY KEY,
  name        VARCHAR(20),
  age         INT,
  phone       VARCHAR(20),
  city        VARCHAR(20),
  create_time DATETIME,
  INDEX idx_age (age),
  INDEX idx_phone (phone),
  INDEX idx_create_time (create_time),
  INDEX idx_name_age_city (name, age, city)
);
```

可以用 `EXPLAIN` 的 `key` 和 `type` 区分没有选择索引、扫描索引和通过索引定位，见[慢查询与 EXPLAIN](#慢查询与-explain)。

### 索引列不是裸列

**函数**：把函数从列上移走，改成对常量计算的范围条件。

```sql
-- 不能用 idx_create_time 定位
SELECT * FROM user WHERE YEAR(create_time) = 2024;

-- 可以用 idx_create_time 定位
SELECT * FROM user
WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';
```

MySQL 8.0.13 起支持函数索引：对表达式的计算结果建立索引，例如 `INDEX ((YEAR(create_time)))`。建立函数索引后，`WHERE YEAR(create_time) = 2024` 可以使用这个函数索引。

**运算**：`WHERE age + 1 = 21` 中的 `age + 1` 是表达式，不能用 `idx_age` 定位；改写成 `WHERE age = 20` 后可以定位。

**隐式类型转换**：比较两个类型不同的值时，MySQL 自动把其中一个值转换成另一种类型再比较。字符串与数字比较时，MySQL 把字符串转换成数字。

```sql
-- phone 是 VARCHAR，13800000000 是数字：phone 被转换成数字，不能用 idx_phone 定位
SELECT * FROM user WHERE phone = 13800000000;

-- 常量写成字符串，可以用 idx_phone 定位
SELECT * FROM user WHERE phone = '13800000000';
```

第一条查询相当于对 `phone` 列套了一层转换。多个不同的字符串会转换成同一个数字，例如 `'13800000000'`、`' 13800000000'`、`'013800000000'` 都转换成 13800000000。这些字符串在 `idx_phone` 中按字符串顺序排列，彼此并不相邻，所以 MySQL 无法在 `idx_phone` 中划出一段连续的记录。

反过来，`age` 是 `INT`，`WHERE age = '20'` 中被转换的是常量 `'20'`，`age` 列本身没有被转换，`idx_age` 仍然可以定位。判断方法：转换发生在索引列上，索引失效；转换发生在常量上，索引不受影响。

JOIN 中也会出现这种情况。两张表的关联列字符集不同时（例如一边是 `utf8`，另一边是 `utf8mb4`），MySQL 把 `utf8` 列转换成 `utf8mb4` 再比较，被转换的那一列不能用索引定位。

### 匹配的记录在索引中不连续

**LIKE 以 `%` 开头**：`idx_phone` 从字符串的第一个字符开始排序。`LIKE '138%'` 确定了开头，以 `138` 开头的值在索引中排成连续的一段，可以定位。`LIKE '%0000'` 和 `LIKE '%380%'` 没有确定开头，匹配的值分散在整个索引中，不能定位。

`SELECT id, phone FROM user WHERE phone LIKE '%0000'` 只查询 `id` 和 `phone`，这两列都在 `idx_phone` 的叶子节点中，构成覆盖索引。这时 `EXPLAIN` 的 `type` 为 `index`：MySQL 扫描整个 `idx_phone`，而不是扫描整张表。`idx_phone` 比整张表小，扫描更快，但这仍然不是用索引定位。

需要后缀匹配时，可以增加一列存放反转后的字符串，把后缀匹配改成前缀匹配；需要任意位置匹配时，可以使用全文索引或搜索引擎。

**违反最左前缀原则**：`WHERE age = 20` 缺少 `idx_name_age_city` 的第一列 `name`，不能用这个联合索引定位。`WHERE name = '张三' AND city = '北京'` 跳过了 `age`，只有 `name` 能用来定位，`city` 只能在索引记录中逐条判断。规则和原因见[最左前缀原则](#最左前缀原则)。

**OR 两边有一列没有索引**：

```sql
-- city 没有单独的索引
SELECT * FROM user WHERE age = 20 OR city = '北京';
```

要找出 `city = '北京'` 的行，MySQL 必须扫描全表。全表扫描无法避免时，MySQL 在扫描过程中一起判断 `age = 20`，不再单独使用 `idx_age`。

`OR` 两边的列都有索引时，MySQL 可以分别用两个索引查出结果，再把两部分结果合并，这种方式叫索引合并（index merge），`EXPLAIN` 的 `type` 显示 `index_merge`。也可以把 `OR` 拆成两条查询，用 `UNION` 合并，见[UNION 与 OR 条件](sql-join-and-union.md#union-与-or-条件)。只有一边有索引时，两种做法都无法避免全表扫描。

### 优化器放弃索引

**匹配的行太多**：

```sql
-- 假设 90% 的用户 age > 18
SELECT * FROM user WHERE age > 18;
```

使用 `idx_age` 时，每条匹配的索引记录都要回表一次。回表按主键逐个到聚簇索引中查找，读取的数据页位置分散，属于随机 I/O；全表扫描按顺序读取聚簇索引的叶子节点，属于顺序 I/O。匹配的行占比很高时，大量随机 I/O 的代价超过一次顺序扫描，优化器选择全表扫描。

“占比多少算高”没有固定的阈值，优化器根据统计信息估算成本。统计信息不准确时，优化器可能选错方案：执行 `ANALYZE TABLE user` 可以更新统计信息；`FORCE INDEX (idx_age)` 可以强制使用指定的索引。

**`!=`、`<>`、`NOT IN`、`IS NOT NULL`**：这类条件不会因为写法本身失效。这类条件通常匹配表中的大部分行，优化器按上面的成本估算放弃索引。如果 `age = 20` 的行占 95%，`age != 20` 只匹配 5% 的行，优化器很可能使用 `idx_age`。

### 容易误判的情况

- `IS NULL` 可以使用索引。InnoDB 的二级索引会存放 NULL 值，NULL 排在索引的最前面。
- 条件的书写顺序不影响最左前缀原则。`WHERE age = 20 AND name = '张三'` 与 `WHERE name = '张三' AND age = 20` 都能用 `name` 和 `age` 定位。

| 场景 | 示例 | 原因 | 改法 |
| --- | --- | --- | --- |
| 函数 | `YEAR(create_time) = 2024` | 索引列不是裸列 | 改成范围条件，或建立函数索引 |
| 运算 | `age + 1 = 21` | 索引列不是裸列 | 把计算移到常量一侧 |
| 隐式类型转换 | 字符串列 `phone = 13800000000` | 索引列被转换成数字 | 常量使用与列相同的类型 |
| 左模糊匹配 | `LIKE '%0000'` | 匹配的值在索引中不连续 | 存放反转字符串，或使用全文索引 |
| 违反最左前缀 | 只有 `age = 20` | 缺少第一列，后面的列无序 | 补上第一列，或调整索引列顺序 |
| OR | `age = 20 OR city = '北京'` | 一边必须全表扫描 | 给另一列建立索引，再使用索引合并或 UNION |
| 匹配的行太多 | `age > 18` | 回表成本超过全表扫描 | 使用覆盖索引减少回表 |

## 慢查询与 EXPLAIN

慢查询是执行时间超过设定阈值的 SQL 语句。MySQL 的 `long_query_time` 以秒为单位设置时间阈值。比如阈值为 1 秒，查询执行了 1.5 秒。开启慢查询日志后，达到时间阈值并满足最少检查行数等记录条件的语句可以写入日志，供后续排查。UPDATE 和 DELETE 也可以进入慢查询日志。

EXPLAIN 显示执行计划，也就是 MySQL 计划怎样找行、选用什么索引，以及多表连接时按什么顺序访问表。

```sql
EXPLAIN SELECT name FROM user WHERE id = 1;
```

传统表格输出中的 `type` 表示当前表的访问方式。下面以 `user.id` 为主键，`user.age` 为普通索引。

| type | 访问方式 | 示例 |
| --- | --- | --- |
| `const` | 用固定值等值查找完整主键或唯一键，查询开始时最多读一行。 | `WHERE user.id = 1` |
| `eq_ref` | 连接时，用完整主键或非空唯一键等值查当前表。前面表每产生一组匹配行，当前表最多匹配一行。 | 先访问 orders，再按 `user.id = orders.user_id` 查询用户。详见[JOIN 的执行方式与驱动表](sql-join-and-union.md#join-的执行方式与驱动表)。 |
| `ref` | 按索引等值查找，同一个值可能匹配多行。 | `WHERE user.age = 20` |
| `range` | 在索引中扫描一个或多个范围。 | `WHERE user.id BETWEEN 10 AND 20` |
| `index` | 按索引顺序扫描，扫描范围可以覆盖整个索引。 | `SELECT age FROM user` 可以扫描 age 索引。 |
| `ALL` | 扫描整张表。 | `SELECT * FROM user` |

`key` 是计划使用的索引，`NULL` 表示该表没有选择索引。 `rows` 是预计检查的行数。判断开销时，还要看访问重复多少次。例如连接前面产生一万行，后面的 `eq_ref` 查找就可能执行一万次。

`Extra` 补充说明执行方式。 `Using index` 表示可以直接从索引取得所需数据，见[覆盖索引](#覆盖索引)。 `Using filesort` 表示 MySQL 需要额外排序。 `Using temporary` 表示需要临时表保存中间结果。 `type = index` 描述访问方式，`Extra = Using index` 描述所需数据能否直接从索引取得。

普通 EXPLAIN 显示计划与估算。EXPLAIN ANALYZE 实际执行语句，并给出各步骤的实际耗时、行数和执行次数。

## 深分页

深分页是指从排序后的查询结果中跳过大量记录，再取靠后的一页。 `OFFSET` 表示要跳过的结果行数。

```sql
SELECT id
FROM user
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

假设结果行数足够，MySQL 先按 id 排序后的顺序跳过前 100 万行，再返回后面的 20 行。即使用主键索引按顺序读取，MySQL 通常也要经过前面的索引项。OFFSET 是结果中的位置，id 是索引键值。偏移量越大，数据库通常要经过的记录就越多。
