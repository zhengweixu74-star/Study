## 并发事务与隔离级别

事务是数据库作为一个整体提交的一组操作。事务隔离级别规定并发事务可以看到其他事务的哪些修改，以及数据库允许哪些并发执行结果。事务的完整性质见[数据库事务与 ACID](ios-data-persistence.md#数据库事务与-acid)。

| 并发问题 | 含义与示例 |
| --- | --- |
| 脏读 | A 读到 B 尚未提交的余额 80。B 回滚后，余额恢复为 100。 |
| 不可重复读 | A 两次读取同一行。B 在两次查询之间把余额从 100 改为 80 并提交，A 两次读到的值不同。 |
| 幻读 | A 两次用相同条件查未支付订单。B 在两次查询之间插入一条符合条件的订单并提交，A 第二次查到了新增订单。 |
| 丢失更新 | A 和 B 都读到库存 10。两个事务都算出扣 1 后剩 9，再分别写入 9，最终少扣了一次。 |
| 写偏差 | 规则要求至少一人值班。A 和 B 都查到对方在值班，再分别取消自己的值班。两次修改都提交后，无人值班。 |

SQL 标准对三种读异常规定了最低保证。「可能」表示标准允许数据库出现该异常。数据库可以提供更强的保证。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed，RC） | 禁止 | 可能 | 可能 |
| 可重复读（Repeatable Read，RR） | 禁止 | 禁止 | 可能 |
| 可串行化（Serializable） | 禁止 | 禁止 | 禁止 |

可串行化要求成功提交的事务产生的效果等价于按某个顺序逐个执行。数据库可以并发执行事务，并在必要时中止冲突事务。

锁等待发生在一个事务申请的锁与另一个事务持有的锁冲突时。死锁是多个事务的等待形成了环。例如 A 锁住第 1 行并等待第 2 行，B 锁住第 2 行并等待第 1 行。InnoDB 检测到死锁后会回滚其中一个事务来解除循环等待。

## MVCC 与两种读法

多版本并发控制（MVCC）是数据库保留数据的多个版本，并根据可见性规则为查询选择版本的机制。InnoDB 用它实现 RC 和 RR 下普通 SELECT 的一致性读，也称快照读。

1. InnoDB 更新行时，把重建旧版本所需的信息写入 undo log（撤销日志）。行中的 `DB_TRX_ID` 标识最后一次插入或更新的事务，`DB_ROLL_PTR` 指向可用于重建上一版本的撤销日志记录。
2. 快照读使用 Read View 判断版本是否可见。Read View 记录创建时活跃的读写事务 ID 和事务 ID 边界。查询可以看到本事务此前的修改，也可以看到创建视图前其他事务已提交的修改。
3. InnoDB 从最新版本开始判断。如果版本不可见，InnoDB 就沿撤销日志逐步重建旧版本，直到找到第一个可见版本。只有当旧版本不再可能被已有快照使用时，后台清理才可以回收相关撤销日志。

RC 下每次快照读建立新视图。RR 下通常由第一次快照读建立视图，后续快照读复用该视图。

当前读读取当前可用的记录版本并加锁，例如 `SELECT ... FOR UPDATE`。当前读无需用 Read View 选择版本。如果其他事务持有冲突的锁，当前读默认等待对方释放锁再继续。

例如，A 在 RR 下先用普通 SELECT 读到余额 100。B 把余额改为 80 并提交。A 随后用 `SELECT ... FOR UPDATE` 读到 80 并加锁。如果 A 没有修改该行，A 再用普通 SELECT 时仍按原来的 Read View 读到 100。

## 索引锁与幻读

InnoDB 的记录锁加在已有索引记录上。间隙锁保护相邻索引记录之间的区间，也可以保护第一个索引值之前或最后一个索引值之后的区间。间隙锁阻止其他事务在受保护的间隙插入新记录。临键锁（Next-Key Lock）由一条索引记录的记录锁和该记录前的间隙锁组成。

| 锁 | 以相邻主键 10 和 20 为例 |
| --- | --- |
| 记录锁 | 锁住已有记录 20。 |
| 间隙锁 | 锁住开区间 `(10, 20)`，阻止插入 15 或 18。 |
| 临键锁 | 锁住 `(10, 20]`，包含 `(10, 20)` 的间隙和记录 20。 |

例如，表的主键只有 10 和 20。A 执行 `SELECT * FROM goods WHERE id = 15 FOR UPDATE`，结果为空。B 随后尝试插入 15。

- **RR**。InnoDB 锁住 `(10, 20)`，B 要等 A 释放锁。A 在事务内再执行同一条加锁查询时，B 的新行尚未插入。范围加锁查询通常会用临键锁保护记录和间隙。用完整唯一键等值查找并命中已有记录时，只需锁住命中的索引记录。
- **RC**。InnoDB 在搜索和索引扫描时禁用间隙锁，外键检查和重复键检查仍可使用间隙锁。B 可以插入 15 并提交，A 再查时就可能看到新行。这样可以减少插入等待，代价是允许出现幻读。

RR 下连续两次快照读也能避免看到其他事务后来插入的行。B 可以提交插入，A 复用原有 Read View，所以新行对 A 的快照读不可见。连续两次当前读则靠索引锁阻止其他事务在受保护的范围内插入新行。

## 乐观锁与悲观锁

乐观锁先读数据，更新时才检查从读取到写入之间是否有其他事务修改过数据。常见做法是在表中增加版本号 `version`，每次修改都更新版本号。

假设 A 和 B 都读到商品 `id = 1` 的 `version = 3`。两个事务都尝试执行带版本条件的更新。

```sql
UPDATE goods
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 3 AND stock > 0;
```

A 更新成功并提交后，版本变成 4。B 的版本条件不再成立，更新影响 0 行。如果 B 仍需扣减库存，应重新读取库存和版本，并在库存充足时再尝试。影响 0 行也可能表示商品不存在或库存不足，调用方需要按条件区分。CAS（Compare-And-Swap）用「预期值相等才更新」的方式检测冲突，版本号校验采用了相同思路。

悲观锁在读取数据时先取得锁。例如 A 通过 `SELECT ... FOR UPDATE` 读取并锁住商品行。B 执行同样的查询时等待。A 更新并提交后，B 取得锁，读取新的库存，再决定是否扣减。多个事务频繁更新同一行时，提前取得锁可以减少因读取结果过期导致的反复计算和重试，代价是其他事务等待锁。冲突少时，乐观锁通常能减少读取阶段的等待。

## 重做日志与二进制日志

### redo log 与崩溃恢复

redo log（重做日志）是 InnoDB 记录数据页修改、用于崩溃恢复的日志。数据页是 InnoDB 读取和写回数据的基本单位。事务把库存从 10 改为 9 时，InnoDB 修改内存中的数据页，并生成重做日志。

默认配置 `innodb_flush_log_at_trx_commit = 1` 下，事务提交会确保对应的重做日志已经写入持久存储。提交成功时，表数据文件中的页可能还是旧版本。若此时崩溃，InnoDB 重启后读取已持久化的重做日志，把尚未写回的修改重新应用到数据页。未提交事务的修改由 InnoDB 在恢复时回滚。

重做日志可以按顺序追加。InnoDB 可以把数据页的写回交给后台处理。同一页多次修改也可以合并为一次数据页写回，因此事务提交无须每次等待所有修改过的数据页写盘。

例如，库存从 10 改为 9，再改为 8。两次实际发生的数据页修改都会生成 redo 记录，即使当前数据页最终只写回一次。redo 记录描述底层页修改。一次 SQL 更新还能修改索引页和撤销日志所在的页，因而无法只根据 UPDATE 次数推算 redo 记录总数。

### binlog 与数据重放

binlog（二进制日志）是 MySQL 服务端记录数据和表结构变更的日志。它可以记录行发生了什么变化，也可以记录修改语句，具体取决于日志格式。

- **主从复制**是把主库的变更应用到从库，使从库跟进主库的数据。例如主库把库存从 10 改为 9，从库应用对应的 binlog 事件后也得到 9。
- **按时间点恢复**是从一个备份出发，应用备份之后的 binlog 事件，直到指定的恢复位置。例如备份后库存改为 9，之后商品被误删。恢复备份后，把日志重放到误删之前，可以恢复库存为 9 的商品。

redo log 帮助 InnoDB 在本机崩溃后补齐数据页修改。binlog 让另一份数据库能重放同一批数据变更。
