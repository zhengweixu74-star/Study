## 持久化与常用方式

数据持久化是把数据保存到磁盘等存储介质中，应用进程结束后数据仍然保留，下次启动时可以重新读取。变量、数组和单例中的数据只在内存中，进程结束后就会丢失。持久化的数据能保留多久，取决于存储位置和清理规则。

iOS 中使用 Swift 开发时，常见方式包括 UserDefaults、文件存储、Keychain、SQLite、Core Data 和 SwiftData。

| 方式 | 保存机制 | 适用场景 |
| --- | --- | --- |
| UserDefaults | 按键值保存设置，通过字符串键定位对应的值 | 少量、非敏感的偏好设置，例如主题和是否显示过引导；不适合保存密码或大量业务记录 |
| 文件存储 | 将数据写入应用可访问的文件；通常由 FileManager 管理目录和文件，由 Data 等类型读写内容 | 图片、视频、文档，以及保存为 JSON、plist 等格式的数据 |
| Keychain | 使用系统提供的加密存储，并由系统控制访问权限 | 密码、登录凭证、密钥等少量敏感数据 |
| SQLite | 将数据组织成表，使用 SQL 定义、查询和修改数据；SQL 是用于操作数据库的语言 | 需要按条件查询、排序、统计或频繁修改的记录，例如消息记录 |
| Core Data | 管理对象、对象之间的关系及对象的变化，并把对象数据保存到持久化存储 | 多种数据类型相互关联的应用，例如笔记与笔记分类；通常直接操作对象，不用自己编写 SQL |
| SwiftData | 使用 Swift 类型定义数据模型，通过框架保存和查询模型对象 | 使用 Swift 模型管理数据，并与 SwiftUI 集成；框架从 iOS 17 起可用 |

数据模型是描述应用保存哪些数据以及这些数据如何关联的类型和规则。例如，笔记有标题、正文和所属分类，分类可以关联多篇笔记。

## UserDefaults 的最小示例

UserDefaults 是按字符串键保存少量偏好设置的系统接口。可以保存的值包括 Bool、String、整数、浮点数、Data、Date，以及由这些值组成的数组和以字符串为键的字典。这些类型统称属性列表类型。自定义对象要先编码成 Data 等属性列表类型，再调用 set 保存。

下面通过键 hasSeenGuide 保存“用户是否看过引导”。键是用于定位数据的名称，true 是保存的值。

```swift
import Foundation

// 保存
UserDefaults.standard.set(true, forKey: "hasSeenGuide")

// 读取
let hasSeenGuide = UserDefaults.standard.bool(forKey: "hasSeenGuide")

// 删除
UserDefaults.standard.removeObject(forKey: "hasSeenGuide")
```

调用 set 后，UserDefaults 立即更新内存中的值，再异步写入磁盘。调用 bool(forKey:) 时，键不存在也返回 false，所以 bool(forKey:) 的返回值无法区分“从未保存过”和“保存了 false”。需要区分时，用 object(forKey:) 读取，键不存在时返回 nil。

SwiftUI 的 @AppStorage 通过 UserDefaults 读写设置，并在值变化时刷新使用这个值的视图。@AppStorage 的数据就保存在 UserDefaults 中。

选择的语言可以保存为字符串：

```swift
UserDefaults.standard.set("en", forKey: "preferredLanguage")
let languageCode = UserDefaults.standard.string(forKey: "preferredLanguage")
// 已保存时得到 "en"；键不存在时得到 nil。
```

UserDefaults 中只保存语言码；切换文案和刷新 UIKit 控件需要另外实现。启动时读取语言码、选择资源和刷新界面的完整流程见 [iOS 本地多语言与即时切换](../ios/localization-and-language-switching.md)。

## 编码、文件格式与持久化的区别

Codable 表示一个类型可以被编码和解码。Codable 只负责类型和数据格式之间的转换，写入磁盘要另外调用文件接口。编码与解码的具体机制见[Swift Codable 与序列化复制](../language/swift-codable-and-serialization.md)。

以 JSON 文件为例，保存流程是：Swift 对象 → JSONEncoder 转换为 Data → 把 Data 写入文件。读取流程是：从文件读取 Data → JSONDecoder 按指定类型还原 Swift 对象。Data 表示字节数据；JSONEncoder 编码完成时，Data 只在内存中，写入文件后才完成持久化。

JSON 和 plist 是数据格式。选择 JSON 或 plist，决定数据用什么格式表示；选择文件、数据库等存储方式，决定数据保存在哪里以及如何读写。

文件存储还需要选择合适的目录。目录用途、系统清理和备份规则见[iOS 文件存储](ios-file-storage.md)。

## Core Data 与 SQLite 的关系

Core Data 负责管理对象和对象的保存过程。SQLite 负责数据库存储和查询。Core Data 可以用 SQLite 作为底层存储，也可以使用其他存储类型。

例如，使用 SQLite 时，应用可以用 SQL 查询某个分类下的笔记。使用 Core Data 时，应用通常通过框架查询笔记对象，再通过对象的关系属性访问笔记所属的分类。Core Data 负责把这些对象数据映射到配置的持久化存储。

Core Data 和 SwiftData 都可以配置为只在内存中存储，这种配置下数据随进程结束而丢失。需要跨应用启动保留数据时，要配置磁盘上的持久化存储，并确认保存操作成功。

## SQLite 建表与数据约束

表用来保存同一类记录。每一行是一条记录，每一列是记录中的一个字段。比如，`conversations` 表保存会话，`messages` 表保存消息。一条会话可以有多条消息，每条消息只属于一条会话。这样的关系叫一对多。消息行用 `conversation_id` 保存所属会话的编号。

数据约束是数据库在写入时检查的规则。下面的例子有两条约束：每条消息必须属于一个已存在的会话；同一个会话内，消息的序号不能重复。

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE conversations (
    id INTEGER PRIMARY KEY
);

CREATE TABLE messages (
    id INTEGER PRIMARY KEY,
    conversation_id INTEGER NOT NULL,
    sequence_number INTEGER NOT NULL,
    sent_at INTEGER NOT NULL,
    content TEXT NOT NULL,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id)
        ON DELETE RESTRICT,
    UNIQUE (conversation_id, sequence_number)
);
```

- `PRIMARY KEY` 声明主键，用于唯一标识表中的一行。不同的消息需要不同的 `id`。
- `NOT NULL` 禁止列存储 `NULL`。`NULL` 表示缺少值。空字符串不是 `NULL`，`NOT NULL` 允许正文为空字符串；要禁止空字符串，需要另加约束。
- `FOREIGN KEY` 声明外键。启用外键检查后，SQLite 检查 `messages.conversation_id` 的值是否已存在于 `conversations.id` 中。`NOT NULL` 和外键一起保证每条消息都有一个有效的会话编号。数据库连接是应用打开数据库后用来执行 SQL 的通道。SQLite 默认不检查外键，直接使用 SQLite 时，要在每个连接上执行 `PRAGMA foreign_keys = ON`，并且在开启事务之前执行。
- `UNIQUE (conversation_id, sequence_number)` 是联合唯一约束，禁止两行的这两列取值同时相同。会话 `1` 和会话 `2` 都可以有序号为 `1` 的消息。给会话 `1` 再插入一条序号为 `1` 的消息会报错。
- `ON DELETE RESTRICT` 阻止删除仍有消息的会话。需要在删除会话时一并删除其消息，可以把删除规则设为 `ON DELETE CASCADE`，SQLite 删除会话时会同时删除关联的消息。

```sql
INSERT INTO conversations (id) VALUES (1), (2);
INSERT INTO messages (id, conversation_id, sequence_number, sent_at, content)
VALUES
    (104, 1, 1, 90, '早上好'),
    (101, 1, 2, 100, '你好'),
    (102, 1, 3, 100, '明天见'),
    (103, 1, 4, 101, '收到'),
    (105, 2, 1, 102, '在吗');
```

### 从 Swift 执行 SQL

参数绑定是先在 SQL 中写占位符，再通过数据库接口单独传入对应的值。例如，查询会话消息时写 `WHERE conversation_id = ?`，Swift 代码在执行前传入会话编号。直接使用 SQLite 的 C 接口时，执行顺序如下：

1. `sqlite3_prepare_v2` 准备语句。
2. `sqlite3_bind_int64` 绑定整数参数。
3. `sqlite3_step` 执行语句并逐行读取结果。
4. `sqlite3_finalize` 释放语句。

多次写入需要一起提交时，在同一个连接上开启一个事务，在事务中执行全部写入。

## 数据库事务与 ACID

数据库事务是数据库作为一个整体提交的一组操作。提交表示数据库把整组修改确认为事务结果；回滚表示数据库撤销当前事务的全部修改。事务中的语句依次执行，提交后，整组修改要么全部保留，要么全部撤销。

数据库通常使用 ACID 描述事务的四项性质：

| 性质 | 含义 | 转账中的要求 |
| --- | --- | --- |
| 原子性（Atomicity） | 一组修改全部生效，或者全部不生效 | 扣款和入账一起保留，或者一起撤销 |
| 一致性（Consistency） | 正确的事务逻辑与数据库约束共同保证数据遵守已定义的规则 | 不允许余额不足时扣款，转账前后总额相同 |
| 隔离性（Isolation） | 数据库按隔离规则控制并发事务之间的相互影响 | 并发扣款需要协调，不能都依据同一份过期余额作出决定 |
| 持久性（Durability） | 存储设备满足写入保证时，提交成功的修改在崩溃后仍然保留 | 重启后仍可查询已提交的转账结果 |

“全部不生效”指：事务中的语句可能已经执行，但回滚后这些修改都被撤销，没有一项保留下来。数据库只检查已声明的约束，其他业务规则由调用方负责：正确编写更新条件、检查执行结果、设置必要约束。

### InnoDB 如何实现 ACID

| 性质 | InnoDB 的实现机制 |
| --- | --- |
| 原子性 | undo log（撤销日志）记录撤销修改所需的信息。应用在扣款后发现入账失败并回滚事务时，InnoDB 根据撤销日志撤销已执行的扣款。 |
| 一致性 | 数据库检查已声明的约束。应用负责定义数据库无法自行推导的规则，例如扣款金额与入账金额相同。 |
| 隔离性 | 锁协调并发修改，例如让试图修改同一账户行的事务等待。查询也可以通过 [MVCC](mysql-transactions-and-logs.md#mvcc-与两种读法) 读取可见的记录版本。 |
| 持久性 | 崩溃后，InnoDB 用已写入磁盘的[重做日志](mysql-transactions-and-logs.md#redo-log-与崩溃恢复)恢复已提交、但还没写回数据页的修改。 |

例如，一笔事务把 A 的余额减去 100 元，把 B 的余额加上 90 元。两项修改一起提交，满足原子性。余额总和却少了 10 元，违反了转账前后总额相同的规则。

## 用一个事务完成转账

假设 A 有 1,000 元，B 有 200 元，A 向 B 转账 100 元。如果分别提交扣款和入账，两次提交之间崩溃就会留下不完整结果：

| 分别提交的顺序 | 第一笔提交后崩溃的余额 | 后果 |
| --- | --- | --- |
| 先给 A 扣款，再给 B 入账 | A = 900 元，B = 200 元 | 总额少了 100 元 |
| 先给 B 入账，再给 A 扣款 | A = 1,000 元，B = 300 元 | 总额多了 100 元 |

无论先扣款还是先入账，两次提交之间都存在崩溃窗口。两个余额保存在同一个 SQLite 数据库中时，应在同一个数据库连接上、用同一个事务完成两次更新。

下面是固定转账 100 元的 SQL 操作示意。A、B 为不同账户，账户 id 唯一；balance 使用整数“分”存储。

```sql
BEGIN IMMEDIATE;

UPDATE accounts
SET balance = balance - 10000
WHERE id = 'A' AND balance >= 10000;

-- 调用方检查：必须恰好更新一行，否则执行 ROLLBACK 并退出

UPDATE accounts
SET balance = balance + 10000
WHERE id = 'B';

-- 调用方检查：必须恰好更新一行，否则执行 ROLLBACK 并退出

COMMIT;
```

BEGIN IMMEDIATE 开启事务，并立即尝试取得 SQLite 的写事务权限。其他连接正占用写事务权限时，当前连接是否等待、等多久后返回错误，由连接的 `busy_timeout` 设置决定。当前连接取得写事务权限后，其他连接要等当前事务结束才能开始写事务。

Swift 调用方依次执行上述语句，并做以下检查：

- A 的更新没有命中一行，说明账户不存在或余额不足，不能提交。
- B 的更新没有命中一行，说明目标账户不存在，不能提交。
- 任一语句报错时，调用方根据数据库接口返回的事务状态结束事务；事务仍然开启时执行 ROLLBACK。
- 两次更新都恰好命中一行后，调用方才执行 COMMIT，并检查 COMMIT 是否成功。

SQL 注释中的检查要由 Swift 调用方编写代码实现，SQL 本身不执行这些检查。

## 执行修改、写入磁盘与提交

执行 UPDATE、把数据写入磁盘和提交事务是三个不同的动作。数据库在执行 UPDATE 时就修改数据，COMMIT 只确认这些修改。

| 动作 | 数据库做什么 | 能否据此认定事务已提交 |
| --- | --- | --- |
| 执行修改 | 执行 UPDATE，更新当前事务使用的数据；当前事务随后查询可以读到自己的修改 | 不能 |
| 写入磁盘 | 按数据库实现和日志模式，将日志或数据写入磁盘 | 不能，磁盘上也可能存在未提交修改 |
| 提交事务 | 完成提交所需的步骤，将整组修改确认为事务结果 | 提交成功后可以；调用方未收到成功结果时还需查证 |

例如，A 原余额为 1,000 元。事务执行扣款后，当前事务可以读到 A = 900 元，其他连接读到的仍是 1,000 元。其他连接能读到什么由数据库的隔离规则决定；SQLite 中，各自独立的连接读不到其他连接未提交的修改。

事务尚未完成提交就崩溃时，数据库恢复后只撤销这个事务的修改，其他已经提交的事务保持不变。

## SQLite 日志与崩溃恢复

崩溃恢复是数据库根据磁盘上的日志信息，在程序重新打开数据库时恢复完整事务状态的过程。日志是数据库保存恢复所需数据和提交信息的记录。

SQLite 的回滚日志和 WAL 是两种不同的日志模式：

| 日志模式 | 提交前的记录与写入方式 | 未提交就崩溃后的恢复方式 |
| --- | --- | --- |
| 回滚日志 | 改写数据库文件前，先把受影响数据页的旧内容保存到回滚日志；提交前，数据库文件可能已经被改写 | 用回滚日志中的旧内容覆盖被修改的数据页 |
| WAL（Write-Ahead Logging） | 把修改后的数据页写入 WAL 文件，并写入提交标记表示事务已提交；之后通过检查点把已提交内容合入主数据库文件 | 忽略没有有效提交标记的修改，继续使用已提交的数据 |

数据页是数据库读写和管理数据的基本单位，每页大小固定。WAL 的检查点是把已提交的 WAL 内容合入主数据库文件的过程；事务在写入提交标记时就已提交，检查点发生在提交之后。

因此，回滚日志模式在崩溃后用旧数据覆盖已改写的数据库文件；WAL 模式忽略未提交的新数据。两种模式恢复后的事务结果相同。

```text
原余额：A = 1000，B = 200
    ↓
事务执行扣款：当前事务读到 A = 900
    ↓
事务尚未提交，程序崩溃
    ↓
数据库重新打开并完成恢复
    ↓
余额仍为：A = 1000，B = 200
```

提交过程中崩溃时，调用方可能不知道提交是否已完成。日志和存储保证成立时，数据库恢复后要么是完整的旧状态，要么是完整的新状态，不会只保留扣款或只保留入账。

上述保证有三个前提：日志模式正确、同步设置正确、文件系统和存储设备遵守写入要求。进程崩溃和设备断电是两种不同的故障：设备断电时，还没同步到稳定存储的数据也会丢失。SQLite 的断电持久性取决于 `synchronous` 等同步设置，不同配置的保证程度不同。

### WAL 下的并发读写

并发访问是多个操作在重叠的时间段里访问同一个数据库。WAL 模式允许一个连接写入的同时，其他连接读取。同一个数据库在任意时刻只允许一个写事务。连接成功执行 `BEGIN IMMEDIATE` 后取得写事务权限；另一个连接此时尝试开启写事务，可能收到 `SQLITE_BUSY` 错误。连接可以设置 `busy_timeout`，让 SQLite 遇到可等待的冲突时先等待一段时间再报错。

读快照是读事务能看到的那一版已提交数据。假设会话中的消息 `101` 有 `is_read = 0`，表示未读。连接 A 执行 `BEGIN`，再用第一次 `SELECT` 建立读快照。连接 B 把 `is_read` 改为 `1` 并提交。只要 A 还在原来的读事务里，再查仍得到 `0`。A 结束原读事务后重新查询，就能读到 B 已提交的 `1`。

修改后的数据页写在 WAL 文件中，主数据库文件中的旧数据页不变，所以读取旧快照的连接可以与写入连接同时工作。读事务长时间不结束时，检查点无法把较新的数据页合入主数据库文件；写入持续进行时，WAL 文件会不断增大。写事务也要尽量短：应用在网络响应返回后再开启写事务，保存数据后立即提交，不在等待网络期间占用写事务权限。

## 锁、actor 与事务的区别

锁用于限制多个线程或任务同时访问受保护的数据。锁只协调运行期间的并发读写；保存旧余额、记录提交状态和重启后恢复数据，都由数据库事务负责。

| 机制 | 主要保证 | 无法单独保证的内容 |
| --- | --- | --- |
| NSLock 或串行队列 | 遵守同一保护约定的代码按互斥或串行规则访问数据 | 多次持久化写入在崩溃后全部保留或全部撤销 |
| Swift actor | 隔离自身状态，协调对隔离状态的访问 | 持久化与崩溃恢复；跨 await 的多步操作自动不可分割 |
| 数据库事务 | 在数据库管理范围内共同提交或撤销修改，并按数据库规则协调并发与恢复 | 自动包含网络请求、其他独立存储或任意外部副作用 |

actor 的访问与重入规则见[Swift 并发：actor、Sendable 与 Task](../language/swift-concurrency.md#actor-的默认隔离与重入)。锁的分类和等待行为见[iOS 线程、GCD 与同步](../ios/threads-and-scheduling.md#锁的分类)。

Swift 的 catch 处理抛出的错误，defer 在退出作用域时执行清理。进程崩溃或被强制终止时，catch 和 defer 中的代码都不会执行。数据库重启后，依靠磁盘上的日志恢复数据。

只存在内存中的余额会随进程结束而丢失，持久化方式见[持久化与常用方式](#持久化与常用方式)。如果“通知 A 扣钱”是调用另一个服务，远端服务的操作不在本地事务范围内，需要另外设计跨服务的提交协调或失败补偿。失败补偿是执行一个新的业务操作，抵消已经完成的操作的效果，例如给已扣款的账户退款；本地数据库回滚则是撤销尚未提交的修改。

## 提交结果不确定与重复执行

数据库已经提交，但程序在收到或显示成功结果之前崩溃时，数据库中已经保存了完整的转账。所以调用方没有收到成功结果时，要先查询数据库确认事务是否已提交。

应用可以为每笔转账分配唯一编号，并在同一个事务中同时保存转账记录、扣款和入账。数据库通过唯一约束限制编号不能重复。

重启后，应用先按原转账编号查询是否已有提交的记录。重试同一笔转账时，应用复用原编号，数据库的唯一约束会阻止重复写入；应用确认这个编号对应原来的账户和金额后，返回已保存的结果。新的一笔转账使用新编号。

例如，T001 已完成 A 向 B 转账 100 元。程序重启后再次处理 T001，结果仍为 A = 900 元、B = 300 元，不再扣除第二次 100 元。

同一操作重复执行多次与执行一次的效果相同，这种性质称为幂等性。本节是本地事务中的去重方法；网络请求的幂等重试规则见[网络请求与代理](network-and-proxy.md#连接超时与幂等重试)。

## SQLite 数据库迁移

数据库结构规定表有哪些列、各列能存什么值，以及数据要满足哪些约束。数据库迁移是把已有数据库改成新版需要的结构，并按新规则保留或转换已有数据。App 升级后打开的仍是旧数据库文件；新版代码查询旧表中还不存在的列时，查询会报错。

应用可以用 `PRAGMA user_version` 读取或设置数据库文件中的版本号。SQLite 只保存这个整数；每个版本号对应什么结构、如何迁移，由应用自己规定和执行。例如，版本 `1` 的 `messages` 没有 `is_read` 列，版本 `2` 增加 `is_read` 列，用 `0` 表示未读、`1` 表示已读。首次安装时，应用直接创建版本 `2` 的表，并把版本号设为 `2`。打开已有数据库时，读到 `1` 就执行迁移，读到 `2` 就直接使用。

下面的迁移基于两条产品规则：旧消息一律显示为未读；新插入的消息没有指定状态时，也按未读处理。

```sql
BEGIN;

ALTER TABLE messages
ADD COLUMN is_read INTEGER NOT NULL DEFAULT 0;

PRAGMA user_version = 2;

COMMIT;
```

`ALTER TABLE ... ADD COLUMN` 给已有表增加列。旧消息的编号和正文保持不变，旧消息的 `is_read` 列取值为 `0`。之后插入新消息时，如果没有指定 `is_read`，SQLite 也使用默认值 `0`。

应用在同一个连接、同一个事务中增加列并更新版本号，两项修改一起提交。任何一步失败时，应用停止迁移，并在事务仍开启时执行 `ROLLBACK`。应用支持跨版本升级时，按顺序执行各段迁移，例如从版本 `1` 升级到 `3` 时，依次执行 `1 → 2` 和 `2 → 3`。

验证迁移时，先准备一份包含真实记录的旧版数据库，再用新版 App 打开这个数据库，检查三项内容：旧记录是否保留、按规则转换的字段是否正确、版本号是否已更新。首次安装时，还要验证新版 App 能直接创建可用的新数据库。
