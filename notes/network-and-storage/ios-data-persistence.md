## 持久化与常用方式

数据持久化是将数据保存到应用进程结束后仍能保留的存储介质中，使应用下次启动时可以重新读取。只把数据放在变量、数组或单例中，不属于持久化。持久化也不等于永久保留；数据能保留多久，还取决于存储位置和清理规则。

iOS 中使用 Swift 开发时，常见方式包括 UserDefaults、文件存储、Keychain、SQLite、Core Data 和 SwiftData。

| 方式 | 保存机制 | 适用场景 |
| --- | --- | --- |
| UserDefaults | 按键值保存设置，通过字符串键定位对应的值 | 少量、非敏感的偏好设置，例如主题和是否显示过引导；不适合保存密码或大量业务记录 |
| 文件存储 | 将数据写入应用可访问的文件；通常由 FileManager 管理目录和文件，由 Data 等类型读写内容 | 图片、视频、文档，以及保存为 JSON、plist 等格式的数据 |
| Keychain | 使用系统提供的加密存储，并由系统控制访问权限 | 密码、登录凭证、密钥等少量敏感数据 |
| SQLite | 将数据组织成表，使用 SQL 定义、查询和修改数据；SQL 是用于操作数据库的语言 | 需要按条件查询、排序、统计或频繁修改的记录，例如消息记录 |
| Core Data | 管理对象、对象之间的关系及对象的变化，并将对象数据保存到持久化存储 | 具有多个关联数据类型的应用，例如笔记与笔记分类；通常直接操作对象，无须自己编写 SQL |
| SwiftData | 使用 Swift 类型定义数据模型，通过框架保存和查询模型对象 | 使用 Swift 模型管理数据，并与 SwiftUI 集成；框架从 iOS 17 起可用 |

数据模型是描述应用保存哪些数据以及这些数据如何关联的类型和规则。例如，笔记有标题、正文和所属分类，分类可以关联多篇笔记。

## UserDefaults 的最小示例

UserDefaults 是按字符串键保存少量偏好设置的系统接口。保存的值不限于 Bool，还可以是 String、整数、浮点数、Data、Date，以及由受支持值组成的数组和字符串键字典。这些值属于属性列表可表示的数据；自定义对象不能直接交给 set 保存，需要先编码为 Data 等受支持类型。

下面通过键 hasSeenGuide 保存“用户是否看过引导”。键是用于定位数据的名称，true 是保存的值。

```swift
import Foundation

// 保存
UserDefaults.standard.set(true, forKey: "hasSeenGuide")

// 读取
let hasSeenGuide = UserDefaults.standard.bool(forKey: "hasSeenGuide")

// 删除
UserDefaults.standard.removeObject(forKey: "hasSeenGuide")
```

调用 set 后，UserDefaults 立即更新内存中的值，再异步写入磁盘。调用 bool(forKey:) 时，如果对应键不存在，方法返回 false。因此，这个读取方法不能区分“未保存过”和“明确保存了 false”。

SwiftUI 的 @AppStorage 使用 UserDefaults 读写设置，并在对应值变化时更新相关视图。@AppStorage 没有提供独立于 UserDefaults 的另一套存储。

选择的语言可以保存为字符串：

```swift
UserDefaults.standard.set("en", forKey: "preferredLanguage")
let languageCode = UserDefaults.standard.string(forKey: "preferredLanguage")
// 已保存时得到 "en"；键不存在时得到 nil。
```

保存语言码只保存用户的选择，不会翻译文案或自动刷新 UIKit 控件。启动时读取语言码、选择资源和刷新界面的完整流程见 [iOS 本地多语言与即时切换](../ios/localization-and-language-switching.md)。

## 编码、文件格式与持久化的区别

Codable 表达类型支持编码和解码的能力，本身不负责把数据写入磁盘。编码与解码的具体机制见[Swift 语言基础](../language/swift-basics.md)。

以 JSON 文件为例，保存流程是：Swift 对象 → JSONEncoder 转换为 Data → 将 Data 写入文件。读取流程是：从文件读取 Data → JSONDecoder 根据指定类型恢复 Swift 对象。Data 表示字节数据；只完成编码时，编码结果仍可能只存在于内存中。

JSON 和 plist 是数据格式，不是独立的存储服务。选择 JSON 或 plist，决定数据如何表示；选择文件、数据库等存储，决定数据保存在哪里以及如何读写。

文件存储还需要选择合适的目录。目录用途、系统清理和备份规则见[iOS 文件存储](ios-file-storage.md)。

## Core Data 与 SQLite 的关系

Core Data 负责管理对象及其保存过程。SQLite 负责数据库存储和查询。Core Data 可以使用 SQLite 作为保存数据的底层存储，但 Core Data 不等同于 SQLite。

例如，使用 SQLite 时，应用可以通过 SQL 查询某个分类下的笔记。使用 Core Data 时，应用通常通过框架查询笔记对象，并访问笔记与分类的关系。Core Data 负责将这些对象数据映射到配置的持久化存储。

使用 Core Data 或 SwiftData 管理了对象，不代表所有配置都会写入磁盘。需要跨应用启动保留数据时，应使用持久化存储，并确保保存成功；只保存在内存中的配置不能满足这个要求。

## 数据库事务与 ACID

数据库事务是数据库作为一个整体提交的一组操作。提交表示数据库将整组修改确认为事务结果；回滚表示数据库撤销当前事务的修改。事务中的语句可以先后执行，但不能只保留其中一部分修改作为已提交结果。

数据库通常使用 ACID 描述事务的四项性质：

| 性质 | 含义 | 转账中的要求 |
| --- | --- | --- |
| 原子性（Atomicity） | 一组修改全部生效，或者全部不生效 | 扣款和入账一起保留，或者一起撤销 |
| 一致性（Consistency） | 正确的事务逻辑与数据库约束共同保证数据遵守已定义的规则 | 不允许余额不足时扣款，转账前后总额相同 |
| 隔离性（Isolation） | 数据库按隔离规则控制并发事务之间的相互影响 | 并发扣款需要协调，不能都依据同一份过期余额作出决定 |
| 持久性（Durability） | 提交成功的修改在相应存储保证下能够在崩溃后保留 | 重启后仍可查询已提交的转账结果 |

“全部不生效”不表示每条语句都没有执行过，而是这些修改不会成为保留的事务结果。数据库也不会自动判断任意业务规则；调用方仍需正确编写更新条件、检查执行结果，并设置必要约束。

## 用一个事务完成转账

假设 A 有 1,000 元，B 有 200 元，A 向 B 转账 100 元。如果分别提交扣款和入账，两次提交之间崩溃就会留下不完整结果：

| 分别提交的顺序 | 第一笔提交后崩溃的余额 | 后果 |
| --- | --- | --- |
| 先给 A 扣款，再给 B 入账 | A = 900 元，B = 200 元 | 总额少了 100 元 |
| 先给 B 入账，再给 A 扣款 | A = 1,000 元，B = 300 元 | 总额多了 100 元 |

交换执行顺序不能消除两次提交之间的崩溃窗口。两个余额保存在同一个 SQLite 数据库中时，应在同一个事务、同一个数据库连接上完成两次更新。

下面是固定转账 100 元的 SQL 操作示意。A、B 为不同账户，账户 id 唯一；balance 使用整数“分”存储。

```sql
BEGIN IMMEDIATE;

UPDATE accounts
SET balance = balance - 10000
WHERE id = 'A' AND balance >= 10000;

-- 调用方检查：必须恰好更新一行，否则执行 ROLLBACK 并退出

UPDATE accounts
SET balance = balance + 10000
WHERE id = 'B';

-- 调用方检查：必须恰好更新一行，否则执行 ROLLBACK 并退出

COMMIT;
```

BEGIN IMMEDIATE 开启事务，并立即尝试取得 SQLite 的写事务权限；其他写事务占用数据库时，能否等待及何时返回错误取决于连接的等待设置。取得写事务权限后，数据库协调其他连接的写入。

Swift 调用方依次执行上述语句。A 的更新没有匹配一行，说明账户不存在或余额不足。B 的更新没有匹配一行，说明目标账户不存在。这些情况都不能继续提交。任一操作报错时，调用方按数据库接口返回的事务状态结束事务；事务仍有效时执行 ROLLBACK。两次更新均符合要求后，调用方才执行 COMMIT，并检查提交结果。

SQL 注释中的检查是调用方必须实现的控制逻辑，不能仅复制整段 SQL 就获得这些检查。

## 执行修改、写入磁盘与提交

执行 UPDATE、把数据写入磁盘和提交事务是三个不同动作，不能认为数据库直到 COMMIT 才开始修改数据。

| 动作 | 数据库做什么 | 能否据此认定事务已提交 |
| --- | --- | --- |
| 执行修改 | 执行 UPDATE，更新当前事务使用的数据；当前事务随后查询可以读到自己的修改 | 不能 |
| 写入磁盘 | 按数据库实现和日志模式，将日志或数据写入磁盘 | 不能，磁盘上也可能存在未提交修改 |
| 提交事务 | 完成提交所需的步骤，将整组修改确认为事务结果 | 提交成功后可以；调用方未收到成功结果时还需查证 |

例如，A 原余额为 1,000 元。事务执行扣款后，当前事务可以读到 A = 900 元，但这不表示其他连接已经能够读到 900 元。其他连接的可见结果受数据库隔离规则控制；SQLite 常规独立连接不会读取其他连接的未提交修改。

如果事务尚未完成提交就崩溃，数据库恢复后不保留该事务的修改。这里撤销的是该事务的修改，不是把整个数据库恢复到某个历史时刻；其他已经提交的事务不会因此被撤销。

## SQLite 日志与崩溃恢复

崩溃恢复是数据库根据磁盘上的日志信息，在程序重新打开数据库时恢复完整事务状态的过程。日志是数据库保存恢复所需数据和提交信息的记录。

SQLite 的回滚日志和 WAL 是两种不同的日志模式：

| 日志模式 | 提交前的记录与写入方式 | 未提交就崩溃后的恢复方式 |
| --- | --- | --- |
| 回滚日志 | 在改写数据库文件前，先按恢复要求将受影响数据页的旧内容保存到日志；提交前可能已经改写数据库文件 | 利用有效回滚日志中的旧内容恢复被修改的部分 |
| WAL（Write-Ahead Logging） | 把修改后的数据页写入 WAL 文件；提交通过有效提交标记确认，主数据库文件随后才通过检查点合入已提交内容 | 忽略没有有效提交标记的修改，继续使用完整的已提交状态 |

数据页是数据库读写和管理的一块固定大小的数据。WAL 的检查点是将符合条件的已提交日志内容合入主数据库文件的过程；检查点不等于提交事务。

因此，“提交前已经改写数据库文件，崩溃后再恢复旧数据”适用于回滚日志模式。WAL 模式通常通过忽略未提交的新数据，得到相同的事务结果。

```text
原余额：A = 1000，B = 200
    ↓
事务执行扣款：当前事务读到 A = 900
    ↓
事务尚未提交，程序崩溃
    ↓
数据库重新打开并完成恢复
    ↓
余额仍为：A = 1000，B = 200
```

提交过程中崩溃时，调用方可能不知道提交是否已完成。在日志和存储保证成立的条件下，数据库恢复后保留完整旧状态或完整新状态，不能只保留扣款或入账。

上述保证依赖正确的日志与同步设置，以及文件系统和存储设备遵守写入要求。进程崩溃与设备断电是不同故障：断电还可能丢失尚未同步到稳定存储的数据。不能把任意 SQLite 配置都视为具有相同的断电持久性保证。

## 锁、actor 与事务的区别

锁用于限制多个执行者同时访问受保护的数据。锁可以协调运行中的并发读写，但不会自动保存旧余额、记录提交状态或在重启后恢复数据。

| 机制 | 主要保证 | 无法单独保证的内容 |
| --- | --- | --- |
| NSLock 或串行队列 | 遵守同一保护约定的代码按互斥或串行规则访问数据 | 多次持久化写入在崩溃后全部保留或全部撤销 |
| Swift actor | 隔离自身状态，协调对隔离状态的访问 | 持久化与崩溃恢复；跨 await 的多步操作自动不可分割 |
| 数据库事务 | 在数据库管理范围内共同提交或撤销修改，并按数据库规则协调并发与恢复 | 自动包含网络请求、其他独立存储或任意外部副作用 |

actor 的访问与重入规则见[Swift 语言基础](../language/swift-basics.md#actor-的默认隔离与重入)。锁的分类和等待行为见[iOS 线程与任务调度](../ios/threads-and-scheduling.md#常见锁与分类维度)。

Swift 的 catch 可以处理正常抛出的错误，defer 可以在正常退出作用域时执行清理。进程崩溃或被强制终止时，不能依赖 catch 或 defer 完成回滚。数据库重启后的恢复依靠持久化日志。

只存在内存中的余额会随进程结束而丢失，具体持久化方式见[持久化与常用方式](#持久化与常用方式)。如果“通知 A 扣钱”是调用另一个服务，本地事务不能覆盖远端操作；需要另外设计跨服务的提交协调或失败补偿。失败补偿是通过后续业务操作抵消已经完成的效果，不等于本地数据库回滚。

## 提交结果不确定与重复执行

数据库已经提交，但程序在收到或显示成功结果前崩溃时，数据库中仍可能保留完整转账。调用方没有看到成功，不足以证明事务失败。

应用可以为每笔转账分配唯一编号，并在同一个事务中同时保存转账记录、扣款和入账。数据库通过唯一约束限制编号不能重复；唯一约束是数据库禁止指定字段出现重复值的规则。

重启后，应用先按原转账编号查询是否已有已提交记录。重试同一笔转账时，应用复用原编号，由数据库唯一约束阻止重复写入；确认编号对应原来的账户和金额后，返回已保存结果。新的一笔转账使用新编号。

例如，T001 已完成 A 向 B 转账 100 元。程序重启后再次处理 T001，结果仍为 A = 900 元、B = 300 元，不再扣除第二次 100 元。

这种重复执行不会增加转账效果的性质称为幂等性。这里补充的是本地事务中的去重方法；网络请求的幂等重试规则见[网络请求与代理](network-and-proxy.md#连接超时与幂等重试)。
