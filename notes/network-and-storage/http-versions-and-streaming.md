## HTTP 版本：含义相同，传输格式不同

HTTP 是客户端和服务端收发请求与响应的规则。HTTP 规定请求包含哪些部分（地址、方法、请求头、请求体），响应包含哪些部分（状态码、响应头、响应体），以及这些内容在网络上写成什么样的字节。

HTTP/1.1 于 1997 年发布，HTTP/2 于 2015 年发布。两个版本的方法、状态码、头部字段含义相同，客户端代码的写法也相同；`URLSession` 在建立 TLS 连接时与服务端协商使用哪个版本。两个版本的区别在于：同一个请求在网络上被写成什么样的字节。HTTP/3 改用 QUIC 传输，见[网络请求与代理](network-and-proxy.md#quictls-与-https)。

### HTTP/1.1：文本格式，一条连接一次处理一个请求

HTTP/1.1 的请求在网络上是一段文本，各部分用换行分隔：

```text
GET /api/chat HTTP/1.1
Host: example.com
Accept: text/event-stream

```

接收方逐个字符读取，遇到换行就知道一行结束，遇到空行就知道头部结束。

一条 TCP 连接同一时间只处理一个请求。客户端在连接上发出请求 A 后，要等 A 的响应全部收完，才能在这条连接上发出请求 B。A 的响应很慢时，B 只能排队。客户端为了减少排队，会对同一个服务器同时建立多条 TCP 连接，每条连接都要经过 TCP 握手和 TLS 握手。

### HTTP/2：二进制帧、stream 与多路复用

HTTP/2 把请求和响应切成帧来传输。帧是一段二进制数据，由帧头和帧内容组成：

```text
┌──────────────────────────────────────┐
│ 帧头：长度 | 类型 | 所属 stream 编号   │
├──────────────────────────────────────┤
│ 帧内容：头部或正文的一部分             │
└──────────────────────────────────────┘
```

HTTP/2 中，一次请求和它的响应合称一个 stream，每个 stream 有一个编号。请求头和响应头放在 `HEADERS` 帧中，请求体和响应体放在 `DATA` 帧中。

每个帧都标明所属 stream，所以不同请求的帧可以在同一条 TCP 连接上交错发送：

```text
同一条 TCP 连接上依次传输：
[stream 1] [stream 3] [stream 1] [stream 5] [stream 3] ...
```

接收方按帧头中的编号把帧放回对应的请求。stream 1 的响应很慢时，stream 3 和 stream 5 的帧照常收发。一条连接同时处理多个请求的能力叫多路复用。

HTTP/2 还会压缩请求头和响应头。相邻请求的头部大多相同，例如每次都带同样的 Cookie，压缩后只传输变化的部分。

| | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 网络上的格式 | 文本，用换行分隔 | 二进制帧，帧头写明长度、类型和 stream 编号 |
| 一条连接同时处理的请求数 | 一个，后续请求排队 | 多个，各请求的帧交错发送 |
| 头部 | 每次原样发送 | 压缩后发送 |

## 流式响应：总长度未知时如何发送

流式响应是指服务端在响应体还没全部生成时，就把已生成的部分先发给客户端，客户端边收边处理。

### Content-Length 与一次性响应

普通响应在响应头中写 `Content-Length`，告诉客户端响应体的总字节数：

```text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 29

{"text":"今天天气不错"}
```

客户端读满 29 字节，就知道响应结束。服务端要写出 `Content-Length`，必须先知道响应体的总长度，所以必须等整个响应体生成完才能发送。HTTP/1.1 和 HTTP/2 各有一种不需要提前知道总长度的发送方式。

### HTTP/1.1 的分块传输编码

服务端在响应头中写 `Transfer-Encoding: chunked`，省去 `Content-Length`。响应体分成多个块依次发送，每块先写本块长度（十六进制字节数），再写本块内容；最后发送一个长度为 0 的块，表示响应结束。

下面的响应中，每个汉字的 UTF-8 编码占 3 字节，所以两个汉字的块长度是 6：

```text
HTTP/1.1 200 OK
Transfer-Encoding: chunked

6
今天
6
天气
6
不错
0

```

执行顺序：服务端发出响应头并保持连接 → 每生成一段内容，就写出一块 → 客户端每读到一块，就取出这块内容 → 客户端读到长度为 0 的块，确认响应结束。服务端写每一块时只需要知道这一块的长度。

### HTTP/2 的 DATA 帧与 END_STREAM

HTTP/2 的每个 `DATA` 帧都在帧头中写明长度，服务端随时可以再发一个帧，所以 HTTP/2 不使用 chunked。同一个响应的帧依次发送：

```text
stream 5: HEADERS 帧（状态码 200、内容类型）
stream 5: DATA 帧 "今天"
stream 5: DATA 帧 "天气"
stream 5: DATA 帧 "不错"，带 END_STREAM 标记
```

客户端收到带 `END_STREAM` 标记的帧，确认这个响应结束。

## SSE：在响应体中标出消息边界

SSE（Server-Sent Events）是建立在 HTTP 之上的单向推送格式：客户端发出一次请求，服务端在同一个响应中持续写出多条消息。SSE 规定响应体的文本格式，用来标出每条消息从哪里开始、到哪里结束。

### 消息格式与执行流程

```text
data: {"text":"今天"}

data: {"text":"天气"}

data: [DONE]

```

SSE 的格式规则：

- 每条消息的内容以 `data: ` 开头。
- 一个空行表示一条消息结束。
- `[DONE]` 是服务端与客户端约定的结束消息，SSE 格式本身不规定结束消息的内容。

执行顺序：

1. 客户端发送 HTTP 请求。
2. 服务端返回 `Content-Type: text/event-stream`，表示响应体使用 SSE 格式。
3. 服务端在 HTTP/1.1 上用 chunked、在 HTTP/2 上用 `DATA` 帧，陆续发出 SSE 消息。
4. 客户端把收到的字节放入缓冲区，每遇到一个空行就取出一条完整消息处理。

SSE 只允许服务端向客户端发送消息。客户端要再发送内容，需要发起新的 HTTP 请求。

### 为什么需要消息边界

TCP 保证数据按发送顺序交给接收方，所以客户端只想在最后得到完整文本时，按顺序拼接收到的字节就够了。流式处理要求数据没收完时就逐条处理，这时客户端必须知道每条消息在哪里结束。客户端每次从网络读到多少字节由网络状况决定，代理服务器也可能合并或拆分块，所以块的边界和消息的边界不一定一致。

**一条 JSON 只有完整时才能解析。** 客户端可能第一次读到 `data: {"te`，第二次读到 `xt":"今天"}` 加一个空行和下一条消息的开头。客户端按读取次数解析时，`{"te` 是不完整的 JSON，解析失败；按空行切分时，客户端等到空行出现再解析 `{"text":"今天"}`。

**不同类型的消息要分别处理。** 一次响应中可以包含多种消息：

```text
data: {"type":"text","content":"今天"}

data: {"type":"card","title":"天气卡片"}

data: {"type":"error","message":"生成中断"}

```

客户端逐条读取 `type`：`text` 追加到正文，`card` 插入卡片，`error` 显示错误提示。

**一个字符的字节可能分两次到达。** UTF-8 中“今”编码为 `E4 BB 8A` 三个字节。客户端可能一次读到 `E4 BB`，下一次读到 `8A`。客户端每读一次就转换成文字时，前一次的结果是乱码；客户端取出完整消息后再转换，就能得到正确的字符。

## WebSocket：双向长连接

WebSocket 是独立于 HTTP 的协议，只在建立连接时借用 HTTP 请求：

1. 客户端发送 HTTP 请求，请求头中带 `Upgrade: websocket`，要求把这条连接切换为 WebSocket。
2. 服务端同意后返回状态码 `101 Switching Protocols`。
3. 此后这条 TCP 连接传输 WebSocket 帧。每个 WebSocket 帧的帧头写明长度，所以消息边界由帧本身确定。

连接建立后，客户端和服务端都可以随时发送消息，不需要发起新请求。WebSocket 适合双向实时交互，例如语音对话中客户端持续上传音频、服务端同时下发回复。WebSocket 连接是一条长连接，长连接的心跳保活、关闭与重连见[长连接：建立、心跳保活、断开检测与重连](long-connection-lifecycle.md)。

## 四种方式的对比

| | HTTP/1.1 chunked | HTTP/2 DATA 帧 | SSE | WebSocket |
| --- | --- | --- | --- | --- |
| 解决的问题 | 总长度未知时陆续发送响应体 | 总长度未知时陆续发送响应体 | 在陆续到达的字节中标出消息边界 | 建立一条长期存在的双向通道 |
| 所在位置 | HTTP/1.1 的传输方式 | HTTP/2 的传输方式 | 响应体的格式，运行在 chunked 或 DATA 帧之上 | 独立协议，握手借用 HTTP |
| 发送方向 | 服务端到客户端 | 服务端到客户端 | 服务端到客户端 | 双向 |
| 结束标志 | 长度为 0 的块 | 带 `END_STREAM` 的帧 | 约定的结束消息，随后 HTTP 响应结束 | 任一方发送关闭帧 |

## 大模型回复的流式输出

大模型逐个生成 token。token 是模型处理文本的最小单位，一个 token 大致对应一个汉字或半个英文单词。模型生成每个 token 时，都要把已生成的内容作为输入计算下一个 token，所以整段回复需要几秒到几十秒才能生成完。

服务端每得到几个 token，就通过 SSE 或 WebSocket 发给客户端；客户端每收到一条消息，就把文字追加到界面。用户在生成刚开始时就能看到内容。底层传输都是 TCP + TLS，流式输出由应用层协议实现。

iOS 客户端可以用 `URLSession.shared.bytes(for:)` 逐行读取 SSE 响应。下面的示例假设每条消息只有一行 `data:`：

```swift
let (bytes, _) = try await URLSession.shared.bytes(for: request)
for try await line in bytes.lines {
    guard line.hasPrefix("data: ") else { continue }
    let payload = line.dropFirst(6)
    if payload == "[DONE]" { break }
    // 解析 payload 中的 JSON，把文字追加到界面
}
```

客户端一次可能收到好几个字。客户端通常把收到的文字放入缓冲区，再按固定节奏逐字显示，形成稳定的打字效果。

生成过程中的三种常见情况：

- **网络中断**：客户端收不到后续消息，回复停在中途。客户端可以带上消息标识重新请求，由服务端从中断位置继续发送，或者重新生成整段回复。
- **用户停止生成**：客户端断开连接或发送取消请求。服务端检测到后停止模型生成，节省计算资源。
- **轮询的代价**：轮询是客户端每隔一段时间请求一次新内容。间隔短时请求数量多，间隔长时显示延迟大。流式连接在内容生成后立即送达，不产生额外请求。
