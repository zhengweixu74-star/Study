## HTTP 请求方法、安全性与幂等性

HTTP 是应用层的请求与响应协议。客户端在请求中指定目标资源和请求方法。服务端根据请求执行操作，并返回状态码、响应头和可选的响应体。请求方法表达客户端希望对目标资源执行的操作。

### 常见请求方法

| 方法 | 含义 | 安全性 | 幂等性 |
| --- | --- | --- | --- |
| GET | 获取目标资源的表示，例如一份 JSON 数据 | 安全 | 幂等 |
| HEAD | 获取与 GET 对应的响应元信息，不返回响应体 | 安全 | 幂等 |
| POST | 让目标资源按自身规则处理请求内容，例如提交表单或创建记录 | 不安全 | 不保证 |
| PUT | 用请求内容创建或替换指定目标资源的状态 | 不安全 | 幂等 |
| PATCH | 按请求中的修改指令局部修改资源 | 不安全 | 不保证 |
| DELETE | 删除目标 URI 与当前资源功能之间的关联 | 不安全 | 幂等 |
| OPTIONS | 查询目标资源或服务端支持的通信选项 | 安全 | 幂等 |

安全性是请求方法的语义属性：客户端没有要求服务端改变业务状态。服务端记录访问日志不违背安全性。这里的“安全”不表示传输经过加密。

幂等性表示：对同一目标重复执行相同请求，产生的预期服务端效果与执行一次相同。幂等性不要求每次响应内容或状态码相同。例如，重复删除同一个资源可以先返回删除成功，再返回资源不存在，但不会因此产生额外的删除效果。

POST 和 PATCH 不保证幂等，不表示所有 POST 和 PATCH 接口都无法实现幂等。接口可以通过服务端去重等约定提供幂等行为。DELETE 的协议语义也不要求服务端立即物理删除存储中的所有相关数据。

客户端、缓存和代理依据请求方法理解操作语义。例如，缓存可以在满足缓存条件时复用响应；客户端可以结合幂等性和失败情况判断是否允许自动重试。不同方法并非只是在 URL 上添加不同的名称，服务端实现也应遵守对应语义。

### GET 与 POST 的区别

| 对比项 | GET | POST |
| --- | --- | --- |
| 核心语义 | 获取资源的表示 | 让目标资源处理提交的内容 |
| 安全性与幂等性 | 安全且幂等 | 均不保证 |
| 常见参数位置 | URL 路径和查询参数 | 请求体，也可以同时带 URL 查询参数 |
| 请求体 | 没有通用定义的请求体语义，通常不发送 | 常用于承载提交的数据，格式由 Content-Type 和接口约定确定 |
| 响应缓存 | 满足缓存条件时可缓存 | 满足 HTTP 缓存规范的条件时也可缓存，但通用实现支持较少 |

请求体是 HTTP 消息中承载本次提交内容的部分。HTTP 请求头则是描述请求及其内容的一组字段。Content-Type 用于声明请求体的媒体类型，即内容格式，例如 application/json 或 multipart/form-data。

GET 与 POST 的主要区别是操作语义，不是“一个能够带参数，另一个不能带参数”。HTTP 也没有规定 GET 参数统一只能有 2 KB；实际长度限制取决于客户端、代理和服务端。

POST 把数据放入请求体，不等于对数据加密。GET 和 POST 都需要通过 HTTPS 获得传输保护。URL 还可能出现在历史记录或访问日志中，因此参数位置与传输加密是两个不同问题。

## 请求正文格式与 JSON 字段

Content-Type 声明请求正文的媒体类型，即正文采用的数据格式。application/json 表示 JSON 格式，multipart/form-data 表示由多个表单部分组成的格式。HTTP 请求正文不必都包含表单分隔行。

| 对比项 | application/json | multipart/form-data |
| --- | --- | --- |
| 字段名的位置 | JSON 对象的键，例如 title | 各部分 Content-Disposition 中的 name 参数，例如 name="title" |
| 字段值的位置 | JSON 对象中对应键的值 | 各部分头部后的空行之后 |
| 内容如何分隔 | 由 JSON 的括号、冒号和逗号等语法组织 | 由 boundary 对应的分隔行组织 |
| 文件内容如何表示 | 按接口约定转换为字符串等 JSON 数据，例如 Base64 字符串 | 可在文件部分直接携带原始文件字节 |

例如，下面的请求正文提交 title 和 count 两个字段：

```http
Content-Type: application/json
```

```json
{
  "title": "hello",
  "count": 10
}
```

title 和 count 已经是 JSON 对象的字段名，因此不需要额外写 name="title"。JSON 对象也不使用 multipart 的 boundary 分隔行。即使 JSON 中存在名为 name 或 boundary 的键，这些键也只是接口数据，不自动具有 multipart 的协议含义。

在 multipart/form-data 中，boundary 是用于构造各部分分隔行的标识字符串；name 是每个部分的 Content-Disposition 中用于标识表单字段的参数。两者的具体结构见本文“multipart 文件上传与请求体结构”。

## 使用 JSON 上传文件

application/json 可以承载文件内容，前提是客户端将文件内容转换成 JSON 能表示的数据，服务端按相同约定还原。JSON 没有直接表示任意二进制字节序列的独立数据类型，不能把任意图片字节直接插入 JSON 文本。

Base64 是将字节序列编码成文本的可逆编码方式，不是加密。客户端可以把 Base64 文本放入 JSON 字符串。下面示例上传一个文件名为 hello.txt、内容为 hello 的文件；请求头使用 Content-Type: application/json。

```json
{
  "filename": "hello.txt",
  "contentBase64": "aGVsbG8="
}
```

1. 客户端读取文件字节，将字节编码成 Base64 字符串。
2. 客户端把文件名和 Base64 字符串写入 JSON，并发送 JSON 正文。
3. 服务端解析 JSON，读取约定字段，再把 Base64 字符串解码为原始文件字节。
4. 服务端根据接口约定保存或处理文件。

filename 和 contentBase64 是示例接口约定的字段名，不是 JSON 规定的文件字段。服务端不会仅凭字段名称自动完成 Base64 解码或文件保存。只发送客户端本地路径或一个文件地址字符串，也不等于在本次正文中发送了文件字节。

对于 n 字节的数据，带标准填充且不插入换行的 Base64 文本长度为 4 × ceil(n / 3) 个字符，ceil 表示向上取整。数据量较大时，编码后的长度约增加三分之一，还需要加上 JSON 字段名等开销。该比较不包含后续压缩的影响。

multipart/form-data 的文件部分可以直接承载原始文件字节，不要求先做 Base64 编码。使用 JSON 还是 multipart，应以服务端接口约定为准；只修改 Content-Type 请求头不会转换正文格式。

## gzip 压缩与抓包正文显示

gzip 是将原始字节压缩为另一段字节、并允许解压还原的无损压缩格式。正文的数据格式与压缩方式是两个不同层次：JSON 正文可以使用 gzip 压缩，解压后仍是 JSON，不会增加 multipart 的 boundary 或部分头部。

| 请求头 | 作用 |
| --- | --- |
| Content-Type: application/json | 声明解码后正文的数据格式为 JSON |
| Content-Encoding: gzip | 声明正文应用了 gzip 内容编码，接收方需要先解压再按媒体类型解析 |
| Content-Length（存在时） | 声明消息正文的字节长度；正文经过 gzip 编码时，对应编码后的长度，不是解压后的字符数 |

发送 gzip 压缩的 JSON 时，标准请求头可以同时包含以下两项；服务端必须支持这种请求内容编码：

```http
Content-Type: application/json
Content-Encoding: gzip
```

客户端先将 JSON 序列化为文本并编码成 UTF-8 字节，再使用 gzip 压缩。接收方先还原 gzip 压缩数据，再将解压后的文本解析为 JSON。序列化是把内存中的数据组织成可存储或传输的格式；解压和 JSON 解析是两个独立步骤。

某些接口使用自定义请求头声明压缩方式。自定义请求头由通信双方约定，抓包工具不一定按标准 Content-Encoding 的规则自动识别。请求和响应各自拥有头部与正文，响应中的 Content-Encoding 不能用于判断请求正文是否压缩。

十六进制视图是逐字节显示数值的方式，不是一种压缩或加密方式。gzip 数据常见的起始三个字节为 1F 8B 08，其中前两个字节标识 gzip，第三个字节表示使用 DEFLATE 压缩方法。这个前缀可以辅助识别，但不能单独证明整段数据完整有效。

抓包工具中的 JSON、文本和十六进制视图是展示方式。把展示方式切换为 JSON，并不等于已经执行 gzip 解压；只有工具先获得有效的 JSON 文本，才能展示 JSON 结构。HTTPS 解密也不会自动消除正文中的 gzip 压缩层。

## multipart 文件上传与请求体结构

文件上传需要客户端发送文件的实际字节。仅发送客户端本地路径，不能让远程服务端读取该路径对应的本地文件。

multipart/form-data 是一种将多个表单项组织在同一个请求体中的格式。每个部分可以承载普通文本或文件数据。客户端是否使用这种格式，应以接口约定为准；文件上传并不必然使用 multipart。

### 文件字段、文件名与两层头部

表单字段是表单中的一个命名数据项。文件字段是承载文件数据的表单字段。file 是示例接口约定的字段名，不是 HTTP 规定的保留名称，也不是 HTTP 请求头中的字段名。

multipart 的每个部分都有自己的头部，用于说明该部分的字段名、文件名和内容类型。这些部分头部位于 HTTP 请求体内部，与描述整个请求的 HTTP 请求头不同。

| 示例内容 | 所在位置 | 含义 |
| --- | --- | --- |
| Content-Type: multipart/form-data; boundary=Boundary-ABC123 | HTTP 请求头 | 整个请求体采用 multipart 格式，并指定分隔标识 |
| Content-Disposition: form-data; name="file"; filename="photo.jpg" | 请求体中，文件部分的头部 | 该部分对应名为 file 的表单字段，提交的文件名是 photo.jpg |
| Content-Type: image/jpeg | 请求体中，文件部分的头部 | 声明该部分的数据格式是 JPEG 图片 |
| 图片的实际字节 | 请求体中，文件部分的内容 | 服务端接收的文件数据 |

name="file" 中的 file 是 name 参数的值。filename="photo.jpg" 表示文件名。把字段名改成 avatar，不会自动把文件名也改成 avatar。声明 image/jpeg 或修改扩展名，都不会把其他格式的数据转换为 JPEG。

### boundary 与完整请求体示例

boundary 是用于构造各部分分隔行的标识字符串。客户端在 HTTP 请求头中声明该字符串，并在请求体中使用相同字符串。下面示例的 boundary 值为 Boundary-ABC123。

HTTP 请求头中的 Content-Type：

```http
Content-Type: multipart/form-data; boundary=Boundary-ABC123
```

请求体包含一个普通文本字段 description 和一个文件字段 file：

```text
--Boundary-ABC123
Content-Disposition: form-data; name="description"

我的头像
--Boundary-ABC123
Content-Disposition: form-data; name="file"; filename="photo.jpg"
Content-Type: image/jpeg

[这里是图片的实际字节]
--Boundary-ABC123--
```

方括号中的文字只是说明位置，实际发送时应替换为图片字节。示例将格式中的换行显示为普通换行，实际分隔行和头部行使用 CRLF，即回车加换行，对应字节 0x0D、0x0A。

普通分隔行是 -- 加 boundary。结束分隔行在末尾再加 --，表示 multipart 请求体结束。每个部分的头部与内容之间有一个空行；前一部分内容结束后，通过 CRLF 接下一条分隔行。分隔行前面的两个连字符不属于请求头中声明的 boundary 值。

boundary 必须避免与各部分内容中的分隔标记冲突。实际构造请求时通常使用包含随机值的字符串，降低冲突概率。HTTP 请求头声明的 boundary 与请求体使用的 boundary 必须一致，否则服务端无法按声明正确解析。

### 服务端如何取得文件

1. 服务端读取 HTTP 请求头中的 Content-Type，确定请求体格式与 boundary。
2. multipart 解析器按分隔标记识别请求体中的各个部分。
3. 解析器读取各部分的 Content-Disposition，取得 name 和可选的 filename。
4. 服务端框架将普通字段和文件字段提供给接口代码。接口代码按照约定的字段名取得对应文件，并保存或处理文件字节。

解析后的逻辑关系可以表示为：

```text
普通字段["description"] → "我的头像"
文件字段["file"]        → photo.jpg 的信息和字节内容
```

文件数据来自请求体，字段名用于标识文件属于哪个接口参数。服务端也可以遍历所有文件部分，但如果接口代码只读取 file，而客户端发送 name="avatar"，文件字节即使已经到达，接口仍可能报告缺少 file 字段。

## Swift 构造 multipart 请求与上传

Foundation 的 Data 是用于存放字节的值类型。URLRequest 描述请求地址、方法和请求头。URLSession 负责执行网络传输。使用 multipart 上传时，调用方先构造符合格式的请求体，再交给 URLSession 发送。

### 分隔行如何变成字节

Data("--\(boundary)\r\n".utf8) 将“分隔行加换行”转换为字节。该表达式可以拆成以下步骤：

```swift
let boundary = "Boundary-ABC123"
let text = "--\(boundary)\r\n"
let bytes = text.utf8
let data = Data(bytes)
```

字符串插值 \(boundary) 将 boundary 的值放入字符串。开头的 -- 是 multipart 分隔行的固定前缀。\r\n 分别表示回车和换行。字符串的 utf8 属性提供 UTF-8 编码的字节视图，Data(bytes) 再用这些字节创建二进制数据。

body.append(data) 将这条分隔行追加到请求体末尾。分隔行和部分头部需要从文本编码为字节，文件内容则直接追加原始 Data，不需要转换为字符串。

### 单个 JPEG 文件的最小示例

下面的示例假设接口接受 POST 和 multipart/form-data，文件字段名为 file。jpegData 必须已经是 JPEG 编码数据，uploadURL 必须是实际上传接口的 HTTPS 地址。异步 upload(for:from:) 在 iOS 15 及以上可用。

```swift
import Foundation

@available(iOS 15.0, *)
func uploadJPEG(
    _ jpegData: Data,
    to uploadURL: URL
) async throws -> Data {
    let boundary = "Boundary-\(UUID().uuidString)"
    var body = Data()

    body.append(Data("--\(boundary)\r\n".utf8))

    let disposition = "Content-Disposition: form-data; "
        + "name=\"file\"; filename=\"photo.jpg\"\r\n"
    body.append(Data(disposition.utf8))
    body.append(Data("Content-Type: image/jpeg\r\n\r\n".utf8))
    body.append(jpegData)
    body.append(Data("\r\n--\(boundary)--\r\n".utf8))

    var request = URLRequest(url: uploadURL)
    request.httpMethod = "POST"
    request.setValue(
        "multipart/form-data; boundary=\(boundary)",
        forHTTPHeaderField: "Content-Type"
    )

    let (responseData, response) = try await URLSession.shared.upload(
        for: request,
        from: body
    )

    guard let httpResponse = response as? HTTPURLResponse,
          (200..<300).contains(httpResponse.statusCode) else {
        throw URLError(.badServerResponse)
    }

    return responseData
}
```

客户端按“分隔行 → 文件部分头部 → 空行 → 图片字节 → 结束分隔行”的顺序构造 body。upload(for:from:) 创建并启动上传任务，完成后返回服务端的响应体和响应对象。responseData 是服务端返回的数据，不是已经上传的图片数据。

示例只检查 HTTP 状态码是否为 2xx。真实接口还可能要求认证请求头，并使用响应体中的业务状态表达结果。调用方需要按照接口约定解析响应，不能仅凭网络传输完成就认定业务处理成功。

### 大文件的内存边界

示例将完整 multipart 请求体组装到一个 Data 中，因此需要在内存中持有整个请求体，不适合直接用于大文件。对于大文件，可以分段读取源文件，并将部分头部、文件字节和结束分隔行依次写入临时文件，再通过 upload(for:fromFile:) 发送该临时文件。

fromFile 指向的是完整 HTTP 请求体文件。如果接口要求 multipart，就必须写入完整 multipart 格式。URLSession 不会根据原始文件路径自动生成 multipart 的 boundary 或部分头部。临时文件应在上传期间保持可读，并在上传完成或取消后按任务生命周期清理。

## 连接、超时与幂等重试

常见 HTTPS 请求链路可分为 DNS 解析、TCP 连接、TLS 握手与 HTTP 交换。TCP 使用三次握手；具体丢包与重传行为需按协议阶段分析。TLS 1.3 不能直接套用旧式 RSA 密钥传输说明。

请求超时表示调用方尚未获得确定结果，不证明服务端没有执行。对同一次业务操作重试时复用操作标识，并由服务端按该标识去重；新的业务操作使用新的标识。幂等重试需要客户端与服务端共同遵守契约。

## TCP 慢启动与快重传

慢启动逐步探测网络能够承受的发送量；快重传根据重复确认推断丢包，在重传定时器超时之前补发数据。以下按经典 TCP 算法说明，具体实现可能使用其他拥塞控制或丢包检测算法。

拥塞窗口 `cwnd` 是发送方对未确认数据量的限制。接收窗口 `rwnd` 是接收方通告的接收能力限制，发送同时受二者约束。`RTT` 是发送数据到收到对应确认的往返时间。

**慢启动：**发送方从较小窗口起步，收到确认新数据的 ACK 后增加窗口。在每个数据段得到及时、独立确认等理想条件下，窗口大约每经过一个 RTT 翻倍，例如 `2 → 4 → 8 → 16` 个数据段；2 只是示例，不是固定初始值。“慢”指起始发送量较小，窗口增长通常接近指数增长。

`ssthresh` 是慢启动阈值。窗口小于阈值时使用慢启动，大于阈值时使用拥塞避免；等于阈值时经典规范允许采用其中任一种。经典拥塞避免阶段近似每个 RTT 增加一个最大数据段的大小。

**快重传：**ACK 是确认报文，累计确认号表示接收方下一步期望收到的字节序号。中间数据缺失时，后续数据到达会使接收方重复确认缺失位置。发送方收到 3 个满足条件的重复 ACK，期间累计确认号没有推进时，推断可能丢包并立即重传。

例如，发送方已经收到 `ACK=1001`，之后又收到 3 个相同确认号的重复 ACK，便重传对应缺失数据段。这里是首次确认之后再收到 3 个重复确认，不是总共收到 3 次相同确认。乱序也可能产生重复 ACK，因此这是一种丢包推断。

快重传决定何时补发；快恢复负责丢包后的窗口与发送控制。

## 代理连接与 HTTPS 隧道

配置代理后，遵循代理设置的网络库会把“连接谁”和“最终请求谁”分开：业务 URL 仍是服务端域名，但实际先建立到电脑代理 IP／端口的连接。IP 找到电脑，端口找到监听的代理进程；代理再根据请求中的目标地址连接服务端，并把响应转回手机。

```text
手机 App → 电脑代理程序 → 目标服务端
手机 App ← 电脑代理程序 ← 目标服务端
```

HTTP 代理请求会带目标 URL／Host 等信息；HTTPS 通过常见 HTTP 代理时，通常先发送 `CONNECT 域名:443` 建立隧道，再在隧道中进行 TLS 通信。仅仅转发 HTTPS 密文不需要解密；要用抓包代理查看明文，通常需要手机信任代理证书并满足 App 的证书校验条件，证书绑定可能阻止这种方式。

这不是把服务端域名的 DNS 强行改成电脑 IP。手机必须能访问代理地址，电脑代理也要监听可访问的网卡地址／端口；自建连接或不遵循系统代理设置的网络栈，不保证所有流量都经过它。

## HTTPS 抓包与两段 TLS 连接

HTTPS 使用 TLS 保护 HTTP 通信。TLS 提供身份验证、传输加密和数据完整性校验。监听网络可以捕获密文以及 IP、端口等信息；查看 HTTP 明文需要具备解密条件。

启用 HTTPS 解密、流量经过代理且客户端接受代理证书时，客户端与代理建立连接 A，代理与真实服务器建立连接 B。两段分别完成 TLS 握手，独立协商并派生密钥。每条连接使用一组密钥，两个传输方向使用不同的密钥。

```text
客户端 ←─ TLS 连接 A ─→ 抓包代理 ←─ TLS 连接 B ─→ 真实服务器
                            │
                       解密并记录明文
```

请求转发顺序：客户端用连接 A 的发送密钥加密 → 代理用连接 A 对应的接收密钥解密并记录明文 → 代理用连接 B 的发送密钥重新加密 → 服务器用连接 B 对应的接收密钥解密。响应按相反方向转发。

代理能够读取明文，是因为代理参与了两次握手，持有两侧所需的密钥。代理不需要取得真实服务器的私钥。只转发密文的普通 CONNECT 隧道不会拆分 TLS 连接。

**iPhone 配合 Charles 的操作步骤：**

1. 让手机能访问电脑，通常连接同一个 Wi-Fi。在手机当前 Wi-Fi 的 HTTP 代理设置中填写电脑局域网 IP 和 Charles 实际监听的端口，并在 Charles 中允许手机连接。
2. 配置代理后，按照 Charles 的移动设备证书安装提示下载证书描述文件，并在系统设置中完成安装。
3. 打开“设置 → 通用 → 关于本机 → 证书信任设置”，启用对 Charles 根证书的完全信任。手动安装证书不等于已经启用 TLS 信任。
4. 在 Charles 中为目标域名和端口启用 SSL Proxying，例如 api.example.com:443。重新建立连接并发起请求，查看请求头、请求体和响应。

证书或公钥固定，是 App 额外要求证书或公钥与预设值匹配的校验。系统信任代理根证书后，这项检查仍可能拒绝代理证书。自己开发的 App 需要在调试版本中提供相应配置。网络请求遵循代理设置和客户端接受代理证书是两个独立条件。

## 证书公钥、CA 签名与会话密钥

公钥可以公开，私钥由持有者保密。数字签名是使用私钥针对数据生成的验证信息；对应公钥用于检查签名，验证数据未被修改及签名者持有对应私钥。CA 是证书签发机构。服务器证书包含域名、公钥、有效期等信息，以及签发者的签名。

以使用证书认证的 TLS 1.3 为例，需要区分两次验证：

| 验证对象 | 签名密钥 | 验证密钥 | 目的 |
|-|-|-|-|
| 服务器证书内容 | 签发该证书的 CA 私钥 | 对应 CA 的公钥 | 验证签发来源和内容完整性，确认 CA 认可域名与公钥的绑定 |
| 本次 TLS 握手相关内容 | 服务器证书公钥对应的私钥 | 服务器证书中的公钥 | 确认当前参与握手的对端持有对应私钥；只有证书副本不够 |

抓包时，Charles 使用自己的 CA 私钥签发目标域名证书。客户端预先信任 Charles 根证书，证书路径、域名等检查也通过后，才能接受该证书。Charles 还使用目标域名证书公钥对应的私钥完成握手签名。

HTTP 请求和响应使用本次连接派生的对称密钥保护。在 TLS 1.3 中，证书公钥用于认证，不直接加密 HTTP 内容；CA 私钥也不是连接的数据加密密钥。

## 证书链、中间 CA 与根 CA 信任

证书链是按签发关系连接的一组证书。根 CA 证书提供客户端已经信任的起点；中间 CA 证书包含中间 CA 的公钥和上级 CA 的签名；服务器证书包含目标域名和服务器公钥。

```text
客户端已经信任的根 CA 证书
    │ 根 CA 私钥签发
    ▼
中间 CA 证书
    │ 中间 CA 私钥签发
    ▼
服务器证书，例如 api.example.com
```

在只有一级中间 CA 的例子中，服务器证书的签发者是中间 CA，中间 CA 证书的签发者是根 CA。客户端使用中间 CA 公钥验证服务器证书签名，再使用已信任根 CA 公钥验证中间 CA 证书签名。实际可以有多级中间 CA；还需检查有效期、用途、CA 签发权限以及目标域名等条件。

根 CA 证书的信任来自操作系统、浏览器或应用的预置配置，也可以由用户或管理员配置加入。服务器发来一张根证书不会让客户端自动信任它，根证书给自己签名也不会自动建立信任。

**缺少中间证书：**服务器证书由中间 CA 签发时，客户端需要中间 CA 公钥验证签名。服务器未提供所需中间证书，客户端也无法从缓存、网络等来源补齐时，可能无法建立到可信根证书的验证路径。根 CA 公钥不能直接替代中间 CA 公钥。

服务器通常发送服务器证书和必要的中间证书，根证书通常不必发送。部分客户端能补齐中间证书，因此同一个服务可能出现“部分设备能访问、部分设备失败”。

## “证书不可用”的归因与排查

仅凭“证书不可用”这句提示，不能确定责任在客户端还是服务端。普通 HTTPS 中，服务端提供证书，客户端执行验证。客户端上报验证失败后，还需要确定哪一方验证了哪张证书。

| 可能来源 | 检查内容 |
|-|-|
| 服务端配置 | 证书过期、证书不包含实际请求域名、缺少必要的中间证书 |
| 客户端环境或配置 | 设备时间错误、不信任对应 CA、请求域名错误、固定证书或公钥与服务端更新后的配置不匹配 |
| 抓包代理 | 客户端未信任代理根证书、App 拒绝代理证书，或代理验证真实服务器证书失败 |

1. 读取底层错误码、失败域名和 TLS 握手日志，区分过期、域名不匹配、不受信任等失败类型。
2. 检查实际收到的证书，包括签发者、域名、有效期及中间证书，确认收到的是服务器证书还是代理证书。
3. 关闭代理重试，并比较不同设备或客户端。对照结果用于缩小范围，不能单独证明根因。
4. 依据证据修复对应配置。例如，在准确系统时间下确认服务器证书过期，就更新服务端证书；确认未信任调试代理 CA，就修复客户端调试信任配置。

双向 TLS 是客户端和服务端都提供证书供对方验证。启用双向 TLS 时，还要检查服务端是否拒绝了客户端证书。证据不足时，只能列出待验证原因。
