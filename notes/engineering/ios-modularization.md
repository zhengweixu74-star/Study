## 组件化与组件边界

组件化是按职责把代码划分为相对独立的单元，并让单元通过明确接口协作的工程方法。组件可以提供基础能力，也可以提供一项完整功能。

职责是组件负责完成的工作，例如“把图片导出为文件”。边界规定组件负责什么、接收什么输入、返回什么结果，以及哪些内部实现不对外暴露。仅把文件放进不同文件夹，没有限制访问和依赖关系，并不代表已经建立组件边界。

例如，页面负责收集用户操作和展示进度。导出组件负责生成图片文件。页面把图片传入导出接口；导出组件在结束后返回文件地址或错误。导出组件不需要知道页面上的按钮或标签。

## 公开接口与协作流程

公开接口是组件允许调用方使用的类型、方法和数据约定。Swift 协议可以描述能力要求，组件的具体类型负责实现要求。协议本身不会执行导出，也不会自动寻找实现对象。

下面用同步接口表示最小协作关系，不展开图片导出的具体实现：

```swift
import UIKit

public protocol ImageExporting {
    func export(_ image: UIImage) throws -> URL
}

final class ExportPage: UIViewController {
    private let exporter: any ImageExporting

    init(exporter: any ImageExporting) {
        self.exporter = exporter
        super.init(nibName: nil, bundle: nil)
    }

    required init?(coder: NSCoder) {
        fatalError("此示例只支持代码初始化")
    }

    func exportImage(_ image: UIImage) throws -> URL {
        try exporter.export(image)
    }
}
```

组装页面的代码创建符合 ImageExporting 的对象，并传给 ExportPage 的初始化方法。页面调用 exporter.export(image)，具体实现执行导出，随后返回 URL 或抛出错误。该示例是同步调用，调用线程会等待导出结束；真实耗时导出应根据执行要求设计异步接口。

跨 Swift 模块使用时，协议及实现中供外部调用的类型、初始化方法和成员需要相应的 public 访问权限。把实现换成另一个符合相同协议的对象时，页面可以继续使用同一接口。

传入实现对象的方式属于依赖注入，即由外部提供对象需要使用的依赖。源码依赖方向、依赖反转和更完整示例见 [设计模式与 Swift 实践](design-patterns.md#依赖反转与依赖注入)。这里的组件化讨论的是职责和工程边界，两者有关联，但并不等同。

## 工程组织方式

模块是编译和名称访问的组织单元。组件是职责单元；一个组件可以对应一个或多个模块，二者不要求一一对应。

| 方式 | 在组件化中的用途 |
| --- | --- |
| Swift Package | 通过 target 划分代码、资源和依赖，可产生可导入的模块 |
| Framework | 用 target 组织模块及其交付产物，可按需求采用静态或动态链接 |
| CocoaPods | 声明、获取和集成组件依赖，具体产物取决于配置 |

组件可以放在同一个仓库，也可以分布在多个仓库。采用多个仓库不是组件化的必要条件。路由是按标识或参数定位页面、能力的机制；只有协作方式需要时才引入，组件之间也可以直接通过明确接口调用。

依赖应具有明确方向。例如“页面 → 导出接口”“导出实现 → 导出接口”，应用的组装代码负责把实现交给页面。避免两个组件互相直接依赖对方的内部类型，否则修改容易在两个组件之间传播。

工程打包和加载的区别见 [编译、链接、嵌入与装载](xcode-and-testing.md#编译链接嵌入与装载)；CocoaPods 的集成机制见 [CocoaPods、Podfile 与依赖管理](cocoapods-and-podfile.md)。

## 收益与维护成本

清楚的组件边界可以缩小修改范围，支持替换实现、独立验证和多人协作。只有依赖与编译组织合理时，组件划分才可能改善增量编译时间；拆成更多模块本身不保证构建更快。

组件化也增加接口设计、依赖管理、版本协调和资源归属的成本。拆分应从实际职责和变化范围出发。规模较小、始终一起变化的代码，可以先保留在同一个模块中，通过清楚的类型和接口组织。
