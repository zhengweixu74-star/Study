## 源码编辑与搜索

### 源码编辑器的列选择

当每行的 `*` 位于同一列时，可以使用**列选择**：按矩形范围选中多行中相同列的字符，再一次删除。

1. 按住 **Option（⌥）**，从第一行 `*` 的左侧拖动鼠标，到最后一行 `*` 的右侧，选中整列 `*`。
2. 松开鼠标，**继续按住 Option**，确认选区只覆盖每行的 `*`。
3. 保持 Option 按下，按 **Delete** 删除选中的字符。
4. 删除完成后，再松开 Option。

如果还要删除 `*` 后面的一个空格，拖动时将这一列空格一起选中；不要选中后续代码。

**操作注意：Option 键要从开始选择一直按到删除完成；中途松开 Option，选区会变成一整段文本。**

### 文本搜索与符号搜索

**文本搜索匹配文件中的字符；符号搜索查询代码索引中的符号名称及其引用。** 符号的定义和引用概念见[符号与引用](../language/swift-basics.md#符号引用与对象引用)。

| 对比项 | 文本搜索 | 符号搜索 |
|-|-|-|
| 搜索对象 | 当前搜索范围内的文件文字 | 代码索引识别的符号及其出现位置 |
| 注释、普通字符串内容 | 可以命中 | 不作为对目标符号的引用匹配 |
| 声明、定义、引用 | 只按字符匹配，结果中声明、定义和引用混在一起 | 索引具有这些角色信息，可按搜索选项筛选 |
| 搜索 `actionHandler =` 等代码片段 | 适合 | 不适合，片段不是符号名称 |
| 索引依赖 | 不依赖代码符号索引 | 未纳入索引或索引未更新时，结果可能不完整或过时 |

`Find Selected Symbol in Workspace` 可以从编辑器中的符号发起搜索，但仍需核对 Find navigator 顶部的查询条件。**按名称搜索符号时，结果包含所有名称符合条件的符号，可能来自不止一个符号。**`Containing` 是包含匹配，`Matching` 是完整名称匹配；大小写设置也会影响结果。同名但属于不同类型的属性，即使完整匹配也可能同时出现。

例如，按名称搜索 `actionHandler` 时，包含匹配可能同时选中 `actionHandler` 和 `ButtonActionHandler`；这两个符号只是名称含有相同字符，彼此是否存在调用或赋值关系要另外确认。完整名称匹配可以排除较长名称，但同名结果仍需结合所属类型判断。

### 沿赋值链查找闭包实现

下面声明一个闭包类型别名和一个可选变量：

```swift
typealias ActionHandler = () -> Void
var actionHandler: ActionHandler?
```

`actionHandler` 是保存闭包的可选变量。`ActionHandler` 是闭包类型的别名，只描述闭包的参数和返回值。实际执行的闭包体写在给 `actionHandler` 赋值的地方，要沿赋值位置查找：

1. 使用 Xcode 默认快捷键 `⌘⇧F` 打开工作区搜索，选择文本搜索并输入 `actionHandler =`，查找直接赋值位置；实际代码若使用不同空白写法或经参数传递赋值，需要继续沿数据来源查找。
2. 也可对 `actionHandler` 使用右键菜单 `Find → Find Selected Symbol in Workspace`，从符号使用位置中筛选赋值，并核对所属类型。
3. `⌃⌘J` 是 Jump to Definition。对属性名使用时，通常跳到属性声明；对类型别名使用时，跳到类型别名定义。两种跳转都只到达声明位置；运行时保存的是哪一个闭包，仍要沿赋值位置查找。

给 `actionHandler` 赋值的最小示例：

```swift
actionHandler = {
    print("执行操作")
}
```

左侧 `actionHandler` 是保存闭包的变量，右侧是闭包值。执行赋值语句只把闭包值存入 `actionHandler`；之后调用 `actionHandler?()` 时，闭包体中的 `print` 才执行。如果闭包存放在对象属性中，getter／setter 只读写闭包值；调用属性取出的闭包时，闭包体才执行。

### 属性、访问器与索引记录

**P 表示属性，M 表示方法。** 实例属性的 getter 和 setter 是访问器方法；索引将访问器归类为方法时，可以显示 M。访问器的职责与编译器优化边界见[属性访问器](../language/swift-basics.md#存储属性计算属性与访问器)。

## 工程与构建

### Target、模块与构建产物

**Target 是构建单位：** 指定参加构建的代码、资源、依赖、设置和产物类型。**模块（Module）是代码的编译与访问边界：** 一组代码具有统一模块名，其他模块通过 `import` 使用其中对外可见的声明。**构建产物是生成的文件或包。** Target、模块和构建产物是三个不同概念。

| Target 或类型 | 产物例子 | 用途 |
|-|-|-|
| DemoApp App Target | `DemoApp.app` | 可执行程序、资源和配置等组成的 App |
| MathKit Framework Target | `MathKit.framework` | 承载库代码、模块接口等，供其他模块使用 |
| 单元测试 Target | `DemoTests.xctest` | 由测试运行器加载的测试包 |
| 资源 Bundle Target | `.bundle` | 可以只放图片、字体等，不包含 Swift 代码模块 |

Target 可以生成 App、Framework、测试包或资源 Bundle 等产物；资源 Bundle 这类产物不包含代码模块。Swift App 的代码也形成模块，但整个 `.app` 还包含资源等内容。普通 Swift Framework Target 通常对应一个模块，Target 名与模块名经常相同，也可以通过 `Product Module Name` 等配置调整。

**用 MathKit 理解“模块”：** 假设下面两个文件都属于名为 MathKit 的 Swift Framework Target：

```swift
// Add.swift，属于 MathKit 模块
public func add(_ a: Int, _ b: Int) -> Int {
    return a + b
}

// Double.swift，属于同一个 MathKit 模块
public func double(_ value: Int) -> Int {
    return add(value, value)
}
```

两个文件里的代码归为同一模块，`Double.swift` 可直接使用模块内可见的 `add`。另一模块使用它们时：

```swift
import MathKit
let sum = add(2, 3)
let doubled = double(4)
```

MathKit 是模块名，Add.swift 是源文件名，add 是函数名；`public` 让函数可在模块外访问。模块由构建配置定义；只创建名为 MathKit 的目录，不会形成 MathKit 模块。

### 构建设置与 Debug／Release

| 设置 | 含义 |
|-|-|
| Swift Language Version | 使用哪个 Swift 语言模式 |
| Optimization Level | 编译优化策略，例如 `-Onone` 关闭优化，方便调试 |
| Deployment Target | 支持的最低操作系统版本 |
| Framework／Header Search Paths | 查找依赖框架、头文件的目录 |
| Active Compilation Conditions | 条件编译标记，例如是否进入 `#if DEBUG` 分支 |
| Product Module Name | 生成的代码模块名称 |

这些设置在 Target 的 `Build Settings` 页面查看。哪些文件要编译、哪些资源要复制、怎样链接依赖，则在 `Build Phases` 等其他页面配置。

Build Configuration 是一组构建设置的名字，例如 Debug、Release。通常 Debug 偏向调试，Release 偏向运行效率；优化级别等实际行为由该配置下各项设置的值决定，与配置的名字无关。

### podspec 与源码范围

`podspec` 是 CocoaPods 的库描述文件，使用 Ruby 语法编写。CocoaPods 是 iOS 常用的依赖管理工具。podspec 可以描述库的名称、版本、源码规则、依赖，以及支持的平台和最低系统版本。

下面用 `source_files` 指定源码范围：

```ruby
s.source_files = 'Sources/**/*.swift'
```

`s` 是 podspec 的配置对象。`Sources/**/*.swift` 匹配 `Sources` 目录及其子目录中的 Swift 文件。只有被 `source_files` 等源码规则匹配到的文件才参与编译，磁盘上的其他文件不在编译范围内。修改源码规则后，需要检查实际匹配到的文件集合。

Podfile 的执行方式、依赖解析、锁文件和工具版本管理，见[CocoaPods、Podfile 与依赖管理](cocoapods-and-podfile.md)。

### iOS JoJo 工程磁盘清理规则

- 处理任意 iOS 项目的磁盘清理时，默认按 JoJo 工程处理；清理前必须停止 Xcode、XcodeMate、MBox/JoJo 的 install、index 和 build 任务，并先用 `df -h /System/Volumes/Data`、`du -sh <候选目录>` 记录空间，只删除已核实用途的精确目录。
- `~/Library/Developer/Xcode/DerivedData` 属于可重建的 Xcode 构建产物，可以在相关构建进程停止后清理；清理后首次索引和编译变慢属于正常重建。
- CocoaPods 缓存按“保留当前依赖、清理未引用版本”处理，禁止直接删除 `~/Library/Caches/CocoaPods` 或执行 `pod cache clean --all`。JoJo 工程的 `Pods/*` 可能软链接到该共享目录，全量删除会同时破坏多个 workspace。
- 清理 CocoaPods 前，必须先让用户确认需要保持可用的全部 JoJo workspace；以每个 workspace 当前 `Podfile.lock` 的顶层 Pod 名称为准，映射对应 `Pods/<Pod>` 软链接并收集其缓存目标，所有 workspace 目标的并集是保留集合。禁止仅凭 `Pods` 目录现存链接判断，因为其中可能包含历史遗留链接。
- 只允许把 `~/Library/Caches/CocoaPods/v1/Pods/Release/<Pod>/<version-hash>` 中不在保留集合内的版本目录列为清理候选；不得删除保留集合、`Specs` 或 CocoaPods 缓存根目录。删除前必须向用户展示候选路径、合计大小和涉及的 Pod/版本，并取得明确确认。
- 清理后在每个相关 workspace 根目录执行 `find -L Pods -maxdepth 1 -type l -print`，并结合当前 `Podfile.lock` 判断：只有当前锁定 Pod 的链接断裂才属于阻塞；未被锁文件引用的历史断链可忽略或单独清理。存在当前依赖断链时，必须在对应 workspace 执行 `mbox jojo install`，不能用其他目录、分支或副本的安装结果代替。
- `Pods`、`.jojo`、`bazel_build` 等依赖或构建目录只能在确认当前 workspace、分支、`Podfile.lock` 和恢复方式后处理；多个 workspace 同时存在时必须逐个核对真实路径，不能因为目录名相近而视为同一环境。

### Bazel、编译器与链接器

Bazel 是构建系统。Bazel 根据源码、依赖和构建配置等输入，决定需要执行哪些编译、链接任务，再调用相应工具完成任务。已有构建结果仍然有效时，Bazel 可以复用结果，减少重复构建。

**Bazel 负责组织构建任务，实际编译由编译器完成。** Swift 编译器 `swiftc` 处理 Swift 源码并生成目标代码，链接器再将目标代码和所需库组合成最终产物。具体执行哪些任务取决于构建目标；例如索引任务执行的工作与完整 App 构建不同。

为了方便理解，可以把 Bazel 类比为“施工调度员”，把编译器类比为“实际施工的工人”。这个类比只说明职责分工；编译的具体阶段见[编译器与机器码](../language/swift-objc-runtime.md#编译阶段机器码与内联)。

### 编译、链接、嵌入与装载

编译把源代码转换为目标代码。目标文件通常以 `.o` 为扩展名，保存代码、数据以及尚需链接器处理的符号信息。构建时链接把目标文件和库提供的定义组织成可执行文件或库，并处理代码中的引用关系。

App 包是包含主可执行文件、资源和配置等内容的目录。嵌入动态库，是把需要随 App 分发的动态库文件复制到 App 包。装载动态库，是在运行时把动态库映射到进程的地址空间，使进程能够访问其中的代码和数据；文件内容通常在被访问时才按页读入物理内存。

“参与链接”“复制进 App 包”和“装载到进程”是三个不同动作。下表只对比常规静态链接和动态链接，可合并动态库在后文单独说明。

| 阶段 | 静态库 | 常规动态库 |
| --- | --- | --- |
| 构建时链接 | 链接器从静态库中取出所需目标文件，再把保留的代码和数据合入目标产物 | 链接器使用动态库的接口信息处理引用，并在产物中记录所需依赖；库的实现通常仍位于独立文件中 |
| App 打包 | 通常不需要把 `.a` 文件作为运行依赖复制进包 | 随 App 分发的第三方动态库需要正确嵌入；系统动态库由系统提供 |
| App 运行 | 相关实现已经属于使用该静态库的可执行文件或动态库 | dyld 准备运行所需动态库，并完成必要的地址关联和初始化 |

### 静态库的目标文件提取与代码裁剪

静态库 `.a` 通常是多个目标文件的归档。默认情况下，链接器根据尚未解析的符号引用，从归档中提取能提供所需定义的目标文件。因此，提取这一步通常以目标文件为单位，一次取出整个目标文件，而不是按业务调用了哪些函数逐个挑选。

假设 `A.o` 包含 `foo()` 和 `bar()`，`B.o` 包含 `baz()`。应用只引用 `foo()`，且没有其他保留条件时，链接器通常会提取 `A.o`，不提取 `B.o`。`bar()` 是否最终保留，还要看后续优化和裁剪条件。

dead stripping 是链接阶段删除不需要保留的代码和数据的优化。链接器从程序入口、要求保留的定义等起点分析引用关系，再删除符合裁剪条件的部分。这种分析只依据构建时可见的信息，与某次实际运行是否调用了某个函数无关。

Xcode 的 `Dead Code Stripping` 设置对应 `DEAD_CODE_STRIPPING`。设为 `YES` 时，常规链接配置会启用链接器的 `-dead_strip` 选项。裁剪作用于最终产物中的代码和数据，不会删除工程里的源文件。

例如，保留入口沿引用关系到达 A，A 再引用 B；另有 C 引用 D。如果没有任何保留入口通向 C 或 D，且不存在导出或显式保留等条件，C 和 D 才可能被裁剪。即使 C 与 D 互相引用，两者也可以一起被裁剪，因为是否保留取决于能否从保留入口到达。

用运行时开关关闭某个功能后，功能代码通常仍留在产物中：开关值要到运行时才能确定，链接器在构建阶段只能保留这条执行路径。动态调用、初始化入口和运行时所需的类型或方法描述也可能让代码被保留。因此，搜索源码中的直接调用次数，无法判断最终包是否包含某段实现。

`-all_load` 要求装入静态归档中的全部目标文件；`-force_load` 针对指定归档执行类似提取；`-ObjC` 会使包含 Objective-C 类或分类实现的目标文件被提取。这些选项只扩大目标文件的提取范围；提取之后，链接器仍可能继续裁剪。最终保留哪些内容，还受初始化代码、运行时元数据和显式保留规则影响。

总结：静态库中未使用的内容可能不进入最终产物，但没有被直接调用的函数仍可能进入 App。判断某段代码是否进入产物，要分两步看：所在目标文件是否被提取；提取后这段代码是否被保留。

### 动态库的打包、启动装载与延迟装载

普通动态库也参与构建时链接。构建时链接器检查所用接口并记录依赖，运行时 dyld 再根据这些信息准备实际动态库。

对于正确嵌入 App 的第三方动态库，库通常以独立二进制文件随 App 分发。链接 App 时，通常不会像处理静态归档那样，只从这个已经生成的动态库中抽取 App 调用的几个函数。因此，动态库中未被该 App 直接调用的代码，也可能随库文件进入 App 包。动态库本身在生成时也可能经过优化和裁剪，因此库的源代码不一定全部保留在库文件中。

系统提供的 UIKit 等动态框架不需要复制进 App 包。动态库是否作为依赖保留、是否嵌入 App 包，也受链接和打包配置影响；某些链接选项可以移除未使用的动态库依赖。因此，把一个库加入工程后，最终包内是否包含该库，以链接和打包的实际结果为准。

程序声明的普通必需动态库依赖，通常在启动阶段、进入 `main` 之前装载，并完成当时必需的准备工作，而不是等到第一次调用库中的函数时才装载。应用使用 `dlopen` 显式请求装载尚未装载的库时，这个库才在运行期间装载；能否装载成功还取决于库是否存在以及平台的执行要求。

库的装载与符号绑定是两个步骤。符号绑定是把函数或变量的引用关联到实际地址。某些绑定方式可以延迟到首次使用时完成，具体行为取决于平台和构建方式。延迟绑定推迟的只是某个函数引用的地址关联；必需的动态库本身仍在启动阶段装载。

与启动过程的关系见 [main 之前的启动工作与 dyld](../ios/app-lifecycle-and-events.md#main-之前的启动工作与-dyld)。

### 静态链接与动态链接的取舍

静态链接可以减少需要独立装载的自定义动态库。库代码合入使用方后，运行时不需要再装载一个独立的库文件；但合入的代码仍随使用方一起装载，地址修正和初始化工作仍然存在。静态库与动态库在各阶段的区别见[编译、链接、嵌入与装载](#编译链接嵌入与装载)。

假设 App 使用一个网络库。静态链接后，网络库中被选入并保留的代码属于 App 可执行文件；动态链接后，App 可执行文件记录依赖，网络库的实现保留在独立文件中。源码按多个模块组织时，最终产物可以只有一个可执行文件，不必拆成多个动态库。

| 考虑因素 | 静态链接 | 动态链接 |
| --- | --- | --- |
| 启动准备 | 减少独立库的装载和跨库地址关联；不消除保留代码的初始化 | 需要准备独立库及其依赖，库数量和大小会影响开销 |
| 开发时构建 | 库实现更新后，使用方需要重新链接并合入新代码 | 使用方不需要合入库实现，某些大型项目因此能缩短构建时间；库本身仍需构建 |
| 多个独立程序使用同一库 | 各自静态链接时，多个产物可能保留相同代码 | 正确配置共享库文件时，多个程序可以依赖同一份库代码 |
| 依赖提供形式 | 需要源码、静态版本或工具支持的可合并产物 | 可以直接使用平台支持的动态版本 |

例如，主 App 和小组件是两个独立的可执行程序。两者分别静态链接同一个库时，各自可能包含一份相同实现；配置为依赖同一份嵌入式动态框架时，可以减少重复打包。两个进程共用同一份库代码文件时，各自的全局变量和对象状态仍相互独立；进程之间的数据访问见[iOS 进程间通信与应用扩展](../ios/interprocess-communication-and-extensions.md)。

主可执行文件变小时，整个 App 安装包不一定变小；比较时还需要计入独立动态库。静态链接要求使用方重新链接，不要求每次重新编译全部源码。实际选择应同时比较发布版本的启动性能、包体积和开发时的构建耗时。

第三方只提供普通动态二进制库，而没有源码、静态版本或可合并信息时，只改配置无法把这个库转成静态库。UIKit 等系统框架由系统提供并优化，App 不能自行把这些框架改成静态链接。

Xcode 15 起提供 Mergeable Libraries（可合并库）。这类动态库携带支持合并的信息，可以在开发构建中保持动态链接，在发布构建中把实现合入使用方，以兼顾构建速度和启动性能。只有携带合并信息的库产物才能这样合并；采用前需要满足工具和库产物的要求。

### IPA、.app 与 Mach-O

IPA、.app 和 Mach-O 分别描述分发归档、应用目录和二进制文件格式，属于不同层级。

| 对象 | 含义 | 作用 |
| --- | --- | --- |
| .ipa | 采用 ZIP 格式的应用分发归档文件 | 把应用代码、资源和配置等内容打包，供分发和安装使用 |
| .app | 按约定结构组织的应用包目录 | 保存主可执行文件、图片、配置以及随应用分发的其他内容 |
| Mach-O | Apple 平台使用的二进制文件格式 | 规定代码、数据和加载描述信息的组织方式；iOS 主可执行文件采用这种格式 |

例如，Demo.ipa 的 Payload 目录中包含 Demo.app；Demo.app 中包含主可执行文件 Demo、应用配置 Info.plist 和图片等资源。Demo 通常没有文件扩展名，但文件内部仍采用 Mach-O 格式。文件格式由文件内容决定，与扩展名无关。

通过 IPA 安装完成后，iPhone 上的应用以 .app 应用包的形式存放。点击桌面图标时，系统启动已安装的应用，加载应用包中的可执行文件，无须每次重新解压 IPA。应用运行后产生的用户数据通常保存在独立的数据目录中，不写回应用包。

### Mach-O 的加载信息

加载信息是可执行文件中供系统读取的描述数据，用来说明如何准备程序的代码和数据，并进入程序执行。Mach-O 主要通过加载命令（Load Commands）保存这些描述。加载命令是文件中供系统读取的结构化记录，CPU 不执行加载命令。

| 信息 | 具体内容 |
| --- | --- |
| 文件位置与内存布局 | 记录代码和数据在文件中的位置、大小，以及预设的虚拟地址和内存范围。文件偏移表示某部分内容距文件开头的字节数 |
| 内存访问权限 | 说明对应内存区域是否允许读取、写入或执行。例如，代码区域通常允许读取和执行，但不允许写入 |
| 动态库依赖 | 记录程序需要的动态库。动态库是在运行时供程序使用的独立代码库；系统库可以由系统提供，无须复制进每个应用包 |
| 程序入口 | 记录应用入口位置，供系统在完成必要的启动准备后进入应用代码 |

启动时，内核和 dyld 根据这些记录准备程序。dyld 是系统提供的运行时动态链接器，负责准备所需动态库，并完成必要的地址修正和符号绑定。系统建立文件内容与程序虚拟内存的对应关系，称为内存映射。建立映射时，系统不会立即把整个文件读入物理内存，文件内容在被访问时才按页读入。

### 预设虚拟地址、ASLR 与物理内存

Mach-O 文件记录的是加载前确定的预设虚拟地址布局，与代码运行时所在的物理内存地址无关。需要区分下列三种地址。

| 地址 | 含义 | 由谁确定 |
| --- | --- | --- |
| 预设虚拟地址 | 可执行文件中记录的地址布局，供加载时计算使用 | 构建时由链接器确定 |
| 实际运行的虚拟地址 | 本次运行中，程序访问代码或数据时使用的地址 | 加载时由系统根据文件布局和本次加载位置确定 |
| 物理地址 | 代码或数据实际存放在物理内存中的位置 | 由操作系统的内存管理机制安排 |

生成可执行文件时，链接器确定代码和数据在文件中的位置及预设虚拟地址。此时程序尚未运行，也没有确定代码将使用哪些物理内存。

ASLR 是地址空间布局随机化：系统在加载程序时引入随机偏移，使程序在不同次启动时可以使用不同的虚拟地址。对于这里讨论的 iOS 主程序代码，实际运行的虚拟地址等于文件记录的预设虚拟地址加上本次加载的偏移量。

实际运行的虚拟地址 = 预设虚拟地址 + 本次加载的偏移量

例如，某处代码的预设虚拟地址为 0x100000000，本次加载的偏移量为 0x200000，则实际虚拟地址为 0x100200000。实际偏移量由系统在每次加载时决定。下一次启动时，系统可以选择不同偏移量，磁盘上的 Mach-O 文件无须随之改写。

同一次运行中，主程序代码的虚拟地址通常保持不变。程序使用虚拟地址访问内存，硬件根据操作系统维护的映射把虚拟地址转换为物理地址。

页是系统管理内存所用的固定大小块。页表是按页记录虚拟地址与物理地址对应关系的数据结构。如果代码对应的物理内存位置发生变化，系统更新页表中的映射；程序的虚拟地址可以保持不变，磁盘上的 Mach-O 文件也无须更新。

运行时需要修正的指针或引用，由系统在加载后的内存中修正；磁盘上的可执行文件保持不变。

### Rebase 与 Binding：地址修正

指针是保存内存地址的值。Rebase 与 Binding 都用于让二进制文件中需要修正的指针指向本次运行中的正确地址；这些地址是程序使用的虚拟地址，不是物理地址。地址随机化的定义和计算关系见[预设虚拟地址、ASLR 与物理内存](#预设虚拟地址aslr-与物理内存)。

**Rebase：修正指向同一个二进制文件内部的指针。** 目标在该文件中的相对位置已知，系统加上本次实际加载位置，就得到正确地址。下面只演示地址关系，磁盘上指针的实际编码格式可能不同。

```text
变量位于库起始位置之后 0x100 字节处。
库加载到 0x1000 → 变量地址为 0x1100。
库加载到 0x5000 → 变量地址为 0x5100。
指向该变量的相关指针必须与本次实际地址一致。
```

**Binding：根据符号确定目标地址，再写入对应的指针位置。** 符号是链接器用来识别函数或变量的名称。典型场景是 App 引用另一个动态库中的函数。App 记录需要该库的 `fetchData`，系统确定函数本次运行的地址，再把地址写入用于访问该函数的位置；后续调用通过写入的地址到达实现，无须每次按名称查找。

两者的区别是：Rebase 已知目标位于本文件的哪里，需要根据加载位置调整；Binding 需要根据符号及依赖信息确定目标。Binding 是动态链接中的地址关联；Objective-C 消息发送则在方法调用时根据接收者查找实现，两者是不同机制。消息发送见[Objective-C 互操作、Selector 与 IMP](../language/swift-objc-runtime.md#objective-c-互操作selector-与-imp)。

地址修正的成本包括读取修正记录、计算或查找目标地址，以及写入需要修正的指针。访问尚未进入内存的数据时，还可能触发存储读取。即使某个业务方法没有执行，只要相关数据需要被加载和修正，就可能产生这部分成本。

现代系统会缓存部分依赖分析与地址查找结果。满足系统版本和二进制格式要求时，系统还可以在数据页被读入内存时完成部分修正；数据页是系统管理内存的固定大小块。因此，每次启动不一定重复全部查找，部分修正也可以在 `main` 之后、数据页被读入时才完成。减少修正数量是否改善首屏耗时，仍取决于这些工作实际发生的时机。

## iOS 包体积优化

### 体积指标与优化顺序

包体积优化的目标是减少用户下载或安装的内容。下载体积是分发时用户需要下载的压缩数据大小；安装体积是应用安装后占用的空间。应用运行后产生的缓存和用户数据应单独统计。

本地归档保存的内容可能包括应用、调试文件及多种设备所需的数据，因此归档目录大小与用户下载体积是两个不同的数值。比较优化前后的结果时，应固定 Release 构建条件和目标设备变体。Release 是通常用于发布的构建配置，具体优化和调试信息行为仍由工程设置决定。

先按资源、可执行文件和随包分发的依赖库分析体积组成，再选择优化项。App Thinning Size Report 是按设备变体列出下载和安装大小估算值的报告；实际分发的大小可结合 App Store Connect 提供的结果核对。

| 优化对象 | 具体做法 | 成立条件与边界 |
| --- | --- | --- |
| 图片、字体、音视频等资源 | 移除无用或重复资源，按显示需求调整分辨率、格式和质量。 | 文件变小后，解码后的内存占用不一定减少；图片内存机制见相关图片笔记。 |
| 功能代码 | 移除已经废弃的功能、已结束实验的旧分支和不再需要的模块。 | 仅在源码中关闭运行时开关不能保证代码不进入产物；若代码原本已被裁剪，删除源码可能没有额外体积收益。 |
| 第三方依赖 | 删除不再使用或功能重复的库，按实际需求选择子模块。 | 收益以最终分发文件为准；只删除源码引用时，独立库文件和附带资源可能仍留在包中。 |
| 编译与链接 | 评估 Swift 的体积优化选项，并启用适用的代码裁剪。 | 编译器改变生成代码的方式；链接器排除不需要保留的代码和数据。两者作用阶段不同。 |
| 资源分发时机 | 让非首次使用必需、且不要求离线可用的资源在需要时下载。 | 这会减少初始包的内容，但仍会产生后续下载量和本地存储占用。首次启动或离线功能必需的资源应满足相应可用性要求。 |

编译优化详见[Swift 编译优化选项与体积](../language/swift-objc-runtime.md#swift-编译优化选项与体积)。链接裁剪条件见[静态库的目标文件提取与代码裁剪](#静态库的目标文件提取与代码裁剪)，独立库的打包边界见[动态库的打包、启动装载与延迟装载](#动态库的打包启动装载与延迟装载)。图片文件大小与内存占用的区别见[iOS 图片加载、解码与内存](../ios/image-loading-decoding-and-memory.md)。

每次调整后，应比较相同设备变体下的下载体积和安装体积，并检查相关功能、资源显示和关键性能。最终包是否缩小，以对比报告中的实际数值为准。

### 符号、调试信息与 dSYM

在编译和链接语境中，符号是用来标识函数、全局变量等程序实体的记录。符号信息可以记录名称、定义位置，或尚需从其他文件取得定义的引用。符号信息只描述程序实体；函数实际执行的机器指令另外保存在代码中。

调试信息描述生成代码与源码之间的对应关系，包括源文件、行号、类型及局部变量等信息。调试器利用这些信息帮助开发者定位执行位置和查看变量；编译优化可能使部分变量或源码位置无法完整还原。

`dSYM` 是独立保存调试信息的文件包。符号化是利用匹配的调试信息，把崩溃记录中的代码地址转换成可读的函数名、源文件和行号。`dSYM` 必须与产生崩溃的二进制文件匹配；UUID 是用于识别并核对这种匹配关系的标识。

常规发布流程会把调试信息单独保存到 `dSYM`，并从发布的可执行文件中剥离可移除的调试信息。`dSYM` 通常保存在开发者或持续集成系统的归档中，不随 App 安装到用户设备。持续集成系统是自动执行构建并保存产物的服务。

因此，删除已经独立保存的 `dSYM` 只会减少开发者一侧的归档存储，不会减少用户的下载体积或安装体积，还会影响崩溃定位。只有实际发布的 App 仍包含可移除的调试或符号信息时，剥离这些内容才可能继续缩小 App。

应保留与发布版本匹配的 `dSYM`，并核对发布产物是否正确剥离。动态链接需要的符号，以及运行时需要的类型或方法描述，在运行时仍会被使用，剥离时必须保留。符号剥离移除的是描述信息；Dead Code Stripping 移除的是不需要保留的代码和数据。

### 资源变体与 App Thinning

资源变体是同一个逻辑资源针对不同设备条件或显示条件提供的不同版本。例如，同名图片可以具有 2x、3x、iPhone、iPad、浅色外观和深色外观等版本。适用条件可以在资源目录 `Assets.xcassets` 中配置。

pt 是界面布局使用的逻辑尺寸单位，px 是图片的像素单位。一张用于显示为 24 × 24 pt 的图片，在 2x 条件下可以提供 48 × 48 px 版本，在 3x 条件下可以提供 72 × 72 px 版本。两个文件表示同一个逻辑图片，只是像素数量不同。

App Thinning 是分发系统针对目标设备减少不必要内容的机制。这里的资源裁剪指：分发系统根据资源声明的适用条件，生成适合目标设备的应用变体，排除已知对该设备不需要的资源版本。

开发者负责提供所需资源变体，并在资源目录中正确标明适用设备、比例和外观等条件。开发者提交完整资源集合；App Store 分发时选择适合设备的内容。开发者通常不需要手工为每个 iPhone 型号分别制作安装包。

只有能确定目标设备不需要的变体，分发系统才可以排除。同一设备运行期间可能切换浅色和深色外观，因此对应的两套资源通常都需要保留，由运行时根据当前外观选择。所有设备共用的资源也需要保留。

App Thinning 只按设备条件选择资源变体，不检查资源是否还被功能使用。业务上无用的资源需要开发者自行查找并删除。开发者应通过相同设备变体的体积报告确认收益。

## 界面预览与 Android 布局预览

界面预览是在开发工具中显示指定视图及其状态，帮助开发者检查布局。Xcode 支持界面预览，但具体页面能否直接预览，取决于界面实现方式、预览入口和项目依赖。

### Xcode 支持哪些方式

| 界面实现方式 | 可视化或预览能力 | 边界 |
| --- | --- | --- |
| Storyboard／XIB | Interface Builder 可以显示和编辑布局。 | 设计时显示的是静态布局，与完整业务流程运行后的界面可能不同。 |
| SwiftUI | 可以在 Xcode Canvas 中预览视图。 | 需要满足视图构造、数据和运行环境要求。 |
| UIKit 纯代码 | 支持通过 #Preview 预览 UIView 和 UIViewController。 | 代码需要能创建并显示目标对象，复杂页面可能依赖业务环境。 |

Canvas 是 Xcode 中展示预览的区域。Xcode 15 引入了直接支持 UIKit／AppKit 的 #Preview 入口。更早的版本可以先用 SwiftUI 包装 UIKit 视图，再预览包装后的 SwiftUI 视图。

### UIKit 页面能够预览的条件

- 预览入口：提供创建目标 UIView 或 UIViewController 的代码，例如 #Preview。只写业务控制器时没有预览入口，需要另外编写 #Preview。
- 构建与运行环境：Xcode、SDK、所选预览运行环境和相关依赖需要相互兼容。Xcode 预览前要先编译相关代码，再运行编译结果来显示界面。
- 视图和布局：目标对象能成功初始化，必要的资源、容器尺寸和布局条件可用。
- 数据和服务：页面需要的参数、显示数据以及实际依赖的服务可用。可以准备真实依赖，也可以注入示例数据或模拟服务，按页面的实际依赖选择即可。

下面是一个不依赖业务服务的示例。导入 SwiftUI 是为了使用预览能力；#Preview 闭包返回的仍是 UIKit 的 UILabel，UILabel 不用改写成 SwiftUI。示例要求使用支持 UIKit #Preview 的 Xcode、SDK 和预览运行环境。

```swift
import UIKit
import SwiftUI

#Preview {
    let label = UILabel()
    label.text = "这是一条示例评论"
    label.numberOfLines = 0
    return label
}
```

预览 API 的可用性和 App 的最低部署版本是两个独立条件。例如 Xcode 15 的 UIKit #Preview 要求预览运行环境为 iOS 17 或更高版本。项目最低支持 iOS 13、Swift Language Version 为 5.0 时，只要预览运行环境满足要求，仍可能使用预览。能否预览以实际工具链和预览诊断为准。

Android 布局编辑器的示例数据，见[Android View、ViewGroup 与 XML 布局](../android/view-system-and-layout.md#android-布局编辑器的示例数据来自哪里)中的同名章节。

## 自动化测试

### 自动化测试与断言

自动化测试把“准备数据 → 执行操作 → 检查结果”写成程序，由工具重复执行。单元测试直接验证函数或状态逻辑；UI 自动化测试通过操作界面验证交互流程。AI 可以帮助生成用例和代码；测试是否通过，由实际执行时的断言结果决定。测试通过只说明被覆盖的场景符合预期，未覆盖的场景仍可能有问题。

下面用“在数组中按 ID 查找评论”演示单元测试：数组包含 A、B、C，查找 B 应返回 B；查找不存在的 D 或查询空数组应返回 nil。示例数据由测试代码构造，不依赖网络接口：

```swift
import XCTest

final class CommentTests: XCTestCase {
    struct Comment {
        let id: String
        let text: String
    }

    func findComment(id: String, in comments: [Comment]) -> Comment? {
        comments.first { $0.id == id }
    }

    func testFindExistingComment() {
        let comments = [
            Comment(id: "A", text: "评论 A"),
            Comment(id: "B", text: "评论 B"),
            Comment(id: "C", text: "评论 C")
        ]
        let result = findComment(id: "B", in: comments)
        XCTAssertEqual(result?.id, "B")
    }

    func testMissingComment() {
        let result = findComment(id: "D", in: [Comment(id: "A", text: "评论 A")])
        XCTAssertNil(result)
    }

    func testEmptyList() {
        XCTAssertNil(findComment(id: "B", in: []))
    }
}
```

`XCTAssertEqual` 检查两值相等，`XCTAssertNil` 检查结果为空；不满足预期就报告失败。若误把查找实现改成无条件返回 `comments.first`，前两项会失败：查 B 却得到 A，查 D 也错误地得到 A。空列表用例仍然通过，因为 `comments.first` 对空数组同样返回 nil；这说明需要用多个用例覆盖不同情况。

测试代码由 XCTest 的测试运行器执行。开发者不用手动进入页面，也不用在 `main.swift`、AppDelegate 或页面里创建测试类并调用测试方法。启动测试后，测试运行器负责创建测试实例、调用符合规则的测试方法、收集断言结果。页面里手动构造数据也可验证逻辑，区别见[页面验证与独立验证](design-patterns.md#独立验证与页面验证)。

### XCTest 与 Swift Testing

| 对比 | XCTest | Swift Testing |
|-|-|-|
| 导入 | `import XCTest` | `import Testing` |
| 测试组织 | 类继承 `XCTestCase` | 可使用结构体、类或独立函数 |
| 标记测试 | 无参数、返回 Void，方法名以 `test` 开头 | 使用 `@Test` 标记函数 |
| 检查预期 | `XCTAssertEqual(a, b)`、`XCTAssertNil(value)` 等 | `#expect(a == b)`、`#expect(value == nil)` 等 |
| 主要适用范围 | 单元、集成、UI、性能测试 | 单元、集成测试 |

二者可以在同一个测试 Target 中共存。新建文件时选项中的 `Language: Swift` 只表示代码语言；继承 `XCTestCase`、使用 `XCTAssert...` 的测试属于 XCTest，与用 Swift 语言编写无关。

### UI 测试与目标 App

`XCTest` 是 Apple 提供的测试框架，支持单元测试、集成测试、UI 测试和性能测试。单元测试调用被测函数并检查结果；UI 测试通过测试运行程序启动或激活 App、查找控件、执行输入，再检查界面状态。UI 测试代码通常在独立的测试运行程序中执行，与被测 App 分属不同进程。

`XCUIApplication` 是 XCTest 中代表某个 App、供 UI 测试查询和控制的对象。创建 `XCUIApplication` 对象不会启动 App，调用 `launch()` 才会启动：

```swift
// 使用 UI 测试目标中配置的目标 App。
let configuredApp = XCUIApplication()

// 显式指定目标 App。
let specifiedApp = XCUIApplication(bundleIdentifier: "com.example.Demo")
specifiedApp.launch()
```

`bundleIdentifier` 使用 App 的应用标识，即用于区分应用的 `CFBundleIdentifier` 值，例如 `com.example.Demo`。显示在主屏幕上的名称可能与应用标识不同。`XCUIApplication()` 使用 UI 测试目标中配置的目标 App，与当前前台显示哪个 App 无关。

`launch()` 启动 App，并在必要时重新启动已经运行的目标 App。需要保留现有运行状态并切到前台时，可使用 `activate()`；需要结束 App 进程时，可使用 `terminate()`。

`XCUIElement` 是 UI 测试中代表一个可查询界面元素的对象。测试按元素类型、标签或无障碍标识定位按钮和输入框，再调用公开 UI 测试方法执行操作。例如，App 已为保存按钮设置 `accessibilityIdentifier = "saveButton"`：

```swift
import XCTest

final class DemoUITests: XCTestCase {
    func testSave() {
        let app = XCUIApplication(bundleIdentifier: "com.example.Demo")
        app.launch()

        let saveButton = app.buttons["saveButton"]
        XCTAssertTrue(saveButton.waitForExistence(timeout: 5))
        saveButton.tap()

        XCTAssertTrue(app.staticTexts["已保存"].waitForExistence(timeout: 5))
    }
}
```

测试先等待按钮出现，再点击按钮，最后检查完成提示。`waitForExistence(timeout:)` 在给定时限内等待元素出现。元素存在时仍可能被遮挡或不可交互；用例要求按钮可点击时，还应检查 `isHittable` 或等待对应的可交互条件。`tap()` 执行完只说明点击已经发出；保存是否成功，要靠最后一步检查“已保存”提示来确认。

### 命令行工具与设备端 Driver

命令行工具（CLI）是接收命令名称和参数并执行工作的程序。设备端 Driver 是运行在设备上、接收自动化请求并调用设备操作能力的程序。这里的 Driver 指自动化执行程序，与硬件驱动无关；Driver 是各工具自己的叫法，Apple 没有规定统一的组件名称。

`ios-use` 是第三方命令行工具。`dom`、`tap`、`swipe`、`input` 等命令名称及参数由工具作者定义。Apple 只提供 XCTest 及相关 UI 测试能力；工具把这些能力组织成自己的请求和执行方式。命令类别可以包括：

| 能力 | 工具命令示例 | 输入或结果 |
| --- | --- | --- |
| 读取界面 | `dom` | 返回可访问元素的名称、类型、状态和区域 |
| 模拟操作 | `tap`、`longpress`、`swipe` | 根据元素或坐标执行点击、长按或滑动 |
| 输入文字 | `input` | 向选定的可输入控件传入文本 |
| 管理 App | `activateApp`、`terminateApp` | 使用应用标识激活或结束指定 App |
| 获取画面 | `screenshot` | 返回屏幕截图 |
| 系统操作 | `home`、`dismissAlert` | 返回主屏幕或按命令约定关闭弹窗 |

各命令的具体参数和支持范围取决于工具版本。表中的名称是工具命令，与 XCTest 的方法名是两套名称。

采用设备端 Driver 的 UI 操作链路通常为：

```text
AI 读取界面并选择动作
    → 电脑上的 CLI 解析命令与参数
    → CLI 将请求编码并通过设备连接发送
    → 设备端 Driver 解析请求并选择处理方法
    → Driver 查询元素或调用测试能力执行操作
    → Driver 返回结果
    → AI 再次观察界面并检查预期结果
```

例如，电脑执行 `tap` 命令后，CLI 先把目标元素或坐标编码成请求，再发送给 iPhone 上的 Driver。Driver 收到请求后解析操作类型，再调用设备上的 UI 测试能力。系统最终将输入事件交给前台 App，App 按正常事件处理流程响应。

命令与 Apple API 不一定一一对应。某个工具可能按标签查找元素后调用 `XCUIElement.tap()`，也可能先取得区域、计算坐标，再合成按下和松开的输入事件。滑动可以通过坐标拖动能力实现。使用私有测试接口的工具还受系统和工具版本约束；私有接口属于特定版本的内部实现，Apple 不把私有接口作为公开 API 提供。

部分 App 管理或设备管理命令可以由电脑直接调用设备服务，不一定经过 Driver。选择设备与选择 App 也是不同操作：建立连接只确定操作哪台设备；App 管理请求还需应用标识；后续 UI 操作作用于哪个 App，由工具的查询策略和当前前台状态决定。

### 无障碍快照与截图

无障碍信息是 App 向系统暴露的界面元素名称、类型、状态和操作语义。自动化工具可以读取某一时刻的元素快照，用这些信息定位控件。

工具命令 `dom` 返回的结果通常是根据无障碍快照组织的元素树。这棵元素树与网页 DOM 无关，也只包含 `UIView` 层级中暴露为无障碍元素的部分。装饰视图可能不暴露为独立元素，多个子视图也可能合并为一个无障碍元素。自绘界面缺少元素信息时，可以用截图和坐标补充操作，但需要考虑屏幕尺寸与布局变化。

元素快照和截图都只反映获取时的界面状态。列表刷新、弹窗出现或页面切换后，应重新查询，避免使用过期元素信息和坐标。AI 怎样把操作结果转成验收证据，见 [AI 辅助验收](../ai/development-review-and-verification.md#ai-辅助验收)。

### 创建和运行 XCTestCase

1. 在 Xcode 的 `File → New → Target` 中选择对应平台的 `Unit Testing Bundle`。已有单元测试 Target 时直接复用。测试是否需要关联宿主 App，按[宿主与运行环境](#宿主-app运行环境与构建范围)判断。
2. 用 `File → New → New File From Template → XCTest Unit Test` 创建文件。配置页 `Class` 填 `CommentTests`（不加 `.swift`），`Subclass of` 保持 `XCTestCase`，`Language` 选 Swift；类名填好后再点击 Next。
3. 保存时选择测试 Target。对已有文件，在 File Inspector 的 `Target Membership` 确认归属。文件是否参与测试构建由 `Target Membership` 决定，与所在文件夹的名称无关。
4. 让一个 Scheme 的 Test 操作包含这个测试 Target，或关联包含它的测试计划；具体关系见[Scheme 与测试计划](#scheme-与测试计划)。
5. 选择适用的运行目的地。macOS 测试可以选择 `My Mac`；iOS 测试选择适用的设备或模拟器。点击测试方法左侧菱形里的播放按钮运行单项；`Product → Test` 执行当前配置选中的测试。运行器会编译所需代码并执行测试，绿色／红色表示通过／失败，失败时查看对应断言信息。

被测代码若和测试文件一起编译进测试 Target，可以直接调用。若来自另外一个 Swift 模块，则导入实际模块名；访问其 internal 成员时，需要该模块启用 `Enable Testability`，并使用 `@testable import 模块名`。`@testable` 只开放 internal 成员，private 成员仍不可见；目标依赖和链接仍需单独配置。被测算法位于命令行可执行 Target 时，可以把算法源文件直接加入测试 Target，测试代码就无需导入那个可执行模块。

### Scheme 与测试计划

Scheme 是构建、运行、测试等操作的执行方案。Scheme 和 Target 是不同概念：Scheme 决定执行哪些操作、使用什么配置；Target 决定构建什么。两者的名称经常相同。

| Scheme 中的配置 | 作用或例子 |
|-|-|
| Build 中的 Target 列表及操作勾选 | 指定哪些 Target 参与 Run、Test、Archive 等操作 |
| 各操作的 Build Configuration | 例如 Test 使用 Debug，采用各 Target 对应的构建设置 |
| Run 的 Executable | 例如构建后启动 DemoApp.app |
| 调试器、启动参数和环境变量 | 是否连接调试器，以及向运行进程传入哪些值 |
| Test 中的测试目标或测试计划 | 决定测试操作要执行哪些测试 |

测试计划通常保存为 `.xctestplan`，集中选择测试 Target、测试类、方法，并保存一套或多套测试配置。其常见选项包括：

| 测试计划选项 | 用途 |
|-|-|
| 语言、地区 | 验证中文／英文等环境下的表现 |
| 启动参数、环境变量 | 向被测进程传值；自定义值需要相应代码读取和处理，不会自动模拟网络错误等行为 |
| 执行顺序、重复方式、超时 | 检查顺序依赖、偶发问题和超时 |
| 诊断检查 | 例如 Address Sanitizer、Thread Sanitizer、Main Thread Checker |
| 代码覆盖率 | 记录测试实际执行过的代码范围 |

例如同一套界面测试可在“中文＋中国地区”和“英文＋美国地区”两套配置下分别执行。测试计划中的配置与 Debug／Release 构建配置是两回事；部分运行参数既可以写在测试计划中，也可以写在 Scheme 中。测试计划是可选的，Scheme 也可以直接列出测试 Target。

### 宿主 App、运行环境与构建范围

**宿主 App** 是承载单元测试运行的 App。使用宿主的 XCTest 单元测试，会先准备并启动宿主 App，再将测试包加载到它的进程里，由 XCTest 执行测试；这个过程中开发者同样不用在 App 入口创建测试类。无宿主的测试配置由系统测试运行器承载，例如独立的 macOS 算法测试。以上进程关系只适用于单元测试；UI 测试的代码运行在独立的测试运行程序中，与被测 App 分属不同进程。

**运行环境** 是代码执行时已经具备的系统能力、服务和状态。例如“加载当前用户评论”可能依赖登录用户 ID、配置好的网络服务、已打开的缓存数据库。App 启动可能初始化其中一些服务，测试也可以自行初始化或注入模拟对象；是否需要宿主，取决于真实依赖和平台／测试工具支持。

`twoSum([2, 7, 11, 15], 9)` 只依赖输入值；前面的评论查找示例也使用测试自己构造的数组。因此这两个例子都不需要宿主 App。**宿主 App 只承载测试运行，测试数据从哪里来由测试代码决定，**可以是构造值、文件、Mock 或真实接口。

点击某个测试方法的菱形，只限定执行哪项测试。构建阶段仍要编译测试 Target、所需依赖，以及 Scheme 中为 Test 启用的其他目标，编译范围比被点击的函数大得多。

## Swift 第三方库与依赖接入

UIKit 是 Apple 官方界面框架，不属于第三方库。SnapKit 是第三方布局库。其他常见第三方库按职责分别记录在以下笔记中：

- [Alamofire：请求与响应模型](../network-and-storage/network-and-proxy.md#alamofire请求与响应模型)：获取用户资料、提交表单和上传文件。
- [Kingfisher：网络图片与占位图](../ios/image-loading-decoding-and-memory.md#kingfisher网络图片与占位图)：头像、商品图片和列表封面的加载与缓存。
- [RxSwift：输入组合与按钮状态绑定](../ios/reactive-programming.md#rxswift输入组合与按钮状态绑定)：表单校验、搜索输入和多个控件联动。

Swift Package Manager 是 Swift 的包与依赖管理工具。在 Xcode 中添加库的包依赖，填写所选库的仓库地址，选择兼容项目工具链和最低系统版本的版本，再把需要的库产品添加到 App 目标。目标及模块的含义见 [Target、模块与构建产物](#target模块与构建产物)。

Alamofire 示例需要 Alamofire 产品，Kingfisher 示例需要 Kingfisher 产品。RxSwift 的 UIKit 示例需要同时添加 RxSwift 和 RxCocoa 产品，然后在源文件中使用对应的 import。依赖由 Swift Package Manager 下载和集成；`import` 只在源文件中导入已经集成的模块。
