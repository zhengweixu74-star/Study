## 进程与线程

进程是操作系统为运行程序创建的运行实例，拥有相应的地址空间和资源。线程是进程中由内核安排执行的单位。一个进程可以包含多个线程；CPU 实际执行的是被调度线程的指令。

同一进程中的线程共享进程地址空间和资源。每条线程有自己的栈与执行上下文；线程切换需要保存和恢复相应状态，不能把保存的上下文等同于永久独占一组物理寄存器。

### 内核的职责与进程信息

内核是操作系统中负责管理硬件资源、进程和访问权限的核心程序。内核是软件，CPU 和内存是硬件；内核在 App 启动之前就已经运行。

- 进程管理：维护进程及其编号、创建时间等信息。
- CPU 调度：从可以运行的线程中选择线程，为线程安排 CPU 执行机会。
- 内存管理：维护进程的地址空间与访问边界，防止进程随意访问其他进程的内存。
- 资源访问控制：检查程序对受保护资源的访问权限。

App 可以通过系统接口查询内核允许提供的信息。查询操作发生在 App 运行期间，但查询结果可以包含更早发生的事件，例如进程创建时间。

### CPU 核心、逻辑 CPU 与并行上限

物理核心是 CPU 内部能够执行指令的硬件单元。逻辑 CPU 是操作系统能够独立调度线程的硬件执行上下文。一个物理核心可以提供一个或多个逻辑 CPU，具体取决于硬件能力和启用配置。

在操作系统调度层面，如果设备有 L 个可用的逻辑 CPU，那么同一时刻最多可以让 L 个软件线程处于执行状态。这是线程数量的上限，不是系统中允许存在的进程数量；这些线程可以属于同一个进程，也可以属于不同进程。

假设设备有 4 个物理核心，每个核心只提供一个逻辑 CPU，且 4 个逻辑 CPU 均可用。同一时刻可以出现以下分配：

| 线程分配 | 正在执行代码的进程数量 | 正在执行的线程数量 |
| --- | --- | --- |
| 4 个进程各执行 1 个线程 | 4 个 | 4 个 |
| 2 个进程各执行 2 个线程 | 2 个 | 4 个 |
| 1 个进程执行 4 个线程 | 1 个 | 4 个 |

超线程是 Intel 对同时多线程技术的一种实现。启用相应能力时，一个物理核心可以向操作系统提供两个逻辑 CPU。因此，讨论线程并行上限时应看逻辑 CPU 数量。逻辑 CPU 仍共享所在物理核心的执行资源，数量翻倍不代表性能翻倍。

### 并发、并行与等待

并发表示多个任务在同一段时间内推进；并行表示多个任务在同一时刻执行。并发可以通过交替执行实现，也可以包含并行执行。单个逻辑 CPU 可以通过线程切换推进多个任务，但不能同时执行多个软件线程。

系统中可以存在远多于逻辑 CPU 数量的进程和线程。就绪线程具备运行条件，但可能尚未获得 CPU；阻塞线程正在等待网络、文件或其他事件满足继续执行的条件。内核按调度策略选择就绪线程执行，不保证所有线程获得相同的执行时间。

创建更多线程不会增加硬件执行位置。线程数量超过可用逻辑 CPU 数量时，部分线程需要等待调度；如果线程正在阻塞等待，内核可以让其他就绪线程使用 CPU。

## GCD 的任务、队列与提交方式

GCD（Grand Central Dispatch）是 Apple 提供的任务调度机制，libdispatch 是其主要实现库。任务是需要执行的工作，队列规定任务如何安排，线程负责执行代码。队列不是线程；普通队列通常不绑定某条固定线程。

| 概念 | 对执行的约束 |
| --- | --- |
| sync 同步提交 | 调用方等待闭包执行完成后，调用才返回 |
| async 异步提交 | 调用方提交闭包，不等待闭包执行完成 |
| 串行队列 | 同一时刻最多执行队列中的一个任务 |
| 并发队列 | 允许多个任务重叠执行，不保证一定同时执行 |
| 主队列 | 特殊的串行队列，任务始终在主线程执行 |

同步／异步和串行／并发描述不同维度。DispatchQueue.async 是提交闭包的方法，不是 Swift 并发中声明异步函数的 async 关键字。主队列 async 也不保证任务一定到下一轮 RunLoop 才执行。

```swift
import Foundation

let serialQueue = DispatchQueue(label: "example.serial")
let concurrentQueue = DispatchQueue(
    label: "example.concurrent",
    attributes: .concurrent
)
```

### sync 的执行机制

```swift
print("A")
serialQueue.sync {
    print("B")
}
print("C")
// 顺序固定为 A → B → C
```

libdispatch 检查队列是否允许任务执行。条件满足时，同步路径可以在当前调用线程直接执行闭包，避免线程切换。条件不满足时，调用线程需要等待；之后任务可能由调用线程执行，也可能由目标线程执行。提交给主队列的任务必须由主线程执行。具体内部函数和等待方式随系统实现变化，不能把 sync 简化为固定的某一种锁或信号量实现。

sync 不等于“切换到目标队列对应的线程”。主线程同步提交耗时任务到普通队列，闭包可能就在主线程执行；即使闭包在其他线程执行，主线程仍要等待，因此仍会影响界面响应。

sync 等待的是闭包执行结束。如果闭包只是启动异步网络请求，闭包返回时网络请求可能仍未完成，sync 不会自动等待网络响应。

### async 的执行机制

```swift
print("A")
serialQueue.async {
    print("B")
}
print("C")
// A 最先输出，B 与 C 的先后没有保证
```

GCD 保存闭包及其捕获内容，将任务交给队列调度。普通队列通常使用系统管理的工作线程，系统可以复用线程；每次 async 不一定创建新线程。主队列中的异步任务仍由主线程执行。

目标队列具备执行条件时，任务可能在 async 返回前开始，调用方后续代码与异步任务之间没有自动建立完成先后关系。异步提交不会抢占当前调用栈；上例的 B 与 C 不确定，是因为 B 可以在另一线程执行。

### 死锁、直接崩溃与系统终止

死锁是任务因循环等待而无法继续执行的状态。死锁不等于一定立即崩溃：libdispatch 能检测部分错误并直接终止进程；未被检测的等待可能持续存在。如果主线程长时间无法完成系统要求的工作，还可能触发 watchdog 终止。watchdog 是系统监控应用是否及时完成必要工作的机制。

在主线程同步提交到主队列，会等待只能由当前主线程执行的任务，形成自我等待：

```swift
// 错误示例：当前在主线程执行
DispatchQueue.main.sync {
    print("任务")
}
```

串行队列中的任务同步提交到同一队列，同样无法推进。外层任务等待内层任务结束，内层任务又必须等外层任务让出串行队列：

```swift
let queue = DispatchQueue(label: "example.serial")
queue.async {
    queue.sync {
        print("内层任务")
    }
}
```

libdispatch 检测到当前线程已持有目标队列时，可能主动触发崩溃。相关诊断信息可能包含“dispatch_sync called on queue already owned by current thread”；具体崩溃位置和表现取决于系统版本与执行路径。

不同串行队列也可能形成循环等待，不能只检查队列名称是否相同：

```swift
let queueA = DispatchQueue(label: "example.a")
let queueB = DispatchQueue(label: "example.b")
queueA.async {
    queueB.sync {
        queueA.sync {
            print("无法执行到这里")
        }
    }
}
```

A 的外层任务等待 B，B 等待 A 的内层任务，A 的内层任务又等待 A 的外层任务结束。实现可能检测并终止，也可能持续等待。不能把“同步提交到同一串行队列必然有问题”直接推广成“所有同一并发队列的普通 sync 都必然以相同方式死锁”；判断依据是实际执行约束和等待关系。

async 也不能保证整个流程无死锁。例如主线程异步提交后台任务后，用信号量等待结果；后台任务又同步提交到主队列。信号量是可让线程等待其他任务发出信号的同步工具，此时双方仍然无法推进。

### 数据竞争、对象生命周期与 UI 线程要求

数据竞争是多个线程未经正确协调访问同一内存，且至少一个线程写入。多个并发任务修改同一个共享数组变量，可能造成结果错误、内存损坏或崩溃；Array 的值语义不保证同一个变量可以被并发修改。

sync 只要求当前调用方等待，不会自动让并发队列中的任务互斥。不同线程各自向同一并发队列调用 sync，闭包仍可能重叠执行。串行队列保护共享数据的成立条件见下文“i++ 的执行过程与线程安全”，不另维护一套访问规则。

异步闭包还需要满足捕获对象和内存的生命周期要求。默认强捕获可以保持对象存活；unowned 不保持对象存活，对象释放后再经 unowned 访问会触发运行时错误。weak 在对象释放后变成 nil，但对 nil 强制解包仍会崩溃。复制 UnsafePointer 等指针值，不会自动延长其指向内存的有效期，释放后解引用可能造成非法内存访问。

在后台任务中调用要求主线程执行的 UIKit API，可能造成显示异常、数据损坏或崩溃，并非每次立即崩溃。应用应把这些 UI 操作安排到主线程。Thread Sanitizer 用于发现数据竞争，Address Sanitizer 用于发现释放后访问等内存错误，Main Thread Checker 用于检查系统 API 的主线程要求。

## Operation 与 OperationQueue

OperationQueue 是 Foundation 提供的任务调度队列。应用把需要执行的工作封装成 Operation，队列根据任务是否就绪、优先级和并发限制安排执行。Operation 表示一个任务，OperationQueue 负责管理多个任务。

BlockOperation 是用闭包封装工作的 Operation 子类。普通同步任务可以直接使用 BlockOperation；需要自定义执行状态或异步生命周期时，才需要进一步封装。OperationQueue 不是线程本身，也不表示每加入一个任务就创建一条线程。

### 并发限制、依赖与执行顺序

`maxConcurrentOperationCount` 限制队列同时处于执行状态的 Operation 数量。例如设为 2，队列最多同时执行两个 Operation，其余任务等待。这个值不是系统线程数，也不是 CPU 核心数。

设为 1 可以让队列同一时刻只执行一个 Operation，但不能把它当作无条件按提交顺序执行的 FIFO 队列。任务是否就绪、任务之间的依赖和优先级会影响选择顺序。queuePriority 影响就绪任务之间的调度，不会让高优先级任务抢占已经开始的任务。

通过 taskB.addDependency(taskA) 可以让 taskB 等待 taskA 完成。依赖只表达完成先后，不保证 taskA 成功，也不会自动传递结果或错误。taskB 是否继续执行，需要应用根据结果决定。

通常创建的 OperationQueue 用于在后台执行工作。OperationQueue.main 把任务安排在主线程执行。图片计算可以在后台队列完成，UIKit 视图更新应回到主线程。

### 最小使用示例

```swift
import Foundation

let queue = OperationQueue()
queue.maxConcurrentOperationCount = 2

let taskA = BlockOperation {
    print("执行任务 A")
}
let taskB = BlockOperation {
    print("执行任务 B")
}

queue.addOperations([taskA, taskB], waitUntilFinished: false)
```

上例创建两个同步任务，并允许队列同时执行最多两个任务。waitUntilFinished 为 false 表示提交方不等待全部任务完成；A 和 B 的打印顺序没有保证。闭包执行结束后，对应的同步任务完成。

### 取消是协作式的

`cancel()` 主要设置 Operation 的取消状态。协作式取消表示执行代码需要检查取消状态，并在能够停止的位置主动结束；取消不会强制中断正在运行的线程或任意函数。

标准 Operation 在开始工作前发现已经取消时，会跳过工作并结束。任务已经开始后，需要在耗时步骤之前以及步骤之间检查 isCancelled。同步解码函数内部没有取消入口时，只能等待函数返回，再停止后续工作或丢弃过期结果。自定义 Operation 必须正确维护自己的结束状态。

已经加入 OperationQueue 的任务不能直接从队列移除。应用可以取消指定任务，或者用 cancelAllOperations() 请求取消全部任务；队列仍会保留相关任务，直到任务结束。

### 异步下载不能只套普通闭包限流

在普通 BlockOperation 中调用 URLSessionTask.resume() 后，闭包通常很快返回，但网络下载仍在进行。BlockOperation 此时已经完成，OperationQueue 会继续启动下一个任务。因此，单靠这层包装的 maxConcurrentOperationCount 不能限制实际进行中的下载数量。

要限制下载并发，可以让图片加载器维护正在执行的下载数量和待调度请求，在网络完成回调中释放名额；也可以使用正确实现异步状态的 Operation，在网络任务真正结束后才设置完成状态。下载取消仍需等待实际结束，不能立即释放名额。

下载与解码分别限流、预取需求和取消流程见[长列表图片任务调度](image-loading-decoding-and-memory.md#长列表图片任务调度)。

## i++ 的执行过程与线程安全

本节用 `i++` 表示普通整数自增的伪代码。多个线程操作同一个共享变量时，普通自增不能默认视为原子操作。原子操作是相对于其他并发访问不可分割的操作。

自增的逻辑过程是“读取旧值 → 计算旧值加 1 → 写回新值”。以显式加载和存储的 CPU 执行方式为例，CPU 把变量读入寄存器，完成加法，再写回对应地址。寄存器是 CPU 内部供指令直接使用的存储位置。读取可能命中 CPU 缓存，写入也可能先更新缓存，不代表每次都立即访问或写回物理内存。

三个逻辑步骤不等于固定三条机器指令。CPU 架构和编译优化会影响具体指令，变量也可能暂存在寄存器中。即使某条指令能够完成内存自增，也不能仅凭“只有一条指令”认定具有跨线程原子性。

**丢失更新示例：**初始值为 0。线程 A 和 B 都读取 0，分别计算得到 1，然后各自写回 1，最终只体现一次增量。这个交错示意用于说明风险；具体语言对数据竞争的后果还有自己的规定，不能把实际结果限定为 1 或 2。

| 线程安全方式 | 保证条件 |
|-|-|
| 互斥锁 | 同一把锁保护完整的读取、计算、写回过程；其他可能并发的读写也遵守同一保护约定 |
| 原子自增 | 使用语言或库提供的原子读改写操作；分别执行原子读取和原子写入，不能保证整个自增原子化 |
| 串行队列 | 把相关访问统一提交到同一个串行队列，不能在队列外直接并发读写同一变量 |

独立计数可以使用原子自增；需要同时保持多个关联字段的一致性时，锁或串行隔离更容易表达整体约束。检查最终计数前，还需要等待两个自增任务完成。线程安全与任务已经完成是两个不同条件。

## CAS 的机制、重试与 ABA

CAS 是原子地比较并按条件更新共享值的操作。调用方提供目标位置、期望值和新值。当前值等于期望值时，CAS 写入新值并报告成功；不相等时，不写入新值并报告失败。比较与条件写入作为一个不可分割的操作完成。

例如，A、B 都通过原子读取获得 0。A 用 CAS 把 0 更新为 1 并成功；B 仍以 0 为期望值时失败。B 重新获得当前值 1，计算新值 2，再尝试 CAS；期间若发生其他竞争，仍可能失败，需要按算法继续重试。

CAS 只负责一次比较与更新，重试循环由调用方算法实现。普通 `if 当前值 == 期望值` 再赋值不是 CAS，因为检查与赋值之间可能插入其他线程的修改。应使用语言或库提供的原子 API。

**ABA 问题：**值从 A 变成 B，再变回 A，CAS 只比较当前值，无法发现中间变化。如果算法关心变化历史，可以把版本号与值一起参与同一次原子比较更新，并处理版本号回绕等适用边界。竞争激烈时，重复失败和重试会消耗 CPU；是否无锁还取决于原子 API 的实现与整体算法。

## 常见锁与分类维度

锁的名称可能描述不同维度。互斥描述同一时刻允许谁访问；自旋描述竞争时如何等待；可重入描述同一线程能否再次获取自己已经持有的锁。

| 类型 | 行为 | 条件与代价 |
|-|-|-|
| 互斥锁 | 同一时刻只允许一个持有者访问受保护区域 | 适合共享可变状态；具体实现可能先短暂自旋，再阻塞等待 |
| 自旋锁 | 获取失败时持续尝试，等待期间占用 CPU | 等待极短时可能减少休眠与唤醒开销；长时间等待会浪费 CPU |
| 读写锁 | 多个读者可同时持有读锁，写锁与其他读写锁互斥 | 读多写少时可能受益，实际效果取决于锁开销与竞争程度 |
| 递归锁／可重入锁 | 同一线程可以重复获取自己持有的锁 | 每次成功获取都需要对应释放，计数归零才完全解锁 |

自旋锁和递归锁都可以提供互斥访问。乐观与悲观主要描述并发控制策略：悲观策略通常先加锁再访问受保护数据；乐观策略先读取和计算，提交更新时检查冲突，再根据结果重试或失败。CAS 可用于实现乐观并发控制，但 CAS 本身不是一套完整的乐观锁方案。

### 获取锁失败后的等待行为

锁被其他线程持有时，调用方如何继续，取决于使用的获取接口和锁的实现。不能仅凭“非自旋锁”这个名称判断接口一定阻塞。

| 获取方式 | 无法立即获取锁时的行为 | 适用场景 |
| --- | --- | --- |
| 阻塞式获取 | 调用暂不返回，线程按锁的实现等待，成功获取后继续执行 | 当前操作必须取得锁才能继续 |
| 尝试获取（try-lock） | 立即返回失败，调用方决定跳过、稍后重试或执行其他工作 | 不希望当前线程等待 |
| 带超时的获取 | 在约定期限内等待；成功获取或等待超时后返回 | 允许等待，但需要限制等待时间 |

对于会让线程休眠的阻塞式互斥锁，可以按以下顺序理解：线程 B 尝试获取线程 A 持有的锁 → B 进入等待 → A 释放锁 → 锁的实现唤醒符合条件的等待线程 → 被唤醒线程获得调度后继续获取锁。

阻塞等待期间，线程不会持续执行轮询指令来占用 CPU。具体实现仍可能在阻塞前短暂自旋。被唤醒不等于已经获得锁；锁的转交和竞争规则由具体实现决定。调用方应以获取接口成功返回作为进入受保护区域的依据。

线程从阻塞状态恢复到可运行状态后，也可能需要等待 CPU 调度。因此，“锁已释放”“线程已唤醒”和“线程开始执行受保护代码”是不同的时刻。

### 自旋等待、内核态与线程阻塞

纯用户态自旋锁通过原子操作反复尝试获取锁，获取和等待本身不要求系统调用。原子操作是相对于其他并发访问不可分割的操作；CPU 可以直接执行相应指令，原子操作不等于进入内核。

用户态和内核态是 CPU 执行代码时的权限级别。用户态代码受到资源访问限制；内核态代码可以执行受操作系统保护的操作。系统调用是应用请求内核服务的入口，调用时可以由同一条线程进入内核执行代码，再返回用户态。

进入内核态不等于线程被挂起。线程阻塞表示线程暂时不能继续运行，需要等待某个条件满足。线程切换表示调度器停止执行当前线程，改为执行另一条线程。这三个动作不是同一件事；一次不需要等待的系统调用可以进入内核并返回，而不阻塞当前线程，也不切换线程。

| 等待方式 | 等待线程做什么 | CPU 使用与调度 |
| --- | --- | --- |
| 自旋等待 | 持续检查锁状态或重试原子操作 | 线程获得执行机会时持续消耗 CPU |
| 让出执行机会 | 调用调度接口，允许调度器安排其他线程 | 不等于已经进入等待锁释放的阻塞状态，也不保证锁持有者马上执行 |
| 阻塞等待 | 通过锁或等待接口等待条件满足 | 等待期间不持续轮询；条件满足并恢复可运行状态后，仍需等待调度 |

“循环等待”只描述重复执行，不能单独确定是否进入内核。纯原子操作循环可以留在用户态；循环中调用休眠、调度或阻塞等待接口时，可能进入内核。实际锁也可能先短暂自旋，再转为阻塞。即使自旋代码没有系统调用，运行期间仍可能发生中断或被抢占，不能据此断言 CPU 始终处于用户态。

### 优先级反转与优先级继承

优先级反转是高优先级线程等待低优先级线程持有的资源，导致高优先级线程无法按其优先级及时推进的现象。互斥锁用于限制同一时刻只有一个持有者访问受保护的数据；等待被占用的阻塞式互斥锁时，线程暂时不具备继续执行的条件。

设单个逻辑 CPU 上运行 H、M、L 三条线程，优先级满足 H > M > L，并使用按优先级抢占的调度策略。L 先持有一把锁；H 随后尝试获取同一把锁并阻塞；此时 M 变为就绪并获得 CPU。M 虽然不需要这把锁，却可以持续延迟 L 的执行，进而延迟 L 解锁和 H 恢复。

H 的优先级最高，也不能在等待锁期间直接执行后续受保护代码。调度器只能从具备运行条件的线程中选择执行者；提高 H 自身的优先级并不能让 L 自动释放锁。

优先级继承是一种缓解机制：支持该机制的锁会在高优先级线程等待时，临时提高锁持有者的有效调度优先级。上述 L 可以临时继承 H 的优先级，优先于 M 执行完受保护代码并释放锁，使 H 获得继续运行的条件。

释放锁后，如果 L 不再受到其他等待关系的优先级提升，L 会恢复原有优先级。优先级继承不能让受保护代码瞬间完成，也不能自动解决死锁。是否支持继承取决于锁和调度机制，不能把所有互斥锁都视为自动支持。

## RunLoop 与运行模式

RunLoop 是在线程上等待并分发事件的循环。UIKit 应用由框架配置并运行主线程 RunLoop；工作线程是否启动 RunLoop，取决于该线程是否需要接收相应事件。RunLoop 在需要等待未来事件时可以让线程休眠；当前模式没有可处理的输入源或 Timer、达到运行期限或收到停止请求时，RunLoop 的本次运行可以结束。耗时回调会占用所属线程，延迟后续事件。

`default` 是一个具体运行模式。`common` 是向一组被标记为 common 的模式注册任务的标记，不是一个独立运行模式，也不代表同时运行多个 mode。RunLoop 的某次运行使用一个具体 mode，处理该 mode 中符合条件的 source、timer 等。

主线程滚动跟踪通常涉及 tracking mode。任务只注册 default 时，在 tracking 期间可能暂停回调；注册 common 可以让它在属于 common 集合的相关模式中被处理。common 不是所有模式，也不会切到其他线程，更不能保证主线程繁忙时准时回调。

### Source0 与 Source1：事件来源、数量与回调

输入源（source）是加入 RunLoop 的事件处理对象。输入源关联事件就绪机制与处理回调。Source0 和 Source1 是 CFRunLoopSource 的两种版本；数字不表示优先级，也不表示先后执行顺序。

| 比较项 | Source0 | Source1（Apple 平台的 Mach 端口源） |
|-|-|-|
| 创建时的版本 | version = 0 | version = 1 |
| 事件就绪方式 | 调用方或框架手动标记 source | 对应 Mach 端口收到消息 |
| 等待中的线程如何被唤醒 | Signal 本身不唤醒；需要及时处理时，再唤醒目标 RunLoop | 端口消息使内核中相关的等待满足唤醒条件 |
| 回调由谁执行 | 正在运行且当前模式包含该 source 的 RunLoop，在所属线程执行 | RunLoop 收到对应端口消息后，在所属线程执行 source 的回调 |
| CFRunLoopSourceSignal 的效果 | 标记指定的 Source0 为待处理 | 不用于触发 Source1，对 Source1 无效 |

一个 RunLoop 可以注册多个 Source0 和多个 Source1，也可以没有某一类 source。API 没有规定统一的固定数量，实际受内存、端口等资源限制。一个运行模式可以包含多个 source；同一个 source 可以加入多个模式，在同一模式重复添加同一个 source 不会增加一个副本。

CFRunLoopSourceSignal(refreshSource) 只标记 refreshSource，不会标记该 RunLoop 的其他 Source0。source 必须有效，并且加入当前运行模式，RunLoop 才能按条件处理它。Timer 是另一类 RunLoop 对象，不属于 Source0 或 Source1。

回调在创建输入源时配置。Source0 的 CFRunLoopSourceContext 中，version 为 0，perform 保存处理回调。Source1 使用 CFRunLoopSourceContext1，其中 getPort 提供端口，perform 处理收到的消息。通过 CFMachPort 创建 source 时，框架负责内部转发，再调用创建 CFMachPort 时注册的回调。

发送事件时不需要把回调函数随消息重新发送。发送方提供就绪信号或消息；RunLoop 查找已注册的 source，再调用 source 对应的处理函数。回调运行在哪条线程，取决于负责处理事件的 RunLoop 所在线程。

### Source0 示例：后台压缩完成后刷新预览

示例目标：后台线程压缩图片，完成后通知主线程刷新预览。主线程预先创建 refreshSource，把刷新逻辑配置为 perform 回调，并把 refreshSource 加入主线程 RunLoop 的相关模式。以下只展示触发端，省略 source 创建、图片数据保存与同步、销毁清理；不是完整可运行程序。

`// 后台任务已完成，refreshSource 已注册到主线程 RunLoop``
``CFRunLoopSourceSignal(refreshSource)``
``CFRunLoopWakeUp(CFRunLoopGetMain())`

1. 后台线程先安全保存压缩结果，再调用 CFRunLoopSourceSignal(refreshSource)，把这个 Source0 标记为待处理。
2. 后台线程调用 CFRunLoopWakeUp(CFRunLoopGetMain())。主线程若正在等待，可以恢复运行；主线程若正在执行其他代码，这个调用不会打断当前回调。
3. 主线程 RunLoop 到达处理 Source0 的阶段，且当前模式包含 refreshSource 时，调用已注册的 perform 回调。
4. perform 回调读取压缩结果，并在主线程刷新预览。

Signal 不会立即执行 perform，也不会自动把业务数据送到回调。Source0 的就绪标记不是消息计数器：处理前连续多次 Signal，不能假设得到相同次数的回调。需要保留每项任务时，应另行保存任务数据，并对跨线程访问进行同步。

Swift 可以显式调用这些 C 接口。这里包括 Core Foundation 提供的 CFRunLoopSourceSignal 和 CFRunLoopWakeUp。通用原理见[Swift 与 C 接口互操作](../language/swift-basics.md#swift-与-c-接口互操作)。只有应用自行管理自定义 Source0 时，才需要在相应触发代码中显式标记；使用已经封装好的框架能力时，框架可能负责标记和唤醒。CFRunLoopWakeUp 应针对负责处理该 source 的目标 RunLoop，不能不加区分地唤醒发送线程自己的 RunLoop。

### Source1 示例：通过 Mach 端口接收完成消息

Mach 端口是内核管理的消息通信端点。发送方持有相应发送权限，接收方持有接收权限；内核把发送到端口的消息交给接收方。这里的端口不是 TCP/UDP 端口号。消息包含头部和消息体，头部记录接收目标、消息编号等信息。

沿用“后台压缩完成后刷新预览”的场景。主线程创建 CFMachPort，并注册接收回调；再通过 CFMachPortCreateRunLoopSource 创建与该端口关联的 Source1，加入主线程 RunLoop。以下描述事件链路，用于说明机制，不是完整 Mach 通信实现。

1. 主线程 RunLoop 在相关模式中等待消息。
2. 后台线程完成压缩，按双方约定向端口发送 Mach 消息，例如把 msgh_id 设置为 1001，表示压缩完成。
3. 消息到达端口后，内核使等待相关端口消息的线程满足唤醒条件。主线程实际何时继续运行，还取决于线程调度。
4. 主线程 RunLoop 根据收到消息的端口定位 Source1，再调用对应回调。回调解释消息编号及数据，最后刷新预览。

此链路不通过 CFRunLoopSourceSignal 触发 Source1，也不要求发送方再手动调用 CFRunLoopWakeUp。内核负责消息传递与唤醒条件；业务回调由主线程上的 RunLoop 执行。如果主线程繁忙或当前模式不包含该 source，回调仍可能延迟。

消息编号属于消息头，不属于 Source1。每条 Mach 消息的 mach_msg_header_t 都有 msgh_id 字段；1001 只是本例约定，不是系统统一编号，也不是每个 Source1 独有的编号。其含义由发送方与接收方的协议决定，消息传输机制不解释其业务含义。

例如，同一端口、同一个 Source1 可以接收 1001（压缩完成）、1002（保存完成）和 1003（任务取消）。这些编号仅为示例。RunLoop 先根据接收端口找到 source；回调再根据消息编号选择业务分支。不要把“按端口分发 source”与“按消息编号分支处理”混为一件事。

## Timer 的调度与重复触发

Timer 保存到期计划和回调，RunLoop 组织执行，系统内核定时设施提供到期通知；不是为每个 Timer 创建一条线程持续计数，也不是 RunLoop 忙轮询一秒是否已过。

1. scheduledTimer 加入当前线程 RunLoop 的 Default Mode，记录首次触发时间、重复间隔和回调。
2. 以 Apple 公开 Core Foundation 的 Mach timer 实现路径为例，内部使用基于 mach_absolute_time 的时钟计数表示截止时间，并通过 mk_timer_arm 设置底层定时通知。
3. RunLoop 无事可做时，通过 mach_msg 等等待机制让线程阻塞。内核到期发送相关消息，等待线程获得恢复运行条件；通知到期、线程获得 CPU 和业务回调开始是不同时间。
4. 线程恢复后，RunLoop 检查有效且到期的 Timer，在该线程执行回调。主线程繁忙或 Mode 不匹配都会延迟它。
5. 重复 Timer 沿原计划时间轴安排下一次。原定 1、2、3 秒，第一次延迟到 1.3 秒且很快结束，下次仍计划在 2 秒；若延迟跨过多个触发点，不会逐次补齐所有遗漏回调，而是执行一次并安排未来的下一个计划点。

tolerance 为系统合并唤醒、节能提供空间，但不保证严格准时。上述私有函数来自公开历史实现，只用于解释机制，不保证所有当前 iOS 版本使用相同私有调用链。

## CADisplayLink 的原理与适用场景

直观理解：

可以把它理解成向系统登记一个“按显示刷新节奏调用我”的任务。创建时指定 target 和 selector，加入 RunLoop 后安排执行。显示系统掌握刷新时序，Core Animation 按这套节奏调度，注册的 RunLoop 所在线程执行回调。回调里由业务计算滚动位置并修改 contentOffset，系统再准备后续画面。

```text
显示刷新时序（VSync）
    → 系统安排 CADisplayLink 回调
    → 注册的 RunLoop 所在线程执行方法
    → 更新动画／滚动状态
    → 为后续画面准备内容
```

- 显示系统提供节奏，RunLoop 执行任务；CADisplayLink 自己不负责业务滚动。
- 普通 Timer 的时间间隔不保证与显示时序对齐；CADisplayLink 接入显示调度。
- 回调不保证每次刷新准时执行；线程忙、模式不匹配和帧率策略都会影响它。不能写死 16.67ms，也不能说运行一轮 RunLoop 就刷新一次。
- 根据实际经过时间计算动画进度，避免靠“回调次数 × 固定位移”导致速度随帧率变化；这不能消除掉帧造成的视觉跳跃。
- 不扩写成未经核实的私有 Source1／Mach 消息细节；下一帧的期望显示时间可参考 targetTimestamp，剩余预算还需结合当前时间。

**用途与取舍：**

已讨论自定义物理／碰撞动画、波浪与动态曲线、音频频谱或音量波形展示、GIF／序列帧／自定义视频呈现，以及合并高频输入后按显示节奏更新 UI。音频采集、解码等有自己的处理节奏，不应都塞进显示回调。GIF 可以每次检查播放时间，但不一定每次更换图片；FLAnimatedImage 是使用 CADisplayLink 并按帧间隔调整回调频率的公开例子。

判断依据：画面是否持续变化、是否需要业务代码持续计算、现有框架是否已提供刷新循环。普通位移、透明度和系统弹簧动画可由系统插值；MTKView 已提供绘制循环时，通常不再叠加一个 CADisplayLink。

回调频率的统计方法及与真实上屏的区别见[FPS 与卡顿监测](rendering-and-performance.md#回调-fps-与卡顿监测)。逐帧变化不等于必须自己写逐帧回调，更不等于必须跑满 120 FPS。依据时间戳计算进度，内容停止变化或不可见时暂停，结束使用时 invalidate。

**昂贵工作：** CADisplayLink 不会让解码大图、复杂布局自动变快或自动转到后台。每帧只保留轻量进度计算和必要 UI 更新；可后台处理的解码／纯计算提前完成，布局与视图操作遵守 UIKit 主线程要求，并通过缓存、下采样与减少重复工作控制成本。
