## 进程与线程

进程是操作系统为运行程序创建的运行实例，拥有独立的地址空间和资源。线程是进程中由内核调度执行的单位。一个进程可以包含多个线程；CPU 实际执行的是被调度线程的指令。内核的职责见[内核、用户态与系统调用](../operating-systems/kernel-and-user-mode.md)。

同一进程中的线程共享进程的地址空间和资源。每条线程有自己的栈和执行上下文。执行上下文是线程暂停时需要保存的状态，包括寄存器的值和下一条要执行的指令地址。内核切换线程时，先把当前线程的寄存器值存到内存，再把下一条线程保存的值装回寄存器，所以多条线程可以轮流使用同一组物理寄存器。

### CPU 核心、逻辑 CPU 与并行上限

物理核心是 CPU 内部能够执行指令的硬件单元。逻辑 CPU 是操作系统能够独立调度线程的硬件执行上下文。一个物理核心可以提供一个或多个逻辑 CPU，具体取决于硬件能力和启用配置。

设备有 L 个可用的逻辑 CPU 时，同一时刻最多有 L 个线程正在执行。这个上限按线程计算：这 L 个线程可以属于同一个进程，也可以属于不同进程。

假设设备有 4 个物理核心，每个核心只提供一个逻辑 CPU，且 4 个逻辑 CPU 均可用。同一时刻可以出现以下分配：

| 线程分配 | 正在执行代码的进程数量 | 正在执行的线程数量 |
| --- | --- | --- |
| 4 个进程各执行 1 个线程 | 4 个 | 4 个 |
| 2 个进程各执行 2 个线程 | 2 个 | 4 个 |
| 1 个进程执行 4 个线程 | 1 个 | 4 个 |

超线程是 Intel 的同时多线程技术。启用超线程后，一个物理核心向操作系统提供两个逻辑 CPU，所以线程并行的上限按逻辑 CPU 计算。同一核心上的两个逻辑 CPU 共享这个核心的执行单元，所以逻辑 CPU 数量翻倍时，性能提升通常达不到一倍。

### 并发、并行与线程状态

并发是多个任务在同一段时间内都有进展；并行是多个任务在同一时刻都在执行。并发可以靠交替执行实现，也可以包含并行。单个逻辑 CPU 通过线程切换可以并发推进多个任务，同一时刻只执行一个线程。

系统中的线程可以远多于逻辑 CPU。内核按线程状态安排执行：

| 线程状态 | 含义 |
| --- | --- |
| 运行 | 线程正在某个逻辑 CPU 上执行 |
| 就绪 | 线程已经可以运行，正在等内核分配逻辑 CPU |
| 阻塞 | 线程暂停运行，等待网络数据、文件读写、锁释放或休眠到期等条件满足 |

阻塞线程等待的条件满足后，内核把线程改为就绪，这一步称为唤醒。被唤醒的线程还要等内核分配逻辑 CPU 才继续执行，所以“被唤醒”和“开始执行”是先后两个时刻。锁、信号量、休眠和 RunLoop 的等待都遵循这个顺序。内核按调度策略从就绪线程中选择执行，各线程分到的执行时间不一定相同。

线程数量超过逻辑 CPU 数量时，多出的就绪线程排队等待；某条线程阻塞时，内核把逻辑 CPU 让给其他就绪线程。所以多创建线程只会增加排队的线程，可用的逻辑 CPU 数量保持不变。

### 线程接口与任务调度接口

`pthread` 是提供线程创建、等待和同步等操作的 C 接口，Foundation 的 `Thread` 是面向对象的线程接口。使用这两种接口时，应用要自己创建线程、指定线程执行的代码，并管理线程何时结束。

使用 GCD 和 `OperationQueue` 时，应用只提交任务，由系统决定用哪条线程执行。Swift Concurrency 是 Swift 的异步任务与隔离机制，用 `Task`、`async`、`await` 等写异步流程，任务挂起时释放线程。

| 方式 | 应用主要管理的对象 | 适用需求 |
| --- | --- | --- |
| `pthread`、`Thread` | 线程及线程上的工作 | 明确需要控制线程生命周期或常驻线程 |
| GCD | 任务闭包及队列 | 简单提交工作、串行访问和回到主线程 |
| `OperationQueue` | `Operation` 任务及依赖 | 管理依赖、并发数量和协作式取消 |
| Swift Concurrency | 异步任务及隔离范围 | 等待异步结果、结构化子任务和保护共享状态 |

GCD 队列和 `OperationQueue` 只负责安排任务。系统从自己管理的一组工作线程中取线程执行任务，线程执行完一个任务后可以继续执行其他任务，所以提交任务时不会每次创建新线程。任务、队列和线程的数量之间没有固定对应关系：串行队列只保证同一时刻最多执行一个任务，不同任务可以由不同的工作线程执行；并发队列允许多个任务同时推进，同时运行的任务数量由系统决定。

下面用 GCD 把计算提交到全局队列，算完后把打印提交给主队列：

```swift
import Foundation

DispatchQueue.global(qos: .userInitiated).async {
    let total = (1...1_000).reduce(0, +)
    DispatchQueue.main.async {
        print(total) // 500500，在主线程执行
    }
}
```

后台闭包先算出 `total`，再把打印闭包提交给主队列。`DispatchQueue.main.async` 提交后立即返回，打印闭包要等主线程执行完当前工作后才执行。`.userInitiated` 是服务质量等级（QoS），表示任务的紧急程度，系统据此安排优先级；执行任务的线程仍由系统选择。

`Task { ... }` 的执行位置取决于创建时的隔离：在 `MainActor` 隔离范围内创建的 `Task` 继承这个隔离，其中的同步计算仍在主线程执行。`async let` 在声明处就创建子任务，后面的 `await` 只等待结果。具体机制和两个请求的示例见[async let 创建子任务与 await 等待结果](../language/swift-concurrency.md#async-let-创建子任务与-await-等待结果)。

## 数据竞争与线程安全

数据竞争是多个线程在没有同步的情况下访问同一块内存，且至少有一个线程在写入。数据竞争可能导致结果错误、内存损坏或崩溃；在 Swift 中，数据竞争属于未定义行为。线程安全是指多个线程按约定访问同一份数据时，结果仍然正确，数据保持一致。

例如多个并发任务同时修改同一个数组变量，就会产生数据竞争。Array 的值语义保证的是复制出的数组互不影响；同一个数组变量被并发修改时，仍要加同步。

在后台线程调用必须在主线程执行的 UIKit API，可能导致显示异常、数据损坏或崩溃，问题也可能偶尔才出现。这些 UI 操作要放到主线程执行。排查时，Thread Sanitizer 用于发现数据竞争，Address Sanitizer 用于发现释放后访问等内存错误，Main Thread Checker 用于检查系统 API 的主线程要求。

### i++ 的执行过程

本节用 `i++` 表示普通整数自增。原子操作是指在其他线程看来不可分割的操作：其他线程只能观察到操作开始前或全部完成后的状态，看不到中间状态。普通自增不是原子操作，Swift 整数的 `count += 1` 也一样。

自增分三步：读取旧值 → 计算旧值加 1 → 写回新值。CPU 把变量读入寄存器，在寄存器中做加法，再把结果写回变量的地址。寄存器是 CPU 内部供指令直接使用的存储位置。读写可能先发生在 CPU 缓存中，不一定每次都访问内存。

这三步对应几条机器指令，取决于 CPU 架构和编译优化。某个平台用一条指令完成内存自增时，这条指令也可能不是原子的。

**丢失更新示例：** 初始值为 0。线程 A 和 B 都读到 0，各自算出 1，再各自写回 1，两次自增最后只加了 1。这只是说明风险的一种交错；数据竞争属于未定义行为，结果可能是 1、2 以外的值，程序也可能崩溃。

### 线程安全的实现方式

每种方式只保护按它的规则访问的数据，使用条件如下：

| 线程安全方式 | 保证条件 |
| --- | --- |
| 避免共享可变数据 | 数据不可变，或每个任务使用独立数据；复制容器时还要检查内部是否继续共享可变对象 |
| 互斥锁 | 用同一把锁包住“读取、计算、写回”整个过程，所有读写这个变量的代码都使用这把锁。常用 API 有 NSLock、pthread_mutex、OSAllocatedUnfairLock 和 Mutex，各自要求的系统版本不同，见[锁的分类](#锁的分类) |
| 原子操作 | 使用 Synchronization.Atomic 等提供的原子“读取—修改—写入”操作；一次原子读取加一次原子写入组成的自增，整体仍不是原子的 |
| 串行队列 | 所有读写都提交到同一个串行队列，队列之外的代码不直接读写这个变量，见[GCD 的队列与提交方式](#gcd-的队列与提交方式) |
| actor / MainActor | 变量由 actor 隔离保护；需要保持一致的“检查 + 更新”写在同一段没有 await 的代码中 |
| 自建并发队列与 barrier | 所有读写通过同一个自建并发队列，写入用屏障任务，见[barrier 与单写多读](#barrier-与单写多读) |
| 初始值为 1 的信号量 | 所有读写使用同一个信号量：先 wait，再访问，最后 signal 一次，见[信号量的计数与配对规则](#信号量的计数与配对规则) |

“检查后修改”要整个放在同一个保护范围内。只保护写入、不保护读取，或者把检查和更新分别加锁时，其他线程都可能在检查和更新之间修改数据。actor 在 await 前后状态可能改变，见[actor 的默认隔离与重入](../language/swift-concurrency.md#actor-的默认隔离与重入)。

用 let 保存类实例，只固定了引用，实例的 var 属性仍可被修改。Objective-C 的 atomic 属性只保证单次读取或单次赋值完整执行；“先读再改”和多个属性之间的一致性要另加同步。

单独的计数器可以用原子操作自增；多个字段需要同时保持一致时，用锁或串行队列更合适。线程安全保证的是结果正确；读取最终计数前，还要等所有自增任务执行完。

### CAS 与 ABA 问题

CAS（Compare-And-Swap，比较并交换）是一个原子操作：调用方提供变量地址、期望值和新值；变量当前值等于期望值时，写入新值并返回成功；不相等时，保持原值并返回失败。比较和写入作为一个整体完成，中间不会被其他线程插入。

例如，A、B 都读到 0。A 用 CAS 把 0 改成 1，成功；B 也以 0 为期望值执行 CAS，此时当前值已是 1，失败。B 重新读到 1，算出 2，再执行 CAS；如果又被其他线程抢先，就继续重试。

CAS 每次只做一次比较和写入，失败后的重试循环由调用方自己写。比较和写入必须由语言或库提供的原子 API 一次完成；自己写 `if 当前值 == 期望值 { 赋值 }` 时，比较和赋值之间可能插入其他线程的修改。

**ABA 问题：** 值从 A 变成 B 又变回 A，CAS 只比较当前值，发现不了中间的变化。算法需要知道值是否被改过时，可以给值加一个版本号，每次修改都加 1，让 CAS 同时比较值和版本号。竞争激烈时，CAS 会反复失败重试，持续消耗 CPU。

### 锁的分类

锁的各种名称描述的是不同方面：“互斥”描述同一时刻允许几个线程访问；“自旋”描述拿不到锁时怎样等待；“可重入”描述同一线程能否再次获取自己已经持有的锁。所以一把锁可以同时是互斥锁和自旋锁。

| 类型 | 行为 | 条件与代价 |
|-|-|-|
| 互斥锁 | 同一时刻只允许一个持有者访问受保护区域 | 适合共享可变状态；具体实现可能先短暂自旋，再阻塞等待 |
| 自旋锁 | 获取失败时持续尝试，等待期间占用 CPU | 等待极短时可能减少阻塞与唤醒的开销；长时间等待会浪费 CPU |
| 读写锁 | 多个读者可同时持有读锁，写锁与其他读写锁互斥 | 读多写少时可能受益，实际效果取决于锁开销与竞争程度 |
| 递归锁／可重入锁 | 同一线程可以重复获取自己持有的锁 | 每次成功获取都需要对应释放，计数归零才完全解锁 |

乐观和悲观描述的是并发控制策略：悲观策略先加锁，再访问数据；乐观策略先读取和计算，提交更新时再检查有没有冲突，有冲突就重试或放弃。CAS 可以用来实现乐观策略的提交检查。

### 获取锁失败后的等待行为

锁被其他线程持有时，调用方是否等待、怎样等待，取决于调用的是哪种获取接口。同一把锁通常同时提供下面几种接口。

| 获取方式 | 无法立即获取锁时的行为 | 适用场景 |
| --- | --- | --- |
| 阻塞式获取 | 调用暂不返回，线程按锁的实现等待，成功获取后继续执行 | 当前操作必须取得锁才能继续 |
| 尝试获取（try-lock） | 立即返回失败，调用方决定跳过、稍后重试或执行其他工作 | 当前线程需要继续做别的事 |
| 带超时的获取 | 在约定期限内等待；成功获取或等待超时后返回 | 允许等待，但需要限制等待时间 |

会让线程阻塞的互斥锁按以下顺序工作：线程 B 尝试获取线程 A 持有的锁 → B 阻塞 → A 释放锁 → 锁的实现唤醒等待线程 → 被唤醒的线程分到逻辑 CPU 后再次尝试获取锁。被唤醒的线程还要重新竞争锁，获取接口成功返回才表示已经持有锁。

等待锁的线程有三种做法：

| 等待方式 | 等待线程做什么 | CPU 使用与调度 |
| --- | --- | --- |
| 自旋等待 | 持续检查锁状态或重试原子操作 | 线程获得执行机会时持续消耗 CPU |
| 让出执行机会 | 调用调度接口，允许调度器安排其他线程 | 线程保持就绪，调度器可能马上再次选中这条线程，锁持有者也可能还没执行 |
| 阻塞等待 | 通过锁或等待接口等待条件满足 | 等待期间不占用 CPU；被唤醒后仍需等待调度 |

纯用户态自旋锁用原子操作反复尝试获取锁，获取和等待都在用户态完成，不需要系统调用。循环中调用了休眠、让出或阻塞等待接口时，线程会通过系统调用进入内核。很多锁先短暂自旋，再转为阻塞。自旋代码执行期间，线程也可能因中断或被抢占而进入内核。用户态、内核态和系统调用的含义见[内核、用户态与系统调用](../operating-systems/kernel-and-user-mode.md)。

### 优先级反转与优先级继承

优先级反转是指高优先级线程在等待低优先级线程持有的锁，结果实际上比中等优先级的线程执行得还晚。

设单个逻辑 CPU 上运行 H、M、L 三条线程，优先级满足 H > M > L，并使用按优先级抢占的调度策略。L 先持有一把锁；H 随后尝试获取同一把锁并阻塞；此时 M 变为就绪并获得 CPU。M 虽然不需要这把锁，却可以持续延迟 L 的执行，进而延迟 L 解锁和 H 恢复。调度器只从就绪线程中选择，阻塞的 H 优先级再高也得不到 CPU，所以提高 H 的优先级无济于事。

优先级继承是缓解优先级反转的机制：高优先级线程等待锁时，锁临时把持有者的优先级提高到等待者的水平。上例中，L 临时获得 H 的优先级，于是优先于 M 运行，执行完受保护代码并释放锁，H 就能继续运行。L 释放锁后恢复原来的优先级。

优先级继承只改变 L 被调度的先后，受保护代码的执行时间不变，死锁也仍要另外避免。os_unfair_lock、pthread_mutex 支持优先级继承；DispatchSemaphore 不支持，因为信号量无从知道哪个线程会调用 signal，也就无法提升该线程的优先级。

## GCD 的队列与提交方式

GCD（Grand Central Dispatch）是 Apple 提供的任务调度机制，由 libdispatch 库实现。任务是要执行的工作，队列决定任务按什么规则执行，线程负责实际执行代码。主队列的任务固定在主线程执行；其他队列的任务由系统选择工作线程执行。

在 Swift 的 GCD 调用中，block 指传给 sync 或 async 的闭包，闭包的内容就是任务要执行的代码。这里的“任务”是一般概念，与 Swift 的 [Task](../language/swift-concurrency.md#tasktaskdetached-与任务局部值) 类型无关。

| 概念 | 对执行的约束 |
| --- | --- |
| sync 同步提交 | 调用方等待闭包执行完成后，调用才返回 |
| async 异步提交 | 调用方提交闭包后立即返回 |
| 串行队列 | 同一时刻最多执行队列中的一个任务 |
| 并发队列 | 允许多个任务重叠执行，实际是否同时执行由系统安排 |
| 主队列 | 特殊的串行队列，任务始终在主线程执行 |

同步／异步描述调用方是否等待，串行／并发描述队列能否同时执行多个任务，两者可以任意组合。`DispatchQueue.async` 是提交闭包的方法；Swift 并发中的 `async` 关键字用来声明异步函数，两者含义不同。

```swift
import Foundation

let serialQueue = DispatchQueue(label: "example.serial")
let concurrentQueue = DispatchQueue(
    label: "example.concurrent",
    attributes: .concurrent
)
```

### sync 的执行机制

```swift
print("A")
serialQueue.sync {
    print("B")
}
print("C")
// 顺序固定为 A → B → C
```

sync 提交时，libdispatch 先检查队列当前能否执行这个任务。能执行时，一般直接在调用 sync 的线程上执行闭包，省去线程切换；不能执行时，调用线程阻塞等待，之后闭包可能在调用线程执行，也可能在其他线程执行。提交给主队列的闭包总在主线程执行。

所以主线程用 sync 向普通队列提交耗时任务时，闭包往往就在主线程上执行；即使闭包在其他线程执行，主线程也要阻塞到闭包结束，界面同样会卡住。

sync 只让调用方等待，并发队列中的任务仍会同时执行：不同线程分别向同一个并发队列调用 sync，几个闭包可能同时运行。

### async 的执行机制

```swift
print("A")
serialQueue.async {
    print("B")
}
print("C")
// A 最先输出，B 与 C 的先后没有保证
```

async 把闭包连同捕获的内容保存下来，交给队列安排执行，然后立即返回。B 由工作线程执行，C 由当前线程继续执行，两条线程的进度互不约束，所以 B 可能在 async 返回之前就开始，也可能在 C 之后才开始。async 只提交任务，当前线程照常执行后面的代码。

向并发队列异步提交 A、B、C、D 时，可能的一种安排是：线程 1 先执行 A 再执行 C，线程 2 先执行 B 再执行 D。A 与 B 同时执行；一条线程可以先后执行多个任务，但同一时刻只执行一个。所有任务何时开始、使用几条线程，都由系统决定。

异步闭包执行时，捕获的对象可能已经被其他代码释放。默认的强捕获让对象保持存活；对象释放后再通过 unowned 访问，会触发运行时错误；weak 引用在对象释放后变成 nil，对 nil 强制解包同样会崩溃。复制 UnsafePointer 等指针只复制地址，指向的内存释放后再读写指针，会访问非法内存。

### 闭包返回与异步操作完成

GCD 和 OperationQueue 跟踪的是闭包返回的时刻。闭包内部如果只是发起一个异步操作，例如启动网络请求，闭包返回时操作还在进行。

所以 sync 的等待、barrier 的独占、DispatchGroup 的自动完成登记、信号量名额的释放和 BlockOperation 的完成，都只覆盖到闭包返回为止。要覆盖异步操作的完整过程，需要在操作的完成回调中结束登记或释放名额，具体写法见[同时限制访问数量并跟踪整体完成](#同时限制访问数量并跟踪整体完成)和[异步任务的并发限制](#异步任务的并发限制)。

### barrier 与单写多读

单写多读是指：多个读取可以同时进行；同一时刻最多只有一个写入；写入期间，其他读取和写入都要等待。“单写”限制的是同时进行的写入数量，写入可以由任意线程提交。

barrier（屏障）任务是提交到自建并发队列时带 `.barrier` 标记的任务。队列先等屏障之前提交的任务全部结束，再单独执行屏障任务；屏障任务结束后，才继续执行后面的任务。读取用普通任务提交、写入用屏障任务提交，就实现了单写多读。

使用条件：

- 对这个变量的所有读取和写入都提交到同一个队列。屏障只约束同一队列中的任务，其他队列的代码直接访问变量时，屏障管不到。
- 写入在屏障闭包返回前完成，原因见[闭包返回与异步操作完成](#闭包返回与异步操作完成)。

`DispatchQueue.global()` 返回系统提供的共享并发队列，进程中所有模块都可以使用。向全局并发队列提交 `async(flags: .barrier)` 时，任务按普通异步任务执行；只有自建的并发队列支持屏障。

屏障会让同一队列中的所有任务等待。假设图片解码、读取 value、屏障写入 value、写日志这四个任务依次提交到同一个支持屏障的队列：写入要等图片解码和读取结束，写日志也要等写入结束，与 value 无关的任务也被拖慢。全局队列不支持屏障，一个模块的屏障就不会拖慢其他模块的任务；这是根据效果作出的解释，Apple 文档只规定了全局队列没有屏障效果。

所以要为 value 单独创建一个并发队列，屏障只约束这个队列中的读写任务，其他队列的任务照常执行。

### 单写多读示例

下面的代码放在 Swift 命令行程序的 main.swift 中运行。读取和写入都异步提交，每个任务用 `Thread.sleep(forTimeInterval: 0.5)` 延长 0.5 秒，便于观察读取同时进行、写入单独执行。

```swift
import Foundation

final class SingleWriterDemo: @unchecked Sendable {
    private var value = 0
    private let queue = DispatchQueue(
        label: "demo.reader-writer",
        attributes: .concurrent
    )

    func read(_ name: String) {
        queue.async {
            print("\(name) 开始读取")
            Thread.sleep(forTimeInterval: 0.5)
            print("\(name) 读取结束，value = \(self.value)")
        }
    }

    func write(_ newValue: Int) {
        queue.async(flags: .barrier) {
            print("开始写入 \(newValue)")
            Thread.sleep(forTimeInterval: 0.5)
            self.value = newValue
            print("写入结束")
        }
    }

    // 仅从该队列之外调用，用于命令行示例等待已提交任务。
    func waitUntilFinished() {
        queue.sync(flags: .barrier) {}
    }
}

let demo = SingleWriterDemo()
demo.read("读任务 A")
demo.read("读任务 B")
demo.write(100)
demo.read("读任务 C")
demo.read("读任务 D")
demo.waitUntilFinished()
```

执行顺序：A、B 读取结束 → 写入 100 → C、D 开始读取。A、B 都读到 0，C、D 都读到 100。A 和 B 同时读取，两者谁先开始、谁先结束不确定。连续提交多个屏障写入时，写入之间也依次执行。

`Thread.sleep(forTimeInterval:)` 让执行这行代码的线程阻塞指定时间，其他线程照常执行。读取任务休眠时，另一个读取任务照常执行；屏障写入任务休眠时，屏障闭包还没返回，所以同一队列后面的任务都要等待。让队列等待的是屏障，sleep 只阻塞当前线程；删掉 sleep，单写多读的顺序依然成立。主线程休眠期间无法处理界面事件，所以界面延时用 `DispatchQueue.main.asyncAfter` 或 Timer，避免在主线程调用 sleep。

write 返回时，写入任务只是已经提交。waitUntilFinished 在已提交的任务之后再提交一个同步屏障，调用方阻塞到这个屏障结束才返回，命令行程序因此会等任务执行完再退出。waitUntilFinished 只等待调用之前提交的任务；在 queue 正在执行的任务中调用 waitUntilFinished，任务会等待自己所在的队列，形成死锁。

@unchecked Sendable 表示由开发者保证这个类可以安全地在线程间传递，编译器不再检查（Sendable 的含义见 [Sendable 与 @Sendable](../language/swift-concurrency.md#sendable-与-sendable)）。示例的线程安全来自私有队列和屏障：value 只在 queue 的任务中被访问；@unchecked Sendable 只关闭检查，本身不提供同步。

### 死锁与进程终止

死锁是多个任务互相等待、谁都无法继续执行的状态。死锁有两种结果：libdispatch 能检测出部分死锁并直接终止进程；未被检测出的死锁会一直卡住。主线程卡住太久时，系统的 watchdog 还会终止应用；watchdog 是系统监控应用是否及时完成启动、响应等必要工作的机制。

在主线程向主队列同步提交任务：主线程等待这个任务结束，而这个任务只能由主线程执行，于是主线程在等自己：

```swift
// 错误示例：当前在主线程执行
DispatchQueue.main.sync {
    print("任务")
}
```

串行队列中的任务向同一个队列同步提交任务，也会死锁：外层任务等内层任务结束，内层任务要等外层任务结束才能开始执行：

```swift
let queue = DispatchQueue(label: "example.serial")
queue.async {
    queue.sync {
        print("内层任务")
    }
}
```

libdispatch 发现当前线程已经在执行目标队列的任务时，会主动触发崩溃，崩溃信息中可能包含“dispatch_sync called on queue already owned by current thread”。

两个不同的串行队列也会形成循环等待：

```swift
let queueA = DispatchQueue(label: "example.a")
let queueB = DispatchQueue(label: "example.b")
queueA.async {
    queueB.sync {
        queueA.sync {
            print("无法执行到这里")
        }
    }
}
```

A 的外层任务等 B 的任务结束，B 的任务等 A 的内层任务结束，A 的内层任务又要等 A 的外层任务结束，形成一个环。libdispatch 可能检测出来并终止进程，也可能一直卡住。这类循环等待发生在串行队列上；同一个并发队列中的任务对本队列普通 sync 提交，通常不会以这种方式死锁。判断是否死锁，要看实际的等待关系。

只用 async 提交也可能死锁。例如主线程用 async 提交后台任务，然后用[信号量](#信号量的计数与配对规则)的 wait 等待后台任务的结果；后台任务又用 sync 向主队列提交任务。此时主线程在等后台任务，后台任务在等主线程，双方都无法继续。

## DispatchGroup 与 DispatchSemaphore

DispatchGroup 把一组任务当作一个整体跟踪，用来判断组内登记的任务是否全部完成。DispatchSemaphore（信号量）内部维护一个计数，计数表示当前可用的名额：wait() 取走一个名额，没有名额时阻塞调用线程；signal() 归还一个名额，有线程在等待时唤醒其中一个。信号量可以用来等待另一个任务发出完成信号，也可以限制同时访问资源的任务数量。

| 对比项 | DispatchGroup | DispatchSemaphore |
| --- | --- | --- |
| 管理内容 | 尚未完成的一组任务 | 可用名额以及等待名额的调用 |
| 登记与完成 | enter() 登记任务，leave() 标记任务完成 | wait() 取走名额，signal() 归还名额或唤醒一个等待者 |
| 等待条件 | 登记的任务全部完成 | 当前这次 wait() 取得一个名额 |
| 等待方式 | notify 注册完成闭包，不阻塞调用方；wait 在组内还有任务时阻塞调用线程 | wait 在没有名额时阻塞调用线程，有名额时直接通过 |
| 数据保护 | 组内任务的互斥要另外保证 | 初始值为 1，且所有访问都配对使用同一个信号量时，提供互斥访问 |

带超时的 wait 超时后返回 `.timedOut`，此时任务尚未完成，调用也没有取得名额。

### 任务登记与完成通知

用 `queue.async(group: group)` 提交闭包时，GCD 自动登记这项任务，闭包返回后自动标记完成。手动管理时，在异步工作开始前调用 enter()，工作真正结束后调用且只调用一次 leave()；成功、失败等每一条结束路径都要调用 leave()。

`notify(queue: .main)` 注册一个在组内任务全部完成后执行的闭包。notify 立即返回；组内任务全部完成后，GCD 把这个闭包提交到主队列执行。注册时组内已经没有任务，闭包会立即被安排执行，所以要先登记任务，再注册 notify。

`.main` 只决定通知闭包在哪个队列执行，组内任务的执行队列由提交时决定。`group.wait()` 让调用线程阻塞，直到组内任务全部完成。组内任务如果还需要这个被阻塞的线程或串行队列才能完成，就会死锁，机制见[死锁与进程终止](#死锁与进程终止)。

### 信号量的计数与配对规则

信号量的初始值与线程数量无关。所有受限的工作都先调用 wait、结束后调用一次 signal 时，初始值 N 表示最多有 N 个工作同时处在 wait 与 signal 之间。初始值为 1 时，同一时刻只有一个访问者，可以保护需要独占修改的数据；初始值大于 1 时，多个访问者可以同时进入，需要独占修改的数据仍会发生数据竞争。

初始值为 0 表示一开始没有名额，wait 要等到有人调用 signal 才能通过。信号量只影响调用了 wait 的代码，所以另一段不调用 wait 的代码可以正常执行，并在完成后调用 signal。

```swift
import Foundation

let semaphore = DispatchSemaphore(value: 0)

DispatchQueue.global().async {
    print("执行任务 A")
    semaphore.signal()
}

DispatchQueue.global().async {
    semaphore.wait()
    print("A 已发出信号，继续执行任务 B")
}
```

B 先执行到 wait 时，B 所在的线程阻塞，直到 A 调用 signal。A 先调用 signal 时，信号量记下一个名额，B 之后执行到 wait 时直接通过。两个闭包谁先开始不确定，但 B 的打印一定在 A 调用 signal 之后。

初始值为 0，而所有任务都写成“wait → 执行工作 → signal”，又没有其他代码调用 signal 时，所有任务都会卡在 wait：负责调用 signal 的代码都在 wait 之后，永远执行不到。

### 同时限制访问数量并跟踪整体完成

下面在 iOS 应用中提交 5 个任务，最多允许 2 个任务同时执行 wait 与 signal 之间的同步工作。group 跟踪这 5 个闭包的完成情况。

```swift
import Foundation

let group = DispatchGroup()
let semaphore = DispatchSemaphore(value: 2)
let queue = DispatchQueue.global()

for index in 1...5 {
    queue.async(group: group) {
        semaphore.wait()
        defer { semaphore.signal() }
        print("执行任务 \(index)")
    }
}

group.notify(queue: .main) {
    print("5 个任务全部完成")
}
```

初始值 2 限制的是同时处在 wait 与 signal 之间的闭包数量。其他工作线程也可能已经开始执行闭包，只是阻塞在 wait 处。这个例子中，group 负责全部完成后的通知，信号量负责限制同时执行的数量。

闭包只是发起另一个异步操作时，要跟踪操作真正完成，就在发起前调用 enter，在操作的完成回调中调用 leave；要限制同时进行的操作数量，就在完成回调中调用 signal。每次 enter 对应一次 leave，每次 wait 对应一次 signal。

## Operation 与 OperationQueue

OperationQueue 是 Foundation 提供的任务调度队列。Operation 表示一个任务，应用把工作封装成 Operation 加入队列，队列根据任务的依赖、优先级和并发上限安排执行。

BlockOperation 是用闭包封装工作的 Operation 子类，普通的同步任务直接使用 BlockOperation 即可；需要自己管理执行状态时，例如封装异步任务，才自定义 Operation 子类。

### 并发上限、依赖与执行顺序

`maxConcurrentOperationCount` 限制队列中同时执行的 Operation 数量。例如设为 2，最多同时执行两个，其余任务等待。这个值与线程数、CPU 核心数无关。

Operation 的 `isReady` 为 true 表示这个任务的依赖都已完成、可以开始。队列从 `isReady` 为 true 的任务中按 `queuePriority` 选出下一个开始执行，所以 `maxConcurrentOperationCount` 设为 1 时，同一时刻只执行一个 Operation，执行顺序仍可能与加入顺序不同。`queuePriority` 只影响尚未开始的任务谁先开始，已经开始的任务继续执行。

`taskB.addDependency(taskA)` 让 taskB 等 taskA 完成后才开始。依赖只规定先后：taskA 失败时 taskB 照样开始；taskA 的结果或错误要由代码自己传给 taskB，taskB 自己判断是否继续。

自己创建的 OperationQueue 在后台线程执行任务，OperationQueue.main 在主线程执行任务。图片计算可以在后台队列完成，UIKit 视图更新要回到主线程。

### 最小使用示例

```swift
import Foundation

let queue = OperationQueue()
queue.maxConcurrentOperationCount = 2

let taskA = BlockOperation {
    print("执行任务 A")
}
let taskB = BlockOperation {
    print("执行任务 B")
}

queue.addOperations([taskA, taskB], waitUntilFinished: false)
```

上例创建两个同步任务，队列最多同时执行两个。waitUntilFinished 为 false 表示 addOperations 立即返回，调用方无需等任务完成；A 和 B 的打印顺序不确定。闭包执行完，对应的任务就完成了。

### 协作式取消

`cancel()` 只把 Operation 的 `isCancelled` 设为 true。协作式取消是指：任务的代码自己检查 `isCancelled`，在可以停下的地方主动结束；正在执行的代码会继续执行到下一次检查。

Operation 在开始前就被取消时，会直接跳过工作并结束。任务开始后，要在每个耗时步骤之前检查 `isCancelled`。正在调用一个不支持取消的同步函数（例如解码函数）时，只能等函数返回，再停止后续步骤或丢弃结果。自定义 Operation 还要在取消后正确设置结束状态。

OperationQueue 只提供取消接口：`cancel()` 取消指定任务，`cancelAllOperations()` 取消全部任务。被取消的任务在结束前仍留在队列中。

### 异步任务的并发限制

在普通 BlockOperation 中调用 `URLSessionTask.resume()` 后，闭包很快返回，网络下载仍在进行。BlockOperation 此时已经完成，OperationQueue 接着启动下一个任务。所以这种写法下，`maxConcurrentOperationCount` 限制的只是启动下载的次数，同时进行的下载数量不受限制。原因见[闭包返回与异步操作完成](#闭包返回与异步操作完成)。

要限制下载并发，可以让图片加载器维护正在执行的下载数量和待调度请求，在网络完成回调中释放名额；也可以使用正确实现异步状态的 Operation，在网络任务真正结束后才设置完成状态。取消下载后，要等网络任务实际结束再释放名额。

下载与解码分别限流、预取需求和取消流程见[长列表图片任务调度](image-loading-decoding-and-memory.md#长列表图片任务调度)。
