## 图层动画与渲染管线

**与 UIView 动画的关系：** UIView 动画是 UIKit 提供的高层接口，底层利用 Core Animation 的图层动画能力。每个 UIView 背后都有 CALayer；UIView 管理[视图层级](uikit-layout-and-mvvm.md#视图层级与父子关系)、布局与交互，CALayer 保存位置、大小、透明度、圆角等视觉状态，Core Animation 根据动画配置计算中间状态并参与渲染、合成。UIView 本身也有绘制和动画 API，不能把这些职责理解为互不重叠。

例如让视图在 0.3 秒内淡出：使用 UIKit 时，在 `UIView.animate` 中把 `view.alpha` 设为 `0`；直接使用 Core Animation 时，为图层的 `opacity` 创建并添加 `CABasicAnimation`，同时处理模型属性的最终值。前者由 UIKit 组织相应的底层图层动画，无需业务逐帧修改透明度。

UIKit 动画依赖 Core Animation，不表示业务代码直接创建了显式图层动画对象。

**动画原理：** CALayer 管理视觉内容与位置、变换、透明度等属性。应用描述起终点、时长、关键帧或弹簧规则，系统依据时间计算中间状态。位移、缩放、淡出通常能复用已有位图／纹理，不必每帧重画内容；这不表示所有内容变化都没有 CPU 开销。

- 模型树保存代码设置的状态；呈现树反映动画中的当前状态，可通过 presentation() 读取；渲染树是系统内部结构。
- 对简单数值属性，可理解为“起点 + 差值 × 时间曲线处理后的进度”，不是每个回调固定增加一段距离。
- CABasicAnimation、CAKeyframeAnimation、CASpringAnimation 和 CAAnimationGroup 分别表达基本插值、关键帧／路径、弹簧与动画组合。
- 显式添加 CAAnimation 不会自动改变模型属性；需要将模型更新为预期最终状态，否则移除动画后可能回到原状态。UIView.animate 是更上层接口，普通 UIView 属性在动画块外修改通常不会自动过渡。
- CATransaction 将图层操作批量提交；隐式事务结合 RunLoop 自动提交。事务与动画类型要区分，显式动画也需要事务提交。

**典型渲染管线：**

| 阶段 | 位置与工作 |
|-|-|
| Event | App 处理触摸、Timer、数据回调，修改视图／图层状态 |
| Commit | App 完成必要的布局、内容绘制，整理并提交图层变化 |
| Render Prepare | Render Server 的 CPU 处理图层和效果，准备 GPU 命令与资源 |
| Render Execute | GPU 完成绘制、采样、变换、混合等工作，生成画面 |
| Display | 显示系统在相应时机呈现已准备好的画面 |

App 的 draw(\_:) 可生成供后续使用的图像内容；渲染服务与 GPU 再按图层属性合成最终画面。不能把 Commit 中的内容绘制和 GPU 合成混为同一阶段，也不能说 Core Animation 完全不使用 CPU。

流水线可以同时处理不同帧，App 准备后续更新时，GPU 可以处理之前提交的内容。60／120 Hz 对应约 16.67／8.33 ms 的显示间隔，不等于一次更新从输入到显示只需要一个间隔，也不能把固定几帧延迟当所有设备与系统的保证。

Commit hitch 是 App 未及时完成事件处理、布局／绘制和提交；Render hitch 是渲染准备或执行超时。主线程不卡不代表 GPU 或渲染服务没有瓶颈。未按时准备好新画面时，旧画面可能继续显示。RunLoop 是线程事件循环，Render Loop 是跨进程、CPU／GPU 到显示的完整流程。

FMP 边界仍适用：willDisplay、布局和事务提交完成，都不能直接等同指定内容真实上屏。

### UIView 与 CALayer 的对应关系

`CALayer` 是 Core Animation 中保存视觉内容和几何、外观属性的对象。支撑图层指 UIKit 为某个 `UIView` 创建并管理、通过 `view.layer` 访问的图层。每个 `UIView` 有一个支撑图层；这个支撑图层可以包含多个子图层。

子图层是加入另一个图层内部的 `CALayer` 对象。`superlayer` 表示直接父图层，`sublayers` 表示直接子图层数组。调用 `view.layer.addSublayer(layer)` 可以添加图层。一个视图的支撑图层与该视图对应，但所有 `UIView` 与所有 `CALayer` 并非一一对应，因为额外创建的图层可以没有对应的 `UIView`。

调用 `parentView.addSubview(childView)` 时，UIKit 会同步组织子视图及其支撑图层的层级。直接向 `parentView.layer` 添加独立图层，不会创建子视图，也不会在 `parentView.subviews` 中增加元素。

### 多个子图层的用途与形状

多个子图层可以把一个控件的不同视觉部分分开管理。例如，一个进度控件可以用 `CAGradientLayer` 显示渐变背景，用 `CAShapeLayer` 显示进度线，再用另一个图层显示装饰。各图层可以分别改变颜色、位置、透明度或动画，而不必把全部内容合并为同一张图片。

`CAShapeLayer` 根据 `path` 指定的几何路径绘制形状。路径是一组描述直线、曲线和轮廓的数据，可以表示矩形、圆、折线或自定义轮廓。`CAShapeLayer` 不会因为自身类型就自动画成圆；例如，用宽高相等的矩形生成椭圆路径，再把路径赋给 `path`，才会得到圆形轮廓。

仅承担视觉展示和动画的部分可以使用独立图层。需要 UIKit 的触摸事件、手势或无障碍交互时，通常由 `UIView` 承担。独立 `CALayer` 不属于 UIKit 的事件响应对象链；虽然图层提供几何命中检测方法，也不会自动获得 `UIView` 的事件处理能力。

额外添加的图层不会自动获得 UIView 的 Auto Layout 约束能力。父视图尺寸变化时，应根据布局更新需要调整子图层的尺寸和路径。拆分图层有助于独立控制视觉部分，但图层越多并不意味着渲染一定更快。

## anchorPoint、position 与图层几何

`anchorPoint` 是 `CALayer` 在自身 `bounds` 中选定的参考点，使用相对宽高的单位坐标，默认值为 `(0.5, 0.5)`。单位坐标表示比例，不是像素或点数；常见取值在 `0...1`，但 API 也允许超出这个范围。

在 iOS 默认坐标方向下，`(0, 0)` 对应左上角，`(0.5, 0.5)` 对应中心，`(1, 1)` 对应右下角，`(0, 0.5)` 对应左边中点。图层旋转或缩放时，以锚点作为变换的参考位置。下面将视图支撑图层的参考点改为左边中点：

```swift
view.layer.anchorPoint = CGPoint(x: 0, y: 0.5)
```

`anchorPoint` 和 `position` 需要配合理解。对于没有变换的图层，`position` 指定锚点在父图层坐标系中的位置；`anchorPoint` 决定图层自身的哪个点与该位置对齐。

| 属性 | 描述的内容 |
| --- | --- |
| `bounds` | 对象在自身坐标系中的边界矩形 |
| `UIView.frame` | 无变换时，视图在父视图坐标系中的位置和大小；非单位变换下不应用它直接推算或设置原始几何信息 |
| `UIView.center` | 视图中心在父视图坐标系中的位置；默认锚点时，与支撑图层的 `position` 对应 |
| `CALayer.anchorPoint` | 在自身 `bounds` 内选定参考点的相对坐标 |
| `CALayer.position` | 图层在父图层坐标系中的定位值；无变换时，指定锚点应处的位置 |

对于未设置变换的图层，可以按两个坐标分量分别计算：`frame.origin = position - anchorPoint × bounds.size`。例如，`bounds = (0, 0, 100, 100)`，`position = (200, 200)`：

| anchorPoint | frame 左上角 |
| --- | --- |
| `(0.5, 0.5)` | `(150, 150)` |
| `(0, 0)` | `(200, 200)` |

只把锚点从中心改为左上角、保持 `position` 不变，图层就向右下方移动了各 50 点。原因是同一个父坐标位置改为对齐图层的另一个内部点。若要改变锚点同时保持原来的可见位置，需要补偿 `position`；存在旋转、缩放等变换时，补偿必须同时考虑变换，不能直接套用这个无变换示例的偏移量。

`CALayer.frame` 是根据 `bounds`、`position`、`anchorPoint` 和变换计算出的父坐标系边界框。存在旋转时，边界框不再等于未旋转的原始尺寸。视图布局与约束的关系见 [frame、Auto Layout 与 SnapKit](uikit-layout-and-mvvm.md#frameauto-layout-与-snapkit)。

## 圆角、边界裁剪与离屏渲染

### cornerRadius 与 masksToBounds 的职责

`cornerRadius` 是 `CALayer` 绘制背景和边框时使用的圆角半径，单位为点。`masksToBounds` 决定图层是否按自身边界裁剪内容及子图层；开启后，裁剪形状也包含 `cornerRadius` 的圆角效果。这里的裁剪是隐藏边界以外的显示区域，不会修改原图片文件。

`bounds` 表示图层在自身坐标系中的边界矩形。`cornerRadius` 不会把 `bounds` 改成圆角形状，也不会改变布局尺寸。基础 `CALayer` 的 `cornerRadius` 默认是 `0`，`masksToBounds` 默认是 `false`。

```swift
imageView.layer.cornerRadius = 12
imageView.layer.masksToBounds = false
```

假设 `imageView` 显示一张不透明矩形图片，图片覆盖到视图的四个角，并且没有其他蒙版或父视图裁剪。此时背景和边框可以按 12 点半径绘制圆角，但图片内容没有被这个圆角裁掉，图片通常仍显示为直角矩形。

改成下面的代码后，图片会按圆角边界裁剪：

```swift
imageView.layer.cornerRadius = 12
imageView.layer.masksToBounds = true
```

两种写法的区别是内容是否裁剪，不是圆角半径有没有设置成功。如果原图四角本来透明，或者图片没有铺到四个角，只看最终外观可能无法区分这两种配置。

| 配置 | 背景与边框 | 图像内容与子图层 |
| --- | --- | --- |
| `cornerRadius = 12`，`masksToBounds = false` | 可以呈现圆角 | 不因该圆角被裁剪；仍可能受其他裁剪影响 |
| `cornerRadius = 12`，`masksToBounds = true` | 可以呈现圆角 | 按包含圆角的边界裁剪 |

### clipsToBounds 与 masksToBounds 的关系

`clipsToBounds` 是 `UIView` 提供的裁剪开关，`masksToBounds` 是 `CALayer` 提供的裁剪开关。对普通 UIKit 视图，设置视图的 `clipsToBounds` 会对应到支撑图层的边界裁剪。设置图片圆角时，通常选择下面的一种写法即可，不需要重复设置两个开关。

```swift
imageView.layer.cornerRadius = 12
imageView.clipsToBounds = true
```

`UIView` 的默认值是 `false`，但部分子类会修改默认值，因此不能假定所有视图初始都关闭裁剪。开启裁剪后，超出边界的子视图内容也会被隐藏。

### 离屏渲染的含义与常见场景

这里的离屏渲染指 GPU 为完成某个图层效果，先把相关内容绘制到中间图像，再将中间结果用于最终画面的渲染。GPU 是执行图形计算的处理器；中间图像是保存临时像素结果的渲染目标。

“离屏”描述绘制结果先写到哪里，不表示代码在后台线程执行，也不表示视图处于屏幕可见范围之外。Swift 只是设置图层属性的语言；是否需要中间绘制由渲染系统决定。

| 场景 | 可能需要中间结果的原因 |
| --- | --- |
| 可见阴影，且未设置 `shadowPath` | 渲染器可能需要先得到内容合成后的透明度轮廓，再生成阴影 |
| 图层蒙版 `mask` | 蒙版用自身各像素的透明度控制目标内容可见程度，可能需要先绘制被遮罩的内容与蒙版 |
| 多个子图层的圆角整体裁剪 | 渲染器可能需要先合成子图层，再保留圆角范围内的结果 |
| `UIVisualEffectView` 的模糊等视觉效果 | 效果可能依赖背景图像，需要采样、模糊和额外的中间绘制 |
| 组透明度，且子图层存在需要整体合成的内容 | 当父层透明度介于 0 和 1、并启用 `allowsGroupOpacity` 等条件成立时，可能先合成一组内容，再统一应用透明度 |
| `shouldRasterize = true` | 要求把图层及子图层绘制成位图；首次生成或缓存失效时产生中间绘制，后续可能复用缓存 |

仅设置 `cornerRadius` 不足以证明发生离屏渲染。简单圆角裁剪存在系统优化，多个子图层和其他效果的组合则可能需要额外绘制。实际行为取决于图层结构、效果组合、系统和设备，不能把 `cornerRadius + masksToBounds` 写成必然触发离屏渲染的规则。

额外的中间绘制会增加像素计算、临时图像和读写开销。开销是否导致卡顿，还取决于绘制面积、发生频率和当时的渲染负载；发现离屏绘制不等于已经证明卡顿原因。

合成指按层级、位置和透明度把多个图像组合为一个结果。例如，组透明度先把重叠子图层组合，再对整体应用一次透明度；逐个修改子图层透明度可能得到不同的重叠颜色，因此不能随意关闭组透明度来替代相同效果。仅设置 `alpha < 1` 或 `opacity < 1`，也不足以证明一定发生离屏绘制。

`shouldRasterize` 的缓存适合某些内容稳定、需要反复合成的图层组合。内容频繁变化会使位图重新生成，可能增加开销，不能把开启光栅化当作通用性能优化。这里的光栅化指把图层内容转换为像素位图。

通过 `draw(_:)` 或图像绘制接口在 CPU 侧生成图像，与这里讨论的 Core Animation GPU 离屏绘制不是同一个阶段。某个视图实现了 `draw(_:)`，不能单独证明该视图还会触发 GPU 离屏绘制。

### shadowPath 与圆角阴影的组合

`shadowPath` 是显式指定阴影轮廓的路径。轮廓已知时，渲染器不必先从整个内容的合成结果推导轮廓，因此可以减少或避免这一步导致的离屏绘制。其他蒙版、裁剪或模糊效果仍可能有额外开销。

圆角卡片同时需要向外显示阴影与裁剪内部图片时，可以使用两层视图。外层 `shadowView` 显示阴影并关闭裁剪；内层 `imageView` 裁剪图片。若在负责阴影的同一层开启边界裁剪，超出边界的阴影也会被裁掉。

下面假设两个视图已经创建，并且 `imageView` 已添加为 `shadowView` 的子视图。先设置外观：

```swift
let radius: CGFloat = 12

shadowView.layer.cornerRadius = radius
shadowView.layer.masksToBounds = false
shadowView.layer.shadowColor = UIColor.black.cgColor
shadowView.layer.shadowOpacity = 0.2
shadowView.layer.shadowRadius = 6
shadowView.layer.shadowOffset = CGSize(width: 0, height: 3)

imageView.layer.cornerRadius = radius
imageView.clipsToBounds = true
```

布局得到有效尺寸后，再更新内层视图和阴影路径：

```swift
imageView.frame = shadowView.bounds
shadowView.layer.shadowPath = UIBezierPath(
    roundedRect: shadowView.bounds,
    cornerRadius: radius
).cgPath
```

`shadowPath` 使用图层自身的坐标，因此示例使用 `bounds`。当尺寸或圆角半径变化时，需要重新生成路径；例如在相应的布局回调中更新。`shadowRadius` 控制阴影模糊程度，`cornerRadius` 控制圆角形状，两者不是同一个半径。

### 性能判断与优化边界

优先使用系统提供的圆角属性。只需要普通圆角形状时，不必额外创建自定义 `mask` 图层。内容和子视图确认不会超出边界、也不需要裁掉图片四角时，才可以关闭裁剪。不能仅为减少开销而去掉界面实际需要的裁剪。

在目标设备上录制实际滑动或动画，再结合 [Animation Hitches](#animation-hitches-的使用流程) 和图层检查信息判断是否存在额外离屏绘制、发生在哪个图层，以及是否造成渲染超时。优化后应重复相同操作，比较渲染时间与外观，不能只凭属性名称判断优化已经生效。

## 回调 FPS 与卡顿监测

可以做轻量监测：主线程忙不过来时，显示回调可能延迟，通过回调频率与间隔观察卡顿迹象。把 DisplayLink 注册到主线程 RunLoop 的 `.common` 模式，让常见列表拖动期间也能执行，避免只注册 `.default` 后因模式切换暂停回调而误判。

回调时记录单调时钟，先保存基准时间，随后累计回调间隔数；在约一秒的统计窗口内，用间隔数除以实际经过时间，得到近似回调 FPS。同时记录每次间隔，避免平均值掩盖某一次明显停顿。例如当前按 60 FPS 调度时正常间隔约 16.7 ms，突然出现 100 ms 间隔值得记录排查；120 FPS 约 8.3 ms，动态帧率下不能统一套用 16.7 ms。应结合实际调度节奏判断，主动降帧不等于发生性能卡顿。

**回调一次不代表新画面已成功上屏。** 这个统计反映 DisplayLink 回调节奏，是近似指标；后续渲染服务或 GPU 也可能错过显示时机，不能仅靠回调次数覆盖所有卡顿，更不能直接据此确定根因。

不限工具时，在真机上用 [Animation Hitches](#animation-hitches-的使用流程) 录制滑动，定位具体停顿和提交／渲染阶段；再结合 [Time Profiler](#time-profiler-的采样与统计边界) 与线程状态，区分主线程在执行耗时计算，还是等待锁、资源等。线上情况可结合 [MetricKit 与 Xcode Organizer](#metrickit-与-xcode-organizer) 的报告分析。

### CADisplayLink 帧时间与卡顿时长统计

基于帧时间戳的卡顿统计，是用相邻回调提供的帧时间与预期显示时间计算延迟，再累计延迟时长。这是一种观察界面流畅度的近似方法；计算结果不能直接等同于某个方法的执行耗时或完整的画面渲染耗时。

**回调来源与执行顺序。** `CADisplayLink` 是 iOS 提供的、按显示刷新节奏调用指定方法的对象。监控器创建 `CADisplayLink`，注册采样方法，并将对象加入主线程的 `RunLoop`。`RunLoop` 是线程接收和处理事件的循环。系统调度显示回调时，会调用采样方法并传入 `CADisplayLink` 对象；采样方法读取帧时间、计算延迟，并保存本次数据供下一次使用。

“本次回调”和“上次回调”指同一个监控用的 `CADisplayLink` 相邻两次调用采样方法。卡顿统计使用对象提供的帧时间，不把进入采样方法的实际时刻直接当作帧时间。

| 属性或表达式 | 含义 |
| --- | --- |
| `timestamp` | 系统提供的最近一帧已经显示的时间。 |
| `targetTimestamp` | 系统提供的下一帧预期显示时间。 |
| `targetTimestamp - timestamp` | 本次回调提供的这两个帧时间之间的间隔。 |
| `duration` | 屏幕按最大刷新率刷新时的帧间隔；不要把该属性直接当作所有调度频率下的实际回调间隔。 |

上述 API 的时间单位是秒。需要以毫秒统计时，应将相关时间统一乘以 `1000`，避免秒与毫秒混算。

**下一帧预期显示时间由系统直接提供。** 监控器读取 `targetTimestamp`，不固定使用 `timestamp + 16.67 ms`。只有当前按每秒 60 帧稳定调度时，两者的差值才约为 16.67 ms；按每秒 120 帧稳定调度时，差值约为 8.33 ms。动态帧率下，应使用系统本次提供的时间。

**逐帧计算。** 在同一段连续采样中，监控器保存上次的 `timestamp` 和 `targetTimestamp`。第一次回调只建立基准；从第二次回调开始，按下面的公式计算。以下公式统一使用毫秒。

| 计算量 | 公式 |
| --- | --- |
| 本次统计时长 | 本次 timestamp − 上次 timestamp |
| 原始延迟 | 本次 timestamp − 上次 targetTimestamp |
| 本次计入的卡顿时长 | 原始延迟 > 过滤阈值时，取原始延迟；否则取 0。 |

过滤阈值决定多大的延迟才进入累计值。例如选择约 8.33 ms，即 `1000 / 120` ms，作为过滤阈值，则小于或等于该值的延迟不计入；超过该值时，累计整段原始延迟，不是只累计减去阈值后的差值。阈值属于指标定义的一部分，不是 iOS 对所有卡顿统计规定的统一常量。

假设按每秒 60 帧稳定调度，相邻两次有效采样取得下列数值：

| 时间 | 数值 |
| --- | --- |
| 上次 timestamp | 1000.00 ms |
| 上次 targetTimestamp | 1016.67 ms |
| 本次 timestamp | 1050.00 ms |

本次统计时长为 `1050.00 − 1000.00 = 50.00 ms`。原始延迟为 `1050.00 − 1016.67 = 33.33 ms`。采用约 8.33 ms 的过滤阈值时，本次计入的卡顿时长为 33.33 ms；正常预期的约 16.67 ms 不计入卡顿时长。

本次计算完成后，监控器保存本次的 `timestamp` 和 `targetTimestamp`。下一次回调到来时，再使用新的 `timestamp` 与这次保存的 `targetTimestamp` 比较。

**累计时长与丢帧时长率。** 本节将“丢帧时长率”定义为：同一采样范围内，累计计入的卡顿时长除以累计统计时长。

`累计统计时长 = Σ 本次统计时长`

`累计卡顿时长 = Σ 本次计入的卡顿时长`

`丢帧时长率 = 累计卡顿时长 / 累计统计时长`

例如累计统计时长为 1000 ms，累计卡顿时长为 100 ms，则比值为 0.1。以百分比展示是 10%；以每秒卡顿多少毫秒展示是 100 ms/s。比较数据时，必须统一分母、采样范围、过滤阈值和展示单位。没有有效统计时长时，不计算比率。

合并多段记录时，先分别累加各段卡顿时长和统计时长，再计算 `Σ 卡顿时长 / Σ 统计时长`。各段时长不相等时，不能直接对各段的百分比取算术平均。

**采样范围与观测边界。** 采样应覆盖需要观察的动画或交互过程。停止采样、进入后台或暂停显示回调后，恢复采样时要重新建立时间基准，避免把中间未采样的时间计为卡顿。拖动期间是否继续采样，还取决于显示回调注册的 RunLoop 模式。

采样方法应只读取时间并更新少量统计值。逐帧执行复杂计算或同步上传数据，会增加主线程工作，影响被监测的界面。

这种方法反映显示回调所提供帧时间的延迟，不能直接证明某段业务代码造成卡顿，也不能完整覆盖渲染服务或 GPU 的所有显示延迟。GPU 是执行图形计算的处理器；渲染服务负责在应用提交图层之后组织后续渲染工作。需要定位具体阶段和原因时，应结合渲染时间线、线程状态及方法调用记录。

如果还要统计“连续丢 N 帧”对应的时长率，必须另外明确帧数换算使用的时间基准、筛选条件，以及分子累计的是延迟时长还是整个帧间隔。使用固定 16.67 ms 换算与使用当前帧间隔换算，可能得到不同的分档结果；不能只凭指标名称比较数值。

## Time Profiler 的采样与统计边界

**Time Profiler 周期性采集正在 CPU 上执行的线程调用栈，再按采样权重估算各调用路径的 CPU 时间。** 它不是在每个方法的入口和出口自动记录时间。Call Tree 展示选定时间范围内的聚合结果；样本本身仍保留采样时刻和调用栈，因此并非完全没有时序信息。

以固定每 1 ms 采样一次为简化示例（不表示所有录制都固定使用该间隔）：

```text
估算 CPU 时间 ≈ 命中相应方法／调用路径的样本数 × 采样间隔
```

不是“最后一次采到该方法的时间 − 第一次采到的时间”。同一方法出现在调用栈中，可以是它自身正在执行，也可以是它调用的子方法正在执行；查看统计时要区分包含子调用的 Weight 与自身的 Self Weight，不能把父子累计值重复相加。

| 一次调用的假设情况 | 数值 |
|-|-|
| 实际开始／结束 | 1.2 ms／4.8 ms |
| 实际经过时间 | 3.6 ms |
| 连续在 CPU 上执行，并在整数毫秒采样时命中 | 2、3、4 ms，共 3 个样本 |
| 按固定间隔估算 | 约 3 ms，而不是 `4 − 2 = 2 ms` |

**统计边界：**

- 采样不保证碰到方法的真实入口与出口；例如 1.2～1.5 ms 执行完的短调用，可能完全落在两个采样点之间而漏采。
- 同一方法的多次调用会按所选调用树口径汇总。显示约 20 ms，不代表单次调用就是 20 ms，也不能据此得出准确调用次数。
- 采样点能说明“这个时刻执行到了哪里”，不能完整还原采样间隔内的全部调用。若第 1、2、3 ms 分别采到 A、B、A，不能仅凭这些样本判断两次看到的 A 是同一次调用还是两次不同调用，也不能还原各方法精确起止时间。
- Time Profiler 的 CPU 采样统计与调用的实际经过时间不同：锁等待、I/O 等等待可能延长返回时间，却不代表 CPU 持续执行该方法。它也不直接测量 GPU 耗时。

| 想回答的问题 | 适合的方式 |
|-|-|
| 某个时间段 CPU 主要花在哪些线程、方法及调用路径 | Time Profiler，选中目标时间范围后看调用树 |
| 这一次快照调用从开始到返回经过多久 | 成对 Signpost 记录调用区间 |
| 每次已标记调用的开始、结束、持续时间及顺序 | Signpost + Instruments 时间线；只覆盖主动标记的操作 |
| 动画是否错过显示时机，问题位于提交还是渲染阶段 | Animation Hitches，再结合调用栈和阶段标记定位 |

## Animation Hitches 的使用流程

**Animation Hitches 是 Apple 的 Instruments 中用于分析动画、滑动卡顿的模板。** Hitch 指运动中的画面没有按预期时机更新，例如滑动评论列表时，新位置对应的画面没及时准备好，旧画面继续停留，视觉上就顿了一下。相关阶段见[Core Animation 渲染管线](#图层动画与渲染管线)。

使用流程：打开 Instruments，选择 Animation Hitches 模板和目标 App，开始录制，再在设备上执行要排查的滑动或动画。工具在时间线上标出卡顿，并提供提交、渲染、GPU、帧生命周期等轨道，帮助判断卡顿发生的时间、持续时长及主要耗时阶段。

以 Push 评论直达为例，可以录制一次自动滚到目标评论的过程，选中停顿所在的时间段，查看 App 的事件处理／布局／提交，还是后续渲染准备／GPU 执行出现延迟。进一步定位具体业务代码时，还要结合 [Time Profiler](#time-profiler-的采样与统计边界) 等工具中的调用栈和线程状态；工具标出阶段，不等于自动给出完整根因。

[CADisplayLink](threads-and-scheduling.md#cadisplaylink-的原理与适用场景) 可通过回调间隔观察流畅度迹象；Animation Hitches 则用于录制、分析一次具体交互的渲染时间线。

### 同次录制中的时间线关联

Animation Hitches 不只是标记卡顿发生的时间，还展示持续时长和相关渲染阶段。定位 CPU 方法时，需要在同一次录制中采集 Time Profiler，才能把帧的时间线与同一时段的线程调用栈对齐；两次独立录制中的相同秒数不代表同一次工作。

Animation Hitches 模板可以组合多个分析工具。开始录制前应检查当前模板是否已经包含 Time Profiler；已经包含时，无需再开一次独立录制，缺少时则把 Time Profiler 加入本次录制。

观察到画面停顿的时刻，不一定就是耗时代码开始执行的时刻。应沿帧生命周期检查导致该帧延迟的事件处理、布局和提交区间，再查看对应 CPU 采样。Time Profiler 反映采样到的 CPU 调用路径，不能单独确定 GPU 执行瓶颈，也不能仅凭某个方法出现在卡顿附近就认定完整因果关系。

## MetricKit 与 Xcode Organizer

**MetricKit 是 App 中接收系统性能与诊断报告的框架；Xcode Organizer 是开发者在 Xcode 中查看 App 数据的窗口。** 这里讨论的是 Organizer 的性能指标与诊断功能。

| 对比项 | MetricKit | Xcode Organizer |
|-|-|-|
| 使用方式 | 在 App 中接入，接收系统提供的性能指标和诊断报告 | 在 Xcode 的 Window → Organizer 中查看 |
| 数据处理 | App 按需保存、上传到自己的监控平台，再做统计或告警 | Apple 收集并汇总数据，开发者查看指标及可用的诊断报告 |
| 典型用途 | 接入公司的线上性能监控体系 | 比较版本、机型上的启动耗时、内存、卡顿及无响应表现 |

**MetricKit 不负责自动上传到公司的平台。** 上传需要业务代码或监控 SDK 实现，可以组成下面的链路：

```text
系统收集数据 → MetricKit 将报告交给 App
            → 公司监控 SDK／业务代码上传 → 平台统计、展示和告警
```

MetricKit 提供系统收集的报告，不是实时逐帧回调。查看 Organizer 的系统性能指标通常不需要专门接入 MetricKit，两者也不是“MetricKit 上传后 Organizer 才有数据”的必需前后关系。

**线上性能数据的取得条件：** 以通过 App Store 发布的 App 为例，Organizer 可显示参与数据共享用户的匿名汇总性能表现。

1. App 上架 App Store 后，用户下载安装并使用。
2. 其中同意向开发者共享相应分析与诊断数据的用户，其设备向 Apple 提供相关数据。
3. Apple 汇总报告；开发者在 Xcode 登录有权限的团队账号后，通过 Organizer 查看。

例如可以比较新旧版本的启动耗时、内存和卡顿指标，并在支持的指标上按机型筛选。这里看到的是统计结果，不能据此逐个查看某个用户的身份及实时运行情况，也不能把一万名使用者理解成一万名都进入统计。

数据需要足够的使用样本，且发布后到报告可见存在延迟；只装给几个朋友测试，不能保证出现性能指标。Apple 的 Metrics 报告面向 App Store 分发；TestFlight 可提供崩溃等报告，不能由此推断全部性能指标都适用相同渠道。线上指标有助于发现某个版本发生性能退化，具体原因仍需结合诊断报告与复现分析。
