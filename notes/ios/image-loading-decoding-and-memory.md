# iOS 图片加载、解码与内存

[返回笔记目录](../README.md)

图片加载包括取得压缩数据、生成像素数据和显示图片。优化前需要区分网络传输量、解码开销、像素内存和渲染开销。

## 共享加载服务与请求流程

图片加载服务是供多个页面共用的组件，统一管理图片的读取、缓存、解码和加载任务。页面请求图片时，向加载服务传入图片来源、目标像素尺寸和优先级。图片来源可以是网络地址、本地文件或应用内资源。当前可见的图片通常比提前准备的图片优先级高。

加载服务收到请求后立即返回取消句柄。取消句柄是页面用来取消本次请求的对象。完成回调是页面传给加载服务的函数，加载服务在加载结束后调用完成回调，并传入图片或错误。底层 API 可能在后台线程回调，所以加载服务统一在主线程调用完成回调，页面在完成回调中直接更新界面。

对于网络图片，加载流程如下：

```text
页面请求图片
  → 内存缓存中有符合要求的图片：返回图片
  → 否则查询磁盘缓存：有效文件存在时，按目标尺寸解码并返回
  → 否则下载图片：按目标尺寸解码并返回
```

下载成功后，服务按缓存策略保存压缩文件；解码成功后，服务把可显示的结果放入内存缓存。磁盘读写和耗时解码在后台执行。本地文件和应用内资源从各自来源读取，不经过网络下载。

### SDWebImage 的图片加载与两级缓存

SDWebImage 是用于异步加载和缓存图片的开源库。UIImageView 的扩展方法把图片地址交给加载管理对象。加载管理对象依次查询缓存、下载和解码，再把图片设置到视图上。默认的网络下载基于 URLSession。图片缓存由 SDWebImage 自己的 SDImageCache 等组件管理，与 URLCache 是两套缓存。

```swift
import SDWebImage

// 在主线程配置视图；url 是调用方提供的有效图片地址
avatarImageView.sd_setImage(
    with: url,
    placeholderImage: UIImage(named: "avatar-placeholder")
)
```

例如，第一次加载头像时没有缓存。加载器下载 JPEG 数据，按配置生成图片对象并完成显示准备，再按存储策略写入内存缓存和磁盘缓存。之后再请求同一缓存键时：内存缓存中有图片，就直接复用这个 UIImage；只有磁盘文件，就读取文件并重新生成图片；两级缓存都没有，才重新下载。

| 缓存 | 保存的主要内容 | 复用时的主要作用 |
| --- | --- | --- |
| URLCache | HTTP 响应信息和响应内容字节；JPEG 响应通常仍是 JPEG 字节 | 按 HTTP 缓存策略减少网络访问 |
| SDWebImage 内存缓存 | UIImage 或其他图片对象（如 SDAnimatedImage）；普通静态图片通常已完成显示所需解码 | 复用图片对象和已有像素数据 |
| SDWebImage 磁盘缓存 | JPEG、PNG 等格式的图片字节 | 减少重复下载，读取后仍需生成图片对象 |

内存缓存保存的是图片对象的引用。图片对象被内存缓存引用期间，图片对象持有的像素数据也一直留在内存中；存入缓存时不会另外复制一份像素数据。因此一条缓存记录的内存成本主要是像素数据，URL 字符串和引用本身很小。例如，一张 1000×1000 像素的 JPEG 文件为 200 KB，解码后每像素占 4 字节，像素数据约 4 MB。计算口径与额外开销见下文的[图片内存的估算](#图片内存的估算)。

SDWebImage 的默认加载流程通常会先完成普通静态图片的解码，再存入内存缓存。内存缓存只负责保存图片对象，不检查图片是否已解码。以下三种情况下，内存缓存中的图片可能尚未完全解码：调整了解码选项；调用方直接存入未解码的图片；使用 SDAnimatedImage。SDAnimatedImage 是 SDWebImage 提供的动图对象，按播放需要逐帧解码，不在一开始解码全部帧。

默认缓存键通常由图片 URL 生成，调用方也可以自定义键的生成规则或图片变换。SDWebImage 自有缓存默认不按 HTTP 缓存头判断内容是否过期。服务端在同一 URL 下更换图片内容时，客户端应使用带内容版本的地址，或者显式指定刷新策略。HTTP 缓存规则见 [网络请求与代理](../network-and-storage/network-and-proxy.md#urlcache-与-http-缓存规则)。

### Kingfisher：网络图片与占位图

Kingfisher 是用 Swift 编写的网络图片加载库，常用于头像、商品图片和列表封面。调用方提供图片地址和 UIImageView，Kingfisher 负责下载、缓存和显示。通用加载顺序见[共享加载服务与请求流程](#共享加载服务与请求流程)。

以下代码假设页面已有 avatarImageView，url 是有效的图片地址，代码在主线程执行，项目已引入 Kingfisher。

```swift
import UIKit
import Kingfisher

avatarImageView.kf.setImage(
    with: url,
    placeholder: UIImage(systemName: "person.crop.circle")
)
```

`.kf` 是 Kingfisher 为 UIImageView 提供的功能入口，Kingfisher 的方法都通过 `.kf` 调用。`placeholder` 是图片取得之前显示的占位图。默认配置下，Kingfisher 先查缓存，缓存中没有可用图片时才下载。下载成功后，Kingfisher 显示图片，并把图片写入内存缓存和磁盘缓存。磁盘写入可能异步进行，图片显示出来时，磁盘写入可能还没有完成。

例如，第一次显示头像时没有缓存，Kingfisher 下载图片。再次使用同一地址时，缓存仍然有效，Kingfisher 就直接复用图片；缓存过期或被清除后，Kingfisher 重新下载。

依赖接入见 [Swift 第三方库与依赖接入](../engineering/xcode-and-testing.md#swift-第三方库与依赖接入)。

## 下载数据与解码像素

下载得到的 JPEG、PNG 等文件数据，是按各自图片格式压缩编码的字节。解码是把这些字节转换成可以直接显示的像素数据。下载完成时，图片还没有解码；创建 UIImage 对象时，系统也可能暂不解码。

UIImage 是封装图片内容、尺寸和方向等信息的对象。一个 UIImage 对象内部可能已经有完整的像素数据，也可能只有压缩数据。例如：

```swift
// data 是已有的 JPEG 文件数据
let image = UIImage(data: data)
```

`UIImage(data:)` 返回非 nil，说明系统创建了图片对象。系统可能把部分像素解码推迟到第一次绘制前，这称为延迟解码。需要提前解码时，调用下文的[显示准备接口](#提前解码与显示准备)，并使用接口返回的新图片。

应用把下载结果作为 Data 保留在内存中时，压缩数据本身就占用内存。应用也可以把下载数据写入磁盘文件，不在内存中长期保留原图数据；下载和读取文件的过程仍然需要临时缓冲内存。

解码器生成像素数据后，解码器不会删除压缩数据。只要应用或框架仍引用压缩数据，压缩数据和像素数据就同时占用内存。把压缩数据写入磁盘后，内存中的那份 Data 只要仍被引用，也不会释放。

## 图片内存的估算

像素数据的内存主要取决于像素尺寸和像素格式。对于每个像素占 4 字节的常见 8 位 RGBA 图像，可以用“像素宽度 × 像素高度 × 4”估算。这个公式只估算像素数据本身，实际占用还包括行对齐、临时缓冲和其他对象。

| 数据形式 | 假设或计算 | 大小 |
| --- | --- | --- |
| 原始 JPEG 文件数据 | 假设文件为 3 MB | 3 MB |
| 完整尺寸的像素数据 | 4000 × 3000 × 4 字节 | 48 MB |
| 缩略图的像素数据 | 400 × 300 × 4 字节 | 0.48 MB |

本表使用十进制 MB，即 1 MB = 1,000,000 字节。应用同时保留 3 MB 的压缩数据和 48 MB 的像素数据时，仅这两部分就约占 51 MB。降采样后，3 MB 压缩数据加 0.48 MB 缩略图像素数据约占 3.48 MB。这组数字只比较保留下来的数据量；峰值内存和解码耗时下降多少，需要另外测量。

## 降采样与服务器缩略图

降采样是减少图片的像素数量，生成刚好满足显示需要的较小图片。缩小 UIImageView 的 frame 或修改 contentMode 只改变显示效果，图片本身的像素数量不变。

显示尺寸通常用 point 表示，像素尺寸需要结合屏幕 scale。例如，100 × 100 point 的显示区域在 scale 为 3 时，对应 300 × 300 像素。计算目标图片尺寸时还需要考虑原图宽高比及实际裁剪方式。

最终生成 300 × 300 像素的图片、每像素占 4 字节时，像素数据约占 360,000 字节，即 0.34 MiB。MiB 是二进制单位，1 MiB = 1,048,576 字节。这个值不包含行对齐、图片对象和解码临时数据。

ImageIO 生成缩略图时直接按目标尺寸降采样，不需要先生成完整尺寸的像素图再缩小，因此省去了完整尺寸像素图的内存和处理开销。实际解码成本取决于图片格式、图片内容和系统实现。

本地降采样的典型流程是：下载原图数据 → 创建图片源 → 在设备上生成缩略图 → 显示。客户端仍然下载了完整原图，所以本地降采样不减少网络传输量。

服务器支持指定尺寸的图片 URL 时，客户端可以直接请求服务器生成的小图。这种方式同时减少下载量和客户端处理的像素数量。服务器缩略图在下载前减少数据量，客户端降采样在下载后减少像素数量。

## ImageIO 与缩略图生成函数

ImageIO 是苹果提供的系统框架，用于读取、解码、编码图片，以及生成缩略图等。Swift 通过 import ImageIO 使用这个框架。

CGImageSource 是图片源对象，负责读取图片数据。应用可以用内存中的 Data 或本地图片文件 URL 创建图片源。CGImageSourceCreateThumbnailAtIndex 函数从图片源中取出指定图片的缩略图。函数的三个参数依次是图片源、图片索引（从 0 开始）和生成选项。普通单张 JPEG 的图片索引是 0。

| 生成选项 | 含义 |
| --- | --- |
| kCGImageSourceThumbnailMaxPixelSize | 缩略图宽和高的最大像素数；缩略图保持原图宽高比 |
| kCGImageSourceCreateThumbnailFromImageAlways | 设为 true 时，始终根据原图生成缩略图 |
| kCGImageSourceCreateThumbnailWithTransform | 按图片的方向信息旋转或翻转缩略图 |
| kCGImageSourceShouldCacheImmediately | 控制图片创建时是否立即完成解码和缓存 |

函数成功时返回 CGImage，失败时返回 nil。应用用 UIImage(cgImage:) 把 CGImage 包装成 UIImage，再交给 UIImageView。CGImageSourceCreateThumbnailAtIndex 同步执行：在哪个线程调用，就在哪个线程生成缩略图。生成耗时较长时，应在后台队列调用。

CGImageSourceCreateThumbnailAtIndex 只在客户端处理已经取得的图片数据。向服务器请求小图时，客户端需要自己构造对应尺寸的图片 URL。

## 提前解码与显示准备

在后台调用 UIImage(data:) 只创建图片对象。解码可能推迟到首次显示时在主线程进行，仍会增加主线程的工作量。

iOS 15 起，UIImage 的 prepareForDisplay(completionHandler:) 可以在后台异步准备图片。需要解码时，系统完成解码，并通过回调提供准备好显示的 UIImage；无法解码时，回调结果为 nil。如果图片已经可以直接显示，系统不需要重复解码。

执行流程是：已有 UIImage → 调用 prepareForDisplay → 后台完成所需准备 → 回调取得准备好的图片 → 应用在主线程更新 UIImageView。应用要使用回调传入的新图片；原来的 UIImage 对象不会因此变成已解码状态。prepareForDisplay 的回调可能在后台线程执行，更新 UIImageView 前要切回主线程。

例如，后台完成图片准备后，把设置 avatarImageView.image 的代码提交到主线程执行。UIKit 要求在主线程修改视图：主线程逐个执行界面修改，视图状态、布局和绘制按框架要求的顺序更新。在后台线程给 image 赋值有时也能显示出来，但可能出现界面更新异常、数据竞争或崩溃。主线程赋值完成后，图片要等到后续的屏幕刷新才显示出来。

```swift
DispatchQueue.main.async { [weak self] in
    self?.avatarImageView.image = image
}
```

代码中 image 是已经准备好的图片，self 是持有 avatarImageView 的页面对象。在复用列表中赋图前，还要在主线程检查 Cell 当前绑定的数据标识，见下文的[缓存、并发与列表复用](#缓存并发与列表复用)。

prepareForDisplay 只对已有的 UIImage 做解码准备，不下载图片，也不缩小图片尺寸。降采样决定输出图片有多少像素；显示准备决定解码在什么时候、在哪个线程进行。降采样和显示准备按需要选用，不必对每张图片都依次执行。

后台解码把解码工作移出主线程，减少主线程阻塞；解码本身的 CPU 和内存开销不变。

## 缓存、并发与列表复用

缓存是保留已经获取或处理过的数据，供后续请求复用。磁盘缓存主要保存压缩图片文件，减少重复下载；内存缓存可以保存已经解码、准备好显示的图片，复用像素结果。只缓存压缩 Data 时，再次使用可以省去下载或读取文件，但仍需要重新解码。

缓存键是缓存容器查找结果时使用的标识。解码结果的缓存键要包含图片来源、内容版本、目标像素尺寸，以及裁剪等会改变结果的变换参数。内容版本用来区分同一来源更新前后的图片。缓存键包含这些信息后，大尺寸请求不会命中小尺寸缩略图，图片更新后也不会命中旧内容。

同时解码大量图片会增加 CPU 竞争和内存压力。应优先处理当前可见区域，适量预加载即将显示的内容，并取消已经不需要、尚未开始的任务。已经开始的同步解码无法通过取消中断，会一直执行到结束。

图片异步返回后，在主线程先检查 Cell 当前绑定的数据标识或请求标识，标识一致再立即赋图。这样，旧请求的图片不会显示到已经被复用的 Cell 上。具体说明见[长列表性能与异步图片复用](uikit-layout-and-mvvm.md#长列表性能与异步图片复用)。

测量时应区分网络等待、CPU 解码和渲染延迟。卡顿时间线与调用栈的关联方式见[Animation Hitches 的使用流程](rendering-and-performance.md#animation-hitches-的使用流程)。

### 缓存移除与图片对象释放

内存缓存是程序在内存中维护的容器，例如保存“图片标识 → UIImage 对象”的字典。清空缓存只删除容器中的记录；其他对象仍引用这张图片时，图片继续留在内存中。

强引用是让目标对象保持存活的引用。ARC（自动引用计数）根据强引用关系管理对象生命周期。缓存和 UIImageView.image 可以同时强引用同一个 UIImage 对象，缓存和图片视图共用这一份图片数据。引用关系的通用规则见[ARC 与 Android GC](../language/swift-memory-and-references.md#arc-与-android-gc引用计数可达性与引用环)。

例如，一份像素数据占 4 MiB。缓存和图片视图同时引用这份数据时，像素数据仍约占 4 MiB，另有缓存条目和对象管理信息的少量开销。只有程序另外生成缩略图，或者重新解码出另一份像素数据时，内存中才多出一份新数据。

假设 cache 是已经保存图片 A 的 Swift 字典，imageView 是图片视图。以下代码在主线程执行：

```swift
imageView.image = cache["A"]
cache.removeValue(forKey: "A")
```

第一行让图片视图持有图片 A。第二行删除缓存条目，解除缓存对图片 A 的强引用。之后通过 cache["A"] 查不到图片，但 imageView.image 仍然引用原来的图片对象，因此视图继续显示图片 A，不需要重新下载。

```text
移除前：缓存 ──────────┐
                     ├→ 同一个 UIImage 对象
        UIImageView ─┘

移除后：UIImageView ───→ 原来的 UIImage 对象
```

页面不再需要显示图片时，可以清除视图持有的引用：

```swift
imageView.image = nil
```

没有任何变量、回调或其他对象强引用这个 UIImage 时，UIImage 对象才会释放。缓存是唯一持有方时，移除缓存条目就会释放 UIImage 对象。视图仍持有图片时，移除缓存条目只解除缓存自己的引用，UIImage 对象不会释放。UIImage 对象释放后，进程的内存指标也可能不会立即等量下降，因为内存分配器或框架可能保留这块存储以便复用。

### 图片内存预算与缓存策略

内存预算是为图片相关数据设定的内存容量目标。控制图片内存时，既要限制单张图片的像素尺寸，也要限制缓存的总成本。内存预算还要计入当前可见图片、少量预取图片、下载数据和解码临时数据。缓存容量上限只约束缓存本身；图片相关内存的总量是以上各部分之和。

缓存成本应按图片实际占用的字节数统计。只限制图片张数时，一张大图和一张小图按同样的成本计算，无法反映实际内存。NSCache 是系统提供的缓存容器，适合保存可以重新取得的数据，并会自动淘汰条目。存入条目时可以传入成本，并设置 totalCostLimit。totalCostLimit 不是严格上限，NSCache 何时淘汰、按什么顺序淘汰也没有保证。需要严格控制应用自己的缓存大小时，应用要自己统计成本并移除条目。当前视图、其他对象和解码任务持有的图片数据不在缓存中，需要另外管理。

缓存超过预算时，先移除长时间未使用、当前也不显示的条目。应用收到内存压力通知后，按以下方式降低内存：

- 保留当前画面需要的图片。
- 停止新的预取，取消已经无效的等待任务，缩小预取范围。
- 减少同时执行的解码任务，降低解码临时内存。

取消加载、移除内存缓存和删除磁盘文件是三个不同的动作。释放内存时，磁盘上已有的压缩文件可以保留，也不需要把内存中的图片再写一遍磁盘。图片暂时离屏时，也不必删除全部缓存；全部删除后，用户反向滑动回来时，加载器要重新读取、解码甚至下载。

累计加载数量是整个使用过程中加载过的图片数量；同时驻留数量是某一时刻仍保留在内存中的图片数量。例如，用户累计浏览了 100 张图片，当前只保留 10 张可见图片和 2 张预取图片，其余已释放，那么内存中只有 12 张图片的像素数据。估算某一时刻的内存时，只统计这一时刻仍存活的数据；多个对象共享的同一份数据只算一次。

图片数量、像素尺寸和像素格式相同时，全部加载完成后的像素数据占用与加载快慢无关。只显示当前画面时，内存中保留当前显示所需的数据即可。连续加载后续图片时，还要计入下载和解码的临时数据。要求下一批图片一进入屏幕就显示时，通常还要提前准备一部分图片；额外占用多少，取决于提前准备到哪个阶段，以及准备结果保留多久。

加载耗时决定何时提前发起请求。例如，图片预计 0.5 秒后进入屏幕，准备需要 1 秒，请求就至少要在图片进入屏幕前 1 秒发出。提前下载时可以只准备压缩数据或磁盘文件，不必同时提前解码并长期保留像素数据。所以加载慢首先要求更早发起请求，不一定需要缓存更多已解码图片。

缓存保留多少屏内容，没有适用于所有列表的固定值；“上下各保留三分之二屏”只是某个场景下的选择。确定预取与缓存策略的顺序是：先根据可见内容的显示要求计算必要数据；再结合滑动速度、加载耗时和是否允许显示占位图，选择预取与缓存策略；最后通过实际测量调整。图片准备速度持续低于用户浏览速度时，任何有限的预取范围都会被耗尽，之后进入屏幕的图片仍会先显示占位图。

## 长列表图片任务调度

快速滚动时，减少浪费的关键有两点：不让无效任务开始执行；让当前可见图片优先下载和解码。把工作移到后台只减少主线程阻塞，网络、CPU 和内存开销不变。

### 下载与解码分阶段调度

图片加载器是协调缓存查询、下载、解码和结果交付的组件。下载主要占用网络资源，解码主要占用 CPU 和像素内存，因此两个阶段分别设置并发上限。同一个图片加载器可以同时管理这两个阶段。

并发上限是同一时刻允许执行的任务数量；频率限制是一段时间内允许启动的任务数量。“最多同时下载 6 张图片”是并发上限：一张下载结束，下一张就可以开始，所以一秒内可能下载超过 6 张。请求一旦失效就应取消，无论并发名额是否已满。

各阶段的执行顺序见[共享加载服务与请求流程](#共享加载服务与请求流程)。命中缓存时，加载器跳过不再需要的阶段：磁盘缓存命中时跳过下载，直接进入解码阶段排队；内存缓存命中时，下载和解码都跳过。

加载器分开管理等待开始的请求和正在执行的任务。等待中的请求按“当前可见、即将可见、较远预取”的顺序出队。并发名额空出时，加载器先检查下一项请求是否仍然有效，有效才启动。提高优先级只改变等待请求的出队顺序，已经在执行的同步解码不会被打断。

请求是某个调用方的一次取图需求；下载任务是加载器从网络获取图片的实际工作。多个页面、Cell 或预取请求需要同一张图片时，可以共用一次下载。共用解码结果时，还要求目标尺寸、变换参数等影响结果的参数都相同。

例如，页面 A 和页面 B 同时请求图片 X。加载器只启动一个下载任务，并记录 A、B 都在等待结果。A 离开后取消自己的请求，加载器只移除 A 的需求，继续为 B 下载。只有 B 也取消且没有其他使用者时，加载器才请求取消共享下载。

```text
页面 A 的请求 ─┐
             ├→ 一个下载任务：获取图片 X
页面 B 的请求 ─┘

A 取消后：使用者集合从 {A, B} 变为 {B}，下载继续
B 也取消后：使用者集合变为空，加载器请求取消下载
```

### 预取回调与可见需求

预取是在内容显示之前提前准备数据。设置 UICollectionView 的 prefetchDataSource 后，UICollectionView 通过 UICollectionViewDataSourcePrefetching 协议的方法，告诉数据源哪些项目可能很快显示。UICollectionView 决定通知哪些项目；应用决定是否为这些项目准备数据，以及何时开始准备。

`collectionView(_:prefetchItemsAt:)` 传入可能很快显示的项目，这只是提示。UICollectionView 不会为每个项目都调用这个方法，因此配置 Cell 时仍要处理三种情况：图片已缓存、图片正在加载、图片尚未请求。没有收到预取通知的项目，也要在配置 Cell 时正常发起加载。

`collectionView(_:cancelPrefetchingForItemsAt:)` 在 UICollectionView 判断之前预取的项目不再需要时调用。例如滚动方向改变后，原方向上的一些项目不再需要提前准备。这个方法只针对预取的项目，Cell 离屏要通过下面的 `collectionView(_:didEndDisplaying:forItemAt:)` 处理。收到取消预取的回调，只说明这个项目的预取需求结束，同一张图片可能仍被可见 Cell 或其他页面使用。

可见需求和预取需求分别记录。`collectionView(_:didEndDisplaying:forItemAt:)` 用来结束 Cell 的可见需求；取消预取的回调只结束该项目的预取需求。项目从预取变为可见时，复用已经开始的加载工作，并提高加载优先级。取消预取时，如果图片仍被可见 Cell 使用，加载继续进行。

IndexPath 表示项目在列表中的位置。数据插入、删除或重排后，同一个 IndexPath 可能对应另一条数据，所以请求要用稳定的数据标识记录。加载器保存每个请求的数据标识和取消句柄，数据更新时同步更新这份映射。

### 取消等待任务与执行中任务

取消要同时阻止后续调度和结果交付。以下步骤用于资源已经没有任何使用者的情况；资源仍有其他使用者时，只移除当前调用方的需求。

1. 使请求标识失效，并从加载器自己维护的待调度集合中移除请求。之后调度器不再为这个请求启动下载或解码。
2. 下载尚未开始时，不调用对应 URLSessionTask 的 resume()；下载已经开始时，调用 cancel()。cancel() 只发出取消请求，下载停止后，URLSession 通常通过后续回调报告取消结果。
3. 解码使用 Operation 时，调用 operation.cancel()。尚未开始的标准 Operation 被取消后不再执行任务代码；正在执行的 Operation 要在代码中检查 isCancelled 并主动退出。代码已经进入不能中断的同步解码函数时，解码函数会执行到结束。
4. 下载回调到达后，先检查请求是否有效，请求无效就不再安排解码。解码返回后再检查一次，请求无效就丢弃结果。
5. 任务真正结束时才释放并发名额。如果调用 cancel() 时就释放名额，旧任务还在运行，新任务又已启动，同时运行的任务数会超过上限。

第 1 步的“移除请求”只修改加载器自己的待调度集合。OperationQueue 没有移除单个 Operation 的接口，要调用 Operation 的 cancel()，由 OperationQueue 把被取消的 Operation 标记为结束并最终释放。只从字典中删除 Operation 或 URLSessionTask 的引用，Operation 和 URLSessionTask 仍会继续执行。

任务表是加载器保存的一份记录，结构为“资源 → 正在执行的任务、任务状态、仍需要结果的请求集合”。添加请求、移除请求、判断是否取消共享任务，这三种操作都读写任务表，要在同一个串行队列中逐个执行，或者用锁等同步机制保护。

例如，A 取消时，B 恰好请求同一资源。如果“移除 A”“添加 B”“检查使用者集合”三步交叉执行，取消逻辑可能在 B 加入之前读到“没有使用者”，随后取消 B 仍需要的下载。三步在同一个串行队列中执行时，加入、取消和完成事件按确定的顺序修改任务表。串行执行的只是任务表的读写，多张图片的网络下载仍然并发进行。

最终赋图时，在主线程的同一段代码中先比较 Cell 当前的请求标识，再设置图片，中间不切换线程或队列。这样检查通过后，其他主线程代码没有机会更换 Cell 的绑定。

### 缩小预取范围的作用与边界

预取范围是应用在可见区域之外提前准备的内容范围。缩小预取范围有两个作用：同一时刻的推测性任务更少；用户突然停止或反向滚动时，为远处内容白做的工作更少。UICollectionView 的预取协议没有“预取 N 行”这样的参数。应用可以筛选收到的预取提示，或者根据布局和滚动位置自己维护预取范围。

例如当前可见第 100～110 行。应用只接受前方 20 行的预取时，准备第 111～130 行；只接受 5 行时，准备第 111～115 行。这里的行数由应用的筛选策略决定，UICollectionView 每次通知的项目数量不固定。

用户持续滚过几百行时，如果每一行一进入预取范围就立即开始下载，预取范围再小，沿途大多数图片仍会启动下载。缩小预取范围只减少提前量，整段滚动中的累计浪费要靠控制任务的开始时机来减少。

控制任务开始时机的做法如下：

- 有效需求先放入有容量上限的等待集合。
- 请求取得执行名额时，再检查一次是否仍然需要。
- 移除已经远离当前区域的等待请求。
- 界面允许短暂显示占位图时，高速滚动期间暂不启动新的低优先级任务，减速或停止后再启动。命中内存缓存的图片仍立即显示。

### 停留位置优先与 Cell 复用

滚动减速或结束后，页面读取当前可见的项目集合，为还没有请求的可见图片发起请求，并把仍在等待的可见请求提到最高业务优先级。滚动结束有以下几条路径：

- 拖动后直接停止：在 scrollViewDidEndDragging(_:willDecelerate:) 中，decelerate 为 false 时处理。
- 惯性滚动结束：在 scrollViewDidEndDecelerating(_:) 中处理。
- 应用支持程序触发的滚动动画时，还要在滚动动画结束时处理。

滚动过程中可见项目变化时，也要随时更新需求；停止回调只负责补齐。高速滚动时是否允许显示占位图、延后哪些任务，由界面的显示要求决定。限制远处预取占用的并发名额后，滚动停下时可见图片的请求排队时间更短。

Cell 每次绑定新的加载需求时，生成一个新的请求标识。结果回到主线程后，只有结果的请求标识与 Cell 当前的请求标识一致时才赋图。Cell 复用时，取消旧请求并先显示占位图。取消旧请求之后仍要检查请求标识，原因见下面的执行顺序。

旧请求的完成回调可能已经提交到主线程队列，正在等待执行。主线程队列中排队的是更新界面的代码，与加载器中等待下载的任务队列不同。一种可能的执行顺序如下：

1. 图片 A 已经下载并解码完成。
2. 加载器把交付 A 的完成回调提交到主线程，回调尚未执行。
3. Cell 被复用来显示图片 B，页面更新 Cell 的当前请求标识并取消 A 的请求。
4. 已经提交的 A 回调随后执行。若回调直接赋图，Cell 就会错误地显示 A。

取消下载任务只影响下载本身，已经提交到主线程的回调代码仍会执行；在这个例子中，下载也早已完成。因此更新图片前，要在主线程执行下面的检查。代码中 cell 是带有 currentRequestID 和 imageView 属性的自定义 Cell，completedRequestID 是本次完成的请求的标识，image 是本次请求返回的图片：

```swift
guard cell.currentRequestID == completedRequestID else {
    return
}

cell.imageView.image = image
```

标识不一致时，回调直接返回，丢弃过期结果。检查和赋图之间不要再异步切换线程或队列。加载器在交付前检查取消状态，可以拦下一部分过期回调；已经提交到主线程的回调仍会执行，所以赋图前的标识检查必须保留。

任务队列的并发限制与取消机制见[Operation 与 OperationQueue](threads-and-scheduling.md#operation-与-operationqueue)。

## 格式支持、失败处理与验证

解码器是把某种图片格式的数据转换成像素数据的组件。加载服务为不同格式的解码器定义统一的调用接口，页面加载任何格式的图片都使用同一套流程。动图由多帧组成，播放时按时间依次显示各帧。播放器可以只缓存当前帧和接下来的少量帧，不必把整段动画的全部帧都解码进内存。

下载或解码失败时，服务向页面返回错误。页面根据显示要求设置失败占位图，或提供重试入口。

验证应覆盖首屏大量请求、快速滑动后立即反向滑动、共享任务中只有一个调用方取消，以及 Cell 复用后旧请求才完成。还应覆盖弱网、大尺寸图片和内存压力场景。

测量指标包括从发起请求到图片显示的耗时、重复下载次数、内存峰值和滑动卡顿情况。根据测量结果调整下载与解码的并发数量、缓存容量和预取范围。
