# iOS 图片加载、解码与内存

[返回笔记目录](../README.md)

图片加载包括取得压缩数据、生成像素数据和显示图片。优化前需要区分网络传输量、解码开销、像素内存和渲染开销。

## 下载数据与解码像素

下载得到的 JPEG、PNG 等文件数据仍然采用相应图片格式的编码。解码是把这些数据转换成可供显示的像素数据。文件下载完成不代表解码已经完成，创建 UIImage 对象也不一定立即完成解码。

如果应用把下载结果作为 Data 保留在内存中，压缩数据已经占用内存。也可以把下载数据写入磁盘文件，避免在应用内存中长期保留完整原图，但下载和读取仍然需要缓冲内存。

解码器生成像素数据后，原始压缩数据和像素数据可能同时存在。解码不会自动删除原始数据；原始数据何时释放，取决于应用和框架是否仍然保留这些数据。将数据保存到磁盘，也不会自动释放仍被保留的内存数据。

## 图片内存的估算

像素数据的内存主要取决于像素尺寸和像素格式。对于每个像素占 4 字节的常见 8 位 RGBA 图像，可以用“像素宽度 × 像素高度 × 4”估算。实际占用还可能包含行对齐、临时缓冲和其他对象，不能把这个公式当作应用总内存。

| 数据形式 | 假设或计算 | 大小 |
| --- | --- | --- |
| 原始 JPEG 文件数据 | 假设文件为 3 MB | 3 MB |
| 完整尺寸的像素数据 | 4000 × 3000 × 4 字节 | 48 MB |
| 缩略图的像素数据 | 400 × 300 × 4 字节 | 0.48 MB |

本表使用十进制 MB，即 1 MB = 1,000,000 字节。如果应用同时保留 3 MB 的压缩数据和 48 MB 的像素数据，仅这两部分就约占 51 MB。降采样后同时保留的两部分约占 3.48 MB。这个比较不表示实际峰值内存或解码耗时也按同样比例下降。

## 降采样与服务器缩略图

降采样是减少图片像素数量，生成满足显示需要的较小图片。仅缩小 UIImageView 的 frame 或改变 contentMode，不等于减少原始图片的像素数量。

显示尺寸通常用 point 表示，像素尺寸需要结合屏幕 scale。例如，100 × 100 point 的显示区域在 scale 为 3 时，对应 300 × 300 像素。计算目标图片尺寸时还需要考虑原图宽高比及实际裁剪方式。

使用 ImageIO 在生成缩略图时降采样，可以避免先生成完整尺寸的像素图再缩小，减少大尺寸像素内存和相关处理开销。具体解码成本仍然取决于图片格式、图片内容和系统实现。

本地降采样的典型流程是：下载原图数据 → 创建图片源 → 在设备上生成缩略图 → 显示。下载的原始字节数没有改变，因此本地降采样不能减少已经发生的网络传输。

如果服务器支持指定尺寸的图片 URL，客户端可以直接请求服务器生成的小图。这种方式可以同时减少下载量和客户端处理的像素数量。服务器生成缩略图与客户端降采样属于不同阶段的优化。

## ImageIO 与缩略图生成函数

ImageIO 是苹果提供的系统框架，用于读取、解码、编码图片，以及生成缩略图等。Swift 通过 import ImageIO 使用这个框架。

CGImageSource 是负责读取图片数据的图片源对象。应用可以根据已有 Data 或本地图片文件 URL 创建图片源。CGImageSourceCreateThumbnailAtIndex 是从图片源中取得指定图片的缩略图的函数，其三个参数分别是图片源、从 0 开始的图片索引和生成选项。普通单张 JPEG 的图片索引通常是 0。

| 生成选项 | 含义 |
| --- | --- |
| kCGImageSourceThumbnailMaxPixelSize | 限制缩略图的最大像素宽度和高度；不表示强制生成同样宽高的正方形 |
| kCGImageSourceCreateThumbnailFromImageAlways | 设为 true 时，根据原图生成缩略图 |
| kCGImageSourceCreateThumbnailWithTransform | 按图片方向等信息对缩略图进行相应变换 |
| kCGImageSourceShouldCacheImmediately | 控制图片创建时是否立即完成解码和缓存 |

函数成功后返回 CGImage，失败时返回 nil。应用可通过 UIImage(cgImage:) 包装成功结果，再交给 UIImageView。该函数同步执行，不会自动把工作安排到后台；耗时的缩略图生成应在合适的后台执行路径中完成。

该函数接收图片源，不负责向服务器请求某个尺寸的图片，也不会自动改写网络 URL。

## 提前解码与显示准备

仅在后台调用 UIImage(data:)，不保证解码工作已经完成。图片可能在首次显示时才解码，因此仍可能增加主线程的工作量。

iOS 15 起，UIImage 的 prepareForDisplay(completionHandler:) 可以在后台异步准备图片。需要解码时，系统完成解码，并通过回调提供准备好显示的 UIImage；无法解码时，回调结果为 nil。如果图片已经可以直接显示，系统不需要重复解码。

执行流程是：已有 UIImage → 调用 prepareForDisplay → 后台完成所需准备 → 回调取得准备好的图片 → 应用在主线程更新 UIImageView。应使用回调提供的结果，不能忽略结果后继续使用原始图片。异步回调不等于主线程回调。

prepareForDisplay 不负责网络下载，也不接收目标尺寸来生成缩略图。降采样主要控制输出像素数量；显示准备主要控制解码发生的时机和执行位置。两者不构成每张图片都必须重复执行的一套步骤。

后台解码把工作移出主线程，能够减少主线程阻塞，但不会消除解码本身的 CPU 和内存开销。

## 缓存、并发与列表复用

缓存压缩 Data 可以减少再次下载或读取文件，但不保证避免再次解码。缓存已经准备好的图片，可以在后续显示时复用像素结果；缓存需要设置容量或内存成本上限。

图片缓存键需要区分图片身份、目标像素尺寸，以及会改变结果的裁剪或变换条件。将不同尺寸的图片都视为同一个缓存结果，可能导致画质或内存占用不符合预期。

同时解码大量图片会增加 CPU 竞争和内存压力。应优先处理当前可见区域，适量预加载即将显示的内容，并取消尚未开始且已经不需要的任务。取消请求不等于可以强制中断已经开始的同步解码。

图片异步返回后，应在主线程检查 Cell 当前绑定的数据标识或请求标识，再连续完成赋图，避免结果写入已经复用的 Cell。具体说明见[长列表性能与异步图片复用](uikit-layout-and-mvvm.md#长列表性能与异步图片复用)。

测量时应区分网络等待、CPU 解码和渲染延迟。卡顿时间线与调用栈的关联方式见[Animation Hitches 的使用流程](rendering-and-performance.md#animation-hitches-的使用流程)。

## 长列表图片任务调度

快速滚动时，减少浪费的关键是限制无效任务开始执行，并让当前可见图片优先取得下载和解码机会。把工作移到后台只能减少主线程阻塞，不能消除网络、CPU 和内存开销。

### 下载与解码分阶段调度

图片加载器是协调缓存查询、下载、解码和结果交付的组件。下载主要占用网络资源，解码主要占用 CPU 和像素内存，因此两个阶段应分别限制并发数量。一个图片加载器可以同时管理两个阶段，不要求必须创建两个独立的任务管理器类。

一次加载的基本顺序是：查询已准备好显示的内存缓存 → 查询磁盘中的压缩数据 → 缺少数据时下载 → 按目标像素尺寸降采样或解码 → 回到主线程校验请求并赋图。缓存命中后跳过已经不需要的阶段。

加载器应区分等待开始的请求与正在执行的任务。等待请求可以按“当前可见、即将可见、较远预取”的顺序选择。并发名额空出时，加载器重新检查请求是否仍然有效，再启动下一项。提高等待任务的优先级不能抢占已经执行的同步解码。

同一张图片可能同时被多个 Cell 或预取请求使用。调用方持有的请求标识代表一次使用需求，底层任务代表实际下载或解码。图片加载器可以合并相同资源的请求；取消一个需求时，只有不存在其他使用者，才取消共享任务。下载可以按源资源合并，解码结果还需要区分目标尺寸与变换条件。

### 预取回调与可见需求

预取是在内容实际显示之前提前准备数据。设置 UICollectionView 的 prefetchDataSource 后，系统通过 UICollectionViewDataSourcePrefetching 通知数据源准备可能很快显示的项目。系统决定回调的项目，应用决定是否接受这些预取需求，以及何时开始实际工作。

`collectionView(_:prefetchItemsAt:)` 提供预取提示。该方法不保证覆盖每个项目，因此 Cell 配置路径仍须处理图片已缓存、正在加载和尚未请求三种情况。预取提示不应成为图片能够正常显示的前提。

`collectionView(_:cancelPrefetchingForItemsAt:)` 在系统认为先前请求的预取数据不再需要时调用，例如滚动方向改变后，原方向上的一些项目不再需要提前准备。该方法不是每个 Cell 离屏都会收到的通知，也不代表对应资源已经没有其他使用者。

可见需求与预取需求应分别管理。`collectionView(_:didEndDisplaying:forItemAt:)` 可以用于结束 Cell 的可见需求；预取取消回调只结束对应的预取需求。图片从预取转为可见时，应复用已有工作并提高优先级。取消预取不应取消仍被可见 Cell 使用的图片。

IndexPath 表示项目在列表中的位置，不能替代稳定的数据标识。数据插入、删除或重排后，位置与数据的对应关系可能改变。加载器应保存发起请求时的数据标识和取消句柄，并在数据更新时同步维护映射。

### 取消等待任务与执行中任务

取消操作应同时控制后续调度和结果交付。以下流程适用于某个资源已经没有使用者的情况；仍有使用者时，只移除当前调用方的需求。

1. 使请求标识失效，并从加载器自己维护的待调度集合中移除请求。调度器之后不再为这个请求启动下载或解码。
2. 下载尚未开始时，不调用对应 URLSessionTask 的 resume()；下载已经开始时，调用 cancel() 请求取消。cancel() 返回不代表下载已经停止，取消完成通常通过后续回调报告。
3. 解码使用 Operation 时，调用 operation.cancel()。尚未执行的标准 Operation 会跳过工作；已经执行的任务需要在代码中检查 isCancelled。已经进入不能中断的同步解码函数时，取消不会强行终止函数。
4. 下载回调到达后，再检查请求是否有效。无效请求不继续安排解码。解码返回后再次检查，避免交付已经失效的结果。
5. 在任务实际结束时释放正在执行的并发名额。不能仅因发出 cancel() 就把名额视为已经释放，否则旧任务还未结束，新任务就可能继续启动。

“移除等待请求”指操作加载器自己的待调度集合。已经加入 OperationQueue 的 Operation 没有直接移除接口；应调用 cancel()，让队列完成被取消任务的状态转换并最终释放任务。只删除字典中的引用，不会自动取消 Operation 或 URLSessionTask。

请求表、使用者数量和任务状态必须通过同一个串行执行路径或明确的同步机制读写。最终赋图时，在主线程连续完成“比较 Cell 当前请求标识”和“设置图片”，避免检查后又被其他主线程逻辑更换绑定。

### 缩小预取范围的作用与边界

预取范围表示应用愿意提前准备的可见区域之外的内容。缩小范围可以减少同一时刻的推测性任务，以及突然停止或反向滚动时已经为远处内容付出的成本。UICollectionView 的预取协议没有直接设置“预取 N 行”的通用参数；应用可以筛选收到的提示，或者按布局和滚动位置维护自己的预取范围。

例如当前可见第 100～110 行，应用向前接受 20 行预取需求时，会考虑第 111～130 行；接受 5 行时，只考虑第 111～115 行。这个例子描述应用自己的接受策略，不表示系统固定按这个行数回调。

如果用户持续滚过几百行，并且每一行进入预取范围就立即开始下载，那么缩小范围仍可能让沿途多数图片启动任务。因此，缩小范围只限制提前量，不能单独解决整段滚动中的累计浪费。

应用还需要控制任务开始的时机：先将有效需求放入有容量限制的等待集合；真正取得执行名额时再检查需求；移除已经远离当前区域的等待请求。对于允许短暂显示占位图的界面，可以在高速滚动期间延后启动新的低优先级任务，并在减速或停止后恢复。已经命中的内存缓存仍可立即显示。

### 停留位置优先与 Cell 复用

滚动减速或结束后，读取实际可见的项目集合，补齐尚未请求的图片，并把仍在等待的可见请求提高到最高业务优先级。可以在 scrollViewDidEndDragging(_:willDecelerate:) 的 decelerate 为 false 时处理拖动直接结束，在 scrollViewDidEndDecelerating(_:) 中处理惯性滚动结束；若支持程序触发的滚动动画，还应覆盖动画结束路径。

可见项目变化时也应持续更新需求，不能只等待停止回调。是否在高速阶段允许占位图，以及延后的任务范围，应由界面的显示要求决定。限制远处预取占用的并发名额，可以降低停留后可见任务排队等待的时间。

Cell 每次绑定新的加载需求时，可以生成独立请求标识。结果回到主线程后，仅当该标识仍与 Cell 当前标识一致时才赋图。Cell 复用时取消旧需求并覆盖占位状态；底层取消不能代替结果身份校验。

任务队列的并发限制与取消机制见[Operation 与 OperationQueue](threads-and-scheduling.md#operation-与-operationqueue)。
